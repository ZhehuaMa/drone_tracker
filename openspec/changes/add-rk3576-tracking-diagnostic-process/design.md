# Design

## Context

目标清晰可见时，跟踪框仍可能消失。当前零散文本日志不能连接检测来源帧、结果读取、恢复跟踪和框发布，需要建立可核查的事件链。动机见 [proposal.md](proposal.md)。本文定义拟实现方案，所有开销门槛尚待验证。

已核对的实现边界：

| 位置 | 当前行为 | 对诊断的要求 |
| --- | --- | --- |
| `src/platform/frame_source_ops.h`、节点 EOF 补取路径 | 等到第一帧后排空积压，仅保留最新帧 | 两条路径都记录真实跳过身份，不能把它们计作采集丢帧 |
| `src/platform/rk3576/ar0234_camera_frame_source.cpp` | 独立采集；SC233HGS 复用该帧源；队列满拒收 | 在合格帧边界记录序号、时间、入队结果，不改驱动缓冲归还顺序 |
| `src/hybrid_tracker/hybrid_tracker.cpp` | 输入通过检查后才增加算法帧号和历史缓存；多处提前返回 | 单独设置调用编号，覆盖未产生算法帧号的调用 |
| `src/hybrid_tracker/yolo_detector.cpp` | 一个待检测槽、一个结果槽；`isBusy()` 只表示待检测槽占用 | 分别记录在途推理、待检测请求、未读结果；记录结果覆盖，保持原规则 |
| `catchupTracker()` | 初始化失败则返回失败；补跟踪单步失败仍继续，整体可成功 | 初始化与每一步分别记录，不把补帧数当成功帧数 |
| `src/drone_tracker_node.cpp` | 框时间为调用前的 `ctx.now_us`；调用返回后才发布 | 保存单调调用时间与发布调用时间，保留现有消息时间戳 |
| `timing_observer.h` | 已有线程局部阶段观察器，回调禁止分配与文件 I/O | 细分记录复用该能力，不直接搬入回放程序的同步 CSV 输出 |
| `deployment/drone-tracker.service` | 主业务服务使用 `KillMode=mixed` | 不能把日志程序放在同一服务中，却声称主业务退出时日志仍存活 |

YOLO 是用于找到目标的检测模型。NanoTrack 是从初始框开始推进目标位置的跟踪算法。历史缓冲只包含提交给跟踪调用且通过输入检查的帧，不包含所有相机帧。连续五次“未确认”可能包含无目标和低匹配度，不能等同于五次检测漏检。

既有规格约束继续适用：ROS 消息及取最新帧语义不变；阶段观测不改变模型处理；CPU 允许范围取自既有策略。相机性能或负载测试已有 180 秒上限，本次按该更短限制设计测试，不引入旧规格中的长测任务。

## Goals / Non-Goals

**Goals:**

- 用完整基础事件解释“检测成功但未恢复”“长调用期间帧去向”和“无效框与没有发布的区别”。
- 在业务线程中以固定成本提交少量数值，在独立进程中完成写盘与文件同步。
- 保存可核查的记录完整性和存储进度。诊断不可用时健康业务仍继续。
- 通过短测量化影响；达到门槛才允许报告基础模式通过验收。

**Non-Goals:**

- 不改变 YOLO 槽位行为、结果覆盖行为、NanoTrack 补跟踪规则或跟踪状态机。
- 不增加截图、逐帧图像副本、全量张量或新的网络/ROS 日志话题。
- 不以软件周期同步保证最后事件在突然断电时留存；不安排实际断电、强制重启或介质损坏实验。
- 不在本次规划阶段实现、编译、启动板端程序或部署。

## Decisions

### 1. 独立日志服务，业务侧不增加日志线程

**选择：** 新增 `rk3576_diagnostic_worker`，由独立的 `drone-tracker-diagnostics.service` 管理。业务端只使用既有控制执行上下文管理连接；不创建专用日志线程。日志进程自身以一个收集循环处理通知、文件写入和同步，不再引入异步写盘线程。

**理由：** 业务进程异常退出后，日志进程仍可读取共享区中已完整提交的记录。日志进程自身的崩溃也可独立恢复。

**替代方案：** 日志线程不能提供业务进程崩溃隔离。主业务服务内直接启动子进程会受同一服务停止策略影响，因此不采用。

**后果：** 新服务可使用 `Wants` 和启动排序，不能通过 `PartOf`、`BindsTo` 或同一服务控制组把它的停止绑定到业务退出。进程准备预算为 500 ms；超时降级。OFF 只结束业务轮次，不停止日志服务。业务进程正常退出时最多等待诊断收尾 2 秒。日志服务全局停止或升级时另行有限收尾，不能无限等磁盘。

日志进程通过业务控制连接关闭及 Linux 的 `pidfd` 监测业务退出。`pidfd` 是代表一个确定进程实例的文件描述符，避免进程编号被复用后认错业务实例。异常退出后只排空共享区中完成提交的槽，并生成异常结束信息。未完成的事件只能标为未知。

### 2. 共享内存承载记录，通知只用于唤醒

**选择：** 使用 `memfd_create` 创建内存文件，并用 `mmap(MAP_SHARED)` 让两进程共享同一组事件缓冲。内存文件保存在内存中，不是持久日志。使用本机 Unix `SOCK_SEQPACKET` 控制连接传递文件描述符；这种套接字保留控制消息边界。通过 `SCM_RIGHTS` 传递共享区域和通知描述符，避免把进程内指针传给另一进程。

**理由：** 每帧不需要发送完整套接字消息、序列化文本或发生阻塞。控制连接只承担建立、确认、收尾及重连。

**替代方案：** 每事件写管道或套接字增加系统调用与复制。业务内同步写文件会把存储等待带入跟踪，因此不采用。

**后果：** 需要版本、字节序、记录长度、共享区域大小和对齐约定。服务验证本机接入身份、描述符类型与长度后才能映射。映射在采集前完成并预触及，减少首次访问才分配内存页的抖动。创建方在共享前固定文件大小，并禁止后续收缩，避免另一个进程访问已被截短的区域。只能由创建方初始化共享原子对象，接收方不能重置它们。

每个预注册业务线程拥有普通和关键两组 SPSC 环形缓冲。SPSC 表示每组只有一个写者和一个读者，避免多线程争抢同一写入锁。定长记录由写者填满后，以 release 操作发布写位置；读者以 acquire 操作读取位置后才能消费。两种操作规定数据可见的先后顺序。对 ARM64 使用并验证天然对齐、无隐藏锁的原子类型；不支持时拒绝诊断连接，不影响业务。不同线程即使在同一处理模块中，也不能共用单写者槽。

`eventfd` 是可被日志进程等待的通知计数器。以非阻塞方式在缓冲由空变为非空或出现关键事件时合并通知，普通通知节流；通知失败不撤销已提交事件。日志进程在可调度且没有阻塞于存储调用时，以 10 ms 为轮询目标主动检查共享区，弥补通知竞争或遗漏。该目标不是磁盘拥塞时的延迟保证。通知本身不携带日志，也不表示已经写盘。

正常流程：

1. 业务控制路径预注册线程、准备共享区，并在 500 ms 内尝试连接日志服务。
2. 业务线程从已有计算结果生成数值快照，写入自己的槽并发布位置。
3. 日志进程收到通知或轮询到新位置，批量读取完整槽并生成磁盘记录。
4. 完整写入后才释放可复用槽；存储同步成功另行推进同步位置。
5. 离线工具按事件身份和时间重建因果关系，并显示缺口。

### 3. 有界内存、关键容量与重连

**选择：** 每个业务进程诊断内存总预算不超过 8 MiB，包括共享槽、注册表、缺口信息和业务端临时记录。MiB 表示 1024×1024 字节。关键缓冲预留不少于总槽容量的 25%，覆盖清框、初始化失败、缓存未命中、推理异常、结果覆盖和诊断故障。记录尝试均递增生产者序号，满时立即放弃，计入缺口计数。

**理由：** 既要防止磁盘停顿拖住实时业务，也要尽量保留失效原因。

**替代方案：** 无限队列会耗尽内存；队列满后等待会引入延迟；直接覆盖未消费槽会造成读取竞争，均不采用。

**后果：** 关键槽同样可能满，不能保证关键事件不丢。共享计数保留丢失总量、首末序号和有界范围列表。列表耗尽时保留数量，并明确详细范围不完整。异常终止且计数未保存时，报告尾部未知。

日志进程最多映射两份 8 MiB 业务区域，并使用最多 1 MiB 输出批次缓冲；达到会话上限时拒绝新的诊断连接，业务继续。进程实际常驻内存还包含代码和库，须另行测量，不能将上述预算当作整个进程内存。

日志进程重启后由既有控制路径每 5 秒至多尝试一次非阻塞重连。仅在旧消费者确定退出、版本匹配且完成新消费者确认后接管原共享区。无法确认时继续降级，不创建第二个消费者，不累计额外区域。日志进程每次接管使用新的文件段，防止向异常尾部续写。事件身份允许离线去重，重连不承诺恰好写入一次。

### 4. 用身份连接各阶段，不依靠时间猜来源

**选择：** 定长事件头至少含 `format_version`、`run_id`、`round_id`、`producer_id`、`producer_seq`、`event_type`、`mono_ns`。`run_id` 标识一次业务进程运行，`round_id` 区分 ON/OFF 轮次；同一生产者的序号包含失败提交。负载字段根据事件类型解释，禁止存放指针、字符串、图像或额外 `FrameRef` 引用。

**理由：** 相机时间、预测时间和完成时间不同，单凭“最近时间”无法准确回答检测对应哪一帧。

**替代方案：** 仅增加文字和墙钟时间仍无法辨认结果覆盖、帧跳过及补帧来源，因此不采用。

**后果：** 拟为现有帧对象增加可选的只读数值诊断元数据：轮次内 `capture_id`、驱动序号与有效标志。`capture_id` 标识实际出队的相机样本，驱动序号需另外保存以处理缺口与回绕。沿已有帧对象携带，不建立持有图像的额外查找表。通用默认访问器返回未知；视频或参考平台不能伪造相机身份，已有像素和时间接口保持兼容。

`update_id` 在每次进入跟踪调用时递增，包括早退。`tracker_frame_id` 只记录既有算法帧号，不能用它替代调用次数。`request_id` 区分每次实际投递尝试，成功请求携带 `source_update_id`、`source_tracker_frame_id` 和采集身份；未投递也保存理由。所有身份均带运行和轮次范围。框使用明确的坐标格式与有效标志，不能把无效框写为正常零框。

墙钟字段包括原帧时间、`ctx.now_us` 和发布调用时的 ROS 时间。耗时使用同机单调纳秒。清理或新轮保存时钟对应关系，系统时钟跳变时报告，不能用墙钟相减计算耗时。`publish()` 正常返回只表示调用结束；若需核对 bag，则记录该消息已有的时间与本地发布编号，不宣称订阅端收到。

### 5. 基础模式记录因果链，细分模式记录成本

**选择：** 下表事件均在基础模式保留，不采样检测生命周期和状态决策。模型细分阶段才由 `detail` 增加。`diagnostics.mode` 启动后固定，RK3576 生产模板默认 `basic`，其他入口默认 `off`。

| 阶段 | 基础记录的主要内容 |
| --- | --- |
| 采集与取帧 | 合格帧时间和身份、入队成功或拒绝、预热与终止处置、驱动缺口、节点实际跳过身份和最终选择帧 |
| 每次跟踪调用 | 入口、返回、输入检查与早退、算法帧号、消费标志、缓存追加和淘汰 |
| 检测投递 | 未投递理由、尝试编号、接受或拒绝、待检测槽、在途请求及结果槽快照 |
| 检测执行 | 来源帧、开始结束、区域/全图/分块及块编号、阈值、候选计数、最终目标框和分数、异常阶段 |
| 结果生命周期 | 产生、被哪个调用读取、未读结果被哪个请求覆盖、轮次清理取消 |
| 跟踪仲裁 | 实际检测框与历史比较框、IoU 和阈值、分支、计数前后值、状态变化与清框理由 |
| 恢复与补跟踪 | 缓存查找范围、未命中；初始化输入及结果；每个后续帧的返回、框、分数和耗时；汇总尝试/成功/失败 |
| 业务输出 | 显示框与实时框及有效性、跟踪标志、状态、发布调用起止与异常、未消费时不发布 |

IoU 是交集面积除以并集面积，用于核对两个框的匹配程度。理由码包括 `NO_TARGET`、`LOW_IOU`、`YOLO_JUMP`、`NANO_JUMP`、`NO_RESULT_TIMEOUT`、`HISTORY_MISS`、`INIT_FAILED`。不同事件分别记录原因，不能用单一失败标志替代。

**理由：** 本次问题需要逐次检测和恢复的证据，只有总体耗时或每秒计数不能追溯。

**替代方案：** 全量图像与模型输出开销过大；随机采样会漏掉决定状态的那次结果；每条消息直接打印增加格式化和输出成本，均不采用。

**后果：** 仲裁和检测共享状态在既有锁内取得定长快照，在锁外提交；不增加业务锁。 初始化底层失败另以数值有效位区分未知：预处理错误域为 1，模型错误域为 2，数值来自原错误枚举。旧记录没有有效位时不解释其负载为错误码。新增跟踪更新失败理由和跳变比较事件追加在既有编号之后，保持版本 1、256 字节布局与 8 MiB 预算。跟踪跳变记录实际修改前值、增加值、最终值；额外有效位区分其计数布局与 YOLO 未确认布局。阈值前目标最高分和过滤计数只在现有候选循环中顺带取得，并记录“阈值前候选”或其他真实范围。未执行、候选不存在和不可观测使用不同有效标志。NanoTrack 框、分数复用已有诊断字段；初始化失败保留第一层失败阶段和底层错误码，长错误文本在非实时故障路径有限保存，不能在热路径拼字符串。

基础模式对重复正常路径采用定长汇总字段减少事件数，但每次调用、每个补帧步骤和每次检测的上述证据不能省略。细分模式复用 `timing::Observation`，以预分配阶段数组承接回调，再输出定长事件；保留未完成阶段标志，不增加模型调用。常规终端健康摘要每秒最多一次，结构化逐帧文件不逐条镜像到 journal。

例如：请求 17 来自算法帧 100，检测成功；调用 139 读取结果时缓存为 110–139；记录 `HISTORY_MISS` 并保持无效输出。这个链条可以确认“检测成功但来源已淘汰”。若请求结束事件存在缺口，则只能报告结果未知。

### 6. 批量写入、周期同步与真实提交边界

**选择：** 日志进程生成版本化二进制记录。每条记录带类型、长度和 CRC 校验；CRC 用于检查记录内容损坏，不提供身份认证。每批有独立完整边界。批量 `write()` 后才释放对应共享槽，默认每 100 ms 执行一次 `fdatasync()`，允许配置 200 ms。`fdatasync()` 请求操作系统把文件数据及必要元数据同步到存储。

**理由：** 批量减少系统调用，短周期降低一般情况下尚未同步的数据量。成功返回与具体数据位置关联，才能说明保存到了哪里。

**替代方案：** 每事件同步造成大量存储等待；仅调用应用缓冲 `flush` 或按固定时间宣称落盘不能说明数据持久化，因此不采用。

**后果：** 按生产者维护三个位置向量：`generated` 是尝试生成的末序号，`written` 是完整写入文件的末序号，`synced` 是已成功同步的记录边界。位置携带已知缺口，序号大不表示此前每条记录都存在。跨生产者及普通/关键区记录可能乱序到盘，因此提交向量只确认真实写入集合和缺口，不能把最大序号当连续完整前缀。

每次周期提交按以下顺序：

1. 写完当前批次的数据及缺口摘要，记录涉及的文件偏移和生产者位置。
2. 数据文件 `fdatasync()` 成功后，追加引用该边界的提交记录。
3. 提交记录自身同步成功后，向共享状态公布 `synced` 和同步完成时间。失败保留原确认位置。
4. 新文件创建和段文件改名完成后，同步父目录，才声明相关路径变化已完成。

离线仅使用完整可校验的提交记录解释此前成功的数据同步边界。运行时确认与重启后可恢复的提交位置分别报告，不能通过文件大小补出成功同步位置。文件底层缓存和系统行为仍有边界，不能保证存储损坏后恢复。

关键事件触发立即调度排空及同步；同一批关键事件合并处理，当前同步完成后再处理新的同步请求。这里的“立即”指不额外等待下一周期，不表示能打断正在阻塞的系统调用。同步期间业务继续提交；缓冲满按缺口规则处理。

### 7. 存储退化、异常恢复与离线工具

**选择：** 默认诊断目录拟为 `/var/lib/drone_tracker/diagnostics`，每次业务运行独立目录，段上限 64 MiB、诊断总量上限 1 GiB、最低空余 5 GiB。达到保护阈值停止新增写入，不自动删除旧记录。配置与模式启动后固定；日志进程配置独立于现有录像同步周期。

**理由：** 诊断必须保存异常证据，同时不挤占已有录像空间或覆盖原文件。

**替代方案：** 自动循环覆盖可能删掉用户尚未备份的失败现场；把二进制诊断附加到 ROS 文本日志破坏检查与轮转边界，因此不采用。

**后果：** 日志进程维护排队等待、同步耗时、最新生成与同步位置、最旧未同步记录年龄及错误码。持续输入且年龄超过 500 ms 标记退化；未知同步位置不能当零。共享状态供既有控制路径检查，每秒至多输出一次健康摘要，状态变化立即输出一次。写入/同步错误不推进确认位置；当前调用阻塞时共享起始时间仍可供业务判断无进展，不要求业务打断写盘。

正常退出在预算内尽量同步并写完成标志。超时或异常退出留下不完整状态。只读 `rk3576_diagnostic_inspect` 输出检查结果、中文时间线、JSONL 和 CSV，导出目录必须新建。JSONL 是每行一条 JSON 对象，CSV 是逗号分列的表格文本。截断或损坏时导出已验证的完整批次前缀，不修复原文件；重复事件按运行、生产者和序号去重并报告。

运行清单保存程序、模型、配置文件指纹和板卡身份。使用已有打包清单和启动配置取得身份，不在每帧计算文件哈希。未知版本或缺少身份时检查报告明确标注；没有完成标志不能据此认为业务全程无事件。内存队列及操作系统未同步缓存都可能在突然断电时丢失，100 ms 周期没有固定最大丢失窗。

### 8. 用短时受控对照验收开销与隔离

**选择：** 基础模式单组目标为事件提交 P99 ≤20 μs、完整跟踪调用 P99 增量 ≤0.2 ms、有效消费帧率相对下降 ≤1%、健康运行无诊断缺口。P99 是按排序后第 `ceil(0.99×N)` 个样本取得的值。执行十组完整关闭/基础成对对照；至少八组同时满足全部单组门槛，任务 7.3 才完成。细分阶段启用开销另列，不能用于基础模式通过结论。

**理由：** 独立进程仍争用 CPU 和同一 eMMC，异步架构不能自动证明没有性能影响。

**替代方案：** 只观察平均帧率会掩盖慢调用；估算并扣除记录开销不能反映实际体验；长时间压力测试超出此次授权边界，因此不采用。

**后果：** 业务事件提交区间使用独立预分配测量数组保存，不通过被测日志反复递归记录。受控输入注入固定检测结果，验证关闭/基础/细分时算法输出和调用次数一致；真实异步模型因调度改变可能选择不同帧，单列处理帧身份与差异，不宣称必然逐条相同。固定输入、同一板卡和模型下再量化端到端影响，保留所有慢样本。

性能样例安排为十组各不超过 150 秒的成对测试：准备/预热不超过 20 秒，两个有效测量窗口各 45 秒，收尾与切换不超过 40 秒。两个窗口的先后次序交替，保持原画录像、bag、HDMI 和模型设置一致，不拼接为一次长测。每组独立计算全部门槛，超时、样本不足或资源未回收均记该组失败。保留全部十组原始数据和慢样本，不删失败组，不以平均指标判定，不把一个测量窗口内的子样本当作不同组。若修复后重测，保留旧批次，并重新执行完整十组，不能只补挑通过组。例如十组中八组各自满足全部门槛则完成；只有七组满足时仍未完成。细分模式使用一轮不超过 150 秒定向对照。稳定性定向运行不超过 150 秒，包含有限 ON/OFF 与资源检查，不能声称长期稳定。

外部单项截止采用 Linux 子收割者（`PR_SET_CHILD_SUBREAPER`）接管脱离会话的后代。以父子关系及进程启动时间核对实例，有限 TERM/KILL 后检查实际存活者。由 systemd 创建的独立服务在启动前登记单元，截止控制器停止其自动重启并核对控制组成员。未知或未回收不得判通过。不支持子收割者的平台拒绝开始这类测试；不能用控制器已退出推断所有资源回收。正式服务的 30 分钟独立恢复守护仅保护维护窗口，不代替单项截止。

所有单次性能或稳定性测试上限为 600 秒，包括准备、预热与收尾；涉及既有相机性能或负载契约时上限为 180 秒，外部控制器应在更早的停止点发出退出，并预留清理时间。同步卡住时控制器有限停止测试进程并报告资源仍未回收，不能用无限等待让测试超限。目标不入镜或有效样本不足就记录未通过，不能延长窗口越过上限。

故障检查覆盖：来源淘汰、单次初始化失败、部分补帧失败、未读结果覆盖、队列满、日志不可用、业务和日志进程分别异常退出、写入/同步错误、文件副本截断及新轮隔离。使用隔离测试实例；不得误杀生产服务。每个故障检查预算不超过 120 秒。以上均不能替代真实断电验收。

## Risks / Trade-offs

- [共享队列或版本错误造成并发读取问题] → 定长协议、对齐检查、单写单读、跨进程测试和消费者唯一性核验；复用录像共享槽的边界经验，不直接混用其图像区域。
- [关键事件也可能丢失] → 预留容量并报告序号缺口；证据不完整时不作确定因果判断。
- [两个独立进程仍共享 CPU 与存储] → 日志进程继承既有允许核心范围，使用普通调度；读回范围，不修改业务职责映射；并行录像与 HDMI 下实测。
- [日志重启遇到未释放的旧消费者] → 不接管、不增加共享区域，诊断降级并保留旧实例信息；业务继续。
- [短周期双阶段同步造成尾部延迟] → 批次合并、关键通知节流，并测实际队列等待与同步耗时；不能静默放宽周期或性能门槛。
- [业务崩溃前的最后事件未完成提交，或突然断电丢失尾部] → 保留可校验前缀与恢复提交位置，标出未知尾部；不承诺最后错误必然可见。
- [其他在途变更修改 NanoTrack 前处理] → 接入只读观测边界，不实现前处理优化；正式对照记录代码与模型指纹，避免混用性能证据。

## Migration Plan

1. 在实施阶段新增协议、日志进程和检查器，再接入业务观测点，先完成受控兼容及故障检查。
2. 构建 ARM64 安装产物，把新增程序、服务与配置加入生产包并校验指纹；系统 RKNN Runtime 保持既定版本。
3. 用隔离实例完成指定生产板短测，保留配置、板卡、模型、输入与全部原始数据；未达到门槛不勾选验收。
4. 后续正式部署使用既有部署流程备份旧入口和配置。日志服务先可用，主业务再连接；连接失败按诊断退化运行。
5. 回退恢复旧业务与服务配置，同时停止不匹配的新日志服务；旧格式、新格式日志均保留，以对应离线工具读取。

本次仅生成上述规划工件，没有执行这些迁移步骤。
