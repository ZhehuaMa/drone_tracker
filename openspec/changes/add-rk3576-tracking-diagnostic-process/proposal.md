# Proposal

## Why

外场视频中的目标仍然清晰时，跟踪框可能连续消失，但当前日志不足以判断是检测失败、结果没有被读取、历史帧已经淘汰，还是恢复跟踪耗时造成了发布间隔。需要记录检测与跟踪之间的完整处理关系，同时把日志写盘故障隔离到独立进程，控制对实时跟踪的影响。

## What Changes

- 增加独立日志进程，负责收集结构化事件、批量写入和周期同步到存储。业务进程不创建专用日志线程。
- 通过预分配共享内存传输事件。业务执行路径只写定长记录，不等待日志消费或存储同步；满队列和日志不可用均显式记录诊断缺口。
- 为采集帧、跟踪调用、YOLO 检测请求及结果建立关联身份。YOLO 是检测目标的模型；NanoTrack 是用检测框初始化后逐帧跟踪的算法。记录检测请求拒绝、结果覆盖、历史缓存未命中、NanoTrack 初始化及逐步补跟踪结果。
- 区分帧源时间、`ctx.now_us` 预测时间、实际调用起止时间，以及 ROS 发布调用时间。记录相机持续采集与节点只取最新帧之间的丢弃关系。
- 提供关闭、基础和细分三种记录模式。基础模式保留诊断因果链，细分模式额外记录模型阶段耗时。生产模板默认基础模式，其他入口保持兼容。
- 默认每 100 ms 请求文件数据同步；关键故障事件促使日志进程尽快同步。报告已生成、已写入和已成功同步的位置，以及缺口和同步落后。突然断电后只能按完整记录恢复，不能保证最后事件留存，也不能将 100 ms 视为最大损失时间。
- 增加只读离线检查与导出工具，输出中文时间线、JSONL 和 CSV。JSONL 是每行一条 JSON 记录的文本格式。原始日志及现有视频、bag 文件保持不变。
- 增加独立日志服务的打包、预检、启停和回退规则。主业务异常退出后，日志服务仍有机会排空已提交记录。
- 验收使用短时对照和受控故障注入。任何单次性能或稳定性测试最长 600 秒；已有规格要求 180 秒的相机性能或负载测试继续按更短上限执行。
- 基础模式开销验收执行十组完整的关闭/基础（`off`/`basic`）成对对照，每组总时间不超过 150 秒。至少八组同时满足全部单组门槛，任务 7.3 才完成。保留全部十组原始数据和失败结果，不以平均值或窗口内子样本代替组数。

例如，一次跟踪调用读取到来自旧帧的成功检测后，可能因历史缓存找不到该帧而无法恢复。变更前只能看到无效框；变更后可以依次查到检测请求身份、成功结果、读取它的调用、缓存范围及未命中原因。若这些记录有丢失，报告会明确标为证据不足。

## Capabilities

### New Capabilities

- `rk3576-tracking-diagnostics`：检测跟踪事件关联、独立进程通信、有界记录、存储同步、异常尾部恢复和诊断开销验收。

### Modified Capabilities

- `production-binary-deployment`：把日志进程及检查工具纳入生产包，安装具有独立生命周期的日志服务，并保持预检、CPU 允许范围与回退一致性。

## Impact

- 观测接入点：`src/drone_tracker_node.*`、`src/platform/frame_source_ops.h`、RK3576 相机帧源及帧元数据、`src/hybrid_tracker/hybrid_tracker.cpp`、`yolo_detector.*`、`nano_tracker.*` 和既有 `timing_observer.h`。
- 拟新增 `src/diagnostics/`，包含定长事件、业务端发送器、Linux 共享内存协议、日志工作进程和离线检查器，并纳入 CMake 安装与测试。
- 生产集成涉及 `parameters/`、`deployment/` 的服务、打包、预检及文档。使用 Linux 原生共享内存、通知和文件同步接口，不增加数据库或网络日志依赖，不替换系统 RKNN Runtime。
- 保持 ROS 话题、消息类型、时间戳、四种 `TrackerState` 数值、检测队列行为、历史缓存容量和算法结果语义。日志开销目标须通过生产板验证，不能承诺绝对零开销。
- 本次交付仅为 OpenSpec 规划工件。实现、构建、实机测试及部署均待后续实施阶段；不包含供电相关能力或实际断电实验。
