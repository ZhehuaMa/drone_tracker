# CPU 绑定退化与诊断收集开销调查

日期：2026-10-28。变更：`add-rk3576-tracking-diagnostic-process`。对应任务：7.3。

## 结论

CPU 3 和 CPU 7 的绑定复测没有证明核心位置是此前失败的唯一原因。本次复算确认，下午两批基础模式的全部 328 次尾部调用都执行了大量历史帧补跟踪。这里的补跟踪，是从检测来源帧开始，逐帧把目标位置推进到当前帧。不同的异步检测完成时刻会改变这项实际工作，因此相同视频不保证两次运行有相同的调用耗时。

同时，工作量变化不能解释全部诊断成本。本次用完全相同的真实模型调用和输出执行固定工作量对照，原收集器仍有 **5.184276 ms** 的完整调用 P99 增量。P99 是排序后第 `ceil(0.99 × 样本数)` 个耗时。修复收集器中两项可避免的工作后，新一轮观测增量为 **3.154330 ms**；普通更新的增量仍为 **0.322776 ms**。这些实验不是正式十组验收，且两个版本顺序运行，不能把两轮差值全部归因于代码。

进一步观测发现，允许范围为 CPU 4–7 的收集器，在每次已采样的最近运行位置中都位于 CPU 4，与跟踪线程相同。把同一优化收集器改到 CPU 7 后，普通调用的成对耗时增量中位数由 **0.198679 ms** 降至 **0.011686 ms**，长调用由 **3.686827 ms** 降至 **0.645095 ms**。跟踪线程可运行却未得到 CPU 的等待也由约 34.13 降至 25.10 ms/s。这些证据强烈支持同核竞争是实际开销的一项来源；顺序实验和稀疏位置采样仍不能证明每次慢调用的唯一原因。

CPU 7 轮的普通调用 P99 增量反而是 **0.782866 ms**，高于前轮 0.322776 ms。也就是说，固定工作量下，典型额外等待明显减少时，两个独立尾部分位数之差仍可能变大。下午完整管线还叠加了不同补帧数量。因此“通过组数更少”不能单独证明绑定核心使实际诊断成本更大。

已实施的修复是用编译期查表替代逐位校验，以及按批次发布共享写入位置。实机独立校验实验证明，256 字节至 512 KiB 输入的校验 CPU 时间减少约 **3.9–4.2 倍**，全部校验值保持一致。KiB 是 1024 字节。阶段实验把大部分剩余增量定位到四种已观测 RKNN 调用之外，而不是 `rknn_run` 本身。该范围还包含预处理、后处理、诊断提交及未观测的共享内存绑定调用，不能统一称为纯 CPU 或设备等待。

**任务 7.3 保持未完成，进度保持 39/40。没有放宽门槛、修改跟踪算法或用本次归因实验代替完整十组。** 正式部署、模型、配置、系统 Runtime 和服务状态均保持原样。

## 下午两批为何不能直接比较通过组数

CPU 亲和性表示线程允许在哪些核心上运行，不表示独占该核心。板端身份和缓存信息确认，CPU 3 属于 CPU 0–3 的核心簇，其二级缓存为 512 KiB；CPU 7 属于 CPU 4–7 的核心簇，其二级缓存为 1 MiB。CPU 3 还与原控制器和 ROS 消息录制程序共享允许范围；CPU 7 与采集职责共享。两种绑定都没有建立独占隔离。

独立校验实验中，CPU 3 的原校验函数耗用 CPU 时间比 CPU 7 高约 18%。这是校验函数的结果，不能外推为完整跟踪慢 18%。两个核心簇的共享数据交互和职责争用也不同；本次没有把它们宣称为已独立测出的完整退化原因。

对下午原始 CSV 和基础事件的重新计算如下。`off` 表示关闭诊断，`basic` 表示基础诊断。每批仍保留原来的全部十组窗口和判定。

| 批次 | 原通过组数 | 基础模式 P99 及以上调用数 | 每个尾部调用的补帧步数范围 | 初始化加补帧区间占完整调用的最小比例 |
| --- | ---: | ---: | ---: | ---: |
| CPU 3、风扇 | 2/10 | 165 | 13–28 | 93.576964% |
| CPU 7、风扇 | 3/10 | 163 | 11–29 | 92.203901% |

这些比例用于定位大段耗时，不是“纯 NPU 时间”。NPU 是运行神经网络的专用处理器；上述区间还可能包含 CPU 处理和内部观测工作。原 `off` 数据没有同级逐步工作量记录，因此不能逐一确定每个失败组的唯一原因。

代码机制与既有调查一致：检测工作线程取走待处理请求后，业务可以再保存一个来源较旧的请求。读取结果时，跟踪器对该来源之后的已消费历史帧逐步恢复。长调用还会改变下一次取最新帧的结果，继续影响后续检测内容和补帧数量。没有改变这一继承自参考实现的处理规则。

## 已实施的修复及其边界

修改文件为 `src/diagnostics/storage.cpp`：

1. 原 `crc32()` 对每个字节执行八轮位运算。CRC-32 是检查日志记录是否损坏的校验值。新实现使用编译期生成的 256 项只读表，以每字节一次表查询计算同一种 IEEE CRC-32。表占 1 KiB，不需要新增依赖或可选 ARM 指令。已保存日志的校验值和记录格式不变。
2. 原 `Storage::append()` 在整个批次完整写入后，仍逐条向共享 `written` 原子计数器写值。该计数器与生产者更新的 `generated` 位于同一个 64 字节缓存行。缓存行是 CPU 在核心之间保持数据一致的基本单位。重复写入会增加这组共享数据的交互。新实现先在收集器私有数组汇总，再对本批发生变化的生产者各发布一次最终位置。

位置仍在完整批次写入成功后发布；写入失败不推进位置。关键标志、缺口、批次内容、两阶段文件同步、100 ms 周期和成功同步位置的规则保持不变。没有减少基础事件、延迟业务提交或增加业务锁。

`src/diagnostics/tests/diagnostic_test.cpp` 增加独立的 CRC 兼容检查：空输入、标准字符串校验值、不同对齐位置、短记录和 4096 字节批次，与原逐位计算逐项核对。板端的独立实验进一步使用 Python `zlib.crc32` 检查全部 100 项结果。

## 新的真实模型对照

为隔离收集器变化，使用已归档的固定工作量程序。它在同一进程中按种子 `20261028` 随机交换相邻 `off`/`basic` 顺序，共 40 对、80 段，每段 40 次调用。每段严格核对一次模板初始化、39 次真实搜索，以及相同框、分数、状态和消费结果。长调用固定初始化并处理 19 步历史帧。

两种模式的内部事件摘要、阶段和模型审计观察器都关闭，仅对称保留外层完整调用时间及线程 CPU 时间。每段切换前确认共享区排空和同步完成。关闭段仍保留空闲收集器及共享区，因此该实验只用于归因，不代表正式关闭模式的全部部署行为。

| 实验 | 收集器 | off 完整调用 P99 ms | basic 完整调用 P99 ms | 原始增量 ms | 连续五相邻对重采样 95% 区间 ms |
| --- | --- | ---: | ---: | ---: | --- |
| 原基线 | 原实现 | 471.823139 | 477.007415 | 5.184276 | [4.042096, 5.783732] |
| 优化候选 | 查表校验、批次位置发布 | 469.966776 | 473.121106 | 3.154330 | [1.877571, 5.138799] |
| 去通知归因 | 同一优化候选，实验程序省略诊断通知写入 | 476.674648 | 480.042386 | 3.367738 | [2.106860, 3.980794] |

重采样以相邻成对数据为单位，并连续抽取五对，保留部分邻近相关性。区间只描述本次运行内的不确定性。各实验顺序进行，不能据其差值或区间重叠宣称已完成跨版本因果比较。

原基线长调用的成对耗时增量中位数为 4.958781 ms，线程 CPU 增量为 0.603661 ms，完整耗时减线程 CPU 的增量为 4.3729995 ms。优化候选相应为 3.6868265、0.4493555 和 3.567065 ms。三项分别求中位数，不能相加当作精确分解。线程没有使用 CPU 的区间可以包含可运行却未被调度的等待，也可以包含设备驱动内的睡眠；不能一律称为 NPU 或磁盘等待。

优化候选收集器在 85.672942 秒资源采样区间内使用 0.708876 秒 CPU，即单核约 0.827421%；可运行调度等待约 0.990509 ms/s。跟踪主线程可运行调度等待约 34.133683 ms/s。原基线的进程观测存在收集缺陷：该板没有 `/proc/PID/io`，过宽的异常处理丢弃了其他有效字段。已将这项缺口明确记录，原件未改写；不能用它比较两轮的收集器 CPU 占用。

### 通知归因没有形成可采用的修复

源码中收集器 `poll()` 仅等待连接监听描述符，未等待 `eventfd` 通知描述符；收集器每 10 ms 主动检查共享区。`eventfd` 是进程之间传递唤醒计数的 Linux 描述符。不能把业务通知次数直接当成收集器被唤醒次数。

本次仅在隔离实验中使用动态加载包装器，核对诊断共享内存名称及描述符类型后，省略该诊断通知的 8 字节写入。没有拦截其他模型或系统描述符。实验确认一个诊断描述符，省略 1644 次通知写入，全部事件仍被原轮询消费，工作量、输出和排空检查通过且无缺口。

省略全部通知后，完整 P99 增量仍为 3.367738 ms。它没有消除剩余延迟，因此没有将通知省略写入正式代码，也没有据此更改通知或同步策略。包装器仅保存在实验原件目录。

三轮全部保留 3200 次调用和全部慢样本；逐步工作、输出、最终排空及检查器核验均通过。分析见 [baseline-analysis.json](baseline-analysis.json)、[optimized-analysis.json](optimized-analysis.json) 和 [notification-analysis.json](notification-analysis.json)。

### 剩余时间主要位于已观测 RKNN 调用之外

新的独立短实验在同一规范程序上执行 16 段、8 对，共 640 次调用。包装器原样转发 `rknn_inputs_set`、`rknn_run`、`rknn_outputs_get` 和 `rknn_outputs_release`，分别表示设置模型输入、执行模型、取得输出及释放输出。它只在预分配数组中记录每次调用的时间和线程 CPU 时间，进程退出后再导出。没有增加模型调用或修改张量内容。

| 成对增量中位数 | 普通调用 ms | 初始化加 19 步补帧 ms |
| --- | ---: | ---: |
| 完整跟踪调用 | 0.254107 | 3.564281 |
| 四种已观测 RKNN 调用之外 | 0.233214 | 3.580140 |
| 其中不计入线程 CPU 的区间 | 0.217343 | 3.558149 |
| `rknn_run` 内 | 0.002321 | -0.054978 |

这些分别计算的中位数不能直接相加。用可相加的成对均值检查，普通调用完整增量为 0.236180 ms，已观测调用内为 0.012443 ms，调用外为 0.223738 ms。它支持主要增量位于该观测范围之外，但不是具体内核等待的唯一归因。

每个调用的 API 顺序和数量均与实际模板、搜索 Backbone 和 Head 工作一致。测量期输入设置和执行各 1264 次，输出取得和释放各 640 次；Backbone 的共享输出路径不增加输出读取。包括准备阶段在内共保存 4424 条记录，观察数组占 251904 字节，无溢出。空观察器在 CPU 4 的墙钟成本中位数为 1.242 μs，P99 为 1.288 μs，空对照中位数为 46 ns。没有扣除这些成本来判门槛通过。

该轮 16 次有效位置观测中，跟踪线程和收集器的最近运行位置均为 CPU 4，收集器 CPU 占用约单核 0.821%。这与前轮约 0.83% 的普通调用相对耗时增加一致，但还不能代替连续调度事件证明逐次重叠。全部结果见 [rknn-stage-analysis.json](rknn-stage-analysis.json) 和 [rknn-stage-telemetry.json](rknn-stage-telemetry.json)。

### 固定工作量 CPU 7 对照支持同核竞争这一解释

另一个新代理将同一优化收集器单独绑定 CPU 7，其他程序、输入、种子、模型、100 ms 同步、普通调度及全部 80 段规则不变，没有加载任何包装器。该轮仍完整保存 40 对、3200 次调用。

| 指标 | 优化收集器允许 CPU 4–7 | 同一收集器绑定 CPU 7 |
| --- | ---: | ---: |
| 普通调用成对墙钟增量中位数 ms | 0.198679 | 0.011686 |
| 长调用成对墙钟增量中位数 ms | 3.686827 | 0.645095 |
| 跟踪线程可运行等待 ms/s | 34.133683 | 25.101198 |
| 完整调用 P99 增量 ms | 3.154330 | 0.964324 |

允许 CPU 4–7 的原优化轮中，全部 86 个已保存位置样本都显示收集器最近位于 CPU 4；CPU 7 轮的 83 个实际调用区间样本中，跟踪线程为 CPU 4、收集器为 CPU 7，调度策略均匹配。等待减少约 9.03 ms/s，与此前收集器约 8.27 ms/s 的 CPU 使用量相近。这解释了为何仅设置宽范围不等于避开跟踪核心。

CPU 7 轮完整 P99 增量的连续五对重采样区间为 [-0.715308, 1.688559] ms，普通调用为 [-0.579082, 1.333349] ms。典型耗时减少不等于已经建立 0.2 ms 的尾部保证。CPU 7 轮也没有并发相机或显示，因此不能把它直接当成正式生产中与采集共享 CPU 7 的结论。CPU 放置条件顺序执行，其他时间因素仍可能变化。

本轮仅改变实验放置，没有修改正式启动策略。现有部署规格要求收集器从同一 CPU 策略读取并读回完整允许范围；不能在未修订该契约时把实验中的单核绑定写成正式修复。分析见 [fixed-cpu7-analysis.json](fixed-cpu7-analysis.json) 和 [fixed-cpu7-telemetry.json](fixed-cpu7-telemetry.json)。
