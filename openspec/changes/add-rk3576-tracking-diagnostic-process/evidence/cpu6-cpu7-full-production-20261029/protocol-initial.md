# 完整生产负载下的 CPU 6 与 CPU 7 对照方案

日期：2026-10-29。对应变更：`add-rk3576-tracking-diagnostic-process`。

## 目的与范围

在同一 HZ-RK3576_WuKong 生产板上，比较把独立诊断收集器绑定到 CPU 6 或 CPU 7 的效果。CPU 绑定表示限制收集器允许运行的核心，不表示独占该核心。CPU 6 当前承担显示，CPU 7 承担相机采集与原画录像。对照应回答它们在实际并发工作下的差异，不能用不包含采集和录像的固定模型实验代替。

这是用户授权的核心放置比较，不是任务 7.3 的新十组关闭/基础验收。任务 7.3 保持未勾选。实验不更改正式启动策略、跟踪算法、模型、阈值、系统 Runtime 或其他业务职责。

## 固定工作负载

使用当前通过 63/63 自动测试的 ARM64 安装产物，其中包含查表校验与批次写入位置发布优化。冻结整个安装目录的文件摘要，所有实验使用同一份副本。SHA-256 是核对文件内容的摘要。

从板端实际 `/opt/drone_tracker/config/camera.yaml` 生成隔离配置，保留以下生产行为：

- SC233HGS 连续采集，1920×1200 NV12，60 FPS，使用当前 `/dev/video22` 和 `/dev/media2` 拓扑。
- 原气球 YOLO、FP16 NanoTrack 模型及原检测、跟踪参数。YOLO 负责检测，NanoTrack 根据初始框推进目标位置。必须从记录确认两者确实执行，不能把“模型已加载”当作已运行完整跟踪负载。
- 独立原画录像启用，12 Mbps，60 秒分段，1000 ms 同步，20 GiB 总量及 5 GiB 空余保护。
- `need_save=true`，使用当前节点的内部 ROS 消息录像，不额外叠加外部 `ros2 bag` 进程。
- HDMI 启用，720×480、60 Hz；`osd.timing_enabled=true`，`visualized_result=false`。保持原生产显示工作，不能套用旧验收程序关闭计时或开启调试图像的设置。
- 诊断模式固定为 `basic`，即完整基础事件记录；独立收集器使用普通 `SCHED_OTHER` 调度和 100 ms 存储同步。

仅重定向实验的诊断端点、诊断目录、原画录像目录和内部消息录像目录。业务继续使用既有职责：跟踪/控制 CPU 4，检测 CPU 5，显示 CPU 6，采集/原画录像 CPU 7。实验控制器使用 CPU 0–3。除收集器的 CPU 6/7 限制外，八轮配置一致。

所有实例使用隔离 ROS 域 198 和本机通信。姿态和位置由控制器各以固定 50 Hz 提供相同的合成输入，发布节奏不随框消息回调数量变化，并记录实际次数。不能把该结果当作实飞验收。已有 interceptor 和 bridge 进程保持运行，不发送会进入其正式 ROS 域的实验命令。

真实相机场景不保证像固定视频一样逐帧相同。应保持目标和照明不变，并记录检测、初始化和补跟踪数量。如果没有目标，或者 NanoTrack 未执行，该轮仍完整保留，但不能列为完整跟踪工作负载的有效样本。

## 顺序、时限与执行身份

计划八轮，每轮为一个独立实验，分别由一个新建子代理执行。核心顺序在结果出现前固定为：

| 轮次 | 收集器 CPU |
| --- | ---: |
| 1 | 6 |
| 2 | 7 |
| 3 | 7 |
| 4 | 6 |
| 5 | 7 |
| 6 | 6 |
| 7 | 6 |
| 8 | 7 |

相邻两轮构成四组核心比较，先后顺序各占两组。这个顺序用于减轻时间和预热趋势的影响，不保证消除相机场景与异步检测的全部差异。实验串行运行，不让两个跟踪实例争用相机、显示或 NPU。NPU 是运行模型的专用处理器。

每轮计划一个 ON/OFF 周期，预热 6 秒，正式测量 60 秒。相机、检测、跟踪、两类录像、显示和诊断同时运行。全部调用保留；测量结束前开始的调用使用完整返回耗时。

每轮由独立 systemd 控制组设置 140 秒运行上限、5 秒停止预算，并设 150 秒外部截止。计时包含启动、模型准备、预热、测量及业务收尾。控制组是系统统一管理并终止的一组进程，必须覆盖后来创建的录像等后代进程。只读离线统计及原件传输可在业务退出后进行，单列其耗时，不延长硬件工作负载。

每次板端访问和传输仅使用 `ssh firefly-production`，并先加载 ROS 环境。正式跟踪服务当前停止，应维持原状态；不修改开机启用设置。每轮开始及结束核对板卡、启动身份、全部程序/配置/模型和系统库摘要。只清理该轮所属进程，不终止既有 interceptor、bridge 或其他程序。

## 指标与有效性检查

主指标是完整窗口内的实际消费帧率和跟踪调用 P50、P95、P99。P99 是排序后第 `ceil(0.99 × 样本数)` 个耗时。另保留最大值及全部慢样本，不截去最慢调用，不以平均值代替尾部结果。

同时报告以下内容，用于解释核心选择和排除负载缺失：

1. 事件提交 P99、诊断缺口、健康状态、完整结束及成功同步边界。
2. 实际采集帧率、驱动序号缺口、队列满拒收及节点取最新帧跳过；区分这些不同原因。
3. 检测执行和成功数量、NanoTrack 初始化、普通更新及补帧步数、有效输出与状态分布。工作量不同时明确标注，不能把额外模型工作算成固定诊断成本。
4. 收集器、跟踪、显示、采集和录像线程的实际 CPU 范围、最近运行核心、CPU 时间及可运行调度等待。可运行等待表示线程已准备执行却未得到 CPU，不等同于设备等待。
5. 原画录像的接收、编码、写入、同步、丢弃、取消及最终成功状态；内部消息录像的接收、写入、丢弃和数据库记录数。
6. HDMI 实际提交证据及卡顿相关日志，不只核对配置开关。
7. 温度、CPU/NPU 频率、内存及存储状态。采样间隔约一秒，原件保留；不把稀疏频率采样当作全时固定频率证明。

每轮均须正常有限退出、释放相机/显示控制权，且控制组无残留成员。缺少必需负载、样本不足、超时、错误或收尾失败都单独记为失败，不删除或改名成有效样本。基础设施错误修复如需重新开始，使用新目录和新代理，并完整保留此前尝试；不得因性能结果不利而选择性补跑。

## 比较与交付

逐轮列出全部指标，再按四个相邻核心对报告差值及方向。结合实际工作量、录像/显示完整性和调度等待判断。每个核心只有四轮短测，不宣称已经证明长期最优。如果不同轮次结论不一致或场景不满足要求，应报告无法选出可靠优胜核心。

完整原件放在 `.docker-artifacts/cpu6-cpu7-full-production-20261029/`，包括控制脚本、冻结指纹、实际 YAML、调用和提交 CSV、基础事件、原画录像、内部消息录像、资源采样、截止与清理记录。报告和摘要放在本目录。原件传输后逐文件核对 SHA-256，保留失败尝试。比较结束后保持正式部署与服务状态不变。
