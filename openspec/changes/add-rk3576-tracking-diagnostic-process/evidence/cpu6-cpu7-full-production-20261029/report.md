# 完整生产负载下的 CPU 6 / CPU 7 收集器比较

日期：2026-10-29，时区 Asia/Shanghai。对应变更：`add-rk3576-tracking-diagnostic-process`。

## 结论与适用范围

本批支持**暂时优先选择 CPU 6**，但优势较小，不能证明长期最优。八轮均实际运行相机、YOLO 检测、NanoTrack 跟踪、原画录像、内部 ROS 消息录像、HDMI 显示和基础诊断。CPU 6 的消费帧率中位数高约 0.94%，调用 P99 中位数低约 0.352 ms（1.65%）。P99 表示该轮排序后覆盖 99% 调用的耗时。

同时，第七轮 CPU 6 出现 49 帧驱动序号缺口，伴随约 870 ms 的相机交付停顿。该轮完整计入比较，没有剔除或补跑。原因尚未确定，不能把本批描述为“CPU 6 无丢帧”或完整生产验收通过。

## 实际负载与数据完整性

用户摆放气球后，独立的新子代理采集 30 帧确认场景。时间为 12:05:08，选取第 30 帧。气球在画面中偏右、亮灯旁清晰可见。该检查未运行模型，也未手动调整曝光；自动曝光使读值发生变化。[场景摘要](scene-check-20261029/summary.json) 保存原始帧及 PNG 摘要。图像位于仓库根目录下 `.docker-artifacts/cpu6-cpu7-full-production-20261029/scene-check-20261029/last-frame.png`。

八轮使用同一冻结安装产物及模型。配置仅有输出目录和诊断端点路径差异，独立分析器归一化这些路径后确认一致。保留以下生产设置与实际工作：

- SC233HGS 相机 `/dev/video22`、`/dev/media2`，NV12 1920×1200、60 FPS，四个相机缓冲。
- 原气球 YOLO、FP16 NanoTrack 模型及原阈值。测量内共 18942 次调用，全部关联诊断身份并产生成功跟踪输出。每轮初始化与四步补跟踪发生在预热阶段；测量内均无重新初始化或补跟踪。
- 原画录像 12 Mbps、60 秒分段、1000 ms 同步、20 GiB 总量及 5 GiB 空余保护。全周期共 24377 帧，接收、编码、写入、同步数一致，录像丢弃和取消均为零。
- `need_save=true` 的内部 ROS 消息录像，不增加外部 `ros2 bag`。八个数据库完整性检查均为 `ok`，消息写入丢弃为零。
- HDMI 720×480@60，屏幕叠加显示的计时开关 `osd.timing_enabled=true`，`visualized_result=false`。每轮有实际显示和提交记录，拒收为零。
- `basic` 基础诊断，收集器普通 `SCHED_OTHER` 调度，100 ms 同步。诊断缺口、健康退化记录及性能采样溢出均为零。

测量内合成姿态、位置输入各发布 2250 次，实际频率 49.9942–49.9974 Hz，漏过时隙为零。资源观察器独立在 CPU 0–3 运行，未阻塞输入发布循环。

除第七轮外，各轮测量内有效采集 2701 帧，约 60.02 FPS；第七轮为 2652 帧、58.93 FPS。独立分析器排除“驱动序号缺口”摘要事件，该事件不应额外计为一帧。节点按既有策略取最新帧而跳过旧帧的数量逐轮为 `320,326,335,308,353,322,303,350`，与驱动缺口、录像丢弃分开统计。

全周期录像、消息录像和显示计数包含预热及收尾，不能直接除以 45 秒。[完整复算](comparison-final.json) 和 [逐轮 CSV](results.csv) 保存各自统计边界。

## 核心竞争的实际表现

CPU 绑定限制允许运行的位置，不表示独占。业务职责保持为跟踪/控制 CPU 4、检测 CPU 5、显示 CPU 6、采集及原画录像 CPU 7，仅改变收集器的 CPU 6/7 限制。

下表来自测量内约一秒间隔的线程记录。先计算每轮累计增量，再取四轮中位数。CPU 百分比以一个核心为 100%；可运行等待指线程已准备执行却未得到 CPU 的时间，不是设备等待。

| 线程指标 | 收集器在 CPU 6 | 收集器在 CPU 7 |
| --- | ---: | ---: |
| 收集器 CPU % | 3.516 | 3.196 |
| 收集器可运行等待 ms/s | 2.426 | 73.378 |
| 显示 CPU % | 27.725 | 27.834 |
| 显示可运行等待 ms/s | 22.889 | 7.882 |
| 跟踪 CPU % | 72.182 | 72.509 |
| 跟踪可运行等待 ms/s | 81.774 | 82.026 |

CPU 6 减少收集器调度等待，同时增加显示线程等待。CPU 7 承担采集和录像，收集器在那里更容易等待 CPU。各轮读取到的线程策略均为 `SCHED_OTHER`；跟踪、采集等线程的 `nice=-19`，显示和收集器为 `nice=0`。`nice` 是普通调度的权重设置，同一策略不表示权重相同。本批未修改这些值，也不推断其设置来源。

该竞争关系与暂选 CPU 6 一致，但不能单独证明全部性能差异的原因。两种放置均无诊断健康退化，收集器调度等待不等于数据丢失。

## 第七轮相机异常

测量开始约 7.62 秒后出现交付停顿。最大相邻有效采集事件间隔为 **870.433066 ms**，最大相邻调用开始间隔为 **860.706005 ms**。前一次调用返回后，到下次调用开始之间有 **841.442117 ms**，不在 `HybridTracker.update` 调用耗时内。停顿后先交付排队的旧帧，再记录驱动序号跳过 49 帧。[缺口分析](run07-camera-gap-analysis.json) 保存前后事件与调用样本。

因此，该轮 P99 为 20.889288 ms，并不意味着输出没有约 0.86 秒的中断。函数耗时不能覆盖等待输入造成的停顿。录像队列无丢弃，也只证明收到的帧成功保存，不能否认上游缺失。

一秒资源样本显示，同期一个采集职责线程的可运行等待增加约 0.862 秒，另一个采集职责线程 CPU 时间上升。没有连续调度轨迹，无法确定唯一原因，也不能将单轮缺口归因于收集器绑定 CPU 6。

结束后只读收集的内核日志包含启动/枚举附近的传感器查询失败和 MIPI CRC/ECC 消息。第七轮测量区间 `12:26:27.892510–12:27:12.897689`、第八轮 `12:29:12.404449–12:29:57.409429` 内没有日志条目。日志缺失不能证明驱动正常或解释停顿。[内核摘要](batch02-run08-cpu7/kernel-summary.json) 保存分类和原件摘要；原文在原件根目录的 `batch02-run08-cpu7/kernel-last20min.txt`。

## 尚未验证

本批使用静止气球、真实相机与生产并发功能，但姿态/位置是固定 50 Hz 合成输入，隔离 ROS 域 198 仅限本机通信。不是实飞闭环验收。自动曝光保持启用，真实图像不是逐帧相同。

采样最高温度逐轮为 `56.384,57.307,57.307,58.230,58.230,58.230,58.230,58.230°C`。一秒样本中小核/大核频率为 2016/2208 MHz，NPU 为 950 MHz，不能据稀疏采样证明全时频率不变。

每轮不足 60 秒录像分段长度，未覆盖分段切换、长期压力或真实掉电。第七轮相机停顿原因仍未确定。任务 7.3 要求的全新十组固定输入关闭/基础成对验收尚未执行，不能由本批替代，也不更改 0.2 ms 门槛。
