# 7.3 性能问题原因调查

日期：2026-10-13。变更：`add-rk3576-tracking-diagnostic-process`。

**本轮已证明，大幅调用尾部变化主要来自不同数量的真实补跟踪工作，以及异步检测来源帧的不同年龄。没有证据把它认定为诊断新增的队列或算法缺陷。没有证明基础模式满足 0.2 ms 开销门槛。** 旧正式十组仍为 7/10；任务 7.3 保持未完成，总进度 39/40。

“补跟踪”是用历史帧逐步推进跟踪位置。“来源年龄”是读取检测结果时，当前算法帧号减去检测来源帧号。每多一帧可能增加一次模型执行，因此相同视频文件不代表两次运行执行相同工作。

本轮只有独立分析副本及七组短时区分实验，没有修改工作区业务代码、算法、门槛或任务框。未提交、归档、正式升级，也没有操作另外两个 change。W6 的三个时间有效位已修复；10 月 12 日独立报告保留为修复前历史。

## 证据范围

历史原件为 `.docker-artifacts/diagnostic-warning-fixes-20261012/raw-complete/ten-final/evidence/`。本轮重新读取完整调用 CSV、窗口及基础事件，独立复算得到原十组的相同 P99 和 7/10 结果。P99 是排序后第 `ceil(0.99×N)` 个样本。

历史十组共有 **170 次**基础模式 P99 及以上调用。其初始化和补跟踪记录至少占每次慢调用的 **93.3337%**。没有初始化的调用 P99 为 **14.380–15.209 ms**，完整调用 P99 为 **189.098–262.621 ms**。例如旧第 7 组基础窗口包含 85 次初始化、884 步补跟踪。复算见 [history-recompute.json](history-recompute.json)。这批 off 原件没有同级工作量记录，因此**不能逐一证明旧第 7–9 组的唯一原因**。本轮实验验证的是同一源码机制及对称观测下的新样本，不把它冒充旧样本缺失的记录。

本轮原件根为 `.docker-artifacts/performance-investigation-20261013/`。`raw/window01`、`window02`、`window03` 分别对应三个维护窗口，包含全部 CSV、实际 YAML、case、控制组窗口、二进制诊断、JSONL 导出、bag、日志和恢复记录。JSONL 表示每行一条 JSON。所有样本均保留，派生的分类 JSON 另行标识。

分析程序从 W6 后源码复制构建。它在 off/basic 两种模式中对称保存预分配数值快照：初始化、每步补帧、请求接受、检测起止/阶段、结果来源、帧选择和跳过。完整调用另存线程 CPU 时间。没有新增模型调用、图像副本、帧引用、共享诊断事件或热路径文件写入。静态断言继续要求共享区及分析数组总量小于 8 MiB。MiB 为 1024×1024 字节。为匹配 20 秒分析窗口，提交数组每生产者由 65536 项改为 32768 项；全部数组实际无溢出。

独立 worker 使用 W6 同一二进制。隔离 `LD_PRELOAD` 包装器只观察真实 `fdatasync` 起止和 CPU 时间，退出后导出。`fdatasync` 是请求文件数据同步的系统调用。它保留真正的双同步流程。观察器本身没有独立标定，也没有执行无观察器的同工作量对照；这些结果不能用于宣称 0.2 ms 量级效应已被排除。

## 已证实的源码链

1. `yolo_detector.cpp:87–112` 的请求函数拒绝已有待检测请求或未读结果，但允许前一请求仍在执行时保存一个新请求。待检测槽保存当时来源帧，之后不会刷新成最新帧。
2. `:133–137` 的 `isBusy()` 只检查待检测槽。`:226–245` 的工作循环取走请求后立即清空该槽。因此业务能够在本次推理期间投递下一个旧来源请求。
3. 检测可能依次执行区域、全图和若干分块。结果被业务读取后，`hybrid_tracker.cpp:409–436` 或 `:604–720` 查找来源历史，并为其后每个已消费算法帧构造补跟踪列表。
4. `:250–300` 初始化一次，然后逐个执行列表中的帧。已初始化分支还可能先执行一次普通 NanoTrack 更新（`:471`），再重初始化。这项普通更新没有独立计时，不能把未被初始化/补帧区间覆盖的时间统称为诊断开销。
5. 长调用期间视频按自己的截止时间继续取帧。节点下一次排空积压，只选最新帧。选择的像素和后续检测区域改变，进一步改变检测阶段数、结果来源及下一次恢复工作。

已用 `git show jetson:<path>` 核对参考实现：Jetson 的请求判断位于 `yolo_detector.cpp:135–154`，工作循环 `:201–215` 同样取出后清空待槽；`hybrid_tracker.cpp:198–221` 同样逐帧补跟踪。**这些是原有管线属性，不是此次诊断引入的排队策略。** 两份完整参考源码及分支提交指纹保存在分析产物中。本轮没有更改请求策略、补帧继续规则或状态机。

### 工作量及异步来源

组 1 的 off 分位调用为 18 步，basic 为 20 步；真实初始化加补帧区间分别 **249.372/278.254 ms**，完整差 **29.889 ms**，记录工作区间差 **28.882 ms**。组 2 的 basic/off 分位调用为 18/12 步，完整差 **70.768 ms**，记录工作区间差 **69.774 ms**。剩余差约 1 ms 是这两次调用未被所列区间覆盖的差，不能解释为固定模式开销。

例如组 1，off 请求 103 来自算法帧 532，在调用 550 被读取；其待槽等待 **238.074 ms**，检测 **148.284 ms**，来源落后 18 帧。basic 请求 36 来自帧 160，在调用 180 被读取；等待 **239.773 ms**，检测 **166.628 ms**，落后 20 帧。两者检测各执行四个阶段。组 2 的两个分位调用则分别执行四个/一个检测阶段。不同来源和检测级联实际改变了恢复工作，并非只有提交成本不同。

全部 14 个窗口中，一次初始化调用的“步数—完整耗时”线性关系解释 **98.51%–99.54%** 的观测方差。这里的解释度是统计关联；源码逐步循环和逐次实测构成机制证据。每个慢调用已记录初始化加补帧区间至少占 **93.452%**。相同步数的全部样本也保存在 [workload-comparison.json](workload-comparison.json)，包括中位数和尾部，不只比较单步中位数。多数同一步数层样本很少，且普通更新分支、初始化成本、检测阶段和来源仍可能不同，不能用这些层断言精确开销通过。

相邻 off/off 的 **45.192 ms** 差中，记录模型工作差为 **45.137 ms**。它说明没有诊断提交和写盘时也会出现几十毫秒变化。它不能证明诊断对异步时序没有影响。

### 提交、通知及 worker 间接作用

基础提交 P99 为 **13.731–14.674 μs**。组 1/2 的 basic 分位调用内，Node 提交区间总和分别 **0.136070/0.113716 ms**。本轮全部慢调用内最大总和为 **0.774542 ms**，不能排除偶发提交长尾。区间含通知系统调用，但不含提交前字段准备和观察器；因此只能排除“已测提交区间本身累计造成几十毫秒差”的简单解释，不能排除 0.2 ms 级别总影响。

`worker.cpp:291–306` 的 `poll` 只等待 listener，超时 10 ms 后才读取 eventfd。eventfd 是事件通知计数器，**没有加入该 poll 的等待集合**。不能把通知次数直接解释为 worker 被立即唤醒的次数。没有修改通知节流，也没有使用每步 5 ms 的假设。

磁盘/tmpfs 两对的同步 P99 分别为 **21.704 ms / 3.588 μs** 和 **3.726 μs / 23.813 ms**。物理持久化等待被明显移除，但完整 P99 没有一致变化方向，且不同恢复工作仍存在。worker 的 CPU 占用由约 **2.43%–2.50% 单核**降至 **1.90%**。这不支持把物理同步直接作为几十毫秒失败的唯一原因；仍不能排除写盘对调度、缓存或异步来源选择的小效应。

CPU 核心对照同样没有一致完整 P99 方向。它也**没有排除 CPU 间接作用**：共享 4–7 的普通调用 P99 为 **14.694/14.477 ms**，移至 0–3 为 **15.496/15.535 ms**。tracking 的 `schedstat` 可运行等待分别为共享 **42.683/44.905 ms 每运行秒**，隔离 **70.590/73.221 ms 每运行秒**；按对应实际调用数为 **1.126/1.302 ms 每调用**和 **1.973/2.186 ms 每调用**。归一使用实际资源采样区间，不拿未经归一的累计值比较。

`schedstat` 等待只表示线程已经可运行、却未获得 CPU 的时间。它不包含睡眠中的驱动阻塞，不能单独定位 NPU 等待。慢调用线程 CPU 时间约占完整时长的 75%–77%；其余也不能统一归类为磁盘、NPU或调度。初始化中位数还在不同窗口出现约 6–25 ms 的变化。现有观测不足以继续拆分 NPU 驱动、模型执行、缓存和普通更新的各自成本。结束后只读频率检查显示 performance 调速策略；未在窗口内同步采集频率/温度，不能反推全部测试期间状态。

## 下一步最小建议

1. 不改默认算法，先在隔离测量程序中固定输入帧序列、检测结果可读取的调用编号和补跟踪列表。对称记录普通更新、初始化及每步模型阶段，同时标定观察器自身成本。这样才能在相同工作量和分支下区分 0.2 ms 级诊断成本、线程可运行等待及 Runtime 等待。它属于额外归因实验，不能代替正式十组。
2. 目前没有找到可确认安全的诊断代码修复，因此不要调整通知、请求槽策略或补帧算法，也不要通过反复碰运气重跑完整十组宣布问题已解决。若后续确认缺陷，先实施最小修复，再用最终产物执行新的完整十组，并保留旧批次。
3. 官方门槛和统计规则保持原值。若用户另行要求改变验收设计，应通过单独批准的 OpenSpec 修订处理；本报告没有提出或采用放宽门槛。

本轮调查已经达到“大幅尾部机制可复算、直接提交与两类 worker 因素分别受检”的范围。旧失败组的逐次 off 工作量仍缺失，精确的小效应归因仍未闭合，均明确保留。任务 7.3 不勾选。
