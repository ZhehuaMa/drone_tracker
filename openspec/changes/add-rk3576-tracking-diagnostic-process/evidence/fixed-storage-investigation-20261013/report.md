# 固定工作量 eMMC/tmpfs 对照报告

日期：2026-10-13。变更：`add-rk3576-tracking-diagnostic-process`。

**把基础诊断的存储目录从物理 eMMC 改为 tmpfs，没有取得完整调用或长调用非线程 CPU 时间显著改善的证据。两种子的完整调用 P99 分别减少 1.304 和 1.088 ms，但相关性重采样区间都跨过零；长调用非 CPU 差的中位数方向相反。结果削弱了“物理持久化是既有约 5 ms 额外长调用成本的主要原因”这一假设，不能证明所有 I/O 或调度影响不存在。**

本轮没有 off 条件。它直接比较两种存储介质下的 basic 调用，不能把历史 off 的数值减到本轮 basic 上，推算新的诊断净开销。也没有证明 0.2 ms 门槛成立。正式任务 7.3 仍未完成，CLI 保持 **39/40**。没有代码修复、提交、归档或正式升级。

## 方法与实机身份

生产目标为 **HZ-RK3576_WuKong Board**，Ubuntu 22.04.5 ARM64、内核 `6.1.141-rt36`。RKNN Runtime 2.3.2、RKNPU 驱动 0.9.8，使用原系统 `/usr/lib/librknnrt.so`，没有覆盖。其 SHA-256 为 `d31fc19c85b85f6091b2bd0f6af9d962d5264a4e410bfb536402ec92bac738e8`。SHA-256 是核对文件字节的指纹。

只修改独立实验源码副本。一个业务进程保留同一真实 Nano 模型实例，一个 Client 持有同一 Recorder 和共享区域，一个 worker 持续消费。Client 管理连接和区域生命周期；Recorder 提交定长事件；worker 负责实际存储。切换只发生在业务完全停止提交、双环排空且 generated/written/synced 一致的段边界。这三个位置分别表示已生成、完整写入和成功双同步的生产者序号。

测试专用控制协议先正常结束旧段并双同步，再关闭旧 Storage，打开选定介质上的新段，保存身份和初始提交记录，最后确认。Storage 是现有的文件记录组件。它从共享区域继承 synced 序号，累计位置没有归零。没有重连、第二消费者、模型重启或 Recorder 地址变化。新段健康周期相位对称重置；正式 worker 默认行为没有改动。详见 [design.md](design.md) 和 [storage.patch](storage.patch)。

eMMC 为 `/dev/mmcblk0p7` 的 ext4 根文件系统，实验目录在 `/home/hzhy/drone-fixed-storage-20261013/`。tmpfs 是仅用于实验的内存文件系统，实际挂载在 `/tmp/drone-fixed-storage-20261013`，明确限制 **128 MiB**，使用 `nosuid,nodev,noexec`。MiB 表示 1024×1024 字节。两介质都保留真实 100 ms 双同步、目录同步、CRC 校验和 8 MiB 最低空余保护。CRC 用于发现记录损坏。每段独立目录避免累计目录数改变空间检查工作量。tmpfs 同步成功不是持久化验收成功，其数据断电后会丢失。

固定输入沿用正式帧源的 `MjpegVideoReader` 首帧亮度读取。视频 SHA 为 `c25aec33208f5dfca315eb9c2c4fb86b04d98883ec5d74b68f5ac7746a669a95`。像素为 1920×1200、`CV_8UC1`、stride1920，SHA 为 `ad27883488764165ad633e74a354d9e02e0f29794e55b33d835c28e6d3146115`。`CV_8UC1` 表示每像素一个 8 位灰度值。OpenCV 实际默认线程数 1。

测量前真实 YOLO 检测一次，得到框 `[755.115234,457.962402,39.9310913,36.562439]`、分数 `0.589952648`。每 40 调用段在调用 20 重放来源调用 1 的结果。真实 Nano 执行 1 次模板初始化、19 步历史补跟踪和 20 次普通更新。补跟踪把旧检测来源逐帧追到当前帧。每段重置跟踪状态，保留模型实例。DCF 关闭，KF 内参为 1333.3，原参数、预处理及状态机保持不变；KF 是用于预测运动的卡尔曼滤波器。

两个完整段预热，保留 `warmups.csv`。测量只保留对称外层完整调用/线程 CPU 计时和真实 API 次数。API 次数是实际模型入口调用数。内部事件摘要、阶段及 submit 计时在性能组关闭。每段先对称等待至少 100 ms，250 ms 内核对排空，再执行最多 500 ms 的切换确认，随后对称等待 100 ms。切换及文件设置成本在完整调用计时外。最多排空耗时 107.463 ms；切换加后置等待最多 119.549 ms。每段计时外刷出 partial CSV，全部慢样本保留。

跟踪主线程 CPU4；worker 单线程允许 CPU4–7，均为普通 `SCHED_OTHER` 调度。实际测量区间 TID 亲和性读回通过；TID 是线程编号。启动时继承控制器 CPU0–3 的早期样本单列，之后按既有策略进入 CPU4。测量期间没有异步 YOLO、相机、ROS、录像、bag 或 HDMI 生产者；active 指针切换没有业务并发。该范围不等同于完整生产管线。

## 同步操作与资源观察

worker 在现有 `Storage::synchronize()` 外保存轻量墙钟起止数组，结束后导出；没有热路径文件输出。这里的“同步操作”包括数据同步、提交记录的 CRC/空间保护遍历/写入及第二次同步，也可能包含调度等待。没有取得纯 `fdatasync` 系统调用时长或该操作的线程 CPU 时间，不能将残余全部解释为调度。

| 种子 | eMMC 同步操作中位/P99 ms | tmpfs 同步操作中位/P99 ms | eMMC/tmpfs 操作样本数 |
| --- | --- | --- | --- |
| 20261013 | 3.130769 / 25.995781 | 0.061411 / 22.423226 | 293 / 349 |
| 20261014 | 3.098731 / 27.164063 | 0.056489 / 22.365427 | 289 / 305 |

tmpfs 明显缩短典型同步操作。它仍未带来稳定的长调用非 CPU 改善。旧报告约 22 ms/4 μs 是 syscall 级包装器的 `fdatasync` 测量；本轮是完整同步操作，**两者不能直接对比**。两介质的批次和提交记录数量可以不同，符合真实时间周期及排空过程；没有关闭同步或强迫相同批次。

1 Hz 资源原件读回 policy0=2016 MHz、policy4=2208 MHz、NPU=950 MHz，全部采样值一致。温度覆盖约 36.1–45.3°C。DMC 频率未取得，不能声称固定。worker 的 last_cpu 采样均为 CPU4，但它只代表采样瞬间，实际允许范围仍为 4–7。

按两个完整混合排列的实际观察秒数归一，跟踪可运行等待为 21.029/21.041 ms 每秒，worker 为 490.431/484.043 ms 每秒。`schedstat` 只统计可运行却尚未获得 CPU 的等待，不包含睡眠式阻塞。1 Hz 间隔长于许多段，无法为两介质分别建立完全位于段内的调度区间，因此该归一包含段边界，不能逐介质归因。原件保留这一缺口。测量时 worker/业务 FD 数分别固定 11/35；FD 是打开资源的描述符。最低可用内存约 3.61×10⁶ KiB，没有内存容量压力证据。

## 内容、提交与模型核对

全部 **132 个测量段**（含独立 4 段 audit）逐段满足 1 模板/39 搜索，40 位置的框、分数、状态、消费标志和输出有效性一致。audit 是独立的数据核对短组，其 240 条真实 API 记录包含两段预热及四段测量。模板/搜索输入与最终 Head 分类/位置输出 SHA 完全一致。Head 根据图像特征输出分类和框参数。设备共享特征张量没有直接读取或哈希，保留这一限制。

每段保存 **275 条业务事件**，两介质内容、顺序和定长序列化均等价。核对只规范化运行/轮次身份、连续序号、调用/请求身份和纯耗时字段，保留真实分支、框、分数、计数、理由及有效标志；全部段规范化 SHA 唯一且相同。worker 的异步健康字段仍保存实际累计位置、时间及同步情况，不能称全文件字节相同。常规段各有 4 条健康事件，最后段另有收尾健康事件；RunStart/RunEnd 保留，初始引导段单列。

独立 Python 校验和实际 ARM64 native inspector 对 **135 个性能/audit 段文件**全部确认 CRC、记录边界、正常结束及真实提交记录。Python 校验另逐生产者核对全局连续序号、首提交承接旧 synced、末提交覆盖下一边界位置，无重复、缺口、降级或晚于 500 ms 的未同步健康记录。全部 partial/full CSV 一致，有限排空通过；无观测数组溢出。原业务事件和必要提交没有因 tmpfs 而省略。
