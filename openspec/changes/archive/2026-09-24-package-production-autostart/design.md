# Design

## Context

生产安装没有可复用的自动部署入口。本变更从已安装版本生成部署包，使其他同型生产板可使用相同配置启动。

生产版本含主节点、录像工作进程和录像检查器。相机参数启用 HDMI 与录像，依赖目标板已有相机节点、系统库和模型。模型是否随包提供是打包选项；未包含时必须验证目标模型内容一致。

## Goals / Non-Goals

目标是部署当前安装内容，配置逐字节一致，程序及子进程的 CPU 亲和性为 4–7。CPU 亲和性表示操作系统允许程序使用的核心集合。

不重新编译，不打包源码、测试程序、RKNN Runtime 或基础系统库，不修改已有拦截程序服务，不自动发送跟踪触发命令。

## Decisions

- 采用 systemd 的 `CPUAffinity=4-7` 并在直接启动入口使用 `taskset`。不使用 shell 登录自启动，因为登录脚本不能可靠覆盖无人登录的开机过程。结果是服务和手动入口均限制核心，子进程继承限制。
- 直接执行已安装节点并传入原配置。不以 `ros2 launch` 作为服务主进程，因为节点退出时外层启动器不一定同步退出。主节点作为服务进程使异常重启有明确依据，节点名称仍为 `drone_tracker_node`。
- 包含必需运行文件和配置；模型按选项随包或仅记录校验值。拒绝打包整个系统安装目录，避免覆盖系统 RKNN Runtime。使用 SHA-256 文件指纹确认传输和配置一致性。
- 服务使用 root，以匹配生产设备和录像路径权限；不新建额外用户，避免改变现有设备访问条件。服务仅执行可信部署内容。
- 默认安装并启用开机启动，提供显式 `--start` 选项立即启动。这样打包与安装不隐式占用相机；已经运行的同名服务升级后恢复运行。
- 启动入口同步停止 `display-manager.service` 及生产板的 `lightdm.service`，再核对显示设备的内核客户端列表为空。服务通过 `After` 排在桌面启动任务之后，避免桌面稍后启动而重新抢占设备。不只在安装时停止桌面，因为下次上电仍需执行相同前置操作。停止或释放检查失败时不执行节点；节点退出后不自动恢复桌面，避免异常重启时争用显示设备。

## Risks / Trade-offs

- 其他板设备编号可能不同 → 安装前检查配置引用的设备，失败时保持旧服务；不擅自改配置。
- HDMI 可能被桌面或其他进程占用 → 启动入口停止桌面并最多等待 5 秒确认客户端列表为空；无法读取占用证据或仍有占用时拒绝启动。运行期间不要手动恢复桌面。
- 当前生产二进制尚无本次运行验收 → 静态检查与打包验证单独记录，不声称相机或上电验证通过。
- 中途安装失败 → 在切换前完成校验和备份，保留旧版本及恢复说明。

## Migration Plan

1. 读取生产板版本和配置，复制运行文件并生成文件指纹。
2. 将部署脚本、服务、运行文件及配置打包。
3. 目标板解压并执行 `sudo ./deploy.sh`，先检查系统、依赖、模型与设备。
4. 备份现有入口、配置和服务，安装新版本并启用自启动。
5. 如需立即运行，传入 `--start`；否则在下次上电启动。回退时停止新服务，恢复备份和旧版本链接。

## 新板缺失 ROS 库的修订

新板未安装 vision_msgs 和 cv_bridge 时，旧包在动态链接预检失败。修订后从源板收集程序依赖的 ROS 库到 `payload/lib/bundled-ros`。动态链接是程序启动时查找所需共享库的过程；私有目录仅服务于本程序，不覆盖 `/opt/ros/humble`。

1. 加载源板 ROS 环境，对三个程序和 vision_msgs、cv_bridge 库执行 `ldd`，取得直接与间接依赖。
2. 复制解析到 `/opt/ros/humble/lib` 的库，并保留加载名称。vision_msgs 类型支持库可能在运行时才加载，因此显式收集其所有非 Python 共享库。
3. 对收集到的库继续检查，缺失依赖则打包失败。记录来源和 SHA-256 指纹。
4. 预检和启动均将私有目录放到 `LD_LIBRARY_PATH` 首位；此变量指定共享库搜索目录。安装后录像子进程继承此设置。

选择私有库随包交付，避免要求新板联网安装 apt 包。仍要求目标板已有 ROS 2 Humble 基础环境、OpenCV、FFmpeg、设备驱动及固定 RKNN Runtime。此包不是完整系统镜像。源板检查不能替代缺少这两个 ROS 包的新板验收。
