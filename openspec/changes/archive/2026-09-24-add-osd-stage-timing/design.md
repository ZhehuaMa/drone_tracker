# 显示诊断设计

## Context

生产 HDMI 新画面更新缓慢，需要确定显示内部哪一段耗时最大。现有实现已将待显示结果限制为一份；问题并非缺少显示丢帧机制。

2026-09-24 对生产板版本 `bundle-20260923T181257Z-2945` 的只读检查发现：PID 1688 日志约每秒采集 60 帧、消费 35 帧、显示 2 帧；一次快照为 submitted=4184、replaced=3967、displayed=215。较早 PID 1690 日志的消费速率约 60 帧/秒，显示仍约 8 帧/秒。证据位于板端 `/var/log/drone_tracker/` 对应进程日志，属于窗口速率判断，不是端到端延迟测量。

`OsdPresenter` 负责从待显示槽取出结果并驱动显示后端；`HdmiBackend` 负责像素处理和显示更新。已有 submit 计时只覆盖结果交接。历史日志还出现约 56.6 天的系统校时跳变，不能以系统时间减帧时间作为本轮诊断的可信延迟。

## Goals / Non-Goals

目标是提供可关联同一轮次、可发现长尾耗时的显示诊断。长尾指少数远慢于通常情况的样本。

本次不优化像素路径，不改变图像与框的配对，不测量屏幕实际发光时间，不修复相机时间映射，也不扩展为全部模型阶段的性能系统。

## Decisions

### 1. 显式开启，统一使用单调时钟

新增 `osd.timing_enabled=false`，遵守全部 `osd.*` 启动参数不可热修改的约定。关闭时不采集新增时间样本，OSD 关闭时不启动诊断资源。选择显式开启而非默认逐帧打印，便于对照测量本身的开销。

以 `steady_clock` 测量持续时间，提交包附加内部单调时刻。它只用于诊断，不覆盖原采集时间。拒绝直接混用系统时间与单调时间；代价是本次只能准确描述提交之后的延迟，无法量化此前采集和跟踪阶段的帧龄。

### 2. 定义互不重叠的后端阶段

| 指标 | 起止与含义 |
|---|---|
| source_copy | 映射源帧、必要输入分配、输入缓存同步及逐行复制，到输入准备结束 |
| scale_convert | 显示几何计算、目标清理、灰度缩放与转换或 BGR 缩放，到视频准备结束 |
| layout | 生成文字、遥测和目标框图层的完整调用 |
| compose | 图层复制、缓存同步、底图复制与硬件混合，到合成结束 |
| commit | 构造显示更新请求、提交授权及实际提交调用 |
| flip_wait | 提交成功后等待显示完成事件 |
| render_total | 取出待显示包后到本次显示处理结束，包含上述阶段和其余处理 |
| pending_wait | 包被接受到渲染取出的时间；只对实际取出的包采样 |
| submit_to_display | 实际显示成功的包，从接受到显示完成的时间 |
| new_frame_interval | 同一轮连续两次新视频成功显示之间的时间 |

RGA 是 Rockchip 图像处理硬件；相关调用目前同步等待。阶段耗时包含主机调度与设备等待，不声称是纯硬件执行时间。`render_total` 是父区间，不能与子阶段再次相加；日志提供 `other` 表示父区间减已记录子阶段的剩余时间。首次分配保留在样本内，并标记首帧，避免隐藏真实启动开销。

选择沿现有执行边界测量，而非重新排列操作，以免诊断本身改变瓶颈。未执行阶段记缺失，不填零。失败或授权拒绝记录结果类型和已完成阶段，成功与失败样本分组。

### 3. 固定内存汇总，独立日志出口

在公共 OSD 层提供固定大小统计器，后端不依赖 ROS。使用固定直方图近似分位数：按 1、2、4、8…微秒上界分桶，直到覆盖至少 60 秒，再设溢出桶。分位数报告桶上界并标记 `approx`，溢出用明确的下界标识；均值与最大值用原值计算。选择固定直方图而非无限逐帧数组，保证持续运行内存有界。

渲染线程只更新数值；ROS 定时回调每秒取走窗口快照并在锁外格式化。复用已有 OSD 诊断回调的独立调度，不从跟踪循环驱动。快照锁只保护固定大小数据，不覆盖图像复制、硬件等待或日志写入。窗口依据实际单调时间计算速率，不能假定回调严格每秒运行。

每组输出包含 round、window_id、窗口时长、new_video 或 repeat 类别、结果类型、count/mean/max/p95/p99，时间单位为微秒。窗口同时报告 submitted/replaced/displayed/rejected/commits 的增量。仅重复显示冻结底图不增加 displayed。空窗口显式 count=0，无耗时样本，不能伪造零耗时。

### 4. 生命周期和更新间隔

处理流程：
1. 接受包时记录单调时刻、轮次及序号；旧包被替换仍按既有计数释放。
2. 取出包时记录 pending_wait，开始 render_total 和后端阶段。
3. 显示完成才记录 submit_to_display 和新画面时间。
4. 日志回调输出窗口快照，下一窗口继续累计。

OFF、输入结束、进入等待过期状态或新轮开始时断开新画面间隔链；重复底图不形成新视频间隔。首份新视频无前驱，间隔样本为缺失。正常退出或显示失败时冲刷最后不足一秒的快照。SIGKILL/断电不能保证尾部日志，文档说明这一边界。

选择按轮次隔离而非整进程计算，避免把几分钟的主动停止当作画面卡顿。仍保留既有累计计数含义，不为了诊断重置既有计数。

## Risks / Trade-offs

- 测量改变线程调度 → 默认关闭，热路径固定内存，生产板执行开关对照并报告原始差异。
- 一秒只有两帧时分位数解释力有限 → 同时给样本数、均值和最大值，生产分析覆盖至少 60 秒。
- 后端等待包含调度延迟 → 仅定位慢阶段，不未经证据将其归因于 GPU、RGA 或 HDMI 设备。
- 日志 I/O 可能阻塞 → 不在渲染线程打印，固定输出规模；保留最终窗口且避免逐帧日志。
- 系统校时破坏原帧时间映射 → 本次诊断用单调时间；校时问题单独跟踪，不据此宣称完整延迟正常。

## Migration Plan

先完成模拟时钟、生命周期和窗口计数验证，再按本地构建约定编译。生产测试记录板卡、构建身份、配置、模型指纹、输入和显示模式。

在明确测试窗口使用原配置与仅切换 timing_enabled 的配置交替运行，各至少三轮、每轮至少 60 秒，记录采集/消费/显示速率和资源变化。测量开销目标为吞吐中位数下降不超过 5%；超出时调查并记录，不能据此声称低开销通过。实机场景无法完全重复时如实说明，不制造因果结论。

关闭 timing_enabled 并重启可回退诊断开关；必要时恢复原版本与配置。生产 Runtime 保持系统版本，不替换库。完成诊断后依据主耗时阶段另行提出优化，不在本变更中顺手改显示实现。
