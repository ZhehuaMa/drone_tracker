## 六轮对照及开销

按关闭、开启、关闭、开启、关闭、开启顺序执行。
每轮检测到相机运行后采样 70 秒；下表时长是从该时刻到进程退出，包含约半秒收尾。
速率使用约每秒记录的累计计数增量除以采样端单调时间间隔。
前 10 秒不进入稳定区间比较，剩余有效端点跨度约 59.57–59.60 秒。
原程序计数日志约每秒更新，端点存在采样误差，所以采集速率可能略高于配置的 60 fps。
该方法不使用系统校时时间差。

CPU 百分比是主节点全部线程的 CPU 时间除以单调时间，100% 表示占满一个核心。
RSS 指实际驻留物理内存，单位 MiB（1024² 字节）；表中为稳定区间中位数。

## 瓶颈判断及下一步

**事实：** 绘制与合成合计约 65.92% 的显示处理时间。复制与缩放合计约 24.66%，
显示切换等待约 8.56%。不能把显示慢全部归因于等待 HDMI 切换。
在单份待显示槽的现有策略下，成功包待显示等待平均仅 16.61 毫秒，
长耗时主要发生在包被取出后的处理阶段。

**尚未验证的解释：** 节点线程采样集中在 CPU 4，内核又隔离了 CPU 4–7，
这支持“线程竞争影响阶段墙钟耗时”的排查方向，但尚未做改变线程分配的因果对照。
当前计时也不能区分 compose 中的 CPU 图层复制、缓存同步和硬件混合各占多少。

下一项优化应另立 OpenSpec：先关联显示线程 CPU 执行时间与阶段墙钟时间，
在受控条件下验证 CPU 4–7 的显式线程分配是否缓解竞争，再细分 layout/compose 内部耗时。
若绘制自身仍占主要 CPU 时间，再评估静态文字缓存或图层更新范围。
本变更没有实施这些优化，也不预先承诺帧率提升。

显示完成事件不等于屏幕像素实际发光时刻。
`submit_to_display` 没有包含此前相机采集和跟踪的全部时间，不能称为相机到屏幕完整延迟。
