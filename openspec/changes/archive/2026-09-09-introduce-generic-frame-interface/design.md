## Context

当前问题是：一帧图像从相机进入队列后，公共跟踪输入、补帧缓存、异步检测和 ROS 图像发布都依赖 Jetson 的 VPI 类型。预期结果是让这些跨模块位置只依赖通用帧契约，同时让现有 Jetson 路径继续管理同一个 `VPIImage`、保持相同像素和时间语义。变更动机见 `proposal.md`，行为要求见 `specs/generic-frame/spec.md`。

VPI 是 NVIDIA Jetson 上的图像处理接口。现有 `VPIImageWrapper` 销毁其持有的 `VPIImage`，并保存采集时间戳，但没有显式声明复制限制、像素格式、尺寸或并发访问协议。主线程会把 VPI 图像映射为 CPU 可读内存；异步 YOLO 工作线程则会先把输入复制到自己的 VPI 图像。两种操作若同时作用于同一源图像，可能破坏 VPI 的锁定协议，因此帧实现必须同时解决生命周期和访问串行化问题。

本次只建立帧边界。YOLO、NanoTrack、TensorRT、相机实现和构建系统仍是 Jetson 专属代码。换句话说，本次完成后公共帧输入不再暴露 VPI，但工程整体仍不能在 RK3576 上构建。当前本地系统不具备 Jetson 的编译和运行环境，因此本 change 不安排 Jetson 构建、设备运行、压力测试或录像回放；这些运行时行为只能作为未验证的兼容约束保留。

## Goals / Non-Goals

**Goals:**

- 建立最小但完整的帧契约，使公共调用方能够读取尺寸、格式、采集时间戳和只读主机视图。
- 通过共享只读引用明确队列、异步任务和补帧缓存之间的所有权。
- 将 VPI 图像的销毁、主机锁定和设备读取协调集中到一个具体实现。
- 让平台类型不匹配成为可诊断的正常失败路径，而不是未定义行为。
- 保留 Jetson 的检测、跟踪、回放和 ROS 发布行为。

**Non-Goals:**

- 不为 RK3576 选择帧内存、RGA 映射或缓存同步方案。
- 不定义通用裁剪、缩放、颜色转换、letterbox 或模型输入接口。
- 不定义通用相机、检测器、跟踪器、推理引擎或平台工厂。
- 不建立运行时平台切换，也不拆分 CUDA、VPI 和 TensorRT 的构建目标。
- 不在本次重排整个 `src/` 目录或修改算法参数。
- 不在本 change 中执行 Jetson 编译、设备运行、VPI/TensorRT 测试、性能测量或固定录像回放。

## Decisions

### 1. 使用 `Frame` 和 `FrameReadView` 两层通用契约

**选择：** 在 `src/frame/frame.h` 定义抽象 `Frame`、抽象 `FrameReadView`、`FramePixelFormat` 和 `FrameRef`。`Frame` 提供宽度、高度、像素格式、微秒采集时间戳，以及创建只读主机视图的操作。`FrameReadView` 提供 `const cv::Mat &`，其对象存活期间图像数据保持有效；映射失败返回空结果。

`FrameRef` 定义为 `std::shared_ptr<const Frame>`。OpenCV 的 `cv::Mat::step` 表达主机视图每行实际占用的字节数，因此行跨度属于视图，不属于整帧元数据。

**原因：** 当前 DCF 和 ROS 图像发布都需要 CPU 读取，而且 DCF 位于逐帧热路径。受生命周期保护的视图既能保留零拷贝读取，也能阻止调用方在解除 VPI 锁后继续使用悬空的 `cv::Mat`。

**拒绝的替代方案：**

- 只抽象尺寸和时间戳：它会让 DCF 和 ROS 编排层继续直接调用 VPI 锁定函数，公共帧边界仍不完整。
- 每次返回一份主机图像副本：实现简单，但会给逐帧 DCF 增加不必要的完整图像复制。
- 返回裸数据指针：裸指针无法表达解除映射的时机，也无法保证底层帧继续存活。

**实际后果：** 通用帧契约继续依赖项目已有的 OpenCV，但不依赖任何硬件 SDK。所有主机访问必须保持 `FrameReadView` 存活，不能保存其内部 `cv::Mat` 后提前释放视图。

### 2. 通用契约只支持当前已验证的像素格式

**选择：** `FramePixelFormat` 首期只定义 `Gray8` 和 `Bgr8`。只读主机视图保留帧的原生格式，不在接口内部自动转灰度或扩展为三通道。DCF 在消费端把 `Bgr8` 转为灰度；图像发布在消费端把 `Gray8` 扩展为 BGR。

**原因：** 当前构造路径只支持 `CV_8UC1` 和 `CV_8UC3`。保持原生格式可以避免隐藏的颜色转换，也便于验证重构前后的像素一致性。

**拒绝的替代方案：** 预先定义 NV12、RGB、浮点张量和 RKNN 专属格式。尚无 RK3576 帧实现验证这些格式的平面布局和缓存语义，提前加入会把未知契约固化到公共接口。

**实际后果：** 遇到未支持格式时，帧创建必须明确失败。新增格式需要以后通过单独的规格变更补充，而不是把未知格式静默标记为 `Unknown` 后继续处理。

### 3. 采集时间戳归属于帧

**选择：** `Frame::timestampUs()` 是采集时间戳的唯一来源。删除 `FrameContext::frame_ts_us` 和补帧缓存中没有独立语义的重复时间字段。`FrameContext::now_us` 继续表示处理或实时外推时刻。

**原因：** 当前 DCF 从帧包装读取时间戳，而状态机和 ROS 发布从 `FrameContext` 读取另一个副本。两个值理论上可以不一致。统一来源可以保证滤波、云台旋转查询和消息时间使用同一个采集时刻。

**拒绝的替代方案：** 保留两个字段并在入口处断言相等。该方案仍允许后续调用方遗漏断言，并继续维护重复状态。

**实际后果：** 节点构造上下文时先从帧读取时间戳，再用它查询 `gimbal_history_`。完整单帧流程如下：

1. 相机创建帧并写入采集时间戳。
2. 节点从帧读取采集时间戳，并查询该时刻的相机旋转。
3. 跟踪器使用同一时间戳执行单调性检查和滤波更新。
4. 图像消息使用同一时间戳；实时边界框仍使用 `now_us` 对应的外推时刻。

### 4. 当前具体实现命名为 `VpiFrame`，不命名为 `CudaFrame`

**选择：** 在 `src/frame/vpi_frame.h` 和 `src/frame/vpi_frame.cpp` 实现 `VpiFrame final`。该类负责由 VPI API 创建或接管的图像，并提供仅供现有 Jetson 代码使用的 VPI 读取访问。内部所有权对象在最后一个引用释放时调用一次 `vpiImageDestroy()`。

提供两个语义明确的创建入口：一个接管已有 `VPIImage`，一个从受支持的 `cv::Mat` 复制创建。禁止默认构造和对象复制。

**原因：** 现有帧实际是具有 CPU 与 CUDA 后端能力的 `VPIImage`，不是一个裸 CUDA 缓冲区。名称应表达真正需要遵守的创建、锁定和销毁协议。

**拒绝的替代方案：** 使用 `CudaFrame` 名称。该名称会让维护者误以为对象只管理 CUDA 内存，并掩盖 VPI 视图、VPI 锁和 VPI 销毁规则。

**实际后果：** 如果未来出现不经过 VPI 的纯 CUDA 帧，它可以作为另一种实现存在，而不需要改变 `VpiFrame` 的含义。

### 5. VPI 主机映射和设备读取共享同一访问协调器

**选择：** `VpiFrame` 的内部所有权状态同时保存 `VPIImage` 和逐帧访问互斥量。`VpiFrameReadView` 在持有互斥量期间调用 `vpiImageLockData()`，在析构时先调用 `vpiImageUnlock()`，再释放互斥量。需要原生 VPI 图像的 Jetson 代码通过 `VpiFrameReadAccess` 访问句柄；这是由 `VpiFrame::acquireVpiRead()` 返回的作用域读取租约，并且持有同一个互斥量。

“读取租约”表示调用方只在一个明确作用域内使用原生图像。调用方向 VPI stream 提交涉及该源帧的操作后，必须在释放租约前完成同步。YOLO 只在复制到工作线程私有图像并完成同步前持有租约，之后立即释放源帧引用。

**原因：** 一个直接返回 `VPIImage` 的裸 getter 无法阻止主机映射与异步 VPI 操作重叠。将协调状态放在帧内部，可以覆盖节点图像发布、DCF、NanoTrack 和 YOLO 复制这些当前访问点。

**拒绝的替代方案：**

- 继续公开不受约束的 `VPIImage get()`：调用方可以绕过帧的并发协议，重现现有竞态风险。
- 把 YOLO 源帧复制改成调用线程中的同步复制：可以规避该竞态，但会增加 `request()` 的前台延迟并改变异步调度时序。
- 假定所有调用天然按顺序执行：节点可能在提交 YOLO 后立即映射同一帧用于图像发布，不能依赖这一假定。

**实际后果：** 同一帧上的 VPI 设备读取和主机映射会串行执行。不同帧各自拥有互斥量，仍可并行处理。本地只能通过检查所有访问入口是否持有同一个协调器来审查该设计，无法验证其实际并发行为和性能。

### 6. 平台转换只发生在当前 Jetson 消费边界

**选择：** 相机队列、`FrameContext` 和补帧缓存保存 `FrameRef`。`HybridTracker` 的公开输入只认识 `Frame`。现有 Jetson 实现准备调用 YOLO 或 NanoTrack 时，通过 `std::dynamic_pointer_cast<const VpiFrame>` 做受检查转换；转换失败则拒绝当前帧并记录期望类型和实际不兼容事实。

DCF 和 ROS 图像发布只使用 `FrameReadView`，不需要转换为 `VpiFrame`。YOLO 和 NanoTrack 仍是现有具体类，其内部继续使用 VPI/CUDA 和 TensorRT。

**原因：** 这能清理跨模块传递类型，同时遵守“不抽象其他接口”的范围。`dynamic_pointer_cast` 每帧只发生在少量边界，开销相对图像处理可以忽略。

**拒绝的替代方案：**

- 在 `Frame` 上增加 `void *nativeHandle()` 和平台标签：这种组合依赖调用方手工保持标签与指针一致，类型错误会成为未定义行为。
- 同时建立 YOLO、NanoTrack 和推理后端接口：这是后续 RK3576 推理迁移的范围，会显著扩大本次验证面。

**实际后果：** 新增非 VPI 帧后，当前 Jetson 跟踪器会给出可诊断失败，而不会自动支持该帧。真正支持 RK3576 仍需要后续后端抽象。

### 7. 只清理帧相关的公共头文件依赖

**选择：** `frame.h` 不包含 VPI 或 CUDA 头文件。`hybrid_tracker.h` 的 `FrameContext` 只包含 `FrameRef`。为避免 `dcf_tracker.h` 通过 `VpiGrayLock` 和 `nano_tracker.h` 间接泄漏 VPI，原有 VPI 灰度锁职责由新的帧读取视图承担，并对只需指针成员的具体类使用前置声明和源文件内包含。

**原因：** 仅替换 `FrameContext` 字段不足以实现公共头文件的平台隔离，因为当前包含链仍会引入 `<vpi/VPI.h>`。

**拒绝的替代方案：** 本次同时把所有源码拆成 common、jetson 和 rk3576 构建目标。那会涉及推理、预处理和相机边界，超出帧接口变更范围。

**实际后果：** 可以用不包含硬件 SDK 的编译单元验证公共帧声明，但顶层 CMake 和现有可执行文件仍要求 Jetson 依赖。

## Risks / Trade-offs

- **[VPI 读取租约释放前遗漏 stream 同步]** -> 将同步前置条件写入具体 API 文档，集中迁移所有原生访问点，并逐个审查租约作用域内是否存在对应同步调用。
- **[只读视图内部 `cv::Mat` 被调用方保存到视图生命周期之外]** -> API 文档明确禁止逃逸；调用点使用紧凑局部作用域，并通过源码审查确认视图没有跨作用域保存。
- **[逐帧互斥增加等待时间]** -> 互斥量按帧分离，YOLO 仅在私有复制期间持有；由于本地无法测量 Jetson 性能，本次不声明性能结论，也不为了推测的性能问题放松安全约束。
- **[时间戳来源合并造成消息时间变化]** -> 逐个追踪滤波、云台旋转查询和 ROS 消息的时间戳来源，确认它们使用 `Frame::timestampUs()`，并保留 `now_us` 的实时外推语义。
- **[公共头文件仍通过其他包含链泄漏 VPI]** -> 增加只包含 `frame.h` 和 `hybrid_tracker.h` 的编译冒烟测试，并检查预处理后的依赖列表。
- **[无法证明 Jetson 构建和运行行为保持不变]** -> 本 change 只执行平台无关的头文件检查、源码扫描和人工审查。VPI、TensorRT、竞态、性能和回放结果均视为未验证项，不设置需要 Jetson 环境才能完成的任务。

## Migration Plan

1. 先增加通用帧契约并完成平台无关的头文件检查，不切换生产调用点。
2. 增加 `VpiFrame`、主机读取视图和 VPI 读取租约，通过源码审查确认元数据、格式、行跨度、锁释放和单次销毁路径完整。
3. 将相机和视频生产者切换为创建 `VpiFrame`，将队列元素切换为 `FrameRef`。
4. 将节点、`FrameContext`、补帧缓存和时间戳读取切换为通用契约。
5. 将 DCF 和图像发布切换到 `FrameReadView`，将 YOLO 和 NanoTrack 切换到受检查的 `VpiFrame` 访问租约。
6. 移除 `VPIImageWrapper` 和分散的 VPI 主机锁代码，清理公共头文件包含关系。
7. 运行公共头文件冒烟检查、`rg` 源码扫描、`git diff --check` 和 OpenSpec 严格校验，不运行依赖 Jetson 环境的构建或测试。

若实现审查发现新接口无法完整替代现有调用链，可在同一变更提交前恢复原有 `VPIImageWrapper` 调用链；本次不改变持久数据、模型文件或外部协议，因此不需要数据回滚。合入后若需要代码级回滚，应整体回退该 change，避免通用与旧帧类型混用。
