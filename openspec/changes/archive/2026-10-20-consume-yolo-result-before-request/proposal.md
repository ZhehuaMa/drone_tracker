# Proposal

## Why

实时录像回放中，一帧有目标而相邻帧无目标时，检测输入的一帧偏移可能决定是否产生跟踪框。当前更新先提交新帧、再取走已完成结果；即使旧结果可以立即读取，新帧仍可能因为“旧结果未读”而失去本次提交机会。

已有六轮中段录像证据表明，两组使用相同源码和模型，却分别只有两轮和一轮初始化跟踪，因此有效框比例的组三轮中位数为 7.48% 与 0%。本变更消除调用顺序造成的可避免拒收；它不承诺命中特定录像帧，也不把同版本波动当作代码改进。

## What Changes

- 将每个正常 YOLO 交互点改为三个阶段：先取走一次已完成结果并保存为本次更新的局部快照，再按原时机尝试提交当前帧，最后处理快照中的结果。
- 同时覆盖未初始化的检测路径和已初始化的跟踪路径。跟踪路径仍先获得当前帧的真实跟踪观测，再进行上述交互；未到提交间隔的更新仍读取结果。
- 将初始化、历史图像查找和补跟踪放在本次提交尝试之后。补跟踪指在检测来源图像上初始化后重放后续缓存帧，可能需要较长时间。
- 保留一个执行中请求、一个最新待执行请求及未读结果保护。读取与提交仍是两个独立调用，不新增原子交换接口、额外轮询或推理线程。
- 增加有明确线程交接点的顺序、并发及回合清理测试；保留所有既有请求身份、诊断关联、来源元数据、提交间隔和仲裁阈值。
- 真实验收比较固定参考版本与实际实现后的不同源码及程序。三个 test-03 区间各运行三轮参考和三轮候选，报告逐轮值、组三轮中位数、范围和候选减参考的差值；test-02 继续按用户指示跳过。

具体前后示例：旧的无目标结果 A 已就绪时，当前顺序先拒绝新帧 B，再读取 A；新顺序先保存 A，再让 B 按原接收规则参与提交，最后处置 A。若 B 之后被更新帧替换，仍按既有规则记录替换，不宣称 B 一定执行。

## Capabilities

### New Capabilities

无。复用现有检测与跟踪仲裁能力。

### Modified Capabilities

- `detection-tracking-arbitration`：增加已完成结果快照、当前帧提交、旧结果处置之间的顺序约束；明确快照后才完成的结果留待下一正常交互点，并保留原提交节奏及未读结果保护。

## Impact

- 实现主要涉及 `src/hybrid_tracker/hybrid_tracker.cpp` 的两个 YOLO 交互点。`YoloV8Detector::get_result()` 与 `request()` 的现有独立接口和锁保护保持原义。
- 测试主要扩展 `src/hybrid_tracker/tests/diagnostic_tracker_test.cpp`，必要时扩展仅用于测试的访问接口；复用现有模拟后端、条件变量及诊断事件。
- `tests/tracking_regression/` 现有工具用于记录真正不同代码版本的实机比较，不改变指标公式、模型、输入像素或有效性门槛。
- 本变更有意改变调用次序及可能被执行的帧集合；ROS 话题、参数、状态数值和配置格式保持兼容，不新增外部 API 或依赖。
- 规划基于 `rk3576` 提交 `7fbb0a2e006f12654a7db0f6d9d152244ec07e0d`。实施及实机结果以本变更的任务状态与验收记录为准，不将预期收益写成已验证结果。
