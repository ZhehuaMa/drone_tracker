# Design

## Context

旧的已完成结果明明可以取走，当前帧却先因“旧结果未读”被拒收。目标是先取走旧结果，为当前提交解除这一既有阻塞，再处理旧结果；动机见 `proposal.md` 的 Why。

源码基线为 `rk3576` 提交 `7fbb0a2e006f12654a7db0f6d9d152244ec07e0d`。Detecting 表示尚未初始化的检测路径，Tracking 表示已经初始化的跟踪路径。已检查下列实现与测试：

- `src/hybrid_tracker/hybrid_tracker.cpp`：Detecting 路径在约 410 行提交、414 行读取；Tracking 路径在约 599 行提交、607 行读取。Tracking 先完成当前帧跟踪及来源观测；持续 NanoTrack 跳变等路径会提前返回。
- `src/hybrid_tracker/yolo_detector.cpp`：`request()` 在锁内以 `UnreadResult` 拒绝未读结果；`get_result()` 在同一互斥锁下复制并清空结果槽。工作线程有一个执行请求和一个可被更新帧替换的待执行槽。
- `src/hybrid_tracker/yolo_detector.h`：`YoloResult` 包含检测框、请求身份、来源身份和按值保存的比较元数据。比较元数据不持有图像；局部保存结果不延长来源图像寿命。
- `src/hybrid_tracker/tests/diagnostic_tracker_test.cpp` 已有 `testUnreadResultAdmission()`，验证拒收不会改写正结果，读走后恢复接收；同文件已有模拟模型、条件变量和回合测试。`diagnostic_test_access.h` 提供仅测试可用的观察入口。

2026-10-19 的中段调查记录了一个具体例子：三个有框运行推理源帧 6391，时间 106.482584 秒、分块最高分约 0.537；三个零框运行推理前一帧 6390，该帧最高分约 0.292。阈值均为 0.5。零框运行提交 6391 时，旧的无目标结果仍未读。两组实际程序相同，因此 7.48% 与 0% 的组三轮中位数是异步采样波动证据，不是此修改的收益证据。

结果仲裁指读取后根据检测结果确认跟踪、判丢或恢复。补跟踪指在检测来源图像上初始化，再重放后续缓存帧。正常交互点是通过既有输入、时间及提前返回检查后，更新原本会与 YOLO 交换请求或结果的位置。

## Goals / Non-Goals

**Goals:**

- 在两个正常交互点落实“结果快照 → 当前提交判定 → 快照仲裁”，使已取走结果不再阻塞当前提交。
- 保留新帧推理与旧结果补跟踪重叠的机会，并验证当前帧来源观测不会被旧结果污染。
- 用可控制的线程交接验证顺序，再用不同程序的真实录像结果评价影响。

**Non-Goals:**

- 不保证特定帧进入推理、不消除所有 `UnreadResult`，不使实时异步检测变成确定性逐帧推理。
- 不改变一个执行请求加一个最新待执行请求的容量，不增加推理线程或原子交换接口。
- 不改变置信度、搜索级联、来源比较、回合清理、丢失计数、看门狗阈值及同步恢复接受规则；不新增结果年龄拒绝。
- 不改变 ROS 接口、状态数值、生产默认参数、模型或像素预处理；不自动部署到生产入口。

## Decisions

### 1. 在调用者保存一次结果，再进行本帧提交判定

**选择：** 每个分支在原交互点先执行一次 `get_result()`，把是否读到结果和完整 `YoloResult` 保存为局部值。随后沿用本分支的 ROI 和提交判定。ROI 是本次推理使用的搜索区域。最后用读取成功标志进入既有结果分支或无结果分支。

**原因：** 问题来自调用者已具备读取机会却先提交。已有锁内取走语义足够，无需更改检测器接收契约。

**放弃的方案：** 删除 `request()` 的未读保护会使结果被覆盖；新增原子“读取并提交”接口会改变并发契约，超出本次选择。

**实际结果：** 一个更新最多读取一次。读取之后才完成的新结果不在本次快照中，不再于同一更新末尾补读。未读结果保护、输入错误及停止/清理拒收仍成立。

### 2. 保留两个分支原有的当前帧准备位置

**选择：** Detecting 在当前帧预测与历史加入完成后读取。Tracking 在 NanoTrack 更新、跳变提前返回判定及真实来源观测快照建立后读取，随后判定 `m_frame_count % yolo_interval`。不把读取提升到 `update()` 入口。

**原因：** 来源观测是本帧实际跟踪框及有效标志；它与旧检测来源不同。提前读取可能使原本提前返回的更新悄悄消费结果。

**放弃的方案：** 在函数开头统一读走结果，或先按旧结果恢复后再为当前帧生成来源观测。

**实际结果：** 输入无效、重复时间及原生跟踪跳变的既有早退不新增读取。Tracking 未到提交间隔时仍取走和处理结果，但只记录原有间隔跳过，不增加提交。

### 3. 先完成本帧请求尝试，再做可能耗时的旧结果处理

**选择：** 局部结果保存后先尝试提交当前帧，再进入原历史查找、初始化、补跟踪或仲裁代码。提交是否成功与是否处置局部旧结果分别判断。

**原因：** 取走结果是短锁内复制；初始化及补跟踪可能长时间占用更新线程。先提交保留工作线程同时推理下一输入的机会。

**放弃的方案：** 完整处理旧结果后才请求；这会将下一次提交额外延后到补跟踪结束。

**实际结果：** 局部快照不依赖共享结果槽的后续内容，不在仲裁中持有检测器互斥锁。诊断中的当前请求关联仅在处理旧结果时切到旧请求身份；新提交仍关联当前帧，不能混用两者。

局部快照仅在本次 `update()` 内存活。保留既有编排中更新与 reset/回合清理的调用关系，不新增同一跟踪实例的并发更新或并发重置契约；清理测试在更新返回后启动，检测工作线程仍按原规则加入及释放资源。

流程示例：

1. 通过本分支原有检查，完成当前帧 B 的预测、缓存及适用的来源观测。
2. 取走已完成 A；若没有结果，只保存“无结果”，不等待。
3. B 到提交时机则执行原请求逻辑；否则记录间隔跳过。
4. 若保存了 A，只处置 A 一次；否则执行本分支原无结果逻辑。
5. 后续完成结果不加入当前局部快照，继续按原结果槽规则留待后续交互点。若工作线程后续覆盖另一未读结果，仍保留既有 `ResultOverwrite` 诊断及完整性判定；本变更不修改生产者发布策略。

### 4. 明确保留读取与提交之间的竞态边界

**选择：** 不承诺两个调用原子执行。若读取为空后工作线程刚好发布结果，后续请求仍可因 `UnreadResult` 被拒绝；该结果留待下一正常交互点处理。

**原因：** 用该边界即可实现用户选择的三阶段顺序，同时保留已验证的未读结果保护。

**放弃的方案：** 重试循环、第二次读取、清空新结果、等待下一帧稳定或禁止待执行替换。

**实际结果：** 即使帧 389 成功进入待执行槽，仍可能在推理开始前被帧 390 替换。结果快照时点前移也可能使较晚完成的结果延后一个正常交互点才重置看门狗；计数公式和无结果分支保持原义，不保证历史逐帧状态完全相同。

### 5. 用受控交接证明机制，用真实不同版本评价行为

**选择：** 在现有诊断测试中使用条件变量、完成状态观察或仅测试的有界交接点控制工作线程。所有等待必须有截止及失败时释放路径，不以固定睡眠或偶然帧序作为通过依据。保持 `testUnreadResultAdmission()` 的直接检测器契约断言。

**原因：** 此次修改的必需性质是调用顺序、旧结果不丢失及原并发边界。某次录像是否命中一帧目标不适合作为机制测试的确定性通过条件。

**放弃的方案：** 只断言有效框比例增加，或用相同二进制的两组新运行冒充代码前后对比。

**实际结果：** 增补确定性用例覆盖已就绪正/负结果、无结果、读取后完成、长补跟踪、Tracking 非提交帧、来源关联、旧回合、提前返回及清理。诊断开启与关闭均覆盖。用现有 `ResultRead`、`RequestDecision`、`RequestSkipped`、恢复和状态事件验证身份与先后关系，不改变事件格式及指标公式。

未来实机验收使用现有 `run_suite.py CONFIG.yaml`：

1. 固定基线提交 `7fbb0a2e006f12654a7db0f6d9d152244ec07e0d`，分别构建参考与实现后候选，记录实际源码、程序及模型校验值。断言参考与候选源码和程序均不同；相关模型、算法参数、工具和比较条件一致。
2. 在同一指定生产 RK3576 板上，以相同 fixture、系统 Runtime 2.3.2、驱动 0.9.8、供帧 CPU 4、准备 P=3600 秒、收尾 C=10 秒及 50 毫秒供帧有效性限制，预先声明三个 test-03 区间各三轮参考、三轮候选，共十八轮。test-02 继续豁免，不重新准备或回放。
3. 每轮独立释放资源；旧组不覆盖，不挑选替换慢轮或零框轮。每项要求每侧三轮完整合格，分别冻结和比较。硬件不可用时明确保持实机任务未完成。
4. 输出每轮有效框数/总发布数、有效框比例、最长无效输出、发布间隔、更新及检测耗时、初始化/补跟踪、队列等待、拒收/替换数和资源观测。保留中位数、范围及候选减参考的差值，专门追踪中段 fixture 388/389 附近的真实执行帧和请求处置，但不要求候选必定推理 389。
5. 报告区分执行合格、调用顺序是否符合设计、行为差异及性能判定。无额外性能门槛时保留 `not_set`；不以有效框比例证明准确率。对中段同时展示各轮是否初始化，避免中位数掩盖 2/3 与 1/3 的差别。

## Risks / Trade-offs

- [异步完成落在两个调用之间] → 保留合法拒收、一次读取边界及其诊断；用受控交接测试，不宣称完全消除拒收。
- [旧结果处理使用了新请求或新结果身份] → 保存完整局部值，测试请求、来源帧、回合、采集时间及元数据一致，禁止二次读取替换快照。
- [读走正结果后过早执行耗时补跟踪] → 断言当前请求判定先于历史查找/初始化；在模拟补跟踪阻塞期间证明已提交请求仍可被工作线程处理。
- [读取时点前移改变一次更新的看门狗分支] → 按快照是否存在使用原分支，保持严格 `counter > lost_max_count * yolo_interval * 3`，测试边界及晚到结果，不新增年龄拒绝或时间上限。
- [既有测试默认同一更新先提交后读取] → 更新调用者顺序相关断言；独立检测器未读保护、最新待执行及回合清理断言保留。
- [录像结果波动被误写为优化通过] → 使用真正不同版本，保存全部逐轮结果及范围；较快的更新必须同时展示有效输出，不隐去零框轮。

## Migration Plan

1. 后续 apply 阶段只修改调用者顺序及必要测试支撑，运行定向算法/诊断/恢复测试和 `./build.sh --test`。主机测试不替代板端时序结论。
2. 本轮恢复的板端实验只通过用户最新授权的 `adb -s 5ceb49407502303d`，目标板有接近 8 GiB 内存。此前只授权的 `ssh firefly-production` 目标为另一块 4 GiB 板，未执行回放且不参与本轮实验。复核生产服务和设备状态，使用隔离实例。用户已授权本轮临时停止正式服务；停止前记录状态并建立独立恢复措施，完成或失败后先恢复服务，不修改频率或系统 Runtime。
3. 验收后先完成测试资源回收和正式服务恢复，再生成最终比较及实现核验记录。本变更不自动部署到生产入口。
4. 无 ROS/参数/schema 迁移。回退为重新使用固定参考程序，先停止并清理候选测试进程；不把两个版本放入同一跟踪回合，不修改历史冻结基线。

## Open Questions

三个 test-03 区间的不同版本比较已完成，逐轮有效输出、执行帧集合及开销见 `implementation-report.md`。实测存在异步波动，性能门槛仍为 `not_set`；后续若需准确率或长期负载结论，应另行定义标注及验收条件，不从本次结果推导。
