# Design

## Context

当前 RK3576 相机把 `need_save=true` 当成不受支持的相机录像请求，节点因而在初始化时退出。目标是让 ROS bag（按话题保存 ROS 消息的文件）与 SC233HGS 原画面录像各自启停；记录配置或写盘故障只影响对应记录，不使健康跟踪或 HDMI 画面停下。见 [proposal.md](proposal.md)。

现有节点在 `openRecording()` 中同时配置帧源和打开 bag。姿态与里程计回调、跟踪工作线程都在各自调用路径中直接写 bag，并以同一把锁与关闭操作互斥。bag 打开失败阻止本轮启动，写入失败设置 `running=false`。SC233HGS 独立录像已经有自身的工作进程和故障状态，但不支持的输入及部分录像参数仍会在节点初始化时抛错。HDMI 实际新视频帧数已有 `displayed` 计数；`commits` 还包含仅刷新叠加层的提交，不能作为视频帧率。

## Goals / Non-Goals

**Goals:**

- RK3576 上，记录功能的开关、故障状态与采集跟踪生命周期分离。相机、模型和跟踪配置仍按既有规则校验。
- bag 工作线程独占写入器；消息生产方不等待磁盘。容量耗尽或故障留下可核对的不完整状态。
- 在生产板用短时成对试验测量跟踪与 HDMI 实际新视频帧率；单次性能或负载试验总时长不超过 180 秒。

**Non-Goals:**

- 不扩大 bag 的话题范围，也不把原始视频录像改成 ROS 图像消息。
- 不修改 Jetson 参考实现的 `need_save` 行为、ROS 话题、状态数值或模型前后处理。
- 不声称线程可以强行中断永久阻塞的文件系统调用；此变更不承诺 bag 收尾的硬实时上限。

## Decisions

### 1. 按平台拆开旧记录调用

RK3576 的节点将 `need_save` 仅交给 bag 会话，不再把它传给相机帧源的旧 `configureRecording()`。`recording.enabled` 仍只选择 SC233HGS 原画面录像。这样保留既有视频输入无相机录像的行为。Jetson 分支继续沿用其原有帧源配置调用。拒绝仅删掉相机初始化检查的做法，因为 ON 时相机帧源仍会拒绝旧录像请求。结果是 RK3576 相机可以在 `need_save=true` 下初始化，并与独立视频录像同时运行。

### 2. 录像专属错误在本轮报告

RK3576 节点将录像专属参数解析和校验结果保存为可诊断状态。AR0234、视频输入或无效的 SC233HGS 录像配置不创建视频录像会话。收到 ON 后，节点报告具体原因，仍启动健康的采集和跟踪。相机设备、模型、内参与时钟配置继续执行原有初始化校验。拒绝把不受支持的录像请求静默当作关闭，因为操作人员会误以为已留存视频。结果是录像开关和录像专属配置不决定节点能否初始化。

### 3. bag 会话由单一工作线程拥有

RK3576 每轮建立独立 `BagSession`，由一条工作线程独占 ROS bag 写入器。消息生产方只提交不可修改的消息引用、话题和原时间戳到队列；写入线程执行打开、话题注册、序列化、写入和关闭。检测框与图像发布路径应共享同一消息对象，避免为了入队再深拷贝整张图。队列同时限制消息数和估算载荷字节数；实现先采用最多 256 条、64 MiB 的上限，并在实机测量实际内存。达到任一上限时立即拒收当前消息、增加按话题丢弃计数并标记会话不完整；不得阻塞跟踪路径。

拒绝继续在消息回调中持锁调用写入器，因为磁盘延迟会直接进入跟踪或 ROS 回调。结果是正常写盘延迟不会直接占用跟踪线程，但消息复制、入队和队列争用仍有成本，必须通过帧率对照实测。`visualized_result=false` 时既不生成图像消息，也不在 bag 中注册 `/fpv/tracker_image` 话题。

一轮的顺序如下：

1. ON 创建本轮身份与队列，启动 bag 工作线程，并启动跟踪轮次。bag 打开失败只更新 bag 状态。
2. 回调与跟踪线程在会话接受阶段入队。写入线程按入队顺序写入，并保留每条消息原有时间戳。
3. OFF、EOF 或跟踪失败时先禁止本轮继续入队；随后处理已接受消息并关闭写入器。迟到的回调只可跳过，不能访问释放后的写入器。下一轮使用新身份，旧轮消息不得混入。

### 4. 明确 bag 完整性与失败隔离

bag 状态至少区分 `disabled`、`opening`、`recording`、`complete`、`incomplete`、`failed`。每轮按话题统计提交尝试、队列接受、成功写入和容量丢弃，并记录打开、写入、关闭错误。仅当打开、写入、关闭均成功，丢弃为零，且已接受数等于成功写入数时，才标记 `complete`。目录排他创建，绝不覆盖旧 bag。打开失败时清理排队消息并报告失败；写入失败时停止该轮 bag 接受，保留原错误并尝试安全关闭。失败不得设置跟踪 `running=false`，也不得改变独立视频录像状态。

拒绝以“文件存在”作为完整性的证明。测试将使用 `rosbag2_cpp::Reader` 重新打开已关闭的 bag，读到结尾并检查话题类型、条数、时间戳和可识别载荷。计数以节点本轮实际接受的消息为基准，不把上游 best-effort 传输未到达的消息算成 bag 丢失。`visualized_result=false` 的测试还检查 bag 元数据不含图像话题。结果是正常完整与明确缺口均可复核。

### 5. 生产板成对测量采用实际计数

在同一块 HZ-RK3576_WuKong Board 上固定相机、模型、场景与采集模式；两轮均设 `visualized_result=false`、`recording.enabled=true` 并启用 HDMI，仅切换 `need_save`。`visualized_result` 只用于调试图像输出，不因性能测试改变生产配置。建议每种状态各运行 60 秒，连同两轮准备和收尾将整次成对试验控制在 180 秒以内。跟踪帧率取 `consumed_frames_` 的窗口增量除以单调时钟秒数；HDMI 视频帧率取显示后确认的 `displayed` 增量除以同一窗口秒数。报告原始计数、绝对与相对差值、相机及 bag 队列丢弃、HDMI 替换与拒绝计数，并注明板卡、模型、输入和 bag 所在存储。

拒绝用配置的 `mv_camera.fps`、HDMI 刷新率或 `commits` 代替实测值。此次只要求如实比较与诊断，不预设未经实机数据支持的相对帧率门槛。

## Risks / Trade-offs

- [bag 文件系统调用永久阻塞] → 独立线程隔离正常延迟，但 `join` 仍可能拖长 OFF；任务中单列故障注入与收尾耗时。若将来要求严格上限，需要另立进程隔离变更，不得以本方案声称已经满足。
- [大图像占用内存] → 双重队列上限与共享消息对象；实机记录进程内存、队列峰值及丢弃，容量不足时报告不完整。
- [录包失败看起来像成功] → 记录状态、错误与按话题计数；验收读取 bag 内容，不以目录存在或关闭调用成功替代完整性。
- [两轮场景或显示负载不同] → 使用同一块生产板与相同输入配置，保存运行窗口和原始计数；报告环境变化，不把一次成对对照解释为普遍性能保证。

## Migration Plan

1. 先更新 OpenSpec、节点与测试；生产参数保持 `visualized_result=false`，且 `need_save` 默认 false，不自动增加调试图像或 bag 写盘负载。
2. 在匹配 RK3576 SDK 的环境构建并运行无硬件测试；在指定生产板执行不超过 180 秒的成对对照和 bag 回查，记录板卡与模型身份。
3. 部署前确认 `save_path` 指向有空间且可写的目录。独立视频录像目录继续遵守原有 ext4 与配额规则。
4. 若出现不可接受的性能或完整性问题，先 OFF 并正常退出节点，再切回上一版本或将 `need_save=false` 后重启；保留已有 bag 与录像证据，不覆盖或删除。
