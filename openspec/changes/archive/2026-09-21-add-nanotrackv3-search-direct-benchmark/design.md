## Context

当前性能基线通过 CPU 取回并整理搜索特征。直接共享内存可以省去这段工作，但初始化时绑定一次的探针产生了错误结果。本设计将已验证的提交后重新绑定规则用于独立测试程序，并保留可核对的 baseline。动机见 [proposal.md](proposal.md)。

backbone 是提取图像特征的模型；head 使用模板和搜索特征计算分类及位置输出。Float32、FP16 分别是 32 位、16 位浮点。普通提交指 `rknn_inputs_set`，由 Runtime 接收主机数据；绑定指 `rknn_set_io_mem`，指定模型输入或输出所用的设备内存。绑定本身不执行模型，也不等于复制特征。

现有 `baseline::runBenchmark(config, ModelLoader)` 可注入后端，公共 NanoTracker 和灰度预处理可以复用。`RknnNanoTrackBackend` 当前将模型输出取回为 Float32，必要时转换排列，再普通提交给 head。`RknnSession::execute()` 保证独立输出所有权，不能把它的返回值改成下一帧会覆盖的设备缓冲区。

### 已完成的实机调查

日期为 2026-09-20，平台为开发板 2，Runtime 为 `2.3.2 (429f97ae6b@2025-04-09T09:09:27)`，驱动为 `0.9.8`。三份模型与已归档 baseline `detailed-006` 的文件指纹一致，测试后再次核对未变化。SHA-256 是文件内容指纹：

| 模型角色 | SHA-256 |
|---|---|
| template backbone | `c0002d937a7a414a7ef829b206f1674e0aff3311bf7bd5514baaa0106c2e7059` |
| search backbone | `8985bc1f825dac3ac28bd1805abfee2cc81112acf8f3945cd495c9d325b4c754` |
| head | `f93e5c0e0b2a2a8bfe0425d9d43e6f0a6659a6464a9b09d94d35f21fa64f15bd` |

search 原生输出与 head 搜索输入均为 FP16、`[1,12,16,16,8]`、49152 字节。原生排列 NC1HWC2 将通道分成组及组内通道；这里 12 组、每组 8 通道，对应逻辑 96 通道。普通输出 NCHW 表示批次、通道、高、宽；普通输入 NHWC 把通道放在最后。直连依据原生属性，不依据普通排列的名称。

| 实验 | 结果 | 含义 |
|---|---|---|
| search 输出只在初始化绑定，随后普通提交图像 | 初版 72 次全部失败；诊断读到全零原生输出 | 不能依赖旧输出绑定跨提交保持有效 |
| 增加等待或先读取同步 | 未解决；等待实验返回 -1 | 不把额外 wait 当作修复 |
| 修正 search 后，head 搜索输入只在初始化绑定 | 0/24 正确 | head 也不能依赖旧绑定 |
| 每次在模板普通提交前重新绑定 head 搜索输入 | 23/24 正确 | 首次失败仍足以否定该顺序 |
| 每次在模板普通提交后重新绑定 head 搜索输入 | 24/24 正确 | 选定可靠顺序 |
| 三个独立进程重复最后一种方式，每个 240 次 | 720/720 正确，两项 head 输出最大绝对误差均为 0 | 混合输入和缓冲复用可行 |

探针使用 0～255 的合成 Float32 灰度图，保留小数并复制到三通道。模板种子为 11、29，搜索种子为 101、202、303；搜索按 A/B/A/C 交替，每四次切换模板。参照使用独立普通 search 会话和普通 head 会话，每个进程产生 6 种不同参照输出，避免双方读取同一错误缓冲区而误判一致。head 完成后才额外读取原生搜索特征作诊断，720 次也均与独立普通输出一致。

完整证据位于开发板 `/tmp/nanotrack-search-direct-check-20260920/`，本机副本位于 `/private/tmp/nanotrack-search-direct-check-20260920/`。`initial-result.json`、`diagnose.json`、`result.json` 保存失败诊断；`confirm-1.json` 至 `confirm-3.json`、`summary.json` 保存重复验证；脚本为 `check_mixed.py` 和 `confirm.py`。这些临时路径可能被清理，以上核心结果及模型身份已在本设计固化。正式实现需产生自己的可持久化验收记录。

2026-09-17 历史探针的不同样本输出指纹相同，且使用相似的初始化绑定顺序。其“与参照一致”不再作为正确直连的充分依据。本次没有证明 Runtime 内部完全无搬运，也没有执行完整录像跟踪、性能测量或长期负载测试。

## Goals / Non-Goals

**Goals:**

- 在测试专用后端内共享搜索特征，CPU 不读取、复制或转换该特征；CPU 仍负责提交、绑定和同步控制。
- 保留 baseline 可观察数值和工作量，单独测量搜索交接方式的影响。
- 将每帧重新绑定的时间和设备完成等待纳入真实端到端耗时。

**Non-Goals:**

- 不优化模板路径、图像输入复制、缩放或搜索输入提交，不加入模板提交缓存。
- 不替换模型、改变精度、融合模型、引入 RGA 或并行流水线。
- 不推广为生产 RKNN 后端，不改变通用会话的独立 Float32 输出契约。
- 不承诺固定提速幅度；性能无收益也是有效实验结论。

## Decisions

### 1. 独立入口、测试专用执行后端

选择在 `tests/nanotracev3_performance_benchmarks/search_direct/` 新增入口及后端，通过已有 `ModelLoader` 注入共享 runner。配置键、精度证据校验、MJPEG 亮度解码、逐帧调度、预热和报告继续复用 baseline。MJPEG 表示每帧独立 JPEG 编码的视频。

原因是现有注入边界足够，既能公平比较，也避免修改生产路径。拒绝复制整套 runner 和直接改写 `RknnSession::execute()`。后果是只为专用后端新增设备内存 API 包装及测试替身；必要的共用辅助函数可做保持行为的提取，但必须回归 baseline。模板会话仍采用现有普通输出语义，search/head 的专用执行保持相同输入准备和 head 输出规范化逻辑。

仓库构建与新目录的无 ROS 独立构建均生成 `nanotrackv3_search_direct`。复用 baseline CMake 目标时避免重复添加目标，不要求用户启动 ROS。沿用 `AGENTS.local.md` 的 ARM64 构建环境；容器 SDK 不替代实机 Runtime 2.3.2。

### 2. 共享一个搜索特征缓冲区，按实际属性匹配

选择在初始化时查询普通及原生属性，按逻辑特征角色定位输入输出。只支持本次 FP16 原生 NC1HWC2 搜索边；不将已测模型哈希作为准入白名单。验证形状、类型、通道分组、有效行/高跨度、字节容量及偏移安全，记录量化元数据但不对浮点数据做反量化。跨度表示相邻行或维度实际占据的存储距离，可能含填充；对于已支持格式按 SDK 约定解释零值，不简单比较字段字面值。

search 用 `rknn_create_mem` 分配 S，head 用 `rknn_create_mem_from_fd` 导入同一内存。FD 是标识可共享内存的文件描述符；两个会话有各自管理对象，但不生成第二份搜索特征。head 输入以 `pass_through=1` 原样读取，分配大小依据经检查的原生属性，不写死为 49152。

原因是普通接口形状相同不能证明物理存储兼容。拒绝直接传递普通输出指针、只匹配元素数或只设置 `want_float=0`。后果是不兼容模型明确失败，不自动转换或回退为普通 CPU 路径。SDK 定义依据 [RKNN 2.3.2 官方头文件](https://raw.githubusercontent.com/airockchip/rknn-toolkit2/v2.3.2/rknpu2/runtime/Linux/librknn_api/include/rknn_api.h)。

### 3. 每次普通提交后重新绑定，保留 baseline 全局调用顺序

已通过探针的完整顺序是：head 提交模板 → head 绑定搜索输入 → search 提交图像 → search 绑定输出 → search 执行 → head 执行。证据仅覆盖这个完整顺序，不将它描述成所有调用重排均已实测。

正式程序选择保留 baseline 的“先 search、后 head”阶段顺序，同时满足已验证的两项局部规则。每次更新执行：

1. 校验输入和有效模板，按 baseline 准备搜索图像 Float32 数据。
2. `rknn_inputs_set` 普通提交搜索图像；随后 `rknn_set_io_mem` 重新绑定 search 输出 S。
3. 同步执行 search，确认当前特征已经写入 S。
4. 按 baseline 每帧准备模板特征的普通提交数据，并只提交 head 的模板输入。索引按角色查询；已测模型模板为 0、搜索为 1，但实现不写死。
5. `rknn_set_io_mem` 重新绑定 head 搜索输入 S，并设置原生透传属性。之后到 head 执行前，不再对该会话普通提交输入。
6. 执行 head，按 baseline 普通接口取得独立 Float32 分类及位置输出，交给公共算法。
7. head 完成后才允许下一帧覆盖 S。

```text
search inputs_set --> bind output S --> search completes
                                              |
                                              v
head template inputs_set --> bind search S --> head completes
                                              |
                                              v
                                         next frame
```

选择此顺序是为了不额外移动 baseline 的模板准备工作，并保持 search/head 计时区间连续。拒绝只初始化绑定、先绑定后普通提交或复制整个历史探针的调度。后果是必须在正式 C++ 设备测试中，将上述顺序与已通过的探针顺序及独立普通参照逐项比较；在该检查通过前不宣称完整实现等价。这个验证属于明确的验收任务，不是再次探索是否支持混合输入。

普通提交与重新绑定使用相同会话，成功路径采用阻塞运行。移除 search 的 `outputs_get` 后仍须确认设备完成，不能把提交返回当作已结束。不得开启异步运行标志；不沿用诊断中返回 -1 的额外 wait 作为正常流程。设备错误后的停止确认单独处理。

### 4. 单一所有者管理缓冲区和失败清理

选择由专用后端持有三模型会话、search 分配对象和 head 导入对象。只允许串行更新。reset 使模板失效，可保留分配的 S，但下次执行必须重新提交和绑定；建立新模板开始时旧模板立即失效。

原因是 S 会被覆盖，不能作为持久公共 Tensor 返回。拒绝把共享地址暴露给公共算法或使用裸指针隐式共享生命周期。后果是初始化中途失败须按依赖关系清理；确认设备停止后，先释放 head 导入对象，再释放 search 原始内存，各自所属会话保持有效直到内存释放完毕，最后销毁会话。释放失败或设备停止无法确认时沿用仓库致命诊断策略，不正常析构可能仍被使用的存储。

绑定失败在运行前停止，不输出预测框；执行后失败使相关后端失效，不重试或复用旧结果。诊断包含模型角色、操作和返回码。缓存策略保持默认，不增加全局禁用缓存同步的优化。正确性测试可以在消费者完成后读取 S；正式计时运行不做这个诊断读取。

### 5. 计时记录真实调用，报告明确区分路径

选择复用 `decode_to_result` 作为唯一端到端指标，保留整数纳秒和父子区间。该指标从 JPEG 解码开始，到框与分数可读结束。search/head 各自的重新绑定区间记录为 `io_mem_bind`，其时间包含在对应模型和推理父区间内。未执行的 search 输出获取、复制、释放和排列转换不伪造零值或空区间。

原因是绑定和等待也是直连成本。拒绝只计 `rknn_run`、从数据中减去绑定开销或把父子耗时重复相加。后果是记录核对工具需要识别两种路径的合法阶段集合，不能再强制每个模型都有普通输出获取；模型执行次数仍严格一致。

在新程序的 manifest、summary 和中文报告记录 `benchmark_variant=search_direct`、`search_handoff=native_fp16_shared`、绑定策略、普通/原生属性和缓冲区容量。新字段及新阶段是版本 1 的兼容扩展；旧字段的含义和数据格式不变，旧 baseline 记录缺少变体字段时按普通路径读取。既有 baseline 不启用共享路径。程序/代码身份必须涵盖新后端，模型导出证据仍沿用原校验。

比较报告先检查板号、版本、模型/录像指纹、首帧框、预热/轮次/帧范围和观测模式是否一致。不同身份不输出可比提速结论。低分、慢帧和失败均保留；未执行阶段为空。端到端处理速率不等同于包含读盘和写盘的系统吞吐率。

### 6. 独立数值参照与性能测量分开

选择三层验证：受控 API 顺序与失败测试、同输入设备数值测试、完整录像对照。正确性模式可额外运行参照和读取诊断特征；其数据不进入正式性能统计。正式每次初始化只执行一次模板 backbone，每次更新只执行一次 search 和一次 head。

原因是历史探针暴露了“双方同错也相等”的风险。拒绝只看调用返回成功、只比较来自共享数据的两份结果或只检查输出有限。后果是必须保留不同输入产生不同参照结果的检查，并验证模板切换和 A/B/A 搜索复用。已测同模型固定输入以 head 输出逐元素相同为标准；正式回放框各分量绝对误差不超过 `1e-4` 像素，分数不超过 `1e-6`，不通过放宽容差掩盖错误。

性能在同板交替执行 baseline 与新程序，两者分别完成细分观测开/关，每组至少三轮、默认预热 30 次。记录温度、频率、模型、录像和程序身份；比较均值和 P50/P90/P95/P99（排序后对应分位点），报告每轮差异。没有速度提升也如实报告，不事后删慢帧。另执行至少 30 分钟持续回放和至少 20 次创建、初始化、reset、销毁循环，资源观测不可获得时明确列出缺口，不以进程正常退出替代资源证据。

## Risks / Trade-offs

- [绑定行为随 Runtime 或模型变化] → 固定 2.3.2/0.9.8，查询实际属性并执行顺序回归；不将本次现象概括成所有版本的内部机制。
- [正式程序的全局顺序不同于探针] → 明列两套顺序和局部约束，先完成同输入 C++ 实机对照再测性能。
- [共享辅助代码引入 baseline 变化] → 限制为行为保持的复用和观测扩展，对旧入口、数值、阶段和记录格式做回归。
- [收益被绑定或输入侧开销抵消] → baseline 历史均值约 22.10 ms，其中 search 输出获取/复制/释放约 0.26 ms；head 提交混合了两路成本，不能据此精确预测提速，最终只采用新实测结果。
- [临时证据被清理] → 本设计固化核心事实；正式验收保存自包含的命令、数据身份及结果摘要，不依赖 `/tmp` 永久保留。
- [缓存或释放错误导致偶发污染] → 默认缓存策略、独立参照、交替输入、失败注入及持续回放分别覆盖，不宣称硬件总线层零搬运。

## Migration Plan

1. 先实现测试专用后端及受控测试，再接入新可执行入口；baseline 继续可单独运行。
2. 完成 ARM64 构建和旧测试回归。设备部署使用开发板 `/tmp` 下新建独立目录，系统 Runtime 不被容器库覆盖。
3. 完成正式程序的顺序、固定输入、回放和资源验收，再生成性能对照报告。
4. 验收失败时停止新程序，保留失败记录，继续使用 baseline；不更改生产入口或默认后端。完成实现与规格一致性核对后，再由后续工作流同步或归档。
