# Design

## Context

当前生产服务停止跟踪时也停止相机，操作者看到的是冻结图像。目标是在服务健康运行期间一直输出视频和 OSD（屏幕上的状态与遥测叠加），同时保留 ON/OFF 控制跟踪和录像。业务动机及范围见 [proposal.md](proposal.md)。

源码基线为 `rk3576` 提交 `fde4f35`。本 change 位于新 worktree，不包含原工作区的未提交修改。调研观察如下：

- `DroneTrackerNode::setupDisplay()` 在节点构造期间启动显示线程，但 `worker()` 只有在 ON 后才启动帧源。
- `processFrames()` 同时取帧、同步调用跟踪、发布 ROS 结果及提交 HDMI。HDMI 提交只发生在 `out.consumed=true` 时。
- `stop()` 结束显示轮次并等待消费线程。`worker()` 的收尾会停止相机、等待 `finishRound()`、关闭记录，再结束显示。
- `OsdPresenter` 的轮次身份同时承担视频接收和跟踪结果隔离。`endRound()` 会关闭全部新画面接收，`PresentationPacket` 的默认状态可能把无结果预览误写成 Detecting。
- SC233HGS 帧源的 `start()/stop()` 包含录像会话创建和关闭。`Ar0234CameraFrameSource::setRecordingSink()` 明确拒绝在采集线程存活时替换录像接收对象。
- 原相机队列只支持单一生产者和单一消费者。当前公共帧具有共享只读所有权，RK3576 帧像素独立于驱动缓冲区。
- ROS 视频测试目前也断言 OFF 冻结。有限视频文件不属于持续预览范围，不能整体替换这些断言。
- 现有 HDMI 规格要求若干长测，ROS 相机短测要求单次运行不超过 180 秒。本 change 对持续预览模式给出唯一的定向验收入口，其他模式及历史证据不重写。

## Goals / Non-Goals

**Goals:**

- 使预览取帧不受推理收尾、录像准备和写盘收尾的等待影响。
- 保持每个有效目标框与实际处理的图像配对。保留原像素、采集时间和 ROS 消息时间含义。
- 为视频流、跟踪轮次和录像会话分别建立身份与计数，防止旧轮结果和统计串入新轮。
- 保留服务入口和配置值，用既有 `osd.enabled` 选择持续预览相机模式。
- 为健康视频、跟踪故障、相机故障和显示故障建立不同的清理路径。

**Non-Goals:**

- 不改变 HybridTracker 的算法状态机、模型前后处理、目标类别或阈值。
- 不改变 `/fpv/tracker_image` 的发布条件，不把 HDMI 预览复制到 ROS 调试图像。
- 不要求跟踪开启时按相机采集帧率显示所有帧。不新增超时后自动切换无框视频的策略。
- 不改造 Jetson、未启用 OSD 的相机、视频文件播放或独立采集工具的启停行为。
- 不自动重连 HDMI、不修改 ISP 链路、不重建 SDK 镜像、不自动部署。

## Decisions

### 1. 按入口条件选择持续预览，并显式启动服务

**选择**：仅当平台为 RK3576、正式 ROS 输入为相机且 `osd.enabled=true` 时启用持续预览。参数、模型、消息接口和显示初始化全部成功后，由 `main` 显式启动视频服务，再进入 ROS 事件循环。服务启动只开相机及预览，不创建记录会话。其他组合继续使用原轮次路径。

**原因**：生产模板已经启用 OSD，无需新增配置。相机和文件的结束语义不同，有限文件不宜因本需求自动循环。

**未采用**：全部输入自动开流，或增加默认关闭的新预览开关。前者改变视频回放，后者使已启用 HDMI 的生产服务仍需另行配置才满足需求。

**影响**：不能在尚未完成构造时让后台线程访问节点。相机启动失败须清理并非零退出。`osd.enabled=false` 是无显示模式，不是“显示旧版冻结视频”的回退开关。

### 2. 一个常驻分发者读取相机队列

**选择**：新增常驻帧分发线程，它是 `waitFrame()/tryFrame()` 的唯一调用方。线程按现有取最新策略读取合格帧，并生成分发信封。信封包含 `stream_id`（视频流会话）、`source_sequence`（本流递增图像序号）、只读 `FrameRef` 和原采集时间。跟踪线程只读取分发后的单槽输入。

```text
Camera --> Source queue --> Frame dispatcher --> Preview packet --> Presenter --> HDMI
                                   |
                                   +--> Latest tracking slot --> Tracking worker
                                                                    |
                                                                    +--> Paired packet --> Presenter
                                                                    +--> ROS outputs
```

“单槽输入”表示最多一份尚未开始跟踪的任务。分发者用最新任务替换旧任务，正在处理的任务不被覆盖。显示仍至多一份待显示包。各槽旧引用在锁外释放，避免析构拖长控制事件。

**原因**：预览需要在跟踪关闭及收尾期间持续取帧；独立线程使模型等待不会堵住相机队列。

**未采用**：显示和跟踪分别消费原队列；或在一个循环中先 `update()` 再显示预览。前者破坏队列假设，后者仍被同步推理阻塞。

**影响**：增加一个常驻线程和一个有界任务槽，不新增视频像素副本。现有算法缓存与 YOLO 在途引用继续按原上限管理，不计入新槽数量。显示缓冲仍归显示后端所有。

### 3. 正常跟踪使用配对画面，其余阶段使用预览

**选择**：将运行状态分成视频流状态和跟踪状态。视频流为准备、运行、失败、退出；跟踪为 `Idle/Starting/Running/Stopping/Failed`。上述名字描述运行阶段，不是 ROS 的四个 `TrackerState` 值。

在 Idle、Starting、Stopping 或跟踪失败阶段，分发者提交无框预览。Running 阶段只接受当前轮次已消费帧的完整跟踪包。这个完整包内的显示框来自 `display_box`，而非外推到当前时刻的 `realtime_box`。

切换到 Running 在分发边界完成：

1. 跟踪线程完成旧轮清理和重置，准备接收新任务。
2. 分发者处理就绪事件，记录当前已分发图像序号作为边界。
3. 显示控制版本失效掉尚未交接的预览包；已交给硬件的包安全完成。
4. 下一张越过边界的合格图像才进入新轮跟踪槽。
5. 首个配对包到达前，显示保留已有底图并更新遥测；不得伪造输入已停止提示。

这样不会把切换前正在显示的较新预览替换为较老的启动结果。等待首个 Running 结果属于正常处理等待；超过 `osd.frame_stale_ms` 时仍按既有规则清框并提示等待。

**原因**：持续输出的需求主要解除 ON/OFF 启停关系。严格同帧配对比把旧框画在新视频上更可靠。

**未采用**：所有采集帧都显示并叠加最近目标框；按固定延迟缓存整段视频等待结果；推理超时后自动切预览并自动恢复。这些方案分别改变框时间语义、增加缓存延迟或引入新的恢复规则。

**影响**：Running 阶段新画面速率仍由实际跟踪消费速度决定。推理卡住且未收到 OFF 时，显示可以进入过期等待；本 change 不保证该情况下仍有全速视频。收到 OFF 后，预览取帧不等待该推理完成。

### 4. ON/OFF 是非阻塞控制请求，旧轮通过代际隔离

**选择**：为每个跟踪轮次分配 `tracking_round`。代际隔离指任务和结果必须携带创建它们的轮次，轮次失效后结果不能进入新的输出。ROS 回调仅改变期望状态并发出控制事件，不执行推理等待或录像准备。

ON 的执行流程：

1. Idle 接受 ON，记下消息时间用于原 bag 命名，建立新轮次并进入 Starting。
2. 跟踪线程执行 `finishRound()` 和 `reset()`，清除旧请求、旧结果和首次状态发布记忆。
3. 分别准备本轮 bag 和显式启用的录像。记录准备失败只报告本轮记录错误。
4. 通过第 3 项的分发边界进入 Running。模型不重新加载，相机不重开，预热不重复。
5. 当前轮次已消费结果按原规则发布 ROS 消息和 HDMI 配对包。

记录准备放在专用记录控制执行路径；不以原画面录像就绪作为允许健康跟踪进入 Running 的条件。bag 的有界消息接收会话须在首个结果发布前建立，文件打开和写入在后台完成；准备失败按原规则报告记录失败，健康跟踪继续。

OFF 的执行流程：

1. 在短控制交接中关闭当前轮次的任务与结果接收，并使显示控制版本变化。
2. 清掉尚未执行的跟踪任务，切回预览，清除目标装饰并展示 TRK OFF。
3. 封闭 bag，关闭录像接收边界，通知各自收尾。
4. 跟踪线程等待当前 `update()` 和 YOLO 在途访问结束，再执行旧检测清理。
5. 记录控制执行路径完成有限收尾；之后报告实际清理完成时间。

停止期间只保留最后一个期望 ON/OFF 状态，不排队积累请求。若最后为 ON，旧模型访问结束后才建立一个新轮。重复 ON 不重置 Running，重复 OFF 不重复收尾。停止发生在记录准备中时，准备完成的资源不能接入已失效轮次。

**原因**：ON/OFF 回调长期等待会阻塞同一 ROS 执行器中的遥测更新。旧请求完成时间不可代替其轮次身份。

**未采用**：OFF 直接销毁模型、清缓存却不等设备访问；停止期间无限保存 ON 请求；通过消息时间戳判断旧结果。这些方式会造成资源提前释放、资源累积或时钟跳变误判。

**影响**：日志分开“请求已接受”与“清理已完成”。结果发布在当前轮次的发布边界再次校验，禁止已经关闭的轮次启动新的发布。停止前已经交给 ROS 中间件的消息仍可能延迟送达；接收端现有排空规则保持。状态数值、变化时发布、图像时间与预测框时间保持原规则。

### 5. 显示流与跟踪轮次使用独立接口

**选择**：将视频流开始/结束和跟踪状态控制分开。显示包标明 Preview 或 Tracking，并使用显式可选算法结果；预览不填入默认 Detecting。包保留流身份、原图序号、跟踪轮次及原图时间。旧的 `beginRound()/endRound()` 语义只保留在非持续预览路径或兼容封装中。

OFF 清除旧跟踪待显示包，但不关闭视频流提交。预览包与配对包经过同一显示槽，不允许两个独立提交方互相覆盖不同模式的包。每个包同时校验流身份、控制版本、包类型和适用的跟踪轮次。包序号用真实图像身份；仅遥测或模式更新不增加新视频计数。

HUD（画面上的信息区）保持原布局，右上角算法文字在无结果时改为 TRK OFF、TRK STARTING 或 TRK ERROR。若 MISSION 覆盖右上角文字，下方原状态提示区域独立说明跟踪关闭/启动/错误。MISSION 仍只在下一次实际发布跟踪状态时解除，ON/OFF 不主动清除。TRIG ON/OFF 继续两秒有效。

**原因**：视频健康与跟踪开启是两件事。现有轮次切换同时重建视频状态和缓存，容易把 OFF 误解释为输入停止。

**未采用**：用状态 -1 发布新的算法状态；重用 TargetLost 表示关闭；OFF 时清掉 MISSION。前两者破坏下游契约，后者改变已批准的任务文字规则。

**影响**：更新 `presentation.h`、`presenter.*` 和布局缓存键。`cached-overlay` 与 `legacy` 同样处理清框和模式提示；不改变字体、准星、目标装饰及图像缩放规则。OFF 清框和关闭提示在健康链路下 500 ms 内提交，但不将显示完成事件称为屏幕实际发光时刻。

### 6. 固定录像入口通过完整帧边界切换会话

**选择**：增加平台无关的可选录像控制能力，默认不支持的帧源保持旧接口。具体拟采用 `CameraRecordingControl` 控制接口，由帧源返回其可选能力；命令只包含轮次和请求，不传 NV12、驱动或 SDK 句柄。SC233HGS 内部提供会话控制执行路径，以及整个采集期间固定存活的录像分发对象。

录像分发对象以共享会话引用保护一次 `stage/publish/cancel` 访问。三者分别表示候选图像暂存、最终发布、撤销。会话准备成功后，以短同步操作在下一张完整合格帧接入。实际像素复制和设备归还仍在采集边界，保留原最终预热/停止检查。

停止边界关闭接收代际，停止边界前只暂存而未发布的候选须撤销。已经接受的帧允许在原预算内编码并收尾。旧会话所有采集引用结束后，才允许销毁接收对象和共享区。关掉录像后不复制录像像素，不关闭相机。资源准备和父进程收尾各维持 3 秒预算；旧进程未退出时保持隔离，不创建额外工作进程。

**原因**：当前 `setRecordingSink()` 与 `Session::sink()` 依赖停机才能保证裸引用安全。必须同时保证控制响应和驱动缓冲快速归还。

**未采用**：运行中替换裸指针；在 OFF 时关闭并重开相机；把录像取帧移到公共灰度队列。它们分别可能导致悬空引用、预览中断和丢失 NV12 色度。

**影响**：会话开始/结束不再调用相机 `start()/stop()`。会话记录新增视频流关联、起止计数快照与接收边界。格式、源码身份、模型身份、存储保护、PTS（视频显示时间）和同步预算不变。PTS=0 仍来自本会话首个实际接受帧，不补录准备期间的图像。预热证据来自流启动，可被多个录像会话引用；须标明发生在会话前，而不是声称每轮重新预热。

### 7. 把故障与最终退出分开处理

**选择**：新增幂等 `shutdown()`，表示重复执行也安全的服务关闭。关闭顺序为：禁止新控制请求及新任务 → 停止录像接收/封闭 bag → 停止并唤醒分发与采集 → 回收相关线程 → 等待模型在途访问 → 收尾记录 → 关闭遥测适配和显示 → 释放模型。采集停止前不得提前析构仍可能被访问的录像分发对象。显示硬件停止读取缓冲后才能释放其资源。

相机首次开流或运行故障使节点安全非零退出，由已有 systemd `Restart=on-failure` 处理。跟踪处理异常只使本轮失效并回到预览，旧模型访问收尾后允许下一次 ON。记录错误只使记录失败。显示运行故障继续沿用隔离契约，不自动重连或因此停止健康跟踪。

**原因**：相机恢复若依赖 ON，控制话题仍间接决定视频生命周期。不同故障不应都进入统一相机停止路径。

**未采用**：相机故障后等待 ON；任何显示或记录故障都重启整个节点；用线程取消强行终止 SDK 访问。

**影响**：相机故障需要从后台传递到主执行路径，使进程真实返回非零；只设置内部 `running=false` 不足以触发服务重启。传递方式需有界且可测试。运行显示故障意味着 HDMI 输出不可用，不声称此时仍满足健康视频输出保证。

### 8. 常驻资源与会话资源分别计时和验证

**选择**：帧分发线程复用 CPU 策略的 Capture 职责，在开始工作前应用并读回亲和性。相机采集和录像仍遵守现有职责映射，跟踪线程使用 Tracking。未提供策略则保持继承行为。控制策略版本和生产默认配置不变。

诊断按单调时钟汇总。单调时钟表示不受系统校时影响的持续时间来源。流计数持续累加，轮次统计从快照求差；分别报告采集、分发、跟踪槽替换、消费、预览/配对显示及录像计数。ON/OFF 不重置视频帧号，不断开健康视频的新画面间隔链；包类型和跟踪轮次变化只标注统计边界。

**原因**：预览持续运行后，原“每轮相机计数清零”不再成立。显示刷新次数也不能代表新视频速率。

**未采用**：增加强制的新 CPU 核心映射、重置流计数适配旧日志、用 HDMI 名义 60 Hz 报告新帧率。

**影响**：生产板必须检查采集、分发、录像共享核心时的实际负载。新增日志须包含流和轮次，不逐帧输出稳定画面。现有耗时阶段名称和定义保持。

## Risks / Trade-offs

- [预览转跟踪时旧包或图像倒退] → 在唯一分发边界建立截止序号，切换显示控制版本，并让新轮只接收之后的图像。
- [OFF 等待推理造成冻结] → 先失效结果并切预览，模型等待只在跟踪执行路径；用受控阻塞推理验证预览仍递增。
- [活跃录像对象被提前销毁] → 固定分发对象、每帧会话引用和停止边界确认；测试暂存到发布之间发生 OFF。
- [记录准备阻塞 ROS 遥测或预览] → 专用记录控制执行路径；记录未准备好时跟踪与预览继续，停止后准备成功也不能接入旧轮。
- [共享核心或额外同步导致性能下降] → 确认亲和性，记录同板相同输入的前后计数；不在采集/显示路径等待锁内 I/O。
- [正常推理速度限制 Running 画面速率] → 文档与规格明确该边界，不声称相机 60 fps 等于跟踪或 HDMI 60 fps。
- [不同入口测试互相覆盖] → 将持续预览相机用例与视频、OSD 关闭、独立帧源用例分组；复用原测试替身但不改变旧断言含义。
- [单次短测不证明长期稳定性] → 明确保留证据限制，不拼接多个短测声称完成历史十分钟或三十分钟负载。

## Migration Plan

1. 先实现并通过模拟提交、ROS 相机集成、录像切换和故障测试。运行既有无设备测试，保留视频文件/无 OSD 路径回归。
2. 使用仓库 ARM64 构建入口 `./build.sh --test`。不修改镜像或系统 RKNN 库；本机没有匹配镜像或 SDK 时记录缺口。
3. 按 `rk3576-continuous-hdmi-stream` 的定向验收在 `HZ-RK3576_WuKong Board` 执行。记录 Runtime 2.3.2、驱动 0.9.8、程序/配置/模型指纹、相机拓扑、显示模式及实际 CPU 策略。每次运行不超过 180 秒。
4. 持续预览模式的生命周期验收以新能力为准，取代重复的历史长测时长要求；其他模式原规格不变。三次定向运行覆盖 cached-overlay 联合负载、legacy 行为回归、OSD 关闭基线。cached-overlay ON 有效窗口仍核对既有性能门槛；不能用短测宣称完成原六轮固定回放性能验收。
5. 后续部署使用已有打包与备份流程。保留原相机 YAML 的模型、算法、bag、录像及显示配置值。明确通知操作者：启动节点立即占用相机，OFF 不释放相机和 HDMI；停止服务才释放。
6. 回退时停止新版服务，确认退出后恢复整个旧 release 及其匹配的启动入口和配置。只改 `osd.render_path=legacy` 不能回退 ON/OFF 生命周期。`deploy.sh --check` 仍不得启动服务或采集。
