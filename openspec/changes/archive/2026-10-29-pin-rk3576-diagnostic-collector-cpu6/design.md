# 设计：只收窄诊断收集器的 CPU 范围

## Context

现有诊断启动入口会覆盖外部单核绑定，使收集器仍可在共享范围内迁移。目标是在同一入口内只绑定收集器自身，并保留业务现有分配。动机见 `proposal.md`。

`run-diagnostics` 通过 `cpu-policy.py` 校验 `/opt/drone_tracker/config/cpu-affinity.yaml`，把允许列表传给 `diagnostic-launch.py`。后者对当前进程调用 `sched_setaffinity(0, ...)`，然后用 `exec` 替换成实际收集器程序；`exec` 保留进程身份和亲和性。服务和手动入口都经过这条路径。收集器工作循环没有另建工作线程。

CPU 亲和性是线程允许运行的核心集合。当前进程只有一个线程，因此只修改当前线程即可约束随后执行的收集器。`SCHED_OTHER` 是既有的普通非实时调度策略。

现行主规格尚未包含诊断入口范围要求；该要求位于旧的未归档变更 `add-rk3576-tracking-diagnostic-process` 中。本变更向已有 `production-binary-deployment` 能力增加专门约束，并明确替代旧变更要求的“收集器使用完整允许范围”。不编辑旧变更，也不以其性能任务 7.3 完成为本变更前提。

## Goals / Non-Goals

**Goals:**

- 在共享生产策略允许 CPU 6 时，两种已安装诊断入口均固定使用 `{6}`。
- 对设置错误、读回不匹配或策略不允许明确失败，且只影响诊断启动。
- 用入口执行、独立旁路线程和生产板实际进程证据核实隔离边界。

**Non-Goals:**

- 不新增 CPU 可配置项或改变共享策略格式。
- 不修改裸收集器二进制的启动语义；独立实验仍可直接运行二进制自行选择核心。
- 不独占 CPU 6，不移动显示线程，不改变其他线程、进程、频率、优先级或系统隔离。
- 不部署新的正式 release，不重跑性能对照，不宣称吞吐、准确率或存储时延改善。

## Decisions

### 1. 在公共诊断启动器选择固定核心

选择：在 `deployment/diagnostic-launch.py` 使用单一固定值 CPU 6。保留调用接口及传入的共享允许列表，只将实际请求集合改为 `{6}`。

理由：这个位置在服务和直接入口执行实际程序前共同生效，且能够保留现有读回和错误出口。

替代方案：外层 `taskset` 或仅添加 systemd 的 `CPUAffinity` 均会被当前启动器覆盖；仅改服务也遗漏直接入口。把共享 `allowed_cpus` 改成 `[6]` 会影响业务，因此不采用。

结果：主业务入口、`cpu-policy.py` 和 `cpu-affinity.yaml` 都保持原样。`run-diagnostics` 只需按实际行为更新说明，不增加另一套核心选择。

### 2. 先检查共享范围，再设置并严格读回

选择如下启动顺序：

1. 原有入口读取并校验共享策略，继续传入完整允许列表。
2. 启动器要求 CPU 6 在该列表中，不通过时报告具体错误。
3. 启动器对自身设置 `{6}`，读回结果必须完全相等；系统拒绝、离线或控制组限制均沿用明确失败出口。
4. 核对普通调度，记录请求与实际集合，再用 `exec` 执行收集器。

理由：固定核心仍须遵守维护者指定的共享允许范围。读回精确相等防止“配置已读取”被误认成绑定成功。

替代方案：无条件越过策略或选择列表中其他核心都会违反固定 CPU 6 的目标，因此不采用。

结果：失败返回非零且没有执行收集器；不会改写策略或联动停止业务。原有共享策略校验失败也继续拒绝启动。

### 3. 围绕可观察边界调整测试

选择：更新 `deployment/tests/test_diagnostics.py` 的真实入口期望，以及 `entry_service_probe.py`、`service_acceptance.py` 中依赖完整范围的断言。覆盖成功、策略排除 CPU 6、设置异常、读回错误、参数传递、调度保持和重启。

理由：现有测试实际执行复制后的安装入口，可以证明核心选择穿过脚本和 `exec`，而非只检查文本。

替代方案：仅搜索硬编码值不能证明实际进程范围，因此不采用。宿主机不允许 CPU 6 时不得偷偷把生产固定值替换为其他核心；用可控系统调用测试错误与成功分支，并把真实 CPU 6 检查放到生产板。

结果：调用方和另一个带工作线程的旁路进程在收集器启停前后保留原允许集合。既有 CPU 策略测试继续确认业务六职责映射未变。

### 4. 生产板采用隔离入口短检查

选择：通过 `ssh firefly-production` 在 `HZ-RK3576_WuKong Board` 进行单次有界验证。每条非交互命令先加载 `/opt/ros/humble/setup.bash`。复用实际 ARM64 收集器二进制，保存其校验值。复制新入口只重定向安装、通信和存储路径，不改固定核心与绑定逻辑。

理由：启动器改动无需相机、模型或跟踪负载即可核实真实内核亲和性。隔离 socket 和测试服务避免占用正式端点及修改正式安装。

替代方案：只运行宿主机替身或 QEMU 无法证明生产板实际核心限制；为绑定变更启动整套相机负载会增加无关验收条件，因此不采用。

结果：分别以直接入口和独立测试服务启动真实 worker，读 `/proc/<pid>/task/*/status` 确认 `Cpus_allowed_list: 6`、实际线程数和普通调度；重启测试服务后再次确认。保存调用方、旁路进程及其线程、可识别的现有业务进程的前后范围。不存在的业务进程如实标为未运行，不为填充证据而启动业务。

## Risks / Trade-offs

- CPU 6 与显示共享 → 只证明执行范围，既有 CPU 6/7 比较仅作背景，不据此作新的性能保证。
- 自定义策略排除 CPU 6 → 诊断按要求失败，业务保持既有退化处理；文档明确该兼容性边界。
- 系统允许范围可能受控制组限制 → 以实际设置及精确读回判定，不把 CPU 在线等同于一定可绑定。
- 旧诊断变更后续归档可能重新引入完整范围文字 → 在本提案和交付记录保留后继关系，归档或同步时核对两者；本任务不修改旧变更。

## Migration Plan

1. 保存新入口校验值、测试结果和板卡身份；确认共享策略与业务入口的内容未变。
2. 隔离板端检查的总预算不超过 180 秒，单个子命令设定超时并预留停止清理时间。启动测试服务前登记唯一名称，失败也停止并清理其进程。
3. 测试前记录正式服务运行、启用状态和现有程序链接；优先不停止正式服务。确需停止时记录所停服务，最终恢复原运行及启用状态，读回并保存结果。原先未运行的服务不擅自启动。
4. 全部工作结束时清除测试服务及所属进程，保留证据；正式 release、配置、Runtime 和模型保持原内容。
5. 正式部署由后续明确部署任务完成。部署时使用匹配的新入口；回退可恢复此前备份的入口，不能靠改动共享 CPU 策略实现收集器回退。
