# Design

## Context

当前 RK3576 HDMI 输出的主要问题不是采集或跟踪吞吐不足，而是每个待显示帧在 OSD 渲染链路中停留过久。完整负载实测中，采集约 60.384 fps、跟踪消费约 34.680 fps，HDMI 仅约 2.416 fps；`render_total` 均值约 422.67 ms。阶段数据表明，逐帧 OpenCV 布局绘制、全帧混合、源帧 CPU 复制和 RGA 缩放转换构成主要耗时。动机和用户可见结果见 `proposal.md`。

本设计涉及两个边界。`src/osd/` 负责把跟踪状态、目标框和遥测转换成可显示的覆盖内容；`src/platform/rk3576/osd/` 负责使用 RGA 图像处理硬件和 DRM 显示接口提交视频平面与覆盖平面。DRM 原子提交是指多个显示平面在同一次屏幕更新中一起生效，它是保持视频与目标框配对的关键约束。

参考实现 `rk_hdmi_osd/osd_bridge` 证明了持久化画布、字形缓存和短 RGA 链路可以流畅运行，但不能原样复制。参考实现会设置性能 governor 和线程亲和性，还使用不同的采集缓冲生命周期。本仓库必须保留默认系统调度策略，并保证源帧缓冲在同步 RGA 操作完成前不会被采集线程复用。

本变更依赖已经实现的 `add-osd-stage-timing` 诊断能力。实现和验收时必须保留原始阶段数据，以便在同一板卡上比较旧路径与优化路径。

## Goals / Non-Goals

**Goals:**

- 把兼容 BGR 输入到 DRM 主平面的处理缩短为一次同步缩放转换；灰度输入采用两次同步 RGA 操作保证中性色彩。
- 把 OSD 从“每帧新建并完整绘制”改为“持久化画布按变化更新”。
- 保持 `OsdPresenter` 已定义的帧遥测配对、单待显示项和关闭冻结语义。
- 让主平面与覆盖平面分别管理缓冲状态，并在翻页完成后才确认显示状态。
- 保留可启动回退的旧路径和可对照的阶段耗时数据。

**Non-Goals:**

- 不改变跟踪算法、三个模型、ROS 话题或消息语义。
- 不引入第二个视频消费者，也不改变 `FrameReadView` 对源帧的只读约束。
- 不默认修改 CPU governor、进程优先级或线程亲和性。
- 不把参考仓库代码或运行时文件复制成本仓库依赖。
- 不在本变更中增加运行期热切换渲染路径。

## Decisions

### 1. 使用主平面纯视频加持久化覆盖平面的双平面结构

**选择：** 优化路径使用两个独立显示平面。主平面双缓冲只保存缩放和格式转换后的纯视频；覆盖平面双缓冲保存完整尺寸的 RGBA OSD 画布。RGBA 是同时保存红、绿、蓝和透明度的像素格式，覆盖平面依靠透明度显示目标框、文字和状态，同时让未绘制区域露出主平面视频。

新视频帧的处理顺序为：

1. 输入：取得只读源帧和与其配对的遥测快照。
2. 视频处理：兼容 BGR 输入由一次 RGA 操作写入主平面后备缓冲。灰度先缩放到持久 YUV 缓冲的亮度平面，再通过第二次操作转换到主平面；色度平面只初始化为中性值。
3. OSD 处理：布局层只更新画布中变化的内容，再把画布上传到覆盖平面的后备缓冲。
4. 显示：一次 DRM 原子提交同时指定新的主平面与覆盖平面缓冲。
5. 确认：收到翻页事件后，两个后备缓冲才变为“已显示”缓冲。

仅遥测变化时不重复处理视频。系统复用当前已显示的主平面缓冲，只准备新的覆盖平面缓冲并进行原子提交。OSD 关闭冻结时采用相同原则。

**原因：** 该结构删除当前优化空间最大的三项工作：中间视频双缓冲、纯视频到 DRM 主平面的额外 `imcopy`，以及把完整 HUD 混入视频的全帧 `imblend`。它也自然支持仅更新覆盖信息。

**拒绝的替代方案：** 保留单一主平面并继续把 HUD 烧录到视频。该方案实现改动较小，但每次遥测变化都要重写整帧视频，无法消除全帧混合，也使冻结视频的低成本更新变得困难。

**实际影响：** 后端需要分别记录主平面和覆盖平面的准备、提交和显示索引。内存占用包括两个主平面 DRM 缓冲、两个覆盖平面 DRM 缓冲和一个持久化 CPU RGBA 画布，但不再需要旧路径的中间视频双缓冲和独立全帧 HUD DMA 缓冲。

### 2. 布局层使用持久化画布、字形缓存和脏区域

**选择：** `src/osd/layout.*` 为优化路径维护一张与输出分辨率一致的持久化 RGBA 画布。固定边框、标签背景和不常变化的装饰在初始化或尺寸变化时生成。文字字形首次使用时栅格化并缓存；“脏区域”表示内容发生变化、必须重新清除和绘制的最小矩形区域。目标框、状态、计时数字和会变化的遥测字段只使各自区域变脏。

第一阶段允许每帧把已经缓存的静态底图复制到持久化画布，再使用字形缓存绘制动态字段，作为正确性优先的过渡实现。最终验收路径必须启用字段级脏区域，避免每帧重新执行完整 `cv::putText`、中文逐字栅格化和整层分配。

**原因：** 当前 `layout` 均值约 181.55 ms，是最大的单项耗时。文字和固定图形的像素结果在相邻帧之间大多相同，缓存能够直接消除重复计算。

**拒绝的替代方案：** 只减少文字数量或降低 HUD 分辨率。该方案会改变可见信息或画质，而且仍保留逐帧分配和重复栅格化，不能解决根因。

**实际影响：** 布局层需要明确画布尺寸变更、状态轮次变更和内容失效规则。缓存不得持有源视频指针，也不得在显示线程之外异步修改正在上传的画布。

### 3. 同步 RGA 直接使用受保护的源帧读视图

**选择：** 优先把 `FrameReadView::mat()` 的有效地址、可见尺寸、像素格式和行步长包装为 RGA 虚拟地址输入。调用使用同步模式，`FrameReadView` 从包装开始一直存活到 RGA 返回；后端不保存其指针，也不把处理交给异步线程。`source_prepare` 记录校验、包装和必要缓存同步耗时，而不是假定必然发生 CPU 全帧复制。

处理示例：宽 1280 的 `Bgr8` 每行有 3840 个有效字节。行步长为 3888 字节时，向 RGA 传递 1296 像素步长。4096 字节不能被每像素 3 字节整除，须逐行重排有效像素到可复用且满足 RGA 对齐要求的缓冲；不能通过取整步长读取。读视图一直保留到同步处理结束。奇数灰度尺寸等硬件无法直接处理的布局同样可在平台边界重排或扩展为等值 BGR，保留全部有效像素。

若生产板的 RGA 驱动不能稳定接受该虚拟地址和步长组合，则回退到平台私有 DMA 帧视图。采集层把 DMA 句柄和只读所有权交给显示后端，显示后端在同步 RGA 完成后再归还缓冲。该回退属于同一优化路径，不允许采用“先把 V4L2 缓冲归还队列，再让 RGA 读取”的参考实现时序。

2026-09-24 生产板探针已证实：虚拟地址导入句柄可用，但单次 Gray8 转 BGRA 出现偏色。用户已确认允许灰度两次同步 RGA 操作，以及仅对不兼容行布局重排。该例外不降低性能门槛，不允许恢复稳定兼容输入的无条件全帧复制。`source_prepare` 包括必要重排；`scale_convert` 包括该输入实际需要的一次或两次硬件操作。

**原因：** 当前每帧逐行复制到 DMA 输入缓冲的均值约 42.94 ms。同步调用使读视图生命周期容易证明，并保持已有单消费者和只读语义。

**拒绝的替代方案：** 立即改成异步 RGA 或直接照搬参考实现的 V4L2 队列时序。异步处理会把源帧所有权扩展到当前接口之外；提前归还缓冲则可能让采集设备在 RGA 尚未读完时覆盖图像，产生撕裂或随机颜色。

**实际影响：** 必须在主机替身测试中验证步长计算，在生产板上验证虚拟地址导入能力。若走 DMA 回退，需要把接口限制在 RK3576 平台边界，不能把 DMA 细节扩散到算法和 ROS 编排层。

### 4. 显示索引采用“准备、提交、确认”状态机

**选择：** 主平面和覆盖平面分别维护 `displayed` 与 `prepared` 索引。状态转换顺序固定为：

1. 从非 `displayed` 缓冲中选择后备缓冲，并写入新内容。
2. 将选中的主平面和覆盖平面索引记录为本次 `prepared` 组合。
3. 提交 DRM 原子请求，但不修改 `displayed`。
4. 收到对应翻页事件后，把成功提交的组合设为 `displayed`。
5. 提交或等待失败时丢弃 `prepared`，继续保留最后确认的 `displayed` 组合。

仅覆盖层更新时，`prepared` 组合引用当前主平面 `displayed` 索引和新的覆盖平面后备索引。这样视频不被重写，但两个平面仍在同一次原子提交中明确配对。

**原因：** 两个平面并不总是同时换缓冲。把它们绑定到单一翻转索引会在仅遥测更新时错误覆盖当前视频，或在失败路径提前复用屏幕仍在读取的缓冲。

**拒绝的替代方案：** 在 `drmModeAtomicCommit` 返回后立即交换索引。非阻塞原子提交返回只表示请求已接受，不代表屏幕已经完成翻页；提前交换会产生缓冲复用竞态。

**实际影响：** 翻页事件必须带有可对应到提交代次的上下文。关闭和析构路径需要取消未确认状态，并按已有超时规则释放资源。

### 5. 静态缓冲只在创建或几何变化时初始化

**选择：** 黑色背景、YUV 色度平面、中间色值和尺寸相关 scratch 缓冲在后端创建、模式设置或几何尺寸变化时初始化。稳定输出期间不执行整帧 `setTo` 或等价清空，除非该缓冲的可见内容确实需要改变。

**原因：** 当前路径每帧清空视频和 scratch 缓冲，产生与画面变化无关的内存带宽消耗。

**拒绝的替代方案：** 继续在每帧开始时清空全部缓冲以简化逻辑。该方式容易理解，但会持续占用 CPU 和内存带宽，且掩盖未完整写入的错误。

**实际影响：** 每个写入操作必须覆盖其声明的全部有效区域。测试需要用非零填充值预置后备缓冲，以发现遗漏写入，而不是依赖清零掩盖问题。

### 6. 通过启动参数保留旧路径并区分诊断名称

**选择：** 增加只读启动参数 `osd.render_path`。最终默认值为 `cached-overlay`，`legacy` 保留一个发布周期。优化路径把源阶段命名为 `source_prepare`，把覆盖层传输命名为 `overlay_upload`；旧路径继续输出 `source_copy` 和原有 `compose`，避免历史报表误把不同工作解释为同一指标。

**原因：** 性能问题必须通过同板 A/B 数据验证。保留旧路径能提供可重复基线，也提供无需更换二进制的现场回退。

**拒绝的替代方案：** 直接替换旧实现且共用原有阶段名称。这样无法区分“无复制的准备”和“真实全帧复制”，发生板端兼容问题时也缺少快速回退手段。

**实际影响：** 两条路径共享 `OsdPresenter`、配置校验和最终外部语义，只在布局与 RK3576 后端内部选择实现。参数运行期不可修改，防止资源图在显示过程中重建。

### 7. 性能验收采用固定输入的同板三轮对照

**选择：** 在同一生产板、同一系统设置、同一真实模型和同一回放输入下，分别运行 `legacy` 与 `cached-overlay` 三次。每次至少 70 秒，排除前 10 秒预热。验收读取阶段计时与帧率日志，同时保留 OSD 关闭基线，用于判断优化是否挤占跟踪线程。

**原因：** HDMI、RGA、CPU 调度和模型负载会共同影响结果。单次短跑或不同板卡之间的比较无法区分实现收益与环境波动。

**拒绝的替代方案：** 只使用微基准或只比较平均耗时。微基准没有完整竞争负载；平均值会隐藏周期性长尾卡顿。

**实际影响：** 验收报告必须包含每轮均值、第 95 百分位、最大值、样本数和新视频帧显示速率。性能 governor 保持测试前的板端设置，两条路径之间不得改变；程序本身不负责设置 governor。

## Risks / Trade-offs

- **[RGA 虚拟地址路径在生产驱动上不稳定]** → 先做最小导入探针和带步长帧测试；失败时启用平台私有 DMA 帧视图，同时保持缓冲到同步调用结束。
- **[脏区域失效不完整导致旧文字或框残留]** → 每类动态元素维护上一次和本次区域的并集；尺寸、主题、跟踪轮次变化时强制完整重建画布。
- **[两个平面的索引状态不同步]** → 以提交代次记录主平面和覆盖平面组合，只在匹配的翻页事件后确认；失败时不推进任何 `displayed` 索引。
- **[覆盖平面上传仍受内存带宽限制]** → 第一版允许全画布上传以降低正确性风险；若 `overlay_upload` 不能达到门槛，再在不改变规格的前提下增加局部更新或持久映射。
- **[保留两条路径增加维护成本]** → `legacy` 只保留一个发布周期；生产验证稳定并完成现场观察后，另行提出删除变更。
- **[严格性能阈值受输入内容影响]** → 固定回放文件、模型、输出分辨率和板端系统设置，并在报告中记录散热、CPU governor 与版本信息。

## Migration Plan

1. 先落地缓存布局和优化后端，但保持测试配置显式选择 `cached-overlay`；使用主机测试验证布局失效、步长和索引状态机。
2. 在生产板完成 RGA 虚拟地址探针、颜色与步长验证。若失败，实施并验证平台私有 DMA 帧视图回退。
3. 以 `legacy` 和 `cached-overlay` 完成固定输入三轮 A/B，并执行 20 轮 OSD 开关、10 分钟满负载、异常退出和 DRM 故障测试。
4. 所有功能与性能门槛通过后，把 YAML 和参数声明默认值设为 `cached-overlay`，更新部署说明。
5. 现场发生回归时，以 `osd.render_path=legacy` 重启节点回退。回退不需要修改模型、ROS 接口或系统设置。
