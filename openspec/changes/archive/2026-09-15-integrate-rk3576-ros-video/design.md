## Context

当前 RK3576 能独立读取视频和执行跟踪，但正式节点尚不能使用该平台。本设计把已有后端接入 ROS，并让同一进程安全重复播放；动机见 [proposal.md](proposal.md)。

已核对的实现边界：

- 根目录 CMake 固定启用 CUDA，节点固定链接 `platform_jetson`。`src/platform/rk3576/CMakeLists.txt` 同时定义独立工程、后端库、工具和测试，不能原样作为生产子目录重复引入公共目标。
- 节点通过公共工厂创建组件，但模型路径仍为三字段。RK3576 已要求 YOLO、模板 Backbone、搜索 Backbone、Head 四文件。Backbone 提取图像特征，Head 比较模板和搜索特征。
- `Rk3576VideoFrameSource` 已有线程安全的私有诊断，状态包括 Ready、Running、Stopped、Eof、Failed；公共接口只能返回布尔取帧结果。
- `HybridTrackerImp::reset()` 重置帧号，却不清空 YOLO 结果。检测工作线程取走请求时已清除 `m_new_request`，因此现有 `isBusy()` 不能证明推理已结束。
- 节点取帧超时会退出 worker，但没有恢复 `running`；直接再次创建线程也必须先回收旧线程。ROS bag 的写入和关闭分散于 worker、触发和姿态/里程计回调。

## Goals / Non-Goals

**Goals:**

- 使用同一个节点和公共算法，平台专属代码留在后端。
- 视频按自身时间持续供帧，允许消费跳帧；跨轮没有旧请求、结果和队列残留。
- 配置和普通失败可诊断；初始化失败不暴露可触发的半初始化节点。
- 测试明确区分无硬件逻辑、ARM64 构建、真实模型运行和质量结论。

**Non-Goals:**

- 不改变运行中请求调度、模型前后处理、阈值或仲裁算法。
- 不实现历史视频与姿态回放同步、相机或加速；不改独立回放的顺序处理。
- 不要求部署吞吐量或真实检测质量达标，不以 RK3576 证据代替 Jetson 实机等价性。

## Decisions

### 1. 一个节点、两套编译期后端

选择根目录先校验 `DRONE_TRACKER_PLATFORM`，默认 Jetson。工程先启用 CXX，仅在 Jetson 分支启用 CUDA并查找其 SDK；RK3576 分支查找已有 RKNN、JPEG、FFmpeg 等依赖。SDK 是编译所用头文件和链接库，目标仍为 Runtime 2.3.2、驱动 0.9.8，沿用既有 2.3.0 构建 SDK。

将 RK3576 后端目标提取到可复用 `src/platform/rk3576/backend.cmake`，由独立入口和根目录选中的平台入口共用。调用方先建立公共算法目标，后端文件不重复执行 `project()` 或建立公共库。独立工具和报告依赖留在独立入口；生产节点不因后端复用额外依赖回放报告模块。测试目标按平台分类，VPI 竞态工具及固定链接 Jetson 的工具仅在 Jetson 下启用。节点通过所选平台的编译定义读取配置策略，不引入 RKNN 头文件。

原因是现有后端已可用，复制源文件清单会导致两入口漂移。拒绝另建一个 RK3576 ROS 节点。结果是两平台共享编排，独立工具仍可单独构建且不依赖 ROS。

### 2. 显式模型角色、路径和相机内参

保留 `tracker.yolo_engine`、`tracker.nano_backbone`、`tracker.nano_head`，增加 `tracker.nano_template_backbone` 和 `tracker.nano_search_backbone`。Jetson 默认值保持原状，新增拆分字段默认空；RK3576 模型字段默认空且要求四角色完整，共享字段必须为空。节点统一组装 `ModelPaths`，装配层继续校验实际模型契约，不推断文件名。

所有模型参数的绝对路径直接使用，相对路径按包 share 下的 `models/` 解析；旧合法相对路径保持原行为。视频由 launch 要求显式传入；文件相对路径沿用进程工作目录含义，文档推荐绝对路径。

RK3576 要求显式 `camera.fx/fy/cx/cy`，单位为像素；采用缺省无效值区分漏填，四值必须有限，fx/fy 必须大于零，cx/cy 允许图像外主点。数值对应实际视频尺寸，不按 `mv_camera.*` 再缩放。Jetson 继续从原物理参数推导内参，不启用这组覆盖。

新增 `parameters/rk3576_video_params.yaml` 和 `launch/rk3576_video.launch.py`。launch 提供 `params_file` 和必填 `video_source`，只覆盖视频路径；DCF（相关滤波辅助跟踪）等算法设置来自参数文件。示例四个模型角色和内参必须显式填写，说明示例标定不是所有录像通用值。配置在运行期间不热重载；RK3576 拒绝运行期更改时钟及本次启动配置，避免参数显示值与实际值不一致。

原因是旧三路径无法表达 RK3576 拆分模型，任意录像也不能沿用旧相机标定。拒绝猜测模型角色、统一更名旧参数或偷偷套用相机默认内参。结果是旧 Jetson 配置兼容，RK3576 配置错误在采集启动前暴露。

### 3. 实时系统时间与既有取最新帧策略

RK3576 ROS 首版要求 `use_history_timestamp=false`、`use_sim_time=false`，初始化时和参数更新时均验证。独立帧源历史能力与独立回放不受此限制。

帧源使用系统起点加视频 PTS 生成帧时间。PTS 是视频帧的显示时刻；等待仍使用不受校时影响的单调时钟。节点继续通过 `waitForLatestFrame()` 排空积压，保留原处理间隔策略，不新增消费队列，不将相机 fps 当作视频 PTS。普通取帧等待可用短超时轮询停止标志；Running 的超时继续等待，不能把十秒 PTS 间隔误判 EOF（文件结束）。

一帧处理过程：

1. 取得原尺寸灰度帧和帧时间。
2. 在相同系统时间基准上读取当前 ROS 时间，查询帧时刻和最新云台姿态；缺数据沿用单位矩阵。
3. 调用真实公共跟踪器，保留其位置预测和仲裁。
4. 发布预测时刻的检测框，以及帧时刻的图像；状态变化时发布状态。

例如 30 FPS 视频约每 33 ms 供帧，60 ms 的消费者可以跳过中间帧，但不重写所处理帧的时间。离线视频配实时姿态只能证明接口接入，不证明物理旋转补偿正确。

原因是历史帧时间不能直接与当前时间相减用于预测。拒绝本次暗中映射历史时间或新增 `/clock` 播放器。结果是首版时间语义清晰，历史 ROS 回放需另立变更。

### 4. 公共状态快照仅提供观测能力

在公共 `FrameSource` 追加非纯虚的只读状态查询，默认返回 Unknown；RK3576 将既有私有诊断映射为 Ready/Running/Stopped/Eof/Failed，包含路径、原因、适用帧号及读入/入队/丢弃计数。查询不取帧、不清队列、不更改状态，后台更新与前台查询同步保护。

RK3576 worker 在 false 后查询状态：Running 继续等待；Eof 在确认已无可取尾帧后结束；Failed 记录失败并结束，不伪装正常结尾。读取状态后若存在生产刚完成与队列入帧的竞争，先再尝试取帧再判定 EOF。主动停止不要求消费剩余队列。清理前保存终止原因，后续 stop 不得覆盖已有 EOF/失败诊断。Jetson 返回 Unknown 时沿用原处理策略。

原因是私有诊断已经存在，布尔取帧不能区分结尾和失败。拒绝在 ROS 层转换具体帧源类型。结果是节点仍只使用公共接口，Jetson 不需要本次重构采集状态。

### 5. 模型常驻，轮次之间等待检测空闲

在检测器增加专用清理操作，在公共跟踪器提供轮次收尾入口。它只能在停止提交 `update()` 后调用，不把现有 `isBusy()` 当成完成屏障。完成屏障表示所有旧推理及其帧访问均已结束。

在请求互斥锁下标记清理中，撤销未执行请求；工作线程显式维护正在执行的标志。清理通过条件变量等待该标志清除，再清空结果与请求引用。工作线程的成功、预处理失败等全部普通返回路径，都必须在释放帧和预处理会话后清除执行标志并通知。等待期间释放互斥锁，检测线程可完成并通知；清理期间拒绝新请求。只在两轮之间调用，保持平常 `request/isBusy` 的调度含义。

ON 前先确保上一轮收尾，然后 reset；帧号从头开始仍安全。OFF/EOF 后模型与检测线程保持加载和空闲。最终析构才停止检测线程并释放模型。设备无法确认停止时继续遵循既有致命失败规则，不能因等待超时释放设备仍在访问的内存。

原因是当前 reset 会复用帧号，旧检测结果可能误配新帧。拒绝每轮重载四个模型，也拒绝只清一个 result-ready 标志。结果是新增跨轮清理能力，但不修改运行中的检测算法。

### 6. 节点生命周期单一控制，工作线程统一收尾

内部状态为 Idle/Starting/Running/Stopping，与公开跟踪状态 0–3 无关。控制回调串行化，start/stop 只由控制侧或 worker 中明确的单一所有者调用，不能同时控制帧源。

- ON：若上一轮 worker 已结束，先 join；完成 reset 和本轮 bag 创建后，创建 worker。worker 执行帧源 start，成功后进入 Running，失败走统一收尾。重复 ON 不启动第二个 worker。
- OFF：控制侧只设停止请求并等待 worker，等待时不持有 worker 收尾所需锁。worker 通过限时取帧和可打断的处理间隔及时观察请求，随后自行调用帧源 stop、等待检测空闲、关闭 bag，最后进入 Idle。
- EOF/普通错误：worker 执行相同收尾，保存明确原因。下一次 ON 先 join 旧线程，再从头播放。
- 析构：请求停止、join worker；若无 worker 但初始化已取得帧源，仍释放其资源；最后停止并销毁跟踪器。

不从 worker join 自己，不持有生命周期锁等待 worker，不在生产或消费仍活跃时重建队列。线程创建、模型加载、跟踪器初始化及 bag 创建失败均回滚；节点初始化失败抛出到主入口并以非零退出，不能只 return 留下半初始化节点。日志和既有状态文本区分 Starting、实际启动成功和失败，不新增公开跟踪状态值。

原因是 `running` 一个标志不足以代表线程已回收。拒绝让触发回调和 worker 分别任意停止帧源。结果是收尾可重复调用，普通文件故障后节点可重试，EOF 后直接 ON 有明确行为。

### 7. ROS 消息兼容与记录互斥

保留当前输入输出话题、消息类型和 QoS（消息队列与可靠性配置），不把轮次结束编码为伪造 TargetLost。下一轮重置节点的上次发布状态，使首次有效处理能发布 Detecting。

ROS bag 是 ROS 消息记录文件。用单独互斥锁封装 writer 的创建、写入、关闭和销毁，所有回调走同一入口；持锁范围不包含 join 或模型等待。锁内检查是否仍有活动 writer，关闭后到达的回调不再写本轮。原话题、消息时间戳和图像开关保持不变。视频输入忽略相机录像配置。

打开、写入和关闭异常需要记录，写入失败请求结束本轮，走统一清理；不能从持有 writer 锁的回调直接等待 worker。目录碰撞不覆盖已有记录，报告启动失败并允许使用新触发时间重试。

原因是当前 writer 同时被多个回调访问。拒绝仅给 close 加锁或为录制新增消息队列。结果是每轮记录完整关闭，记录失败不会变成无声成功。

### 8. 分层验证，固定模型和输入身份

选择公共可控模型、ROS 集成、ARM64 构建和开发板四层验证。可控模型是由测试指定输出的替身，不是生产降级选项。将节点 main 与可测试节点实现分离，使用测试构造入口注入公共工厂/可控组件，不增加生产参数来选择假模型。

可控测试先阻塞检测，再异步请求 OFF，断言收尾尚未完成；测试线程释放旧检测后，等待 OFF 完成，再发送 ON，断言旧框不能进入新轮。覆盖已经就绪、尚未执行、执行中三类旧任务。以真实公共跟踪器驱动捕获/丢失/恢复，并订阅 ROS 消息核验帧时间、预测时间、状态和图像开关。记录测试并发发送姿态/里程计，同时 EOF/OFF，验证 bag 可打开读取和正确关闭。

开发板使用固定已有 YOLO 与完整纯 FP16、纯 INT8 NanoTrack 文件，各执行基础发布/EOF/重启/退出检查；记录 SHA-256 文件指纹。资源验收选择固定纯 INT8 配置，在同一节点和已加载模型上至少 20 轮启停及额外至少 30 分钟重复播放负载，时长不含前面的功能轮次。记录实际处理帧、RSS（进程驻留内存）、线程、文件描述符、停止耗时及残留进程。设备内存未测时明确注明，不把进程内存替代设备内存。无需两种精度重复长负载，因为本阶段验证共享节点生命周期；真实检测质量单列，不用降低阈值满足验收。

原因是无目标输出也能验证运行，但无法证明跟踪状态发布正确。拒绝只看程序退出码或以无目标测试替代状态逻辑测试。结果是检测效果不会阻塞接入验收，同时证据边界不被夸大。

## Risks / Trade-offs

- 检测收尾等待真实推理，停止耗时随推理变化 → 分别记录消费停止和检测等待；不承诺设备挂起时强制安全退出。
- 实时时钟可能被系统校时 → 播放等待用单调时钟，沿用公共跟踪器时间检查；本次不保证系统大幅跳时后的预测质量。
- 共享清理代码影响 Jetson → 公共替身回归验证正常调度不变；无 Jetson SDK/硬件时只做源码审查，保留实机验证缺口。
- 软件解码与发布可能造成跳帧 → 记录实际吞吐和积压表现，不将本次接入完成声明为性能目标通过。
- 旧回放 delta 仍声明拒绝视频和 RK3576 根构建 → 本次 delta 以当前主规格为基线；旧 change 后续同步必须协调历史条款，禁止回退已实现能力。

## Migration Plan

1. 按任务清单实现可复用构建、公共清理与诊断，再接通节点和配置。
2. 在约定临时 ARM64 容器构建并检查依赖；保留独立工具，公共测试和专用 ROS 测试分别执行。
3. 在开发板独立安装前缀部署新产物，使用既有模型和固定 MJPEG 文件，不覆盖旧可运行产物。
4. 完成基础、异常和资源验收，保存命令、版本、文件指纹与报告。
5. 核对两份 delta、实现和证据；旧回放质量任务继续未完成。同步/归档按后续明确请求执行。

回退时停止新节点并切回原安装前缀，独立回放继续可用。没有模型转换、数据格式迁移或旧配置覆盖。
