## 独占显示检查

后端在分配显示缓冲之前请求 `drmSetMaster()`，随后根据打开的字符设备次设备号读取 `/sys/kernel/debug/dri/<次设备号>/clients`。该文件是内核提供的实际显示客户端列表。只接受一行客户端，并要求其编号等于打开设备的渲染线程编号、设备号一致、`master=y`。DRM 在本板保存的是打开设备的线程编号，并非进程主线程编号。

不能读取、不能解析、有其他客户端或本线程不持有控制权时，后端立即关闭 DRM 文件并拒绝初始化。报错包含设备、具体原因和“停止桌面服务并确认设备释放后重试”的提示。节点不停止或恢复桌面，不自行挂载 debugfs。

| 场景 | 证据与结果 |
|---|---|
| 桌面占用，libdrm 接口误判 | Xorg 的 `master=y`，新打开的 Python 客户端 `master=n`；`drmIsMaster=1`、`drmSetMaster=0`。后端仍拒绝 Xorg 占用 |
| 正式节点拒绝初始化 | 退出码 1，错误明确；退出后客户端列表只有 Xorg |
| 内核记录不可读 | 在独立挂载命名空间内把记录映射为空文件；探针拒绝启动，退出后没有客户端。没有修改主机挂载 |
| 桌面释放后启动 | `lightdm=inactive`，列表只剩表头；探针初始化后只有渲染线程且 `master=y` |
| 退出与再次打开 | 两次后端打开均成功；退出后列表为空，随后恢复 `lightdm=active` |

正式节点另外完成两次 EOF、输入缺失、新轮恢复及 OFF 后 30 秒遥测阶段。该阶段内核列表仅有正式节点的渲染线程，`lightdm=inactive`；退出后列表为空，桌面恢复 active。对应 `clients-boundaries-running.txt`、`desktop-boundaries-running.txt`、`clients-boundaries-after.txt` 和 `desktop-boundaries-restored.txt`。这部分证明 OFF 仍占有设备，不能据此声称用户已观察到遥测画面。

CPU 使用进程 CPU 时间增量除以实际运行时间计算，100% 表示使用一个 CPU 核。两次窗口长度不同，且输入限制为 20 FPS，所以这些结果是运行对照，不是最大吞吐基准；不能把 0.1 次/秒差异解释为 OSD 提高跟踪速度。

同一 PID 20811 先完成 20 轮 ON/OFF，再执行第 21 轮 610.208 秒。前 20 轮每次停止后线程数均为 17，文件描述符均为 49；长轮运行中线程数为 19。所有轮次均验证 OFF 后不再输出，且新轮消息时间戳不来自上一轮。源码的模拟帧存活计数测试继续覆盖共享帧释放边界；实机采样未发现随启停轮次累积的线程、文件句柄或持续增长的内存。

长轮第 56.19 秒，文件描述符由 50 一次增加到 56，此后保持到结束；OFF 关闭视频句柄后为 55。新增六项是 DRM 导出的共享缓冲区，大小为 98304、12288、393216、12288、8192、4096 字节。前后两份 fdinfo 中所有句柄的内核 inode 编号一致，证明后段使用的是同一批对象。OSD 关闭对照也出现六项共享缓冲区增加，之后稳定；因此不能把该台阶认定为 OSD 泄漏。这些尺寸和模型输入/输出缓冲相符，但未跟踪 Runtime 内部每次分配调用，不声称完成驱动内部内存审计。
