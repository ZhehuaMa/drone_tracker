# Design

## Context

当前程序能够生成跟踪框和 ROS 调试图像，但不能直接向 HDMI 屏幕呈现配对的视频、框和飞行信息。本设计增加进程内 OSD（屏幕信息叠加）模块，停止采集后保留最后画面并明确标为冻结；动机与范围见 proposal.md。

现有 `DroneTrackerNode::processFrames()` 是帧源的唯一消费者。`FrameRef` 是共享只读帧引用，`mapRead()` 返回只能在视图对象存活期间访问的像素。公共格式为 Gray8（八位灰度）与 Bgr8（三通道彩色），没有公开设备共享内存句柄。`TrackerOutput` 已提供显示框 `display_box`、处理时刻预测框 `realtime_box`、状态与绘制信息。OFF 当前停止整个采集与跟踪轮次，保持这一语义。

参考项目采用 CPU 绘图、RGA 合成和 DRM/KMS 显示。RGA 是 Rockchip 二维图像处理硬件；DRM/KMS 是 Linux 底层显示接口。参考代码只用于核对行为和硬件约束，不作为构建、运行或源码目录依赖。本仓库自行实现和维护所需模块，不复制其相机采集管线。

## Goals / Non-Goals

**Goals:**

- 一次提交的帧、框、跟踪状态作为整体显示，任何并发和丢帧都不拆开这组数据。
- 显示线程独占硬件资源，跟踪线程不等待显示刷新或执行像素复制。
- 保持公共帧、跟踪算法、ROS 发布和采集规格；HDMI 故障不改变算法状态。
- 让无 HDMI 设备的测试验证配对、停止、资源和遥测行为，生产板另行验证硬件输出。

**Non-Goals:**

- 不提供独立于跟踪速度的视频显示支路，不保证新视频达到 60 fps。
- 不输出所有 YOLO 候选框，不新增跟踪置信度或目标编号算法。
- 不扩展公共帧格式或暴露 DMA-BUF（设备可共享内存的文件描述符）。首版不宣称全链路零拷贝。
- 不改变 OFF 后停止采集的行为，不提供 Jetson HDMI、视频编码、推流或屏幕快照服务。

## Decisions

### 1. 同进程内部库，按职责隔离

选择在 `src/osd/` 新增公共显示代码，并在 `src/platform/rk3576/osd/` 实现硬件后端。ROS 适配可放在 `src/osd/ros_telemetry.*`，但使用独立构建目标；绘图核心不链接 ROS。建议职责如下，具体类名可在不改变契约的前提下调整：

| 组件 | 职责 |
|---|---|
| `PresentationPacket` | 拥有帧引用、轮次号、轮内序号、帧时间、框列表及同次跟踪状态 |
| `OsdPresenter` | 接收完整结果、处理轮次状态、管理最新待显示结果和渲染线程 |
| `TelemetrySnapshot` | 保存各组遥测值、有效标记和最近有效接收时间 |
| `OsdTelemetryAdapter` | 订阅外部 ROS 话题，校验数据、换算单位并计算显示派生量 |
| `OsdLayout` / `OsdLayer` | 决定布局、绘制文字图形、维护需要重绘的区域 |
| `DisplayBackend` | 公共显示接口，可注入模拟实现进行无硬件测试 |
| RK3576 后端 | 复制输入像素、管理共享内存、RGA 合成及 DRM/KMS HDMI 输出 |

原因：共享帧和结果无需序列化，硬件依赖不会进入公共算法。拒绝独立 `osd_bridge` 进程及外部仓库链接；代价是本仓库承担维护与回归测试。最终仍安装 `drone_tracker_node`，不单独安装 OSD SDK。

### 2. 原消费者一次性提交完整显示结果

选择在 `tracker_->update(ctx)` 返回且 `out.consumed=true` 时构造完整显示包，通过 `submit(packet)` 一次提交。包中的框取 `out.display_box`，有效性依据 `is_valid` 并检查尺寸；状态直接取 `out.state`。框从中心坐标转换为左上角加宽高，裁剪到原图范围，再由布局映射。首版最多提交一个目标框。没有框时提交空列表，不沿用上一帧的框。

不调用 OSD 的独立 `set_boxes()` 更新实时管线，不订阅本进程 `/fpv/target_bbox`、`/fpv/tracker_image`、`/fpv/tracker_state` 来构造显示包。不改动跟踪器算法，不让它反向依赖 OSD。标签只使用已知配置或已有状态；没有置信度和 ID 时隐藏对应字段。

原因：用户优先要求图像和框配对。拒绝分别更新帧与框，以及把当前预测框默认叠到采集时刻画面。代价是画面等待跟踪结果；`display_box` 仍继承现有算法的历史状态语义，不承诺每个框都是当帧新检测。ROS 仍发布 `realtime_box` 与预测时间，不受此选择影响。

具体流程：

1. 原消费者取得帧 F，保存采集时间 T。
2. 跟踪器处理 F，产生显示框 B 和状态 S。
3. 提交 `{round_id, sequence, F, T, B, S}`，不复制图像像素。
4. 渲染线程取出整包，复制并缩放 F，绘制 B、S 和最新遥测。
5. HDMI 提交成功后，记录该包为最后实际显示结果。

### 3. 单份最新结果与有界所有权

选择一个互斥保护的待显示槽，容量为一。新包原子替换旧待显示包；渲染线程移出后解锁，再进行所有映射、复制和硬件调用。旧包释放放在提交锁外，避免长时间持锁。一次提交只做轻量元数据和共享引用交接，不能等待渲染完成。

渲染侧最多持有一个正在处理的源帧，待显示槽最多持有一个源帧。最后显示图像保存在后端自有的视频底图缓冲区，不长期持有采集帧。字符串及框列表由包拥有，不借用临时 `const char *`。像素只在 `FrameReadView` 有效期内读取；硬件使用后端缓冲区完成前不得复用该缓冲区。

原因：跟踪不能因 HDMI 变慢而累积延迟。拒绝无界显示队列及 OSD 从帧源竞争取帧。代价是允许整包跳帧，最新结果槽不是额外采集队列，与现有 platform-factory 规格兼容。

### 4. 显示生命周期独立，OFF 冻结最后实际显示图像

选择 OSD 随节点启动和结束，采集轮次仍由 ON/OFF 控制。显示状态与 `TrackerState` 分开，避免把 OFF 或输入失败伪装成 TargetLost。

| 事件 | 视频背景 | 框与提示 |
|---|---|---|
| 启动且未有已显示帧 | 黑底 | 无框，显示“等待输入” |
| ON 后等待首个完整包 | 保留旧底图，若无旧图则黑底 | 无旧框；旧图保持冻结提示，并显示“等待新画面” |
| 当前轮完整包成功显示 | 新包图像 | 使用该包框与状态，移除冻结提示 |
| OFF | 最后实际显示的底图 | 清框，显示“画面已冻结：输入已停止” |
| EOF（文件正常结束） | 最后实际显示的底图 | 清框，显示“画面已冻结：播放结束” |
| 输入或处理失败 | 最后实际显示的底图 | 清框，显示“画面已冻结：输入/处理故障” |
| 从未显示过图像便停止/失败 | 黑底 | 无框，显示相应原因 |

停止事件具有优先级，立即关闭当前轮提交入口、丢弃待显示包。渲染线程在提交硬件前再次检查轮次和停止版本，迟到结果不能解除冻结。已经交给显示硬件的提交先安全完成，再进入冻结；将该帧作为最后实际显示帧，并在下一次可完成的显示更新中清框标记冻结。健康显示下，从收到停止事件至冻结提示出现不超过 500 ms。

节点接受 ON 并开始新轮时使用递增轮次号，轮内序号重新开始。运行中重复 ON 沿用原行为，不重置显示轮次或清除正在显示的框。旧轮结果一律拒绝。正常长间隔等待未消费新帧时可重复显示，但自上个新包接收超过 `osd.frame_stale_ms`（默认 1000 ms）后清框并显示“等待新帧”；这不是 EOF，也不主动停止帧源。

冻结时继续按新遥测重绘，帧时间保持最后图像的采集时间，系统时钟另行显示，避免把旧图标为当前采集。中文冻结提示使用本仓库维护的固定字形资源；普通飞行模式可保留原 ASCII 字符串。

原因：用户选择保留最后画面，并要求区分实时与停止状态。拒绝 OFF 黑屏或静默冻结；代价是需要独立保存不含旧框和旧 HUD 的视频底图，以及阻止迟到包的状态机。

### 5. 外部遥测经 ROS，内部状态直接传递

选择复用当前节点的 ROS 执行线程接收遥测；回调只更新状态，不访问显示硬件。10 Hz 汇总快照，渲染线程按互斥保护读取。过期判断使用单调时钟（不受系统校时影响的计时源），显示日历时间使用系统时间，图像时间仍来自帧。

| 外部话题 | 类型 | 显示或计算 |
|---|---|---|
| `/mavros/imu/data` | `sensor_msgs/msg/Imu` | 校验并归一化四元数，计算航向、俯仰、横滚 |
| `/mavros/state` | `mavros_msgs/msg/State` | 连接、飞行模式、解锁状态、计时及记录返航点的事件 |
| `/mavros/extended_state` | `mavros_msgs/msg/ExtendedState` | 落地状态，用于地面气压基准 |
| `/mavros/battery` | `sensor_msgs/msg/BatteryState` | 电压、电流、剩余比例或容量；按消息字段含义转换 |
| `/mavros/gpsstatus/gpsraw` | `mavros_msgs/msg/GPSRAW` | 卫星数、地速、航迹方向；处理未知值标记 |
| `/mavros/global_position/global` | `sensor_msgs/msg/NavSatFix` | 有效经纬度，计算返航距离与方向 |
| `/fpv/static_pressure` | `sensor_msgs/msg/FluidPressure` | 相对气压高度 |
| `/fpv/temperature_baro` | `sensor_msgs/msg/Temperature` | 温度 |
| `/fpv/failsafe` | `std_msgs/msg/Bool` | 失效保护告警 |
| `/fpv/radar_state` | `std_msgs/msg/Int8` | 独立雷达状态文字，不覆盖本地跟踪状态 |
| `/fpv/low_level_feedback` | `quadrotor_msgs/msg/LowLevelFeedback` | 可选飞控电池告警等级 |

`/fpv/tracker_trigger` 沿用现有 Header 订阅，将收到的 ON/OFF 事件同时通知显示逻辑；不增加第二个控制回调，也不接受显示模块反向控制跟踪。遥测话题允许 ROS remap。IMU、GPS、气压、温度使用 best-effort（允许丢失旧消息、优先最新数据），其余使用 reliable（可靠传送），深度均为 10；现有业务话题 QoS 不变。

各组记录最近有效接收时间。默认 `osd.telemetry_timeout_ms=2000`，未收到、非法或超过期限的数据显示 `--` 或隐藏相关图形，并保留相应未知/过期标记。告警条件的来源失效后不能继续声称其为当前事实。告警行按连接丢失、失效保护、电池严重/低电量排序；冻结提示使用独立区域，不被告警覆盖。

返航点仅在有效定位、连接及解锁上升沿同时成立时记录；解锁时 GPS 不可用则本轮不补记伪返航点，解除解锁后清空。未解锁且落地状态都新鲜时，用指数平滑（新气压权重 0.05）更新地面气压，随后通过标准气压比公式计算相对高度。返航箭头需有效航向与位置；水平仪需有效姿态。

电池 `charge` 按剩余 Ah 处理，不照搬参考代码将其直接标为已耗电量。容量与剩余量都有效且在物理范围内时，已耗 mAh = `(capacity-charge)*1000`；其余情况隐藏该项。单节电压只在显式配置节数或有效单节数组可用时显示，不以电压猜节数。未启用可选低层反馈时显示已有电池信息，不凭空生成飞控告警等级。

原因：外部遥测不与每一帧严格同步，快照足够；本地框和跟踪状态必须一致。拒绝订阅自己发布的状态和让雷达状态覆盖本地状态。代价是需要显式有效性和可选消息包构建分支。

### 6. 首版显式复制到显示内存，硬件合成保持图像与框同一变换

选择通过 `mapRead()` 按实际行跨度复制 Gray8/Bgr8 到后端自有 DMA-BUF，再提交 RGA。Gray8 使用中性色度的 NV12 中间图（亮度与色度分开存储），规避参考实现已发现的直接灰度转 RGB 问题；Bgr8 使用对应颜色转换路径。原有 SC233HGS 解包由帧源负责，OSD 不重复处理 Y10 或再次打开相机。

默认输出 720×480p60；配置显式指定 DRM 设备与连接器，运行时枚举可用资源，不硬编码 plane ID。plane 是显示控制器的一层画面。视频保持宽高比居中留黑边，需满足硬件对齐时向内取整；框映射必须使用最终采用的视频矩形。1920×1200 示例为 720×450，垂直起点按偶数对齐为 14；其他尺寸动态计算，不能写死相机尺寸。

HUD（遥测文字和固定图形层）由 CPU 绘制，RGA 合入主画面。目标框放在独立透明层，由显示控制器叠加。主画面和目标框使用相同的显示版本，通过 DRM atomic commit（一次提交多个显示层）在同一刷新边界切换，不能更新正在扫描的单份目标层缓冲区。若生产板不支持所需原子提交或透明层格式，报告明确不可用，不静默退回可能错配的路径。

显式等待显示完成后再复用缓冲区，初始化保存必要原状态，退出禁用自己占用的显示层并释放资源。显示等待有超时和停止唤醒路径。不得在节点内部停止桌面服务、改变 CPU 调频策略或默认绑核。

原因：现有公共帧没有设备句柄，先复制最容易证明安全。拒绝首次接入就修改采集实现以追求零拷贝，以及照搬参考实现提前归还采集缓冲区的行为。代价是额外内存带宽，需在真实跟踪负载下测量。

### 7. 可选构建与明确失败

选择新增 `DRONE_TRACKER_BUILD_OSD=OFF`，只有显式开启并选择 rk3576 才查找 libdrm/librga；Jetson 请求该后端时配置明确失败。公共布局和模拟测试不依赖这两个库。可选 `DRONE_TRACKER_OSD_LOW_LEVEL_FEEDBACK=OFF` 控制 quadrotor_msgs 适配，开启但缺依赖时报错，不自动下载或修改构建镜像。

新增运行参数：`osd.enabled=false`、`osd.drm_device=/dev/dri/card0`、`osd.connector=HDMI-A-1`、`osd.width=720`、`osd.height=480`、`osd.refresh_hz=60`、`osd.frame_stale_ms=1000`、`osd.telemetry_timeout_ms=2000`、`osd.craft_name=FPV`、`osd.battery_cells=0`。0 节表示未配置；相关数值须校验范围与有限性。全部为启动参数，运行期修改拒绝。运行开关与 `visualized_result` 相互独立。

上述超时、开关默认值、固定中文文案及可选低层反馈安排是本提案为实现和验收明确的设计默认值，不是现有程序已经具备的能力。用户已确认的核心边界是同帧统一提交、显示随跟踪更新、外部遥测走 ROS，以及 OFF 保留最后图像并标明冻结。

编译未包含 OSD 却请求启用时，初始化失败。用户显式启用但显示初始化失败，也明确失败并回收已创建的节点资源，不能静默成功。运行中的显示故障停用显示后端、记录错误并继续既有跟踪与 ROS 发布；首版不自动重连，恢复显示需重启节点。显示线程不得直接抛异常穿出线程入口。

原因：保持无显示设备的既有工作流可用，且不能把没有画面的部署误报成功。拒绝强制所有构建依赖显示 SDK，拒绝在运行时显示故障后更改算法状态。代价是区分构建能力、运行启用和运行健康状态。

### 8. 关闭桌面显示是启动 OSD 的强制前提

选择由部署人员或外部启动流程先关闭桌面显示，再启动启用 OSD 的节点。关闭桌面显示是指停止桌面显示服务并释放其占用的显示设备，不是仅关闭窗口或使屏幕变黑。OSD 运行期间必须保持桌面关闭；采集 OFF 仍会保留冻结画面，因此 OFF 不代表可以恢复桌面。

生产板隔离诊断表明：桌面开启时独立 HDMI 测试四次失败；停止桌面后，同版本后端独占显示连续 610 秒通过。详细证据见 `isolation-diagnosis.md`。这一结果支持强制独占显示，但不代表真实模型联合负载验收通过，也不能据此断言 `ENOSPC` 的具体内核资源原因。

部署顺序固定为：

1. 部署人员或外部启动流程停止目标板的桌面显示服务。已验证生产板使用 `lightdm`，对应操作为 `systemctl stop lightdm`。
2. 确认桌面服务已停止，且桌面进程已释放目标 DRM 显示设备；仅凭停止命令成功不能认定资源已释放。
3. 启动 `osd.enabled=true` 的节点。后端必须可靠取得或验证独占显示控制权；无法确认时清理部分资源、拒绝节点初始化，并记录设备、原因及关闭桌面后重试的提示。
4. OSD 运行期间保持桌面关闭，包括采集 OFF 后继续显示冻结画面的阶段。
5. 退出节点并确认显示资源已释放后，才由部署人员或外部流程按需恢复桌面，例如 `systemctl start lightdm`。

DRM master 表示底层显示设备的控制权持有者。本板 root 环境中，`drmIsMaster()` 曾将非 master 文件描述符误判为 master，因此不能将该函数返回成功作为唯一控制权证据。具体取得或验证方式须在生产板验证，无法可靠确认时必须拒绝启动。节点不自行停止或恢复桌面服务。

实施确认：本板 `drmSetMaster()` 也可能对非 master 返回成功。因此后端请求控制权后，再读取目标设备的 debugfs `clients` 记录。debugfs 是内核提供调试状态的文件系统；本实现要求该记录可读且格式可识别，并且只有打开设备的本渲染线程一行、设备号一致、`master=y`。缺少这一证据时直接拒绝，不退回仅检查 libdrm 返回值。内核记录使用打开设备的线程编号，核验不能用主线程编号替代。实机证据见 `final-validation.md`。

原因：桌面与 OSD 共同操作显示设备已产生可重复故障。拒绝允许二者并存后依靠提交重试掩盖竞争，也拒绝由节点隐式关闭桌面。代价是部署必须安排桌面服务的停止与恢复，并补充启动拒绝和资源释放验证。

### 9. RKNN 同步完成证据

2026-09-23 用户要求修正已阻塞联合验收的 RKNN 完成确认。生产会话固定使用初始化标志 0 和 `rknn_run(context, nullptr)`，即阻塞执行。该调用成功返回后记录设备访问已完成，不再等待此路径没有提供的 fence（设备完成通知凭据）。不启用异步标志，不调整模型、布局或等待时限。

执行返回错误仍不能证明设备已停止，保留原有完成确认与无法确认时终止进程的保护。同步执行成功之后，输出取回失败只使会话失效并清理，不能把已完成的设备重新视为在途。共享输出的缓存策略保持默认，不将设备完成与禁用缓存同步混为一谈。证据及逐级回归见 `rknn-sync-validation.md`。

## Risks / Trade-offs

- [显示复制增加带宽] → 在生产板对相同模型、输入和参数做 OSD 开/关对照，报告跟踪吞吐、提交耗时、CPU、内存和端到端延迟；没有数据不承诺零性能影响。
- [处理速度低时视频不流畅] → 单份最新结果避免累积，分别统计新包提交、替换、实际新帧显示和屏幕刷新，禁止用刷新频率冒充新视频帧率。
- [停止与提交竞争] → 轮次号、停止版本及硬件提交前检查；模拟阻塞显示提交，验证迟到包不能解除冻结。
- [冻结占用采集缓冲区] → 保留自有、不含 HUD/框的视频底图，停止后释放源帧引用。
- [底层显示故障无法在屏幕上提示] → ROS 日志保留诊断；不声称屏幕仍可更新，先确保设备停止访问再回收内存。
- [外部消息包缺失或含义不同] → 标准消息按字段定义处理；quadrotor_msgs 独立可选；部署记录真实生产者和消息版本。
- [参考文档与当前源码有差异] → 以本变更测试契约为准，不继承模拟框自动配色、时间戳覆盖及 mAh 字段误用等行为。
- [硬件原子提交能力尚待本项目验收] → 在完整集成前先在生产板验证层格式、同步切换和资源释放；不满足时记录阻塞并修订设计，不能以开发板结果替代。

## Migration Plan

1. 完成公共提交、布局、遥测及模拟后端测试。既有 OSD 关闭构建继续通过。
2. 使用生产板现有 SDK 路径构建启用 OSD 的程序，记录 libdrm/librga 版本及动态库解析；不覆盖系统 RKNN Runtime 2.3.2。
3. 复核相机节点映射。按决策 8 停止桌面显示服务，确认目标显示设备已释放，再验证生产板的 HDMI 模式、原子提交与透明层；后续 OSD 测试期间保持桌面关闭。
4. 使用可识别帧号的合成输入验证配对、缩放、中文冻结提示；再使用已批准真实模型和相机/视频验证集成。
5. 同一进程至少 20 轮 ON/OFF，另做至少 10 分钟持续运行；验证 EOF、输入失败、显示失败、遥测过期和退出。单独记录 OSD 收尾与整个节点停止耗时。
6. 交付部署文档、配置及验证记录，包含停止桌面、确认设备释放、启动 OSD 和退出后恢复桌面的顺序。回退可设置 `osd.enabled=false` 并重启；若动态库缺失导致程序无法启动，则回退到保留的 OSD 关闭构建。两种回退均保留原算法与 ROS 行为。恢复桌面前必须确认 OSD 已退出并释放显示资源。
