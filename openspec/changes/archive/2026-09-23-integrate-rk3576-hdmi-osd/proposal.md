# Proposal

## Why

当前跟踪程序不能直接在 HDMI 屏幕上同时呈现相机画面、目标框和飞行遥测，操作者需要依赖其他显示程序。此次增加 OSD（屏幕信息叠加），让同一程序输出可配对的图像与跟踪结果，并在停止采集后明确提示画面已经冻结。

## What Changes

- 在本仓库维护 OSD 绘制、布局、遥测适配及 RK3576 HDMI 后端；构建和运行不引用外部参考仓库，不启动外部 `osd_bridge` 或第二个采集器。
- 现有取帧路径仍是 `FrameSource` 的唯一消费者。跟踪完成后，通过一次进程内调用提交共享只读帧 `FrameRef`、该次 `display_box` 和 `TrackerState`，并附带轮次与帧标识。
- 使用独立渲染线程和单份最新待显示结果，优先保证图像与框配对。新视频画面的更新速度受跟踪处理速度限制；HDMI 重复刷新同一帧不计为新视频帧。
- 飞行姿态、电池、GPS、气压、温度等外部遥测继续通过 ROS 2 话题输入。框和本地跟踪状态不经 ROS 回传给 OSD。
- OFF 后保留最后实际显示的图像，清除目标框，显著标注“画面已冻结”，继续更新遥测。新轮首帧到达前不得把旧画面标成实时。
- 增加独立的 OSD 构建和运行开关。保持现有 ROS 图像、预测框和状态发布语义；不改变跟踪算法及采集 ON/OFF 行为。
- 将关闭桌面显示作为启用 OSD 的强制前提。部署人员或外部启动流程必须先停止桌面显示服务，并确认显示设备已释放；OSD 运行期间保持桌面关闭。节点必须可靠取得或验证独占显示控制权，无法确认时拒绝初始化并提示关闭桌面，不自行停止桌面服务。退出并释放显示资源后才能恢复桌面。

例如，原先一帧只产生 ROS 框和可选调试图像；接入后，该帧与其显示框一次性提交给 OSD，并在 HDMI 上一起出现。收到 OFF 后，屏幕保留这张图像，但目标框消失且出现冻结提示。

## Capabilities

### New Capabilities

- `osd-presentation`: 成对显示提交、只读帧所有权、最新结果缓冲、绘制布局、冻结与轮次隔离。
- `osd-ros-telemetry`: 外部 ROS 遥测到显示快照的转换、有效性、过期处理和告警。
- `rk3576-hdmi-osd`: RK3576 图像适配、RGA 合成、HDMI 输出、配置部署和生产板验收。

### Modified Capabilities

无。沿用 `generic-frame`、`platform-factory`、`rk3576-ros-camera` 和 `rk3576-ros-video` 的既有要求。新增待显示结果位于跟踪输出端，不改变帧源队列，不增加采集转发线程。

## Impact

- 拟新增 `src/osd/` 公共显示逻辑、ROS 遥测适配及测试；新增 `src/platform/rk3576/osd/` 硬件后端。
- 修改 `src/drone_tracker_node.*` 的结果提交和生命周期连接点；调整 `CMakeLists.txt`、RK3576 构建配置、参数文件及部署说明。`HybridTracker` 算法和公共帧接口不引入显示硬件类型。
- 启用 HDMI 构建时新增 `libdrm`、`librga` 开发依赖。低层反馈使用的 `quadrotor_msgs` 作为可选遥测适配依赖，不使缺少该消息包的既有构建失效。
- 发布形式仍为 `drone_tracker_node` 可执行程序；OSD 是本仓库内部静态库，不单独发布 SDK 或 ROS 可执行程序。
- 本次不提供 Jetson HDMI 后端、独立高帧率视频支路、录像/推流或快照服务，也不移植参考项目的相机实现、CPU 调频与绑核行为。
- 验收目标为生产 `HZ-RK3576_WuKong Board`。已有参考项目的实机结果不替代本仓库的集成、资源和持续负载验证。
