## Context

当前同一管线的相机、帧和模型分别创建，接入另一平台时可能遗漏某个入口。目标是统一平台选择，并在不兼容资源改变跟踪状态前拒绝它；动机见 proposal.md 的 Why。

现有 `FrameRef` 是共享只读帧引用。`YoloPreprocessor` 和 `NanoTrackPreprocessor` 分别准备检测和跟踪输入。`YoloBackend` 与 `NanoTrackBackend` 运行模型，后者组合 Backbone 特征提取和 Head 预测。上述接口可复用，不需要重新设计模型数学处理。

仍需处理的实际边界：

- `DroneTrackerNode::setup()` 创建 `MVCamera`/`MVVideo`，ON 回调还将帧源转换成 `MVCamera` 配置录像。
- `MVCameraBase` 的队列已经传递 `FrameRef`，但公开 VPI 回调和 Jetson 缓冲区辅助方法。VPI 是 Jetson 图像处理库。
- `HybridTrackerImp::init()` 直接创建 Jetson 组件，并在 NanoTrack 创建前启动 YOLO 线程。
- `HybridTrackerImp::update()` 在更新计数之前强制转换 `VpiFrame`。此处已有提前拒绝位置，应保留位置并替换机制。
- 回放、压力测试直接创建 VPI 帧或 Jetson 组件。
- 顶层和算法 CMake 无条件启用 CUDA；算法库直接链接 VPI/TensorRT。TensorRT 是现有模型执行库。

现有规格要求默认生产使用 Jetson。新增构建选择后，默认值仍为 Jetson，并修改 `model-backends` 的装配要求。`model-input-preprocessing` 的现有 TensorRT 生产要求在本阶段仍成立，不修改其数值和同步消费约定。

## Goals / Non-Goals

**Goals:**

- 让公共节点和算法只使用行为接口，具体硬件类型留在平台内部。
- 让一条管线只取得一套匹配依赖，同时保留模型、预处理器和检查能力的测试注入。
- 保留正常输入的状态序列、时间戳、队列、录像和模型复用语义。
- 形成无需硬件开发库即可编译并测试的公共算法目标。

**Non-Goals:**

- 不实现 RK3576 采集、RKNN/RGA 后端或模型量化支持；本变更没有 RK3576 可运行交付物。
- 不引入运行时切换、插件加载、全局工厂单例、多设备调度或自动跨平台图像转换。
- 不合并预处理接口，不重写状态机、后处理或队列实现，不批量移动已有平台源文件。
- 不安排 Jetson 平台的编译、运行或测试。相关硬件验证不属于本变更的完成条件，也不作为待办任务保留。

## Decisions

### 1. 一个生产工厂入口，分别创建帧源和成套模型依赖

选择 `CreatePlatformFactory()` 返回 `PlatformFactory`。其接口提供 `createFrameSource(config)`、`createFrameBuilder()` 和 `createTrackerComponents(model_paths)`。`FrameSourceConfig` 只包含输入类型、路径、尺寸、帧率、翻转、镜像及历史时间戳配置，不包含 ROS 节点或硬件句柄。模型路径由节点沿用现有 share 目录拼接逻辑后传入。

`TrackerComponents` 是只能移动的依赖集合：包含 YOLO 的预处理器和模型后端、NanoTrack 的预处理器和模型后端，以及 `FrameCompatibility` 帧检查能力。只能移动表示这些有状态组件的所有权转交后，原调用方不再拥有它们。生产工厂必须成套返回；测试可以显式构造模拟集合，公共跟踪器初始化时拒绝缺失成员。

理由：相机尺寸参与节点相机内参计算，因此帧源创建不能强行与跟踪器全部合成一个黑盒。成套模型依赖则能避免生产调用方交叉选择模型和预处理器。

不采用五个互不相关的生产工厂函数，也不让 `HybridTracker` 反向调用平台工厂。结果是节点负责装配顺序，算法只消费依赖，平台目标不会成为算法目标的链接依赖。

```text
Node / Replay / Stress
          |
          v
  PlatformFactory
          |
          +--> FrameSource --> FrameRef
          |
          +--> FrameBuilder --> FrameRef
          |
          +--> TrackerComponents --> HybridTracker
```

帧源或 FrameBuilder 产生的 FrameRef 交给 HybridTracker。FrameBuilder 用于回放帧创建，不负责模型装配。

### 2. 公共帧源适配现有队列，保留录像边界

选择新增 `FrameSource` 接口，由 Jetson 适配器持有现有 `MVCameraBase` 实例。接口提供异步启动、停止、运行状态、尺寸查询、限时等待取帧、非阻塞取帧，以及启动前录像配置。取帧直接委托现有队列的出队操作，保留节点先等待最多一秒、再连续取出更新帧的流程，不增加转发队列、转换线程或像素复制。

节点沿用现有 `video_source` 分类规则生成明确输入类型，不顺手修复其字符串判定。尺寸查询必须返回相同值，以免影响相机内参。适配器将相机录像配置委托给 `MVCamera::setup()`；视频输入接受该调用但不创建相机录像。ROS bag 仍由节点管理。

节点与无硬件测试共用 `frame_source_ops.h` 中的公共调用函数。`waitForLatestFrame()` 执行限时等待和排空积压；首帧回调保留节点在收到首帧后、排空前记录计时起点的顺序。`configureFrameSourceRecording()` 将启用标志、目录和前缀一起交给帧源。测试向这些真实函数注入模拟帧源，不在测试内重写取最新帧的循环。

理由：现有队列的单生产者、单消费者假设必须保持。公共节点实际不使用原生图像回调，没有必要复制它。

不直接把 `MVCameraBase` 改造成跨平台大接口，也不让新接口公开 VPI 回调。原生回调、`create_nv_buffer` 和旧相机类继续留在 Jetson 内部。结果是适配改动较小，节点头文件只依赖公共帧源声明。

### 3. 帧由创建能力和原生采集路径协同产生

选择 `FrameBuilder::copyFrom(mat, timestamp_us)` 返回带诊断的通用帧结果。Jetson 实现委托 `VpiFrame::copyFrom()`，保留八位灰度、BGR、非连续行跨度和复制所有权语义。BGR 帧可创建，不代表当前模型预处理接受 BGR；后者继续按已有规格拒绝。

相机内部继续使用 `VpiFrame::takeOwnership()` 接管原生图像，工厂通过选择该帧源保证其产物属于 Jetson。无需让每一帧绕回工厂，也不把原生句柄暴露为公共 `void*`。

理由：主机图像复制与原生资源接管的所有权不同。不采用统一裸指针入口，避免无法验证类型和释放责任。创建失败增加公共诊断，但不改变已有像素转换规则。

### 4. 在入口注入帧检查，消费边界继续检查实际资源

选择 `FrameCompatibility::validate(frame)` 返回成功或带原因的失败；Jetson 实现检查实际 `VpiFrame` 类型。此对象不改变帧或跟踪状态，可由多个只读检查调用安全使用。工厂保证它与整套组件匹配。

`HybridTrackerImp::update()` 在现有类型检查位置调用它，早于时间戳记录、帧计数、缓存、滤波和检测提交。失败返回已有未消费结果，保留当前状态并报告平台类型不匹配。测试使用两类模拟帧和模拟检查能力驱动同一真实入口。

预处理器内部的具体帧检查、准备输入的 `PlatformTypeMismatch` 错误和执行器存储检查继续存在。平台标识可用于诊断，但不能替代类型与存储检查。

理由：工厂只能保证自己的产物，不能控制所有外部调用。不采用仅比较平台字符串，也不要求来自同一个工厂实例。实际兼容的独立帧仍可使用。未来有设备上下文限制时，由平台检查能力表达真实约束，本阶段不增加实例令牌。

### 5. 创建阶段不启动线程，明确两种停止边界

选择将资源创建、跟踪器初始化和业务启动分开。工厂只创建资源；`HybridTracker::CreateInstance(settings, components)` 接收依赖；`init()` 负责公共组件组装和检测线程启动。仓库内全部调用点迁移，不在公共算法中保留隐藏的 Jetson 默认创建逻辑。

启动顺序：

1. 节点取得工厂，创建帧源，查询尺寸并计算现有相机内参。
2. 工厂创建三个模型及两类预处理器，执行加载阶段能完成的契约检查，再返回完整集合。动态输出形状等仍在真实推理时按已有规则验证，不声称加载成功代表模型完全等价。
3. 跟踪器建立检测器、NanoTrack/DCF 和滤波所需对象，成功后才启动 YOLO 线程。DCF 是现有相关滤波跟踪组件；它的算法保持不变。
4. ON 回调配置录像并启动既有节点工作流程，再开始采集。

普通失败统一转换为包含平台、组件、模型路径或输入路径及原因的创建诊断。内部现有异常可在平台创建边界捕获。使用 RAII，即由对象析构自动释放拥有的资源，保证前两个模型在第三个加载失败时被回收。组件不依赖工厂对象的借用地址；必须共享的底层状态由资源所有者持有。

两种停止边界：

- OFF：沿用现有工作线程结束和帧源停止顺序，保留已加载模型及现有检测线程管理语义；下一次 ON 执行既有 reset。不借本次重构调整待处理检测结果的仲裁行为。
- 最终销毁：先禁止新工作，结束节点及采集流程，再停止并等待 YOLO 工作线程，最后释放跟踪缓存、模型和源资源。可以保留帧的外部消费者继续通过共享所有权读取有效数据。重复清理必须安全，普通启动失败也进入同一清理路径。

理由：现在 YOLO 提前启动，后续创建失败增加清理难度。不采用工厂构造即启动，也不让 OFF 卸载模型。设备无法确认已停止访问存储的致命失败仍执行现有立即终止政策，不能笼统捕获后继续析构设备缓冲区。

### 5.1 旧相机的最小失败清理修复

相机在构造期间已经打开设备并分配采集缓冲区，之后才由节点装配模型。仅包装原 `stop()` 不足以保证失败回收：旧代码在未开始采集时提前返回，且 `cleanup()` 跳过未完成初始化的部分资源。

将该内部修复纳入本变更。`stop()` 不再以是否已初始化或开始采集作为跳过清理的条件；先停止并等待已创建线程，再释放设备与采集缓冲区。`cleanup()` 按各资源是否存在进行回收，释放后清空指针、容器和文件描述符，允许重复调用。

初始化入口在每次失败返回或异常后执行清理，避免重试覆盖旧资源。构造异常还释放已创建的 VPI stream 和 JPEG 编码器；它们在正常 OFF/ON 期间保留，最终销毁时释放。帧源创建检查相机是否真正初始化成功，失败时由公共工厂返回带输入路径的诊断。采集启动失败同样停止已创建线程并清理本轮采集资源。

例如，相机缓冲区已分配，但 Head 模型加载失败：局部组件先自动回收；节点构造失败释放帧源，帧源销毁相机，相机在没有采集线程的情况下仍关闭设备并释放缓冲区。

仅修改清理、失败诊断和启动失败回收，不重写采集循环、录像、队列或时间戳规则。本项通过源码逐路径审查验收；不增加 Jetson 编译或执行验证。

### 6. 构建选择与目标依赖一并收口

选择在启用 CUDA 和查找硬件库前校验 `DRONE_TRACKER_PLATFORM`。默认 `jetson`；`rk3576` 报“后端尚未实现”，未知值报“不支持”，两者都列出当前支持值。只在选中 Jetson 的路径启用 CUDA，并创建 Jetson 工厂实现目标。

建议依赖方向：

- `platform_interfaces`：公共接口声明，只需要通用类型；不链接平台实现。
- `hybrid_tracker`：公共状态机、检测调度、后处理、DCF、滤波，依赖公共模型验证及几何代码。
- `platform_jetson`：工厂、帧源适配器、VPI 帧、预处理和 TensorRT 执行实现，依赖上述公共声明。
- 节点、回放、压力程序显式链接公共算法及选中的平台实现。

现有 `model_common` 编译的 `model/jetson/jetson_model_backend.cpp` 不直接使用硬件 SDK，可继续供模拟执行器测试，不为目录名进行无关搬迁。创建真实模型的 `jetson_model_factory.cpp` 和实际存储、执行代码进入平台目标。`drone_frame` 和 `mv_camera` 可作为平台内部子目标保留。

扩展现有 `DRONE_TRACKER_PREPROCESS_TESTS_ONLY` 独立入口，使其能构建公共跟踪器和工厂契约测试，不需要顶层 ROS 或硬件依赖。测试用工厂不加入生产后端选择列表。现有 `vpi_race_repro` 保持 Jetson 专属，本变更不编译或运行它。回放和压力程序仅迁移创建入口，不安排这些 Jetson 程序的编译或执行。

理由：只替换创建函数仍会让公共算法传递链接硬件库。不采用在单个算法库中靠宏切换整套平台代码，避免编译依赖继续泄漏。此次只保证 Jetson 与公共目标分离，RK3576 支持由后续变更扩展。

## Risks / Trade-offs

- 相机适配改变队列时序 → 直接委托现有队列，无中间缓冲；检查容量、丢帧、取帧循环和消费者数量。
- 尺寸或录像配置变化影响外部行为 → 静态对照重构前 Jetson 代码，检查内参输入值、录像前缀、ROS bag 与视频输入路径；公共委托逻辑使用模拟依赖验证，不运行 Jetson 相机或视频程序。
- 提前检查误拒绝兼容帧 → 检查真实类型与资源，加入独立创建器兼容测试，不使用工厂实例相等作为条件。
- 模型已加载但动态契约不兼容 → 保留执行期验证及已有模型契约测试，初始化只承诺完成静态检查。
- 工厂销毁导致悬空引用 → 组件不得借用工厂，帧、视图、准备输入与模型输出继续自行保持资源所有权。
- 公共构建拆分漏掉间接 SDK 依赖 → 同时检查公共头文件编译、目标链接关系和真实无硬件测试构建。
- Jetson 平台执行验证不在本变更范围 → 使用源码审查检查适配关系，使用平台无关编译和模拟测试验证公共契约；交付时明确这些证据不能证明 Jetson 构建成功、真实行为等价或设备资源安全，不将范围外验证列为未完成任务。

## Migration Plan

1. 增加公共接口及模拟装配测试，明确错误结果和所有权。
2. 实现 Jetson 工厂、帧源和帧创建适配器，复用现有模型加载方法。
3. 修改公共跟踪器依赖注入与入口检查，调整初始化顺序。
4. 同步迁移节点、回放和压力测试；移除公共层具体 Jetson 头文件及类型转换。
5. 拆分构建目标，加入平台选择检查；仅构建和运行无需 Jetson SDK 的公共测试。对 Jetson 目标的依赖关系只做源码与 CMake 配置静态审查，不配置或编译其生产目标。
6. 汇总公共测试与静态审查证据，检查适配代码、输入配置和生命周期关系是否符合规格。Jetson 编译、固定录像回放、真实相机和设备压力测试均不纳入本变更任务或验收前置条件。

本变更保持原有默认构建和参数入口，无模型或数据格式迁移，不安排 Jetson 部署或运行。若公共验证失败，应修正或回退对应代码及构建改动，不通过平台回退掩盖问题。验证记录保留提交标识、公共测试环境、模拟输入和检查命令，以便复现；明确 Jetson 执行验证未纳入本次范围。
