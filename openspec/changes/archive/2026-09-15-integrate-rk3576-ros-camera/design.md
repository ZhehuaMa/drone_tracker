## Context

当前正式节点无法用相机运行跟踪；独立相机帧源只支持连续采集。本设计使 ON 启动周期软件触发和真实图像处理，OFF 能完整停止并恢复本轮修改的控制项。动机见 [proposal.md](proposal.md)。本变更同时涉及设备控制、两线程生命周期和 ROS 参数，因此需要独立设计。

已核对 `camera_device.*`、`camera_frame_source.*`、`production_factory.cpp`、`drone_tracker_node.*` 以及相机设备/帧源/独立工具测试。现有采集线程在退出时自行关闭设备；直接增加触发线程会造成仍在发命令时句柄已关闭的风险。公共采集配置已有 `trigger_mode` 布尔值，默认 true；独立相机调用显式填 false。正式工厂未开启相机，节点只按固定长度识别 video0 一类输入，且尚未映射媒体设备和传感器实体。

2026-09-15 开发板 2 短测：1920×1200 GREY；每行 2048 字节，实际像素宽 1920。不触发的 0.5 秒内无帧，五次单发得到五帧。10 Hz 为 120/120，15、20 Hz 各为 60/60；30 Hz 为 120/60，60 Hz 为 120/30。斜线前后分别表示命令和返回帧数。高频命令调度符合请求，控制调用最长不足 0.9 ms，但原因尚未确定。恢复连续模式后 60 帧约 59.73 FPS。短测不代替新实现验收。

历史原始数据位于开发板 2 `/tmp/camera-trigger-20260915-085012`、`/tmp/camera-trigger-periodic-20260915-085051`、`/tmp/camera-trigger-confirm-20260915-085156`。它们是临时文件，实施前先归集；如已丢失则重测，不将本段摘要视为原始证据。

## Goals / Non-Goals

**Goals:**

- 让正式节点复用已有相机后端、公共帧队列及真实跟踪器。
- 让定时发命令与等待图像互不阻塞，并由一个生命周期所有者回收设备。
- 明确设备帧率、触发频率、图像时间和预测时间的不同职责。
- 使设备接入质量和模型识别质量可以独立验收。

**Non-Goals:**

- 不增加额外图像转发线程或改变 YOLO 异步调度、DCF（相关滤波辅助跟踪）及卡尔曼预测。
- 不实现外部引脚触发、自动曝光、曝光时间修正、图像录像或 ROS bag 消息记录。
- 不保证任意请求频率都逐次出帧，不默认提升当前模型性能或补齐 Jetson 实机验证。

## Decisions

### 1. 保留公共边界，在相机后端内增加触发执行器

选择扩展 `CameraDevice` 的控制能力及 `Rk3576CameraFrameSource` 的生命周期。V4L2 是 Linux 视频设备接口；控制编号、设备句柄和系统调用仅在 RK3576 后端中使用。正式工厂显式开启相机，独立工厂默认关闭行为保留。

拒绝在 ROS 回调或跟踪器中调用相机控制；那会把平台细节和推理耗时带入采集。结果是 ROS 仍只使用公共帧源的启动、停止、取帧和诊断接口。

```text
ON/OFF --> ROS round owner --> Camera source owner
                                    |       |
                                    v       v
                               Trigger    Capture --> Frame queue
                                                         |
                                                         v
                                            ROS worker --> HybridTracker
                                                               |
                                                               v
                                                         ROS outputs
```

图像队列仍只有采集线程一个生产者和 ROS 工作线程一个消费者。满队列丢新帧，消费者取最新帧；触发线程从不操作图像队列。复制后立即归还设备缓冲，公共帧及只读视图可以跨源对象存活。

### 2. 显式模式与分开的频率

新增相机专用参数，保持视频和 Jetson 路径不受新必填项影响：

| 参数 | 规则 |
|---|---|
| `video_source` | RK3576 接受 video 加一个或多个十进制数字，或绝对 /dev 路径；其余仍按本地视频规则处理，禁止网络输入。实际打开后核验视频采集能力 |
| `mv_camera.capture_mode` | 相机必填 continuous 或 software_trigger；不从设备残留模式推断 |
| `mv_camera.fps` | 正整数设备帧率，必须与实际协商值一致 |
| `mv_camera.trigger_rate_hz` | 软件模式必填有限数值，范围 1 至设备 fps；连续模式为 0，拒绝非零混填 |
| `mv_camera.media_device`、`sensor_entity` | 相机必填，启动时解析并核对拓扑 |
| `mv_camera.buffer_count` | 默认 4，范围 2–32 |
| `mv_camera.width_px/height_px` | 实际采集像素尺寸，输出原尺寸或 0 表示不缩放 |
| `camera.fx/fy/cx/cy` | 图像像素坐标中的焦距和主点；全部显式且有限，fx/fy 为正 |

公共配置末尾追加 `camera_trigger_rate_hz`，ROS 模式映射到已有 `trigger_mode`。保留旧字段顺序和默认值；RK3576 软件模式缺有效频率时报错，已有显式 false 调用继续表示连续模式。避免新增第二个可与布尔值矛盾的公共模式字段。设备能力查询如能获得更严格范围，再执行该范围校验；查询不到最短周期不等于任意频率已通过。

选择保留 fps 的设备含义，拒绝用它同时表示命令频率。例如设备 fps=60、trigger_rate_hz=20 是两个独立设置。示例候选为 20 Hz，不静默降频。软件模式未验收频率的实际输出不足仍需报告；若连候选频率也不能稳定通过，保留验收未完成，不悄悄替换示例。

新增 `rk3576_camera.launch.py`，接受 params_file 与显式 video_source，仅覆盖输入路径。`rk3576_camera_params.yaml` 列出所有现有算法参数，模型路径为空，部署时须填写。按用户于 2026-09-15 的确认，1920×1200 图像暂用模拟内参 `fx=fy=1000.0、cx=960.0、cy=600.0`，单位为像素。焦距为人为选定的测试值，主点暂取图像中心，不代表实测标定。允许用这组值继续 ROS 接入和资源测试，但不据此验收旋转补偿精度或正式跟踪质量。正式标定后替换四值并重启节点。缺失或非有限内参仍被拒绝。设备信息使用需复核的示例，不作为硬编码。配置在节点生命周期固定，包括模式与频率；运行期修改明确拒绝。

### 3. 周期触发使用单调时钟，落后不补发

选择直接调用已实测的 soft_trgone 控制接口，不为每帧启动 shell 命令。线程使用可停止的条件等待，计划时刻为本轮起点加 n 个周期。若落后，跳过已经错过的周期并记录，不突发追赶。不因推理慢、队列满而自动改变拍摄频率。

拒绝在读取一帧后才触发下一帧，因为它会把复制及调度开销加入拍摄周期。相机控制调用失败即请求终止本轮；接口成功只计为发送成功，不作为曝光或相机接受的证明。

### 4. 高频能力检查先于最终实机验收

选择在现有独立验证工具中补充命令与帧计数，再核查触发模式、一次触发帧数、曝光时长、最短周期及可用的相机计数器。优先读取现有驱动或已核实厂家接口；不盲写寄存器。正式软件模式要求每次触发一帧；若帧数控制可查询/配置则核对为 1 并纳入恢复，若无公开控制则以有限单发测试验证，不能宣称已经读回。

拒绝将低分辨率、降低曝光或换模型作为默认解决办法。当前高频原因是独立调查项，不阻止实现已选架构；结论可以是证实设备限制或明确未归因，但未满足逐次出帧的频率不能通过验收。

独立工具停止发送后允许限时收集尾帧，然后关闭采集，分别报告正常收到、关闭时尚未确认的请求和工具超时。ROS OFF 以尽快停止为目标，不为凑计数继续处理尾帧；因此不能把运行中计数差或 OFF 截断都标为触发丢失。

### 5. 三个记录时间不替代真实曝光时刻

选择保留驱动帧时间作为公共帧依据。单调时钟不随系统校时跳变；每轮固定偏移把它换算到系统时间。已有未知来源回退到主机出队时间、非法或重复时间失败的规则不变。

| 时间 | 事件 | 用途 |
|---|---|---|
| 命令调用前/后 | 主机要求拍摄 | 调度和控制耗时 |
| 驱动帧时间 | 驱动给图像附带的时刻 | 公共图像时间依据 |
| 主机出队时间 | 采集线程拿到图像缓冲 | 交付延迟诊断 |

假设命令在 100 ms 发出，相机在 102–107 ms 曝光，驱动标记 115 ms，程序在 120 ms 取帧。这三个已记录事件不能证明曝光发生在 100、115 或 120 ms。此例仅解释含义，不是实测延迟。当前驱动标记 ts-src-eof（帧结束来源），不能当作曝光结束证明。

拒绝照搬 Jetson 的经验帧周期补偿，也不按命令 FIFO（先进先出顺序）把每个触发与下一帧强行配对。高频缺帧会破坏这种对应。触发与帧报告分别记录时间；没有可靠关联证据就不输出逐帧“触发到曝光延迟”。

图像消息继续使用帧时间，框消息继续使用当前预测时间；姿态查询按现有规则，无姿态时保留单位旋转矩阵。系统时间在轮次中跳变的事件应留诊断，不伪造新的帧时间；本步不声称已解决外部时钟同步。

### 6. 两工作线程只有一个设备清理所有者

选择由源对象的生命周期路径唯一释放设备，修改现有采集线程退出即调用 finish 的行为。工作线程只发布失败、设置停止并唤醒等待；不自行关闭共同资源，不互相 join。控制操作串行，状态锁不跨阻塞系统调用或 join。

初始化验证不发触发命令、不启动采集线程。对本次要修改的可恢复控制项先读取快照；无法读取则在修改前失败。创建阶段若做配置验证，退出该阶段时也恢复。格式及媒体拓扑沿用既有配置行为，不宣称恢复整个系统的历史拓扑。

控制写入后的读回确认允许设备延迟生效：每个控制项写入成功后，以单调时钟计时，最多等待 100 ms，每隔 5 ms 重新读取，首次一致即成功。初始化设置和恢复原值采用相同规则；等待期间不重复写入。超时报告设备、控制名、预期值、最后读回值和实际等待时间。系统调用自身报错仍直接保留，不伪装为值不一致。该期限限制用户态确认等待，不能强制中断阻塞的驱动调用；实机整体停止仍须满足 1 秒门槛。

ON 顺序：

1. 回收旧 ROS 消费线程，完成旧检测请求收尾和状态重置。
2. 清空旧图像队列、统计与时钟基准，重新打开并核对设备。
3. 保存控制快照，配置模式/来源/设备帧率及已支持的一触发一帧设置。
4. 申请缓冲并开流，建立采集工作线程就绪握手。
5. 软件模式启动触发线程，连续模式不启动该线程。
6. start 返回成功后 ROS 开始消费；首帧超时仍单独监测。

OFF、线程失败及部分启动失败共用收尾路径：

1. 撤销继续运行请求并唤醒两个等待点。
2. 回收触发线程，确保没有在途控制调用。
3. 回收采集线程，再停流并释放缓冲。
4. 在控制句柄仍有效且设备允许时恢复快照，关闭设备。
5. 保留首次故障并追加清理/恢复错误，等待本轮检测访问结束。
6. 回到 ROS 空闲，允许设备恢复后再次 ON。

拒绝用 detach 或关闭在途调用所用句柄强行满足停止耗时。驱动调用无法返回时记录验证失败，不宣称可可靠恢复。普通等待下相机停止保持无设备 250 ms、实机 1 秒门槛；节点整体 OFF 包含模型推理，另行报告。

### 7. 明确故障、正常超时与计数差

选择首帧从开流起计时，之后从最近成功出队计时；连续 2 秒无帧为故障。触发频率下限 1 Hz，避免合法周期超过该规则；不实现按需低频单拍。短暂等待超时继续等待，OFF 不等待两秒阈值。格式、时间、序号非法或触发接口失败终止本轮。

每轮报告请求频率、实际发送频率、周期跳过、调用成功/失败、帧数、驱动序号缺口、队列入队/丢新帧、ROS 消费数、时间来源和停止/恢复结果。每秒最多一次常规汇总，结束输出最终统计；错误立即报告。新增公共诊断字段必须为通用值，不泄漏硬件类型；平台专有详细原始数据保留在独立工具报告。

拒绝把“成功命令减去当前帧数”直接命名为丢触发。正常曝光/传输在途、OFF 截断、相机拒绝及驱动丢失尚未区分。持续数量不匹配产生诊断，只有明确控制/采集错误自动停止，不私自增加未经定义的质量阈值或自适应降频。

### 8. ROS 接口和记录范围

选择复用现有 ON/OFF、模型复用及旧轮检测收尾。三个输入和三个输出的话题、类型、QoS（队列与可靠性设置）及状态数值不变。相机无 EOF（文件正常结尾）；设备错误通过运行诊断表达，不产生伪造的 TargetLost。

首版相机在初始化时要求 need_save=false，避免 ON 后才发现录像不支持。不选择只保存 ROS bag 而默默跳过图像录像，因为现有参数绑定两种行为。视频和 Jetson 的记录逻辑不变；将来拆分记录功能另建变更。

### 9. 验证与部署

选择先设备后 ROS 的验证顺序，复用既有设备系统调用替身和可控模型测试。替身可模拟真实设备返回与失败，用于确认线程/资源契约，不能当作实机证据。

- 独立软件模式：无触发、有限单发、10/15/20/30/60 Hz 短测至少三轮；区分启动、稳态和停止尾部，正式选定频率必须逐次出帧。保持高频失败原始记录。
- 新实现独立软件模式：20 轮启停、100 次新建销毁、至少 10 分钟慢消费；连续模式执行像素、时间及启停回归。
- ROS：同一 YOLO，NanoTrack 分别为纯 FP16（16 位浮点）和纯 INT8（八位整数），各执行两模式基础消息与失败检查。固定 INT8 软件模式同进程 20 轮 ON/OFF，再额外至少 30 分钟持续负载。模型四文件只加载一轮，跨 ON/OFF 复用。
- 报告采集及节点停止耗时、主机内存、线程、文件描述符、实际处理量和设置恢复。未测 NPU 设备内存明确注明。画面不清晰及未捕获单独记录，不改阈值制造通过。
- ARM64 构建遵守 AGENTS.local.md 的现有临时容器约定；检查 RK3576 无 Jetson 依赖，保留视频与公共测试回归。缺实机或数据的任务不勾选。

拒绝用过去独立采集或 shell 触发测试替代新两线程实现验收，也不重复用已知不通过素材制造模型质量通过结论。

## Risks / Trade-offs

- 高频调用成功但返回帧不足 → 核对模式与触发周期，正式频率以完整计数及负载验收为准，不承诺 60 Hz。
- 驱动帧时间不等于曝光 → 保留来源标记，不做无证据时间补偿，旋转同步单独验收。
- 设备清理与控制并发 → 唯一清理所有者，故障只发布请求，先回收线程再关闭句柄。
- 外部进程同时配置设备 → 部署前检查占用，运行期禁止并发外部相机控制；不停止未知服务，不覆盖无法确认的他人会话。
- 控制恢复失败或驱动阻塞 → 保留错误和未恢复项，实机验收失败，不以成功进程退出掩盖。
- 相机灰度帧复制增加负载 → 先测真实负载，不在本步加入硬件加速。

## Migration Plan

1. 归集短测证据并完成具体能力检查，保留高频原因未确定的边界。
2. 实现并验证独立触发及安全收尾，再开放正式工厂和 ROS 参数。
3. ARM64 构建后在开发板 2 独立目录部署，保留旧二进制与完整配置。
4. 执行规定矩阵，记录程序、模型及配置 SHA-256（文件内容指纹），补齐独立报告和 ROS 结果。
5. 回退时先停止新节点并核对设置恢复，再运行原视频入口或旧独立相机工具。不迁移模型或改变既有话题。

## Open Questions

- 30/60 Hz 缺帧的设备内部原因：按任务中的能力检查调查，不改变软件模式、诊断与未通过频率不得宣称支持的契约。
- 曝光与驱动帧时间的实际关系：本步不修正时间，未知结论不阻止按驱动来源完成接入验收。
