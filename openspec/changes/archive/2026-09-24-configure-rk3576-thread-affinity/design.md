# Design

## Context

生产板使用隔离核心 CPU 4–7。现有服务和启动脚本只设置允许范围，不能保证多个可运行线程分散。实机审计对照中，负载集中于 CPU 4；按职责分配后，持续跟踪并录像时 HDMI 从 6.838 提升到 53.351 帧/秒，显示处理平均耗时从 145.597 降到 15.007 毫秒。此结果证明调度分配是当前卡顿的重要原因，不代表算法必然达到 60 帧/秒。

已有验证使用临时注入库识别线程创建位置。它不是正式实现，不能依赖其二进制地址、线程编号或创建顺序。完整证据保存在 `evidence/`。

## Goals / Non-Goals

目标是用统一配置管理职责与 CPU 的对应关系，在工作开始前确认分配生效，并覆盖每次 ON 创建的线程和录像进程。部署服务与手动入口使用相同策略。

不修改跟踪算法、模型、ROS 契约、帧框配对、内核隔离参数、调频或调度优先级。不把临时注入库产品化。不重新实施 OSD 渲染优化，也不重做该优化已有的全部验收。

## Decisions

### 1. 独立配置作为唯一来源

安装文件为 `/opt/drone_tracker/config/cpu-affinity.yaml`。示例：

```yaml
version: 1
mode: role-pinned
allowed_cpus: [4, 5, 6, 7]
roles:
  control: 4
  tracking: 4
  yolo: 5
  display: 6
  capture: 7
  recording: 7
```

`allowed_cpus` 是整个策略的允许范围；每个职责指定一个核心，允许多个职责共用核心。`role-pinned` 表示按职责绑定；`inherit` 表示仅保留启动入口设置的总范围，不逐职责绑定。直接运行程序且未提供策略路径时不改变亲和性。

拒绝不支持的版本或模式、空或重复的允许列表、负数或离线核心、缺少职责、职责超出范围以及显式指定但不存在的文件。策略在进程启动时读取一次，修改文件后必须重启。

选择独立文件是为了避免修改相机参数和重复维护服务配置。拒绝在 systemd、脚本和节点各自硬编码映射；代价是部署包需要额外管理一个配置文件。

### 2. 在线程入口绑定，并向创建者确认

入口通过 `DRONE_TRACKER_CPU_CONFIG` 接收绝对路径，在 ROS 初始化和创建后台线程前加载策略，并绑定控制线程。平台无关接口描述工作职责；Linux 亲和性调用留在 RK3576 平台实现中。复用已有线程启动接口，在主跟踪、YOLO、显示和相机采集的工作入口执行绑定，再读回核对。

创建者等待启动结果，成功后才宣布工作线程就绪。失败通过现有初始化或轮次失败路径回收线程和资源，不能让异常逃出线程入口，也不能静默继续运行。显示绑定失败属于启动失败；运行中的显示设备故障仍按已有隔离契约处理。

每次 ON 都重新处理新建的跟踪和采集线程。常驻 YOLO 和显示线程保持原策略。未单独管理的库线程继承创建者，日志和短测核查其实际行为。不能将新线程继承的单核掩码误当作策略总范围：例如继承 CPU 4 的显示线程仍需切换到配置允许的 CPU 6。外部系统限制以绑定系统调用及读回结果校验。

选择显式入口是为了消除创建顺序竞态。拒绝扫描线程编号后补绑、动态注入或二进制地址识别；代价是需要在线程启动边界增加小型启动握手。

### 3. 录像进程使用本轮不可变策略

通过现有录像启动描述传递策略快照。录像工作进程在创建编码器和写入线程之前绑定 recording 核心，子线程继承该核心；失败返回启动错误并清理本轮资源。父进程的监控线程保持其创建者策略。新录像进程不能依赖上一轮进程的线程编号或运行状态。

这比只依赖父进程当前核心可靠，因为主跟踪位于 CPU 4，而录像需位于 CPU 7。策略日志记录进程、线程、职责、请求核心、实际掩码和适用的轮次，能够区分“配置被读取”与“分配已生效”。

### 4. 部署入口统一解释配置

服务调用 `run-camera`，取消服务模板固定 `CPUAffinity=4-7`；入口从策略生成 `taskset` 总范围并传递配置路径。节点在此范围内分配职责。预检和启动共用解析规则，避免 YAML 解释不一致。

打包新增显式 `--cpu-policy <file>` 选项；未指定时复制源安装已有策略。旧源安装没有策略时，要求显式提供仓库中的已验证模板，记录来源及 SHA-256，不静默生成或覆盖。相机配置仍逐字节复制。安装前校验配置和目标 CPU；`--check` 不修改服务状态。升级备份策略、原配置和入口，恢复时恢复完整组合。

选择统一入口避免两份核心范围失配。`inherit` 可用于诊断回退，但不会承诺隔离核心上的负载自动均衡；完整回滚恢复上一版本及其配置。

## Risks / Trade-offs

- CPU 4 在持续跟踪测试中约占用 92.9%，仍可能限制算法吞吐。此次解决线程争用，不承诺稳定 60 帧/秒。
- 不同设备的在线核心或外部 CPU 限制不同；预检及入口读回失败必须清晰报告。
- 第三方库可能自行修改线程亲和性。已有 2071 个稳定样本未发现变化，正式实现短测仍应抽查，不声称证明所有未来库行为。
- 录像停止边界已有一次取消记录，首轮存在少量队列丢帧。验收检查已接收帧完成写入和错误原因，不能将既有证据描述为所有链路零掉帧。

## Migration Plan

1. 完成策略解析、平台绑定和线程入口接入，保留无配置默认行为。
2. 更新打包、安装和启动入口，以显式选择的生产模板升级。
3. 执行一次相关自动检查及目标平台构建，然后做下面的定向短回归。
4. 失败时仅重测受影响项；必要时恢复旧版本及完整配置。此次规划不执行部署。

## Validation Plan

既有三轮各 75 秒的实机结果和同进程三次短切换作为可行性证据复用，不重新执行性能对照。正式实现后默认只做一轮约 30 秒的目标入镜测试，同时启用跟踪、显示和录像；排除前 5 秒，记录阶段耗时、帧率、线程掩码及录像计数。再做同进程两次各约 5 秒的 ON/OFF，确认新线程和录像进程重新应用策略并完成清理。

短测需具有持续跟踪的有效窗口；目标未入镜或未进入跟踪时不能判为通过。与历史结果比较，明显回落时分析原因，不要求精确复现 53.35 帧/秒或宣称达到 60 帧/秒。正确性门槛是所有受管职责掩码正确、无绑定失败、无新增死锁或资源遗留，已接收录像帧完成处理；任何取消或丢帧单列原因。性能数据用于识别明显退化，不以场景不一致的固定阈值代替判断。

自动检查只覆盖配置边界、入口失败清理、重复创建和部署一致性等本次新增风险，各执行一次。除非失败或出现新证据，不追加多组长测。原 OSD 渲染相关完整验收要求不在此变更中改写；此次复用历史验收，仅验证新增调度边界。
