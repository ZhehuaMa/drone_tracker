# Proposal

## Why

生产板在跟踪目标并录像时，HDMI 画面仍明显卡顿；同一程序将关键线程分散到不同核心后，实测显示从约 6.84 提升至 53.35 帧/秒。现有启动方式只允许程序使用 CPU 4–7，却没有让线程在这些隔离核心上实际分散，因此需要把已经实机验证的分配方式固化为可配置、可诊断的启动策略。

## What Changes

- 新增 RK3576 线程亲和性策略。亲和性表示线程允许在哪个 CPU 核心执行；按工作职责绑定，不使用会随启动变化的线程编号或创建顺序。
- 提供已验证的生产配置：控制及主跟踪 CPU 4、异步 YOLO 检测 CPU 5、HDMI 显示 CPU 6、相机采集和录像进程 CPU 7。辅助线程继承创建者策略；显式管理每次 ON 后重建的工作线程。
- 使用独立 `cpu-affinity.yaml` 作为部署、手动启动和节点的统一策略来源。取消服务模板与启动脚本各自写死的 `4-7`，保留按配置限制总范围和回退到仅继承范围的能力。
- 在线程执行工作前应用策略并读回核对。绑定失败走现有初始化或轮次失败清理，不能带着错误分配继续宣称策略生效。
- 保持算法、模型、ROS 话题、状态数值、相机格式和 OSD 帧框配对语义。程序不改内核隔离参数、CPU 调频或线程优先级。
- 保存现有实机证据，后续只做一次相关自动检查和一轮短实机回归。默认不重做多组 75 秒对照、20 轮切换或 10 分钟长测。

具体例子：输入一份允许 CPU `[4,5,6,7]` 的策略；启动时显示线程绑定 6、YOLO 线程绑定 5；收到 ON 后，新建跟踪线程绑定 4、采集和录像绑定 7。OFF 后再次 ON，新线程重新应用同一策略，不依赖上一轮留下的线程编号。

## Capabilities

### New Capabilities

- `rk3576-thread-affinity`：启动策略配置、按职责绑定、录像继承、失败处理、诊断，以及复用已有实机证据的定向短回归。

### Modified Capabilities

- `production-binary-deployment`：将固定 CPU 4–7 改为统一策略配置；增加策略文件的打包、预检、安装、备份与恢复要求。
- `rk3576-hdmi-osd`：明确显式线程策略可以在显示线程入口绑核；未配置时保持默认不改变绑核的既有约束，显示后端本身不决定 CPU 策略。

## Impact

- 入口与平台支持：`src/drone_tracker_main.cpp`、`src/drone_tracker_node.*`、`src/platform/` 下的策略接口和 RK3576 实现。
- 线程接入：`src/osd/presenter.*`、`src/hybrid_tracker/yolo_detector.*` 的现有线程启动接口、RK3576 相机帧源，以及 `src/platform/rk3576/recording/` 的会话和工作进程。
- 部署：`deployment/package.sh`、`deploy.sh`、`run-camera`、服务模板、CPU 策略模板与说明。相机配置继续逐字节安装，不把 CPU 策略混入模型或相机参数。
- 兼容性：未显式启用时不改变普通程序启动或 Jetson 行为。旧安装升级时由打包流程明确生成并记录新策略文件，不静默改写已有文件。
- 实机证据见 `evidence/README.md`。诊断辅助库仅证明方案可行；正式实现不用 `LD_PRELOAD` 动态注入、二进制地址表或线程轮询来绑核。此次仅创建规划工件，不部署或实现代码。
