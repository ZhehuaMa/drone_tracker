# 按职责绑定 CPU 的实机验证

2026-09-24，firefly-production，HZ-RK3576_WuKong Board。未生成 OpenSpec 变更，未修改正式源码或部署配置。

结论：按职责在指定隔离核心上绑定线程的方案已通过本次实机可行性验证。持续跟踪时，算法输出约 53.37 fps，HDMI 新画面约 53.35 fps；相同 cached-overlay 程序的原分配对照约为 24.11 和 6.84 fps。启动入口绑定与后续 ON/OFF 重建线程均得到核查。结果支持将这种机制作为后续实现方向，但不是对所有目标、场景及长期负载的正式验收。

## 验证方法

使用现有发布二进制，加载独立诊断辅助库 role_affinity.so。辅助库拦截 pthread_create，通过创建调用栈和发布二进制的函数地址识别职责，在工作函数执行前设置 CPU 亲和性。亲和性表示该线程允许在哪些核心执行。记录绑定返回值、读回掩码和当前核心。录像进程在启动早期绑定，并在其线程入口核查。

这不是按 TID 或线程出现顺序轮流分配。roles.tsv 来自该版本二进制的符号，包含 OsdPresenter::start、YoloV8Detector::init、DroneTrackerNode::run、Ar0234CameraFrameSource::start 的地址范围。该范围只适用于当前二进制，不能把诊断库原样当作跨版本生产配置。正式实现应在线程入口按职责直接调用绑定函数。

| 职责 | CPU |
|---|---:|
| 主跟踪流程，NanoTrack、DCF 和仲裁 | 4 |
| 异步 YOLO | 5 |
| HDMI 显示 | 6 |
| 相机采集 | 7 |
| 录像进程及其工作线程 | 7 |

控制线程及尚未显式分类的库线程继承创建者的分配；诊断模式下节点主线程先绑定 4，辅助 ROS 线程主要继承 4。测试不改变 nice 或实时调度等级。对所有稳定区间采样线程另行核对入口记录与实际掩码，以检查是否存在库线程遗漏或后续改绑。

正式服务在测试期间停止，测试进程使用同一二进制、同一 camera.yaml。完成后关闭所有测试进程并恢复正式服务。所有长测都加载同一个辅助库；audit-baseline 只识别记录、不改变亲和性，减小诊断方法不一致造成的偏差。

## 固定条件

- SC233HGS /dev/video22，1920×1200@60；HDMI 720×480@60。
- cached-overlay，阶段计时开启，气球混合精度 YOLO、NanoTrack FP16、DCF 开启。
- 独立录像开启，12 Mbps；模型、相机配置、内核隔离配置未调整。
- 二进制 SHA-256：66414023f3f528bef8526551560b0a837efe14eaf2d07a0d641618dee868e513。
- camera.yaml SHA-256：91e6b85400545dc4a1498251bf132c1cace64b6654b5e02237dbfd81214fdb69。前后指纹一致。

先完成 8 秒有效采集短测，再运行职责绑定、原分配对照、职责绑定三个约 75 秒长测。第二轮职责绑定结束后，同进程再运行三次约 5 秒 ON/OFF。所有测试都确认实际收到 ON，不把 ROS 发现阶段的空跑纳入统计。

统计排除前 10 秒，只纳入完全位于稳定区间内的计时窗口，均值按样本数加权。P95 合并直方图后取桶上界，表示至少 95% 样本不超过该值；它不是精确的逐帧百分位。

第一轮前段以检测为主，后段目标入镜，出现一次持续框跳变导致的重初始化，没有 Target lost。用户随后保持气球目标入镜；原分配对照和第二轮职责绑定的主测试段各有一次初始化，之后没有 Target lost。这两轮覆盖真实跟踪、显示和录像并行负载。第二轮日志中额外三次初始化属于随后三次 ON/OFF，不应误算为长测中反复丢失。

算法输出取 OSD submitted 计数，本次与主循环消费对应。提交至显示包括显示等待与渲染，不包括相机采集和算法处理，不能当作完整光学端到端延迟。

实时目标的位置和尺寸并非逐帧相同，所以不把比值当作严格固定输入的加速系数。此次也没有 legacy 渲染路径对照。

## 核心负载

|---|---:|---:|---:|---:|
| split-1 | 24.4% | 68.7% | 20.5% | 20.3% |
| audit-baseline | 98.9% | 0.0% | 0.0% | 0.0% |
| split-2 | 92.9% | 67.3% | 28.4% | 27.1% |

原分配仍集中在 CPU 4。职责绑定后四个核心实际承担不同工作。持续跟踪轮中 CPU 4 达 92.9%，显示所在 CPU 6 为 28.4%，采集/录像所在 CPU 7 为 27.1%。这说明该示例分组在本轮没有把采集和录像核心压满；下一步若继续追求稳定 60 fps，主跟踪核心的负载值得优先测量。不能由本轮直接断定其具体瓶颈是 DCF、NanoTrack 预处理或模型推理中的哪一项。

## 绑定、继承与重建检查

- 所有已识别职责线程的绑定与读回返回码为 0，实际掩码与预定单核一致。
- 第一轮 1045、第二轮 1026 个稳定线程样本，共 2071 个样本；全部线程都有入口记录，未发现亲和性相对入口记录发生变化。
- 第二轮进程包含一次长测和三次重启采集，共创建四个跟踪工作线程，均绑定 CPU 4；四个采集线程均绑定 CPU 7。
- 四个录像进程各自启动及创建工作线程时都绑定 CPU 7；显示和 YOLO 长驻线程保持 6、5。
- 三次额外 ON/OFF 全部完成，三个长测进程均正常退出，退出码 0。该检查证明本次线程生命周期可覆盖，不代表已验证异常崩溃、断电或所有第三方库版本。

## 录像与采集边界

三个长测录像分别完成 4503、4547、4517 帧，accepted、encoded、written、synced 一致，dropped=0、cancelled=0。三个短周期分别完成 287、288、288 帧，已接受帧全部写入并同步。其中第一个短周期 cancelled=1，必须保留这一停止边界记录，不能声称所有计数均为零。

第一轮算法队列丢弃 14 帧；原分配累计 sequence_gaps=12；第二轮长测算法队列丢弃 0、sequence_gaps=1。显示和录像验证通过并不意味着相机驱动全轮无任何缺口。本次没有下载并逐帧解码录像，没有目标位置真值，不能据此确认图像内容正确率或跟踪精度。

## 实现建议

可保留“线程入口按职责绑定”的方向。正式实现应通过统一配置指定可用核心及各职责核心，校验在线状态与允许范围，失败时明确报告，并记录实际读回结果。采集重新 ON 和录像新进程启动都必须重复应用策略。不能仅在部署脚本设置一个 4–7 范围，也不能依赖运行后的 TID 顺序。

当前示例把主控制和辅助线程也留在 CPU 4，持续跟踪时该核心接近满载。正式分配应给辅助线程明确策略，并通过更长时间、不同目标大小的负载验证决定是否调整。无需先修改内核 isolcpus 配置；本轮保持该配置就已取得效果。

## 诊断过程与最终恢复

首次短测因独立启动遗漏 AMENT_PREFIX_PATH 而退出，随后修正了测试入口的 ROS 环境加载。第二次仅验证到启动线程，首次 ON 未被新节点收到，未计入有效采集；随后增加 Round starting 确认。第三次短测获得 480 帧有效录像并正常完成，之后才进入三轮长测。失败与空跑日志均保留，没有计入性能表。

辅助库在板端使用 g++ -std=c++17 -Wall -Wextra -Werror -O2 构建通过，实机短测和长测通过。未对未改动的正式工程重跑 CTest；诊断库未运行 clang-tidy/clangd 静态检查。

正式服务已恢复 active，CPUAffinity=4-7，cached-overlay 和阶段计时仍开启。正式进程映射中无 role_affinity.so，配置与二进制哈希未变化。因此本次方案尚未永久部署，原部署性能问题仍可能出现。
