# Design

## Context

外场录像中，目标清晰时跟踪框仍反复消失。需要让修改前后的程序处理同一段输入，自动比较框输出的连续性和恢复开销。动机见 `proposal.md`；可观察要求见 `specs/rk3576-tracking-regression/spec.md`。

原始数据为 `test-01-20260929-1513`，位于外部测试数据目录。录像是 1920×1200 的 H.264 MP4。逐帧日志提供 `pts_us`，即帧在原视频中的整数微秒位置，另有采集时间和驱动帧序号。录像约 60 帧/秒，但帧间隔不完全相同。

代码核对得到以下边界：

- 现有 `src/replay/` 顺序回放逐帧处理，处理结束后等待下一周期。它不复现长调用期间采集继续、随后跳过积压帧的行为。
- 生产节点通过 `waitForLatestFrame()` 取最新帧。异步 YOLO 执行中仍可能接受一个待执行请求；待执行请求槽或未读结果槽占用时会拒绝新请求。结果还可能被覆盖，不能仅凭检测成功数量推断恢复数量。
- `DroneTrackerNode` 支持工厂注入，可只替换输入帧源并复用真实跟踪和发布路径。生产视频帧源目前只接受 MJPEG。
- `src/diagnostics/` 已有更新、请求、结果、历史缓存、初始化、补跟踪及发布调用事件。对应 `add-rk3576-tracking-diagnostic-process` 尚未完成全部验收；本变更实施时必须核对其可用性。
- 当前没有人工框标注。现场约 388 ms 是某次调用的观测值，不是这个截取用例的基线。截取后从空状态开始，也不保证复现现场相同秒点和补帧数量。

本设计只规划新增测试能力。已有跟踪状态机、生产话题、模型处理契约和其他变更的性能门槛保持原要求。

## Goals / Non-Goals

**Goals:**

- 用不可变的像素、时间和姿态输入衡量代码变化。
- 保留真实异步竞争、历史缓存及取最新帧行为。
- 将每轮原始记录保存到新目录，使指标可以重新计算并解释缺失原因。
- 用同一具体生产板上至少三轮合格结果形成冻结基线，自动产生候选与基线对比。

**Non-Goals:**

- 不评价准确率、误跟踪率或框与真实目标的重叠度。
- 不复现全部相机、显示、录像和飞行负载，不宣称回放等价于实飞。
- 不让每个录像帧都必须产生框，不延用上一有效框掩盖空白。
- 不改造既有顺序回放，不把旧流式回放的失败证据当作整片预解码方案验收。

## Decisions

### 1. 用逐帧清单固定素材，保留亮度像素

**选择：** 固定用例名 `wlcb-1513-loss-recovery`。按 `55,000,000 <= pts_us < 75,000,000` 选取原解码序列，得到 1,200 帧。准备工具逐帧解码原视频，保存 8 位灰度亮度平面，使用 FFV1 无损编码存为 `clip.mkv`。FFV1 保证这些解码像素不因再次压缩改变；Matroska 容器的时间精度不作为回放依据。

`frames.jsonl` 每行保存用例帧号、原解码帧号、原驱动序号、原采集时间、`pts_us`、相对片段边界的 `relative_us=pts_us-55,000,000`，以及该帧亮度像素的 SHA-256。SHA-256 是内容校验值，用于检查文件或像素是否改变。`fixture.json` 保存文件校验值、帧数、尺寸、像素格式、准备工具与 FFmpeg 版本。读取路径可变，内容身份不可变。

| 固定属性 | 值 |
|---|---|
| 原视频从零开始的帧号 | 3302～4501 |
| 首帧 `pts_us` / `relative_us` | 55,015,721 / 15,721 |
| 末帧 `pts_us` / `relative_us` | 74,992,663 / 19,992,663 |
| 原 MP4 SHA-256 | `11d45885dc32859c5aba16541ecc83f769ad47ba9ae66b54908b19d805d4c152` |
| `000001.frames.jsonl` SHA-256 | `3faf3d09ede981fb8792679eca2c5113c162abee59def4458e51aae066e03ae0` |
| `000002.frames.jsonl` SHA-256 | `938f931b2ef4c3debb3f820a86634356deaf02fc0154bbcce5f316bc37f265e0` |

源录像相对测试数据根的路径为 `test-01-20260929-1513/session-ac89d6c15b83faf1c92abed84a07ab02/test-01-20260929-1513.mp4`。姿态来自同次测试 ROS bag，即记录 ROS 消息的数据库中的 `/fpv/gimbal`。准备时校验源文件，提取 `[55,75)` 秒姿态及边界前最近一条姿态。保留源 bag 和 `session.json` 的校验值。派生文件校验值在未来实际准备后计算，不在提案阶段编造。

姿态采用生产回调实际使用的消息 `header.stamp`，即消息头携带的时间。通过逐帧日志的 `timestamp_us-pts_us` 核对原视频时间零点，再将姿态消息头时间转换为原视频位置和片段偏移。bag 存储时间仅保留为来源证据，不替代消息头时间。清单保存转换依据；无法确认帧与姿态共享时间基准时拒绝准备正式用例。回放时姿态消息头按同一 `E0` 重映射，姿态内容保持不变。

**理由：** 原帧日志可确定精确集合与间隔，解码亮度符合本用例的灰度处理输入。

**替代方案：** 拒绝按关键帧快速截取、有损重编码及固定 60 fps 重采样。这些方法可能改变边界、像素或帧间隔。

**后果：** 大型视频、模型和运行结果外部保存。仓库只保存准备工具、清单格式、小型测试样例和操作说明。任何输入校验错误均在加载模型前终止。

### 2. 独立实时供帧，只替换生产节点的输入边界

**选择：** 在 `tests/tracking_regression/` 提供测试专用帧源和运行入口。通过工厂注入把该帧源交给 `DroneTrackerNode`；模型、跟踪器、姿态处理和框发布仍采用生产组件。帧源自己的线程按原间隔供帧，不等待 `tracker_->update()` 返回。它复用生产消费者的取最新帧策略，不复制一套跟踪主循环。

用例在同一配置下关闭 OSD、图像可视化和录像，保留框发布；诊断采用 `basic` 模式。OSD 是显示画面上的叠加输出，本用例不以其刷新速度评价跟踪。此配置作为比较条件存档，不能把其耗时直接外推到全部外设开启的现场。

解码采用整片预解码：准备阶段将全部 1,200 帧的 Gray8 亮度像素保存在内存中，移除 256 MiB 缓存上限，不设置替代的固定内存上限。素材原始像素占 2,764,800,000 字节，另需模型、队列及解码器资源。帧源单生产者与生产消费队列的线程假设保持一致。队列容量和供帧迟到预算写入版本化运行配置；配置版本升级为 2，并固定 `input_mode=predecode_all`，旧有限预取配置不可作为新比较组。迟到预算 `max_supply_lateness_us` 必须在首个正式基线前明确设置并冻结；不得根据候选成绩自动放宽。

**理由：** 只有独立推进的输入才能暴露长调用导致的跳帧和检测结果变旧。已测流式解码没有达到原时间供帧要求；2026-10-13 同一 adb 板卡只读查询得到系统可见内存 8,112,044 KiB，足以开展整片缓存方案。每轮记录当时的系统可见、可用内存与进程内存，不把用户所述标称容量当作固定运行证据。

准备顺序为：①校验不可变文件、帧与姿态映射；②只解码一次，在实际缓存像素上逐帧核对 SHA-256；③全部帧验证完成后释放解码资源，记录准备就绪；④加载真实模型；⑤建立回放时钟并按原时间供帧。准备失败、帧数不符、内存分配失败或外部截止发生时，不建立有效回放时钟，不生成合格轮。缓存归帧源所有，供给生产处理的帧使用独立像素副本，避免算法写入修改尚待回放的输入。

**替代方案：** 拒绝修改现有顺序回放或同步逐帧检测；也不为生产视频工厂新增 FFV1/H.264 格式。

**后果：** 测试输入自身的迟到可使轮次不合格。迟到、队列拒收、消费者跳帧和正常处理分别计数。回放不是要求每帧处理的算法准确性测试。

### 3. 保留首帧偏移，分开输入、预测和实际调用时间

**选择：** 整片缓存校验及模型准备完成后建立本轮单调起点 `M0` 和系统时间起点 `E0`。单调时钟不受系统校时影响。第 i 帧计划供给时间为 `M0 + relative_us[i]×1000` 纳秒，帧时间为 `E0 + relative_us[i]` 微秒。初始姿态在起点前装载，后续姿态按同一相对时间推进，禁止提前使用未来样本。

保留生产 `use_history_timestamp=false`、`use_sim_time=false` 的预测语义。`ctx.now_us` 仍是实际调用前读取的时间，不能假装它等于录像帧时间。记录单调时间与系统时间的对应关系，检测系统时间跳变；发生异常的轮次不进入正式比较。

帧源产生 `fixture_frame_id`，即该固定用例内的帧身份。测试记录通过精确时间映射关联实际选中帧，不靠最近时间容差猜测。原驱动序号只是素材来源信息，不冒充本轮真实相机采集序号。请求和结果则用诊断中的请求身份、更新身份关联。

**理由：** 消息的预测时刻早于实际发布，直接以消息时间计算停顿会低估恢复耗时。

**替代方案：** 拒绝首帧归零、`index/fps` 生成时间以及把日志输出时间当成所有阶段的时间。

**后果：** 例如首帧在 15.721 ms 才到期；一次调用在 14.486205 秒开始、14.874 秒发布时，报告同时保留二者。时延使用单调时钟关系计算，而 ROS 消息仍保留其既有时间语义。

### 4. 分层保存原始证据，完整性先于指标优劣

**选择：** 输出按以下层次另存，目录已存在时拒绝覆盖。JSONL 是每行一个 JSON 记录，CSV 是按列组织的数据表。

```text
fixtures/wlcb-1513-loss-recovery/
  fixture.json  clip.mkv  frames.jsonl  attitude.jsonl  algorithm.yaml
runs/<comparison_group>/<run_id>/
  identity.json  preparation.json  input.jsonl  events.bin  events.jsonl
  frames.csv  messages.csv  metrics.json  completion.json
baselines/<baseline_id>/baseline.json
comparisons/<comparison_id>/report.md  comparison.json  comparison.csv
```

帧源保存计划、实际入队、拒收及退出时残留帧身份。诊断导出保留全部事件字段，包括数组和关联身份；不能只导出字段较少的 CSV 然后丢弃信息。框记录由生产更新输出和真实发布调用边界关联，正常发布返回只证明调用完成，不证明订阅端收到。

每轮保留文件校验值及结束清单。结束清单核对 1,200 个输入帧去向、窗口后正常收尾、必要事件成对及诊断健康状态。EOF 是输入结束标记；输入结束后留在队列中而未被选取的帧记为收尾残留，不伪造为已更新。窗口后完成的调用保留原始记录。

诊断缺口、身份歧义、未配对必要事件、发布失败、供帧超预算、解码失败或截止超时均有独立原因。此类轮次保留证据，但不进入正式比较。已有诊断组件若不能提供必要字段，停止正式测量并说明依赖缺失；不悄悄以部分日志替代。

**理由：** 删除慢调用或丢失输出会产生虚假的性能改善。

**替代方案：** 拒绝仅保存摘要、从文件存在推断成功及把未知计为零。

**后果：** 原始事件与计算器版本一起可重算指标。没有发生补跟踪是完整运行的正常结果，不等于缺日志。

### 5. 明确无标注指标的分母、窗口和未完成事件

**选择：** 计算全片 `[0,20)` 秒及核心 `[13.5,17.5)` 秒。除供帧统计按计划输入时间外，运行事件按相对 `M0` 的实际单调时间归入窗口。更新按调用开始，检测按执行开始，发布按调用正常结束归入；时长保留整个已完成调用，不在窗口边界截短。跨度指标则计算与窗口的交集。输出另保留来源帧位置，方便按画面排查，不将其与实际运行窗口混用。

有效发布需同时满足正常返回、跟踪有效、坐标有限及宽高为正。它只表示程序输出有效格式的跟踪框，不表示框在真实目标上。

| 指标 | 计算与单位 |
|---|---|
| `valid_publication_ratio` | 有效发布数 / 正常发布总数；分母为零时 null，并单列总数、有效数及无效数 |
| `max_invalid_span_ms` | 首条无效输出到下一条有效输出的跨度与窗口交集；连续无效消息不重复起算。没有消息单独统计，不推断为无效 |
| `max_no_publication_gap_ms` | 正常发布时间及窗口边界组成的相邻间隔最大值；无消息但完整记录时等于窗口长，未知记录不能这样推断 |
| `clear_count_by_reason` | 实际清空跟踪状态的次数及原因；不把每次未确认检测重复计为清框 |
| `recovery_latency_ms` | 清框实际时间到下一有效发布实际时间；未恢复为 null，另报已等待下界和截断标记 |
| `update_duration_ms` | `UpdateStart` 到配对 `UpdateEnd`；包含调用内初始化和补跟踪，不把嵌套耗时再相加 |
| `frame_age_at_publish_ms` | 实际发布单调时刻减来源帧计划时刻；标识不明则 null |
| `prediction_lag_at_publish_ms` | 实际发布时刻减预测时刻在本轮时钟中的映射；与帧年龄分开 |
| 请求及结果生命周期计数 | 接受、拒绝及理由、执行、完成、读取、覆盖、取消、成功结果缓存未命中；按请求身份计数 |
| `detector_inference_count` | 检测阶段中的实际推理调用数；一次请求可能含局部、全图及分块推理，不与请求次数混算 |
| 初始化及补跟踪 | 分别统计尝试次数、成功失败次数、补帧尝试和成功失败步数；初始化起止、补跟踪阶段及整个恢复调用耗时分开 |
| 帧去向 | 计划供帧、实际入队、供帧迟到、队列拒收、选取、消费者跳过、收尾残留；尽可能按身份核对守恒 |

跨越窗口起点的无效或恢复状态从此前事件继承，跨度只取窗口内部分并标记左侧截断。到窗口终点仍无有效输出时标记右侧截断。未出现过输出的前缀是“尚无输出”，不当作已知无效跟踪。对已结束的恢复延迟取完整耗时，并按清框时刻选择样本；未结束项保留下界，不混入已完成耗时分位数。

每个指标包含 `metric_version`、`unit`、`window`、`sample_count`、`availability` 和 `reason`。状态至少区分可用、没有事件、记录不完整及不适用。真实零次数与空时长样本严格分开。没有补跟踪时计数 0，耗时 null，理由为 `no_event`。

耗时报告样本数、均值、P50/P95/P99 和最大值。P95 是排序后 95% 位置的耗时，用于查看慢调用；分位数使用从一开始的 `ceil(p×N)` 项。跨轮中位数在偶数样本时取中间两值均值。实际更新吞吐率用窗口内更新次数除以窗口秒数，不平均每帧耗时的倒数。

**理由：** 无效消息、没有消息和未知记录对应不同问题。没有标注仍可以比较连续性和调用开销。

**替代方案：** 拒绝按每个录像帧是否有叠框计算实时覆盖率，也不使用检测分数或模型间重叠作为准确率。

**后果：** 输出更连续只能说明有效消息更多。一次候选无须恢复属于合法行为，不强制现场第几帧恢复或补 24 帧。

### 6. 比较条件一致后，显式冻结至少三轮参考结果

**选择：** 每轮独立进程、空跟踪状态、同一模型准备步骤。参考和候选各至少三轮完整合格运行。保存全部尝试，失败轮不进入统计，也不因成绩差而删除合格轮。批次事先固定轮数；只因资格失败补跑时记录原因。首次参考必须重新运行固定 20 秒素材。

比较组由以下条件决定：素材像素与时间、姿态、模型内容、有效算法配置、同一具体板卡、Runtime/驱动及系统库指纹、ROS/OpenCV/FFmpeg 等关键依赖、CPU 策略及亲和性、并发工作负载、观测模式、测试驱动版本、指标格式和计算器版本。程序代码版本允许不同；同时记录提交、未提交差异或源码快照身份及二进制校验值，不能只记提交号而忽略工作区修改。

算法配置从原 `session.json` 的运行身份及记录中冻结，包括 YOLO 检测间隔、丢失阈值、历史缓存和 NanoTrack 参数。不直接复制当前板端可能已修改的配置。模型文件按内容校验值识别，不要求在两版本中具有相同绝对路径。

`baseline.json` 显式引用选定的参考轮及其校验值，不可变更。候选运行只生成新目录；比较命令不具备自动替换基线的行为。换模型、算法参数或板卡时创建新比较组。旧程序如果缺少必要诊断协议，也不能直接与新程序正式比较；需要采用行为不变且同观测模式的参考构建，记录其源码身份。

**理由：** 异步线程会产生轮间变化。至少三轮及各轮范围比单次数字更能显示稳定性；严格身份检查避免把环境变化误认为代码收益。

**替代方案：** 拒绝把现场约 388 ms、完整视频结果或其他 25 帧恢复基准作为本用例基线，拒绝逐帧 CSV 必须一致的判定。

**后果：** 基线是可追溯的实际运行集合，不是历史缺陷的正确行为模板。温度和瞬时频率等运行观测另存，报告波动；固定配置是可比条件，瞬时测量不要求数值完全一致。

### 7. 自动比较聚合值，变化与通过判定分开

**选择：** 比较器先验证基线冻结清单、候选轮资格和比较组身份。条件不符时列出字段差异，返回不可比状态，不输出性能通过结论。条件一致时，每项展示各轮值、跨轮中位数、最小最大范围及差值。

差值为 `candidate - baseline`。非零基线的相对变化为 `100×差值/baseline`。基线零、候选非零时百分比为 null，并显示零基数或新增事件；两者均零时为 0%。比例由 0.80 到 0.90，报告 `+10 个百分点`，相对变化另列 `+12.5%`。缺失或没有事件的耗时不参与数值差值，保留状态变化；不为凑中位数静默删除某轮。

报告同时输出中文 Markdown、JSON 和 CSV。首次基线尚未设置性能门槛时，默认只显示增加、减少、不变或不可比。可另行传入版本化门槛文件，逐项写明比较方向、允许变化及是否必需；没有规则则明确显示“未设置判定规则”，不合成总体分数。输入完整性和运行资格仍必须检查，它们不等于性能门槛。

**理由：** 快了一项但有效输出减少，不能自动宣布整体更好。零基数和空事件在新算法中很常见。

**替代方案：** 拒绝候选自动成为基线、以参考结果绝对相等判定及未经定义的加权质量总分。

**后果：** 示例参考三轮最大发布间隔为 380、400、420 ms，候选为 240、250、270 ms。报告中位数 400→250 ms、差值 -150 ms、相对 -37.5%，并保留两个范围。这是报告示例，不是已测结果或门槛。

### 8. 以隔离实例和外部截止保障可执行性

**选择：** 真实模型正式比较只在同一块 HZ-RK3576_WuKong Board 上执行，使用系统 Runtime 2.3.2 与驱动 0.9.8。工具在独立 ROS 通信域、独立诊断连接和输出目录启动测试，避免与正式节点通信；`ROS_DOMAIN_ID` 表示 ROS 的通信隔离域。并发负载不符时拒绝正式测量，工具不自动停止业务服务；人工执行已授权的隔离测试时必须恢复原服务状态。

每轮由外部控制器从启动开始计总时间，包括文件校验、整片预解码及逐帧校验、模型加载、20 秒输入及收尾。110 秒发出停止请求，120 秒上限前结束隔离实例，所有等待和停止宽限都包含在上限内。超时轮保留已写证据及原因，不把未收尾数据当完整结果。预解码耗时、缓存字节数、进程内存及冷启动和加载时间单列，不混入更新调用耗时。

**理由：** 卡住的模型或线程不能让整批测试无限等待。目标板结果才反映实际 NPU 推理行为。

**替代方案：** 拒绝节点内部单独超时、容器耗时替代实机数据及工具自动修改频率、系统 Runtime 或生产部署指针。

**后果：** 测试构建通过与实机性能结论分别报告。平台协议和数据处理可用小型模拟样例验证，但不能形成真实模型基线。

## Risks / Trade-offs

- **没有标注，可能出现框持续但跟错目标** → 报告只解释运行行为，附原始框供人工复核，不宣称检测质量提升。
- **截取后初始状态改变，原秒点不完全复现** → 所有版本在片段起点清空状态。使用全片及核心窗口，不把现场事件时间作为硬性断言。
- **解码、观测或磁盘写入改变调度** → 回放前完成整片解码和校验，诊断沿用独立写线程，保存供帧迟到与运行负载；观测模式必须一致。
- **异步竞争使三轮差异明显** → 展示各轮值和范围，预定轮数，不挑最好轮；必要时在同一比较组增加预定重复轮数。
- **诊断能力尚未验收** → 实施先验证事件、发布关联和健康标记；能力不足则不生成正式可比结论。
- **测试素材和运行证据较大** → 外部管理并保留不可变清单，仓库只放小样例和工具；不覆盖原数据或基线。
- **用例不包含全部现场负载** → 报告固定测试配置和边界；显示、录像或实飞验收另行进行。

## Migration Plan

1. 完成已有诊断依赖的字段核对和可用性检查，按可选测试目标构建新增工具。
2. 从原录像与日志准备独立素材目录，校验 1,200 帧、逐帧像素、首末偏移和姿态。原始文件保持不变。
3. 在指定生产板的隔离测试目录准备已有模型和冻结配置，检查供帧能力并固定迟到预算。只有用户已授权时允许临时停止正式服务；停止前设置独立恢复保障，结束后恢复原状态。
4. 参考版本执行至少三轮合格回放。显式冻结参考集合，保存板卡、源码、模型、输入及计算器身份。
5. 候选版本按同组条件执行至少三轮合格回放。运行比较器生成新目录，展示全片和核心窗口的差异。
6. 回退时仅重新选择既有参考构建或基线；无需变更生产入口，不能通过覆盖旧证据完成回退。

以上步骤为可复现的执行流程；实施进度以 `tasks.md` 的复选框和验收记录中的实际证据为准。整片预解码方案须重新完成目标板测量，旧流式失败轮保持原身份和状态。
