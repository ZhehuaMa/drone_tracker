# Design

## Context

RK3576 下游当前只能接收整数目标框，不能把目标方向、角速度与同一时刻的框关联起来。本设计增加成对观测，并保留已经运行的相机、HDMI 与 OSD（叠加状态信息）生命周期。动机与选择性移植范围见 [proposal.md](proposal.md)。

来源提交为 `f176960cd6e1e98c5ea341b5fcac856b508b9865`，实施基线为 `7fbb0a2e006f12654a7db0f6d9d152244ec07e0d`。源码检查确认：

- `FrameContext` 使用 `FrameRef` 共享只读帧，时间来自 `timestampUs()`；不使用 Jetson 的 `VPIImageWrapper`。
- `processFrames()` 当前在更新前取系统时间，随后用整数 `realtime_box` 发布框。HDMI 使用同一输入帧的 `display_box`。
- `run()` 与 `trackingLoop()` 是普通轮次、持续 HDMI 轮次的两个启动路径；两处都需要初始化观测状态。
- `control_mutex_` 和显示控制版本拒绝 OFF 后的旧结果。`sourceLoop()` 是持续模式唯一取帧者；跟踪待执行位置最多保存一帧。
- `BagSession` 独占写盘线程，容量为 256 条消息、64 MiB。当前根据 `visualized_result` 注册并记录图像。
- 诊断事件格式为版本 1、每条 256 字节。当前回归工具把 `Output.other_box` 的整数预测框当作实际发布框，按 update 身份配对一次框发布。
- 三个 RK3576 参数模板已有显式像素内参。相机和视频帧源已报告实际交付尺寸；现有配置无需复制 Jetson 的输出缩放公式。

本文的 KF 指卡尔曼滤波器，用于估计并预测框的位置与尺寸。update 身份指一次跟踪更新调用的编号。QoS 指 ROS 的队列与可靠性设置；best-effort 允许丢弃消息，reliable 请求可靠传输，depth 表示队列深度。

现有规格中“当前预测时间”“QoS 不变”和“启用图像时写入 bag”与选定需求冲突。本 change 的四份既有能力 delta 显式替换这些要求；不改写主规格，也不吸收其他进行中的诊断或回放 change。

## Goals / Non-Goals

**Goals:**

- 让框、LOS（目标视线方向）和角速度使用同一几何与参考时间。
- 将算法计算、ROS 消息构造、磁盘记录分开，维持现有设备与线程所有权。
- 用可重算证据区分算法输出、观测抑制、两个发布调用和停止通知。
- 明确消费者迁移与接口验收边界，避免把模拟内参测试当作角度标定验收。

**Non-Goals:**

- 不增加 `enable_preview` 或 ROS 预览线程，不在 ON/OFF 切换时重开持续预览相机。
- 不更换模型、Runtime、驱动、阈值、跟踪仲裁或 CPU 放置策略。
- 不增加独立顺序回放的实时取帧、ROS 发布或新配置要求。
- 不修改 `jetson` 分支；本次新增 ROS 行为只在 RK3576 编译入口启用。公共输出结构可以扩展，原 Jetson 配置路径继续编译检查。

## Decisions

### 1. 复用公共数学计算，保留平台边界

选择：将来源 `target_los.h` 的数学逻辑移入 `src/hybrid_tracker/`；`src/target_observation.h` 负责将结果装入 ROS 消息。公共算法目标不链接 ROS 或硬件 SDK。`TrackerOutput` 增加 `cv::Rect2d observation_box` 和 `reset_los`，保留原整数显示框。

原因：浮点观测需要卡尔曼滤波的原始预测，不能从显示整数反推。替代方案是在 ROS 节点重复预测或复制 Jetson 整个跟踪器；这会丢失 RK3576 的新仲裁实现并引入两套预测。结果是只在既有预测出口补充输出，保留 `306e33b` 等已有来源关联与请求替换语义。

`observation_box` 先按实际帧宽高裁剪，再作为观测依据。有效性要求跟踪有效、四个分量有限、宽高为正。`reset_los` 只在已有成功重锚定导致滤波器重置时置位，不把一般 YOLO 确认当作重锚定。显示仍使用原同帧框，不把未来观测覆盖到更新预览帧。

### 2. 方向和角速度严格使用来源约定

选择：FLU 表示相机的前、左、上三个坐标方向。对中心 `(u,v)` 使用 `r=(1,-(u-cx)/fx,-(v-cy)/fy)`，输出 `pitch=atan2(-r.z,hypot(r.x,r.y))`、`yaw=atan2(r.y,r.x)`。俯仰向下为正，偏航向左为正，单位为 rad；角速度单位为 rad/s。

每个有效样本按以下顺序处理：

1. 用当前相机到世界旋转矩阵，将上一视线及上一滤波速度转换到当前相机系。
2. 计算已消除相机自转的角度差，并用 `atan2(sin(delta),cos(delta))` 处理角度跨界。
3. 用采样间隔求速度，再以 `alpha=1-exp(-dt/tau)` 平滑；`tau=0` 直接使用差分。
4. 保存当前样本；首样本或间隔大于 0.3 秒时速度为零。

原因：仅对像素或相机角度直接差分，会把云台自转当作目标运动。替代方案是未经补偿的差分。代价是必须区分真正缺失的相机姿态与用于保持旧 KF 行为的单位阵；前者不能生成有效 LOS。

### 3. 时间参考必须与姿态配对

选择：新增启动参数 `publish_prediction=false`。默认观测参考时刻为采集时间。开启时，仅当最新姿态满足 `frame <= pose <= now` 且 `now-pose <= 300000 us`，才采用该姿态时间及其旋转；否则回退采集时间和采集姿态。

原因：一个旧姿态不能被重标为当前姿态。替代方案是继续预测到处理开始的系统时间；它与选定 Jetson 协议不等价。结果是 `publish_prediction=true` 也不是旧协议的兼容开关，需要按新协议迁移消费者。

实例：`frame=10.000 s`、`pose=10.030 s`、`now=10.050 s` 时，默认框与 LOS 均用 `10.000 s`；开启预测时均用 `10.030 s`。图像时间始终是 `10.000 s`。推理返回后的真实发布时刻单独记录。

采集姿态继续沿用已有最近邻查询，不新增未批准的姿态年龄阈值；300 ms 限制只约束预测参考选择。姿态不存在时 KF 继续允许既有单位阵回退，但 LOS 标为无效。拒绝非有限或零范数四元数，以及非有效旋转矩阵。

姿态时间相等时忽略重复，倒退时清空姿态历史并清空 LOS 速度历史。单个倒序姿态不能使本轮消息时间倒退；成对发布时间守卫仍有效。真实系统时钟回退不通过伪造时间或自动重置整个算法掩盖：较早观测被抑制并记录原因，操作方可 OFF 后重新 ON。新轮在旧访问结束后清空时间守卫，允许新的时间基准。该限制与恢复步骤须进入运行说明。

### 4. 成对观测是逻辑一致性，不是网络原子事务

选择：消息构造器一次创建 `Detection2D` 和 `TwistStamped`。浮点框中心及宽高进入检测消息；LOS 的 `linear.y/z` 存角度，`angular.y/z` 存角速度，其余分量为零。有效 frame_id 分别为 `camera_frame`、`camera_flu`。

原因：两个独立计算路径容易产生时间或复位不一致。替代方案是分开构造。结果是相同逻辑观测共享时间和内部观测序号，但 ROS 的两个独立话题仍可能分别延迟或失败；正常发布返回也不证明接收。

构造前处理重锚定及失效复位，再检查本轮时间守卫。若时间重复或倒退，整对抑制；状态与调试图像仍按各自规则处理。有效框但无合法旋转时，保留 bbox 的 `camera_frame`，LOS 的 frame_id 为空。无目标时两者 frame_id 均为空。新 ON、目标失效、缺失/非法旋转、成功重锚定及长采样间隙均有明确复位测试。

### 5. 在现有控制边界完成停止通知

选择：构造器、最后时间和停止通知标记由现有 `control_mutex_` 保护。推理和图像映射在锁外。普通 `run()` 和持续 `trackingLoop()` 均在旧访问结束后重置构造器；重复 ON 不重置有效轮次。

锁顺序固定为 control → bag 生命周期 → bag 队列。姿态锁只用于复制姿态、更新历史和记录历史代次变化，释放后才进入控制或记录边界。姿态回退通过代次变化在下次构造前清空 LOS 速度，不在持有姿态锁时修改消息构造器。磁盘线程不持有控制锁，也不在持有队列锁时回调节点，避免反向加锁。

OFF 对已经建立的轮次依次执行：

1. 关闭正常结果接收并使当前显示控制版本失效，清除待执行跟踪任务。
2. 如本轮尚未发送 OFF 通知，构造一对无效消息，时间取 `max(node_now_us,last_stamp_us+1)`，标为控制通知而非帧结果。
3. 在同一顺序边界提交该对记录并启动两个发布调用，然后封存本轮 bag。
4. 继续现有异步模型/记录收尾，健康相机与 HDMI 预览不等待推理或磁盘。

原因：把通知放在 worker 收尾之后会延迟失效，直接让 callback 重置算法会访问在途资源。替代方案是照搬 Jetson 的 stop/join/reopen。结果是增加一个经过允许的无效控制通知；旧 worker 返回后仍被轮次与版本检查拒绝。重复 OFF、首次 ON 前的 OFF 均不制造额外通知。

EOF、设备错误和进程退出保留现有终止处理，不额外引入来源提交没有的周期失效发布。它们结束后不能再启动正常结果发布；最终退出可能没有可用 ROS 通信，不能承诺末条通知必达。

### 6. 用 RK3576 异步队列接入记录变更

选择：扩展 `BagSession` 的话题表，注册原有 gimbal、odom、bbox 和新增 LOS、MAVROS IMU；移除图像注册与提交及构造参数中仅为图像服务的字段。`need_save` 控制 bag，`recording.*` 控制原画面录像，`visualized_result` 只控制有效轮次内的 ROS 调试图像。

成对观测采用一次容量检查、一次持锁追加的双消息提交。每对消耗两条消息额度，按两个消息的总字节数检查 64 MiB 上限；不能把 256 条消息偷换为 256 对。容量不足时两条均计为 attempted/dropped，轮次为 incomplete。普通 IMU 和 odom 沿用单条提交。

原因：分别提交在队列只剩一个位置时会录下半对。替代方案是同步直接写 writer 或无条件分别入队。结果是只保证队列接纳成对；写盘中途失败仍可能留下半对，必须报告 failed/不完整，不能保证存储事务。

`/mavros/imu/data` 的回调保留原消息与 header 时间，只提交 bag，不改变云台历史。新增提交继续使用 bag 生命周期锁；OFF 通知在 seal 前提交。写盘失败、队列溢出和关闭失败继续隔离，不拖停健康跟踪、录像或 HDMI。

### 7. 配置与几何复用 RK3576 契约

选择：在节点头文件及 `rk3576_video_params.yaml`、`rk3576_ar0234_camera_params.yaml`、`rk3576_sc233hgs_production_params.yaml` 增加 `publish_prediction=false`、`los.rate_filter_tau=0.12`。专用 launch 继续只通过 `params_file` 和显式输入配置节点。新增参数运行期修改失败；tau 要求有限且非负。

RK3576 直接复用显式像素内参供 KF 和 LOS 使用，保留非等比的 `fx/fy`。实际 `FrameRef` 尺寸负责裁剪；帧源声明尺寸与交付尺寸一致性由帧源/集成测试核对。不更改传感器输出、不重采样、不按 HDMI 尺寸缩放内参。

原因：Jetson 的尺寸修正针对其原相机封装；RK3576 已有实际像素契约。替代方案是复制缩放公式或默认图像中心。结果是现有生产模拟内参仍可用于接口测试，但不能据此验收物理角度精度。

依赖在根 `CMakeLists.txt` 和 `package.xml` 显式声明 `geometry_msgs`。纯数学测试保留无 ROS 构建能力；消息构造测试使用 ROS 消息头。新增行为通过 RK3576 编译入口接入，原 Jetson 配置检查继续覆盖未启用新 ROS 行为的路径。

### 8. 诊断证据显式升级而不重解释旧字段

选择：保留现有 `Output` 的整数显示/预测字段含义，新增观测载荷与 LOS 发布事件。事件仍为固定 256 字节；使用新格式版本 2，消费者显式识别版本 1 和 2。新增类型追加到枚举末尾，不改旧编号。

新增观测载荷保存内部观测序号、原始纳秒时间、有效性和 double 精度的发布框/LOS 值。既有 `values` 数组可通过无别名违规的位复制存放 double 载荷，分别用 bbox 与 LOS 载荷事件承载。两条载荷使用相同轮次和观测序号；不把 double 强转为整数或仅记录 float 显示框。

框保留原 `PublishStart/End` 作为按 update 配对的帧发布边界，LOS 使用独立发布起止类型。OFF 使用独立控制发布事件和 Control 生产者，避免与 update=0 或跟踪线程的单生产者缓冲混用。重复时间抑制有独立原因，不能记成未消费、无目标或诊断缺口。部分发布失败保留两个调用各自结果。

单生产者缓冲只允许一个指定线程提交记录。控制通知必须使用控制线程的生产者身份，不能借用跟踪线程的身份；测试同时覆盖两类事件的并发对账。

原因：现有 collector 会把每个 update 的第二对 Publish 视为重复，且从整数 Output 推断框。替代方案是静默重解释旧字段。结果是要同步更新 worker、inspector、collector、metrics、schema 与格式说明；旧日志的新字段标为 unavailable，旧 worker 不兼容时诊断降级而业务继续。

回归比较身份增加观测协议版本、时间策略与 tau。旧 current-time 协议和新 capture/pose-time 协议不能自动进入同一正式比较组；可在保留不可比标记的说明性报告中并列查看。不改写旧基线、不以抑制减少消息解释为处理变快。无目标框与无 LOS 独立计数，OFF 通知不进入帧级有效框比例和 FPS（每秒实际消息数）分母。

## Risks / Trade-offs

- [默认时间及可靠性改变会影响下游] → 文档列出时间实例和 best-effort 订阅示例；先做接收端配对与 QoS 检查，再更新生产配置。
- [慢云台使多个帧选择同一姿态，输出频率下降] → 记录 duplicate suppression，分别统计消费量、框发布量与 LOS 发布量，不调整算法阈值掩盖差异。
- [实际校时回退影响单轮单调性] → 保留抑制证据和 OFF/ON 恢复步骤；不自动重标时间，不新增系统校时操作。
- [最近邻姿态可能很旧] → 明示 300 ms 仅用于预测参考，不宣称采集姿态已具备新鲜度保证；精度验收记录姿态条件。
- [双话题或写盘中途失败产生半对] → 分别记录发布成功与失败；队列成对接纳，存储失败保留不完整状态，不能宣称端到端原子性。
- [OFF 并发触发旧轮输出或 bag 越界] → 用现有控制锁确定顺序，按新旧轮阻塞测试验证；不在控制路径等待推理或磁盘。
- [新事件破坏旧日志解析] → 版本 1/2 双读与拒绝未知格式测试，冻结旧基线；格式升级与业务变化单列说明。
- [硬件与标定证据缺失] → 容器只证明构建和无设备逻辑。生产板、模型或录像不可访问时相应任务保持未完成，不借历史验收补齐。

## Migration Plan

1. 先实现公共数学、浮点输出和无设备测试，再接节点时间与双话题，最后接 bag 和新证据格式。每一步保留现有跟踪仲裁测试。
2. 更新三个 RK3576 参数模板、依赖、配置测试与平台说明；明确没有 `enable_preview`。只创建计划，不在 propose 阶段实施这些修改。
3. 执行 `./build.sh --test`，保留所选后端及 ARM64 输出身份。用同一固定输入建立新协议参考，不覆盖旧 current-time 基线。
4. 在指定生产 HZ-RK3576_WuKong Board 使用现有模型完成两个时间模式、记录开关及图像开关检查。持续预览验收包含至少 20 次 ON/OFF、至少 60 秒跟踪/录像/HDMI 联合有效负载，以及启动和最终 OFF 各至少 10 秒预览；每次性能或负载运行总长不超过 180 秒。
5. 保存板卡、程序、配置、模型、输入、Runtime 2.3.2、驱动 0.9.8 和系统库指纹。检查 OFF 清框仍满足 500 ms、无旧轮新发布、资源回收、bag 可读及系统 Runtime 未替换。生产内参为模拟值时只验收接口，不验收真实角度精度。
6. 部署需要后续明确的实施/部署请求。部署前保留上一可运行包与配置。回退须成套恢复二进制、参数及兼容的诊断工具；单改 `publish_prediction=true` 不能恢复旧时间协议。新旧 bag 及诊断证据分别保存，不执行数据回写。
