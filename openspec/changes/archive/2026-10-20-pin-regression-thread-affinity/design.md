# Design

## Context

现有回归能复现恢复耗时波动，但只证明供帧线程绑定在 CPU 4，无法证明更新和补跟踪实际使用哪个核心。预期结果是：回归配置能稳定分开受管工作，并保存足以核对放置和比较成本的证据；性能收益仍由新的实测结果决定。

CPU 亲和性是线程允许执行的核心集合；掩码是该集合的表示。TID 是 Linux 线程标识，PID 是进程标识。`sched_getcpu()` 返回调用时实际执行的核心，与允许集合不同。内核控制组的有效 CPU 集合是操作系统对进程的外部限制，程序不能自行放宽它。

已核对的代码边界：

- `tests/tracking_regression/main.cpp` 很早调用 `cpu_affinity::initializeControl()`，随后完成全部输入解码，再建立节点和模型。
- 节点通过 `cpu_affinity::start(Role::Tracking, ...)` 创建工作线程。该线程在 `DroneTrackerNode::worker()` 中调用帧源 `start()`。
- `RealtimeSource::start()` 此时才创建 `supplier_`。其 `configureSupplier()` 要求 `supplier_cpu` 位于当前继承掩码。因此仅把 Tracking 改成 CPU 5 会使其子供帧线程请求 CPU 4 失败。
- 生产亲和性机制已支持独立角色、启动确认和失败传播。生产 YAML 当前为控制/跟踪 4、YOLO 5、显示 6、采集/录像 7，不适合作为本次测试策略。
- `run_batch.py` 的身份包含实际依赖、CPU 策略及全部顶层回归驱动文件校验值。`compare.py` 与 `baseline.py` 对比较组执行严格一致性检查，不能直接比较不同 CPU 策略。
- `diagnostics::Measurement` 已支持预分配观测及业务结束后导出；原诊断格式仍为 256 字节事件，并有 CRC、事件配对、完整结束和丢失判定。新增位置证据不应改变该协议。

现有生产线程亲和性规格继续适用于生产入口。本设计只扩展 `rk3576-tracking-regression`。公共算法与平台边界沿用 `RK3576_REFACTORING_PLAN.md`；既有 `4871442` 的检测快照、请求/跳过、仲裁顺序保持不变。

## Goals / Non-Goals

**Goals:**

- 为测试独立分配供帧、更新、检测和日志工作，并让创建、就绪、放行、停止均有明确所有权。
- 同时保留请求策略、读回结果及实际执行核心，避免把配置文件当成生效证明。
- 对亲和性差异采用精确、可审计的实验身份规则，保持普通比较和失败门槛。
- 在同一块用户指定板卡完成三个区间、每侧每区间三轮的新对照。

**Non-Goals:**

不修改生产策略、部署、ROS 接口、模型或算法参数。不增加生产线程，不调整实时优先级、调频、内核隔离或 NPU 调度。固定 CPU 不隔离 NPU、缓存及内存带宽争用。未知库内部线程只做观测，不承诺未经验证的固定线程数量或角色归属。不重复 test-02。

## Decisions

### 1. 在现有回归配置中加入可选策略，复用现有生产角色机制

选择在套件 `run.settings` 中增加 `cpu_affinity` 对象。对象使用独立 `version: 1`，支持 `mode: inherit` 与 `mode: role-pinned`。绑定模式明确 `allowed_cpus`、`control_cpu`、`tracking_cpu`、`yolo_cpu`、`logger_cpu`、`supervision_cpus`。既有 `supplier_cpu` 仍是供帧请求的唯一来源。增加独立 `cpu_observation` 对象，声明共同的版本、容量和采样规则，供两侧使用。

公共套件仍为 schema 1，内部运行配置仍为 schema 3，通过增加可选属性保持旧配置有效。新增位置证据及实验清单各有独立 schema 1。原 identity 2、metrics 2 和 comparison 2 的普通路径不变；实验结果保存独立的 `experiment_version: 1` 区段，完整保存两侧原始比较组及清单校验值，不把它们伪装成相同组。

建议绑定值如下：

| 工作 | 绑定值 | 验收范围 |
|---|---:|---|
| 独立供帧 | 4 | 供帧 TID 及实际掩码 |
| 跟踪更新 | 5 | NanoTrack、裁剪、恢复初始化、补跟踪、卡尔曼与本线程发布 |
| YOLO 工作线程 | 6 | CPU 预处理、RKNN 调用及解码后处理的受管入口 |
| 独立诊断日志进程 | 7 | 共享缓冲排空、CRC 和磁盘写入所在进程及其线程 |
| 主线程与单线程 ROS 执行器 | 1 | 主线程实际掩码及执行点 |
| 控制监督和已知 ROS 中间件辅助线程 | 0–3 | 监督进程入口；中间件通常继承控制核心 1，实际逐线程观测 |

选择复用现有 `cpu_affinity::Policy` 和角色启动，而不是引入第二套生产调度接口。测试控制器从已验证快照生成私有、绝对路径的生产格式策略，补齐关闭功能所需的合法占位角色；显示、相机、录像不启动。该文件只传给测试子进程，不写正式部署。外部 `DRONE_TRACKER_CPU_CONFIG` 与显式回归策略冲突时拒绝，不允许环境覆盖快照。省略新策略保持旧路径，包括原先仅指定 `supplier_cpu` 的行为。

后果是生产 API 与默认 YAML 无需变化；配置和实际证据都可以表明本次测试采用另一套分配。相比直接修改正式 YAML，该选择将影响范围限制在回归入口。

### 2. 先创建并停驻供帧，再缩小主线程范围

选择回归专用的提前就绪握手。停驻是已绑定的线程等待条件变量，不执行输入供应。`RealtimeSource` 始终拥有 `supplier_`，析构及失败路径负责唤醒和 join，节点不接管该线程。

绑定模式启动顺序：

1. 在任何缩小范围前记录初始允许集合、在线核心及控制组有效集合。要求配置中的所有目标都在合法初始范围内，并保存证据。创建测试子进程时保留已验证的初始范围；控制监督进程在完成必要子进程创建后将自身限制为 0–3，且在计时放行前核验。
2. 测试主线程仍有初始合法范围时完成全帧解码和像素校验。准备结束后创建供帧线程，让它从该范围继承，按原检查绑定 CPU 4，写出读回并停驻。此时不创建回放时钟，也不调用姿态供应。
3. 主线程才调用控制绑定到 CPU 1，然后构造 ROS 节点及真实模型。已有角色机制让 YOLO 入口确认 CPU 6。ROS 中间件辅助线程通常继承 CPU 1；需逐线程记录，不能据此假定所有库线程都相同。
4. 节点创建 Tracking 线程并确认 CPU 5。帧源 `start()` 复用已就绪的供帧线程，不从 CPU 5 新建 supplier。确认模型、缓存、供帧及必要绑定证据均已就绪后，建立 `m0/e0` 时间映射并放行供帧。
5. EOF、取消或异常都沿既有停止路径通知停驻/运行线程并回收。准备后模型构造失败也必须回收 supplier。

拒绝“只修改角色 YAML”和“删除 supplier 继承范围检查”：前者无法跨 CPU 5/4 启动，后者会掩盖非法 CPU 请求。也不采用定时扫描线程后强制重绑。后果是测试源需要区分“就绪”和“播放”，但真实供应时钟、像素、原帧间隔与队列语义不变。未启用策略时保留原启动时点。

### 3. 有界位置证据独立于原诊断协议

选择在受管入口登记 PID/TID、角色、单调时间、请求和实际集合、调度策略。在更新起止、恢复初始化、每个实际补跟踪步、YOLO 预处理/推理/后处理关键边界及必要发布位置采集执行 CPU。每条记录带轮次和可用的更新/请求身份，不以最近时间猜测关联。

优先将默认关闭的观测接入挂在已有诊断或测量调用点；仅回归配置安装接收器。记录使用按生产者分开的预分配数组，避免多个线程争写同一个索引。初始容量可设每类 262144 条，并在运行前固定；最终容量及精确采样规则进入身份。必要关键点逐次记录，不能抽掉慢更新或补跟踪。热路径不写文件、不动态分配、不扫描 `/proc`、不读取掩码。掩码读回在入口和受控检查时进行，工作点用轻量执行 CPU 查询；导出在业务线程停止后进行。记录写入开销、容量、溢出和丢失计数，任何必要记录溢出使放置证据不合格。

另由现有外部监督进程每秒至多一次扫描节点及日志的 `/proc/PID/task`，并在模型就绪和回放结束前保存快照。每个线程记录读取开始的单调时间，避免整轮扫描跨越绑定登记时点。它记录实际 TID、名称、允许集合、调度及采样时可见的执行 CPU；线程退出竞态须保留而非崩溃。外部 last_cpu 只是离散观测，不能替代受管更新点的证据。八个 FFmpeg 解码线程属于准备阶段；确认解码器已释放，不将其计作计时回放工作。

准备阶段的线程合法继承初始范围；登记时点是角色已绑定并读回的边界。仅对线程读取开始时间不早于其登记时点的快照核对稳定掩码。登记前记录完整保留为准备证据，登记后错误掩码仍失败。旧快照无逐线程时点时沿用其整体时间，不能修写历史失败记录。

拒绝扩大原 256 字节事件或在每步打印日志：这会改变诊断协议或引入磁盘开销。后果是新增独立证据文件、模式和收集校验，但原 CRC、提交同步、生产者序列及正常结束门槛保持完整。对 opaque（无法从公共接口识别职责的）RKNN/OpenCV 内部线程，仅记录实际状态及未知归属，不批量猜测重绑。

### 4. 亲和性实验只允许清单中的精确差异

选择在单文件套件的 `compare.cases.<case_id>` 增加可选 `affinity_experiment` 清单路径。路径像其他输入一样解析、校验、快照并参与输出保护。未提供时完全使用现有比较逻辑。

处理清单在运行前冻结，内容包括：实验版本和身份、未绑定/绑定预期策略、两侧基线提交与源码/二进制/项目库校验值、编译器及构建参数、共同驱动和观测补丁校验值，以及允许差异的精确字段路径和双侧预期值。禁止通配符、整个对象排除及用户任意忽略字段。比较器只接受亲和性策略和经审阅的配套身份差异类别。`cpu_policy` 内的供帧、隔离核、调频信息仍需相同；允许差异仅为声明的角色、主线程/监督/日志范围及相应策略内容校验值。运行配置中的 affinity 字段逐项核对；输入方式、预算、队列等保持相同。

`test_driver.sources` 当前包含所有顶层回归源文件，因此必须保留并逐文件审计其差异。新控制器应作为共同驱动用于两侧；应用源码归属与运行工具身份分开记录。若仍有驱动列表差异，清单保存实际不同的文件名和两侧哈希，且对照冻结的完整补丁确认只包含亲和性行为或共同观测接入。它不能允许 `metrics.py`、诊断事件口径、模型或算法改变。报告输出允许的差异和所有未允许差异；后者仍不可比。基线冻结对同一侧的三轮继续严格一致，不放松运行合格性。

拒绝删除整个 `cpu_policy`、`test_driver` 或 `observation` 后比较。这些对象也保护无关条件。后果是实验报告可解释两侧为何不同，普通版本比较仍会拒绝 CPU 策略不同的运行。

### 5. 固定算法基线加共同观测，比较两个不同构建

选择参考算法基线 `4871442dda37d3d64087fda0b7756692c8f7e473`，在独立源码副本上应用与候选相同的“仅观测补丁”。该补丁只提供 CPU 工作点采样及导出，不含绑定、供帧启动顺序或算法修改。修复后参考必须标为“4871442 算法基线 + 共同观测补丁 + 共同供帧支持修复”，不得称为未经改动的原提交。候选包含本变更亲和性实现、同一观测逻辑和同一供帧支持修复。共同供帧支持补丁与仅观测补丁单独保存。两侧源码树、补丁、二进制及项目库哈希全部保留，使用相同编译器、构建选项和外部依赖。

参考保留旧启动行为：控制、更新、YOLO 和日志不按角色绑定，节点初始允许 0–7；仅 supplier 固定 4。候选启用第 1 节映射。共同观测和控制器不能悄悄把参考固定到 CPU 1 或其他单核。两侧所有受管角色都保存实际状态，参考报告允许范围与实际核心分布，候选核对目标单核。执行两份不同二进制，不能用一份二进制切换配置代替用户要求的对照。

拒绝使用历史九轮当新参考，也拒绝仅靠外部进程采样声称旧参考的精确补跟踪执行 CPU。后果是需要额外的参考观测构建，但能在保持算法来源清晰的同时获得对称的位置证据。若共同补丁涉及算法或调度行为，应修正补丁及身份后重新运行两侧。

### 7. 两侧共同移除计时供帧中的整幅像素分配

首次正式参考轮在 `copyGrayFrame` 内耗时 210.926 毫秒，其中线程实际执行仅 2.506 毫秒。原轮未跟踪内核等待，不能把重叠的 YOLO 预处理直接认定为原因。后续真实管线诊断在同一帧号捕获 `malloc` 扩展存储时的 `mprotect` 等待。`mprotect` 是内核调整进程内存访问权限的系统调用；该调用在 `do_mprotect_pkey` 的内核锁等待中休眠。后续样本约 9.118 毫秒，并未重现原轮的 210 毫秒幅度。

选择增加 `retainGrayFrame`，对已拥有的八位灰度图像（Gray8，每像素一个灰度字节）保留一份只读引用。使用真实 `HostFrame`，即 RK3576 后端原有的图像与时间戳帧对象，不引入冒充后端类型的包装。引用计数使最后一个帧或读取视图释放后才回收像素。该接口拒绝无所有权的外部缓冲区。调用方必须保证所有别名不写像素；回归缓存完成 SHA-256 校验后不再修改，满足该前提。既有 `copyGrayFrame` 和 `copyHostFrame` 继续深复制，生产调用点不变。

供应器继续持有全部 `decoded_` 缓存直到停止，避免改变整个缓存的保留期。每次供应只构造帧元数据并共享对应像素，不再请求约 2.3 MB 的新像素存储。时间戳仍在原时间轴生成，队列仍为 32，拒绝新帧及清理规则不变。帧和读取视图可以在源停止、清空缓存后继续安全读取。小型帧元数据仍可能分配，因此本修复不承诺消除所有内核等待或调度波动。

拒绝预热或延后建钟来隐藏早期帧，也不放宽 50000 微秒供应限制。拒绝把原缓存逐帧移走，因为那会改变缓存保留期及内存分布。共同支持修复必须同时进入参考与候选，参考仍不按角色绑定。旧失败、追踪扰动运行和合格诊断轮全部保留；它们不能替代最终源码重新冻结后的十八轮。

控制验证需同时保存旧、新真实管线的供帧调用耗时、线程 CPU 时间、缺页及内核分配调用。单元检查必须证明计时供应不向 OpenCV 请求像素分配、生产深复制仍独立、保留帧维持实际后端类型、像素/步长/时间戳不变，以及源和帧销毁后的读取视图仍有效。原 210 毫秒等待的具体锁持有者若未直接捕获，报告必须明确该证据限制。

## Risks / Trade-offs

- 提前 supplier 生命周期增加等待状态 → 所有失败分支可唤醒、可 join，增加模型失败、取消和重复停止测试；默认路径保持原行为。
- 内核或外部控制组随时限制 CPU → 启动前及实际入口读回，失败拒绝，不以初始快照授权越过后续内核限制。
- CPU 工作点观测有开销 → 两侧同一接入、固定容量、无热路径文件操作，报告观测成本；不得当作完全无扰动测量。
- 库线程可能不按预期继承 → 清单与快照如实保留，区分受管契约与未知线程；不声称完整线程隔离。
- 调度、NPU 或内存争用仍可导致波动 → 三轮分布和实际恢复工作量同时呈现，不预设正收益。
- 新比较例外可能掩盖条件变化 → 精确双侧值和类别限制，加负向测试，普通比较路径保持严格。
- 验证后发生代码修复使旧结果失效 → 对最终源码和二进制重新执行完整十八轮，不复用修复前结果作最终候选。

## Migration Plan

新增能力仅由回归配置启用，旧配置无需迁移；旧记录继续按原模式只读校验。退出绑定测试后不保留策略进程或系统修改。回滚为禁用新字段并使用旧入口，不修改正式 YAML。

本变更顺序为：完成实现及自动检查，生成完整十八轮证据，再做独立实现/规格验证。若验证只读且未修代码，后续回归步骤核查证据后可复用该十八轮；若验证修代码，必须补做最终版本的完整新比较。规格同步、归档和提交只在这些步骤全部成功后进行，不属于本提案创建阶段。
