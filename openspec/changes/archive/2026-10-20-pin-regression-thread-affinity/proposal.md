# Proposal

## Why

相同录像在多轮回归中出现不同的恢复耗时，但现有记录无法说明跟踪工作实际在哪个 CPU 核心执行，因此不能区分工作量变化与调度影响。需要一个仅由回归配置启用的核心分配方案，并用新的未绑定参考和绑定候选运行验证实际放置及运行代价。

## What Changes

- 增加回归专用、显式启用的 CPU 亲和性策略。亲和性是线程允许执行的 CPU 集合。建议映射为独立供帧 CPU 4、跟踪更新 CPU 5、异步 YOLO 检测 CPU 6、独立诊断日志进程 CPU 7、主线程及 ROS 执行器 CPU 1；控制监督与中间件辅助工作使用 CPU 0–3 范围。
- 调整测试供帧线程的启动握手，先在合法初始范围内创建、绑定并停驻，再缩小控制及跟踪线程范围。停驻指线程已就绪但等待回放放行，不能提前供应任何帧。模型和全部像素验证完成后才建立回放时钟。
- 记录受管入口的进程、线程标识、实际掩码及执行 CPU。受管入口指项目能够直接控制启动或调用位置的工作。跟踪更新、恢复补跟踪及 YOLO 关键点增加有界观测；对 RKNN/OpenCV 等库的内部线程记录实际线程清单与掩码，不假定其线程数或放置。
- 增加显式的亲和性实验比较方式。实验处理维度指此次有意改变的条件，即 CPU 分配。仅接受预先声明并校验的亲和性差异，继续核对输入、模型、算法、具体板卡、依赖、负载、观测工具及指标口径。普通版本比较仍要求 CPU 策略完全一致。
- 对 test-03 的三个既有区间各执行三轮新未绑定参考和三轮新绑定候选，共十八轮。两侧共同修复供帧阶段的重复像素分配：直接持有已验证且不再修改的完整缓存，不在计时供应中再次分配和复制整幅像素。保留零有效框、慢轮及失败轮，不预设性能改善，不将历史记录充作新结果。

例如，之前先把跟踪线程绑定到 CPU 5，再从它创建供帧线程，会使供帧请求 CPU 4 被继承范围检查拒绝。修改后，供帧线程先确认 CPU 4 并等待；跟踪线程确认 CPU 5 后启动原有业务；全部准备就绪才放行原时间轴的输入。

## Capabilities

### New Capabilities

无。回归线程放置和对照比较属于现有回归能力。

### Modified Capabilities

- `rk3576-tracking-regression`：增加回归专用职责分配、安全启动、实际执行证据和受控亲和性实验；明确普通版本比较与实验比较的边界。

## Impact

补充范围包含 `src/platform/rk3576/host_frame.{h,cpp}` 的显式只读存储保留接口。既有生产深复制接口和调用点保持不变。参考标签改为“4871442 算法基线 + 共同观测补丁 + 共同供帧支持修复”，不能再称为仅观测参考。

主要涉及 `tests/tracking_regression/` 的配置、实时供帧、启动控制、身份、收集、比较、模式文件及说明。复用 `src/platform/cpu_affinity.{h,cpp}` 的现有职责机制；仅在必要的公共调用点增加默认关闭的观测接入。独立日志进程复用现有诊断程序，不改诊断事件协议、校验与完整性限制。

生产 `deployment/cpu-affinity.yaml`、默认策略及接口保持兼容。`4871442dda37d3d64087fda0b7756692c8f7e473` 中“先取检测结果快照，再请求或跳过，最后仲裁”的算法行为保持不变。不增加生产线程，不修改模型、NPU 分配、实时优先级、调频、ROS 话题或状态数值。仅使用用户指定的同一块板卡进行新的性能比较；容器检查不代表实机验收。
