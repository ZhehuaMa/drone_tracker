# 实施前发现的设备故障资源决策

检查日期：2026-09-10。变更：`extract-model-execution-backends`。发现时任务进度为 0/25。用户已选择方案 2；本记录中的待选内容仅保留为决策背景，阻塞已解除。

## 问题与证据

任务 2.5 要求在设备结束访问前保留存储。`design.md` 第 4 节还要求“提交后失败必须先结束设备对存储的访问”，并要求析构回收资源。

当前 `src/hybrid_tracker/trt_engine.cpp` 的同步失败分支调用 `cudaStreamDestroy`，随后抛出异常。异常退出会销毁局部输出，调用方也可能释放准备输入的租约。租约是阻止预处理缓存被复用的存储所有权。

NVIDIA 的 [CUDA Runtime API 执行流文档](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__STREAM.html) 说明：如果设备仍在执行流中工作，`cudaStreamDestroy` 会立即返回；执行流资源在工作完成后才释放。因此，该调用本身不能作为应用输入和输出可安全释放的证据。这是静态审查结论，未在 Jetson 上复现设备故障。

已对照 `git show jetson:src/hybrid_tracker/trt_engine.cpp`。参考分支未检查同步返回值，因此也没有可直接迁移的完整故障处置方案。

## 待选择的方案

### 1. 保留故障资源并返回错误（建议）

发生提交或同步错误后，先尝试等待设备工作结束。只有确认设备不再访问存储时，才释放本次输入与输出。

如果无法确认结束，将执行器标记为失效，并保留本次输入租约、输出及相关执行资源。保留期限持续到能够确认安全回收，或进程退出。后续调用返回未就绪，不再次提交推理，不返回部分输出。

需要调整设计：允许失败返回时仍保留未完成访问的资源；明确执行器析构也不能提前释放这批资源。这意味着严重故障后可能占用内存直到进程退出，不能把它描述为普通析构即完成回收。

实现应避免在已经提交工作后才分配保存所有权所需的容器，以免异常路径因分配失败而丢失资源保护。公共模拟测试应覆盖失效状态、输入租约不被复用及不返回部分输出。设备停止与最终释放仍需要后续 Jetson 验证。

### 2. 无法确认设备停止时终止进程

把不可恢复的同步故障升级为进程级故障，由进程退出结束资源生命周期。

该方案需要明确改变故障时的对外行为：节点退出，而不是只返回当前帧失败。它也无法保留当前规格中“后续调用返回未就绪”的路径，因此必须先修改相关设计与规格。

## 暂停范围

两个方案都涉及目前未明确的故障生命周期或行为约定，不作为普通实现细节自行决定。选择后应先同步设计、相关规格与任务说明，再继续实施。

本次未执行编译或测试；未修改生产代码。缺少 Jetson SDK 不是本次暂停原因，原定公共测试及静态审查的验收边界保持不变。

## 已确认决策

2026-09-10 选择方案 2。同步失败无法证明设备停止时，记录模型身份与 CUDA 错误，使用 `std::_Exit(EXIT_FAILURE)` 立即终止进程，避免栈展开或静态析构释放仍可能被设备访问的内存。提交失败但同步成功时可以安全返回失败，同时使实例失效。规划文件已同步，继续原实施任务。
