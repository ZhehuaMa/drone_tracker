# Design

## Context

维护者目前无法把多段录像和各自的选帧范围写进一份配置。新入口需要一次读取明确的用例列表，并完整执行各项选择的帧。背景见 `proposal.md` 的 Why。

现有 `tests/tracking_regression/` 已实现不可变输入、独立实时供帧、原始事件采集及基线比较。不可变输入称为 fixture，即包含片段、帧映射、姿态及校验清单的一组测试文件。基线是显式冻结的参考运行集合，不是现场历史数值。

目前限制散布在多层，不能只增加外层循环：

| 位置 | 已观察到的限制 |
| --- | --- |
| `common.py`、`prepare_fixture.py` | 固定源路径、源校验值、`[55,75)`、1,200 帧及原帧号 |
| `verify_fixture.py`、`schema/` | 固定用例身份、1920×1200、二十秒及首末帧偏移 |
| `realtime_source.*`、`main.cpp` | 固定尺寸、帧数及二十秒供帧结束；模型前整片预解码 |
| `run_batch.py` | 公开命令行传入路径和轮数；控制器固定 110 秒停止、120 秒总截止 |
| `collect.py`、`metrics.py` | 固定输入数量、缓存字节数及 full/core 分析窗口 |
| `baseline.py`、`compare.py`、`identity.py` | 单一用例身份、固定范围和冻结参考集合 |

主规格也明确固定二十秒和 120 秒限制。本变更通过 delta spec 修改这些要求，不把旧限制解释为已经支持任意录像。输入仍需真实逐帧时间、对应姿态和算法配置；本次不推断视频缺失的姿态。

## Goals / Non-Goals

**Goals:**

- 由一份可审查配置确定用例、操作及所有执行参数。
- 严格区分源录像帧选择、选中片段的回放时间和程序外部截止时间。
- 保持各用例输入、状态、基线和证据隔离。
- 沿用整片预解码、实际缓存像素验证和原时序独立供帧。

**Non-Goals:**

- 不改变生产检测、跟踪、姿态补偿或框发布算法。
- 不新增固定内存上限、分块缓存或运行中解码模式。
- 不支持没有必要逐帧时间或姿态记录的视频自动成为正式比较输入。
- 不修改 `build.sh`、SDK 测试脚本或 `rk3576_tracker_replay` 的参数接口。
- 不自动部署、停止生产服务或更换系统 Runtime。

## Decisions

### 1. 单一公开入口及配置快照

**选择：** 新增 `run_suite.py CONFIG.yaml`，把现有准备、运行、冻结和比较功能作为可调用组件复用。`operation` 从 `prepare`、`run`、`freeze`、`compare` 中选择一次显式操作。所有业务参数来自同一文件；公开入口不提供额外覆盖选项。

**理由：** 一份配置能记录输入及操作，避免混用命令行与旧运行配置后无法确认实际条件。

**替代方案：** 给现有全部脚本分别增加一套多用例命令行。它会产生重复解析和多个参数优先级，因此不采用。

**影响：** 旧公开参数接口退出支持，并给出新入口的迁移提示。底层控制器的私有子进程调用不属于用户接口；保持外部监督能力。C++ 测试程序改为读取控制器生成的一份完整运行请求文件，包含 fixture、运行设置、输出和诊断 socket，继续强制校验证书，不能绕过预检。诊断 worker 自身的内部启动协议不改。

新增 Python 配置解析模块使用安全 YAML 解析，接受 YAML 及其 JSON 子集。明确声明 `python3-yaml` 为工具依赖，并在现有 SDK/运行环境检查中验证，不能在普通测试过程中联网安装。拒绝重复键、未知键、非有限数、布尔值冒充数字和不支持的 YAML 自定义类型。整个配置先校验，再创建本次操作输出。源内容的完整校验和生成仍由有界准备操作完成，不要求预检阶段提前解码所有用例。

相对路径统一相对于配置文件目录解析。`case_id`、`suite_id` 和批次标识限制为安全的字母数字、连字符和下划线，禁止作为目录穿越路径。模型定位路径在解析后转为绝对路径，仍以内容校验决定是否为原模型。

以下是计划中的配置形状，示例路径代表外部文件，不表示这些文件已经存在：

加载后保存原始文本、解析结果及其 SHA-256，后者是内容校验值。后续子进程使用保存的快照，不能重新读取外部配置。每轮只接收本用例配置，避免另一个用例的变动污染当前比较条件。

### 2. 使用明确的帧选择区间

**选择：** 字段名固定为 `frame_selection_interval`；显式设置时同时要求 `start_seconds`、`end_seconds`，语义为源录像时间的 `[start,end)`。`start_seconds` 必须是数值；`end_seconds` 可以是数值或精确标记 `end`，后者表示正常录像结束。省略整个字段选择全部帧。null、空对象及单边边界均无效，不能靠漏写终点表达至末尾。

**理由：** 名称直指“哪些帧参加测试”，避免与运行超时混淆。显式区间的两端同时出现，便于审查。

**替代方案：** 使用 `duration` 或将该字段传给超时控制器。前者容易误读，后者会把解码耗时变成选帧条件，均不采用。

**影响：** 配置数字按十进制精确转换到整数微秒，不使用二进制浮点近似决定边界。`end` 在准备阶段使用经过验证的源录像结束时间解析为整数微秒；清单和比较条件使用解析后的数值范围，快照另保留原写法。拒绝负数、非有限数、精度超过整数微秒、数值 `end <= start`、越出视频有效范围、未知终点标记及空选择，不静默钳制终点。

整段模式逐帧解码到正常文件结束，并与源帧日志逐项对应。完整录像边界来自源时间轴和已验证的最后一帧持续时间；可用解码帧持续时间或经核对的流结束信息确定终点。缺少可信终点时拒绝并指明元数据问题，不凭名义帧率补出尾部，也不删去最后一帧。源时间轴起点使用日志与流时间基准核对后的起点，不能把首帧偏移强行消除。

选帧和准备流程：

1. 验证源录像、按配置顺序列出的帧日志及姿态记录具有一致的时间基准。
2. 解析完整录像边界，确定显式区间或整段选择。
3. 按源日志整数 `pts_us` 选择帧，保留原帧号、实际时间和顺序。
4. 从源解码亮度平面生成无损 FFV1 片段，并记录每个选中帧的像素校验值。FFV1 是用于保存像素、不增加压缩损失的视频编码。
5. 选择起点不晚于区间起点的最近姿态，以及区间内的后续姿态；不合成缺失值。
6. 保存不可变 fixture 清单，回读校验，再允许测试运行。

例如 `[55,75)` 仍选择原帧 3302–4501，首帧相对选择起点为 15,721 微秒。另一段录像省略区间时必须选中它自己的首帧至末帧，不读取参考录像的边界常量。

### 3. 把用例元数据贯穿所有校验层

**选择：** 新 fixture 记录用例身份、源校验值、选择模式、已解析起止微秒、完整回放长度、实际尺寸、帧数及窗口。Python 校验、C++ 帧源、采集器、指标计算和基线校验都使用这些经过验证的值。

**理由：** 仅改变准备脚本会被 C++ 的 1,200 帧检查或采集器的固定字节数拒绝；只放宽检查又可能接受缺帧输入。

**替代方案：** 去掉固定断言但不增加元数据一致性校验。它无法区分“新用例”和“旧用例损坏”，因此不采用。

**影响：** 检查必须以该用例清单为准，而不是变成无检查。图像尺寸允许不同，但源和派生亮度尺寸必须一致，算法相机参数必须有效。像素格式继续是 Gray8，即每个像素一个八位亮度值。参考用例保留专用回归断言：源校验、1,200 帧、原帧号及首末偏移仍受测试保护。

`full` 窗口固定为本用例 `[0,D)`，其中 D 是已解析选择范围长度。可选窗口相对于选择起点；保留 `full` 名称并拒绝同名覆盖、负范围及越界窗口。`core` 不再全局默认，参考用例在配置中明确声明原 `[13.5,17.5)`。分位数、发布间隔、有效框比例、无事件 null 等计算公式保持原语义。

### 4. 保持全量预解码及串行资源生命周期

**选择：** 每轮仍在模型加载前把全部选中帧解码到内存并验证实际缓存像素。用例与轮次均串行执行，不增加固定缓存内存上限。

**理由：** 这是现有独立供帧结果的基础，也符合不设置内存 bound 的当前要求。新输入范围不构成授权改变供帧语义。

**替代方案：** 自动切换为流式或有界预取。它将解码竞争加入测量窗口并改变比较条件，因此不采用。

**影响：** 每次轮次使用独立子进程和诊断资源。图像缓存由本轮帧源独占；输入队列中的帧持有自己的像素副本，不能借用已释放缓存。原供帧线程仍是唯一输入生产者，跟踪器仍按生产行为排空积压、处理最新帧。姿态回调只在节点存活期间有效。停止必须唤醒等待、加入线程、排空诊断并释放模型和缓存，再启动下一轮。

缓存字节数按实际帧矩阵累计核对，不使用固定 `2764800000`。不增加人为内存门槛；内存不足、被操作系统终止、校验失败都产生不完整证据。若不能确认进程树已回收，套件停止并标出后续未执行项；不能继续运行并污染后续负载。

### 5. 运行截止独立于帧选择

**选择：** 配置提供独立的正数准备预算 P 和收尾预算 C。准备包括每轮预检、缓存解码及模型加载。已解析片段回放长度为 D 秒。外部控制器在运行前记录准备截止和总截止 `T = P + ceil(D) + C`，绝不把区间的起点、终点或二十秒差值直接当程序超时。

**理由：** 未选择区间的长视频需要完整回放时间，同时失控测试仍需可实施的外部截止。

**替代方案：** 保留所有用例固定 120 秒，或取消外部监督。前者会拒绝本可完成的长输入，后者会失去进程树退出保证，均不采用。

**影响：** 示例 P=90、C=10、D=20 时总截止仍为 120 秒；D=180 时为 280 秒。准备可使用少于 P 的时间，实际回放从完整准备完成后才开始；输入的时间原点和间隔不因剩余预算改变。准备未在 P 内完成即失败。最迟在 T-C 开始强制收尾，所有停止、kill、等待、控制器和完成记录最终化必须包含在 T 内。预算在基线前冻结，不根据候选结果自动放宽。fixture 生成属于独立 `prepare` 操作，每项也使用明确的准备预算，不混入跟踪更新耗时。

这显式替换旧控制器的 110/120 秒常量和旧主规格的统一上限。配置中的 `frame_selection_interval` 不改变任何截止预算。

### 6. 每用例冻结、匹配及汇总

**选择：** 每个用例分别建立至少三次完整合格的参考和候选运行集合。套件汇总只引用各自比较结果，不把不同录像的指标样本拼接。

**理由：** 不同录像长度、目标出现方式和恢复事件不同。跨录像混算会掩盖具体回归。

**替代方案：** 给整个套件一个平均分或将所有帧合并计算分位数。它会使某个用例的失败消失，因此不采用。

**影响：** 输出结构为 `fixtures/<case_id>/`、`runs/<cohort_id>/<case_id>/run-NNN/`、`baselines/<baseline_id>/<case_id>/`、`comparisons/<comparison_id>/<case_id>/` 及套件汇总。每次操作使用全新的目标目录；源和已有输出不能重叠。配置错误在首轮前拒绝；执行错误保留本轮，清理成功后继续既定计划，不自动补选快轮或重试。

比较条件保存本用例像素、源时序、规范化区间、姿态、算法、模型、窗口、截止预算及既有平台和负载身份。原配置文本、路径、操作、输出位置及其他用例列表属于来源记录，不让无关用例改变当前用例可比性。省略区间及显式完整范围若解析为同一帧集合和时间范围，可以有相同的有效输入身份；原写法仍保留在配置快照中。

用例按 `case_id` 和内容匹配，不能按列表位置匹配。不同套件执行顺序记录为运行上下文；每项仍必须通过既有 CPU、负载及观测检查，不宣称顺序改变没有热状态影响。缺少或新增用例均在汇总列出。缺失、不可比、不完整或未设置门槛不能产生整个套件通过结论；同时保留“操作执行成功”和“性能判定通过”的区别。

### 7. 版本和迁移边界

**选择：** 新 suite 配置从版本 1 开始；新逐轮运行配置从现有版本 2 升为 3。需要改变结构的 fixture、准备、身份、完成、指标容器、基线及比较记录各从现有版本 1 升为 2。原始诊断事件协议和未改变的指标公式版本保持原值。新增显式旧格式只读分支。

**理由：** 固定二十秒证据与新可变范围不能仅靠字段缺省混同。结构版本和公式版本分别记录，便于审查含义是否改变。

**替代方案：** 直接覆盖旧 JSON 结构约束或原基线文件。它会破坏已经冻结的证据，因此不采用。

**影响：** 旧记录只能按原固定用例规则验证和读取，未知版本拒绝。新旧版本运行不能未经显式证明混入一个正式集合；本次不实现跨版本自动转换。参考用例可以用新入口重跑并冻结新组，历史基线保持原样。文档保留历史验收日期及范围，不能把新功能存在误写为已在生产板验收。

### 8. 明确测试供帧线程的 CPU 放置

**选择：** 新运行设置允许可选的 `supplier_cpu`，即仅供帧线程使用的一个 CPU 编号。省略时保留继承行为。配置中的编号进入比较条件；板端预检要求该 CPU 在线且属于控制器允许集合。线程在建立回放时钟前设置并回读自身 CPU 亲和性。亲和性表示操作系统允许线程运行的 CPU 集合。实际线程编号、策略及 CPU 集合另存为 `source-scheduling.json`。设置失败不得启动回放，也不得静默回退。

**理由：** 2026-10-16 现场内核参数将 CPU 4–7 从普通负载均衡中隔离。原先的 `0-7` 允许集合不能证明供帧线程会获得这些核心。供帧线程应可单独使用明确的可用核心，避免跟踪计算竞争使供帧超限。

**替代方案：** 放宽 50 毫秒、提前记录供帧时间、改变录像时钟，或将整个跟踪进程改到其他 CPU。前几项破坏输入有效性；最后一项同时改变被测计算条件，均不采用。

**影响：** 设置只作用于测试供帧线程，不修改生产策略、频率、跟踪线程或模型。固定新条件后必须新建参考和候选集合。诊断使用同一二进制、真实输入和固定 CPU 竞争负载对照继承与单线程放置，保存失败及操作系统调度证据。旧日志没有这些分段证据，因此不能声称已证明旧两次事件的唯一原因。正式十八轮不运行人工竞争负载；仍逐帧检查原 50,000 微秒限制、完整输入和独立截止。

## Risks / Trade-offs

- [长片段缓存可能超过生产板内存] → 保持无固定内存上限；记录计划帧数、实际缓存字节及内存观测。失败不自动截短或改变输入模式。
- [整段录像的尾部长度或初始姿态无法确认] → 准备阶段核对元数据并明确拒绝缺失输入，不根据名义帧率或模拟姿态伪造完整运行。
- [指定叠框录像目前不在本机，配套数据尚未核对] → 实施任务明确交付四项配置并核验真实来源、末帧及时间映射。无法访问时保留待执行状态，不用其他录像替代。
- [输入数量及统计窗口的常量遗漏] → 对准备、C++ 供帧、完整性、指标、基线各层增加不同帧数和长度的验证，保留参考用例精确断言。
- [配置或文件在两阶段之间变化] → 保存快照、内容校验和预检证书；C++ 启动后仍重新核对绑定内容。
- [多个用例串行失败后残留进程污染负载] → 外部进程树回收后才进入下一项；回收失败停止计划。
- [新字段掩盖旧基线含义] → 分版本只读处理旧证据，新结果进入新比较组。
- [主机缺少生产板访问] → 无设备测试只证明工具契约；实机任务独立保留，不能用 QEMU 运行替代真实性能结论。
