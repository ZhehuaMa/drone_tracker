## Context

开发板 2 的 FP16 气球模型在初始化时被拒绝。本设计让兼容模型进入现有检测与跟踪链路，并验证图像只归一化一次。动机与范围见 proposal.md。

FP16 是十六位浮点数；INT8 是八位整数。模型输入类型与应用提交缓冲类型可以不同。当前 `rknn_yolo_contract.cpp` 将输入限定为 INT8、NHWC `[1,640,640,3]`、zp=-128、scale=1/255。NHWC 是批次、高、宽、通道排列。`rknn_runtime.cpp` 实际提交 UINT8 图像；UINT8 表示无符号八位整数。`rknn_session.cpp` 已支持 FP16 属性、非直通输入转换和浮点输出获取。

2026-09-16 在开发板 2 只读检查了 `/home/firefly/Desktop/models/balloon_best_zoo6_fp16.rknn`，部署目录中的同名文件是指向它的符号链接。其 SHA-256 为 `69fd2fb4753b4fcd91820acd54fc648b82a74a4ec37a5459a8bb3f42b1f2b232`。文件可读元数据包含 mean=[0,0,0]、std=[255,255,255]、rgb2bgr=False。编译输入为 FP16 NHWC；用户提供的 Runtime 2.3.2 日志报告 AFFINE、zp=0、scale=1。六个输出尺寸符合单类别检测结构。此证据只确认文件记录的配置，不代表数值对照或检测质量已经通过。

现有主规格仅允许 INT8，且生命周期条款保留 Runtime 2.3.0。本 change 明确扩展输入契约并采用项目当前的 Runtime 2.3.2、驱动 0.9.8 基线。主规格中独立工具阶段的历史平台描述不在本次改写范围，实际集成复用当前生产工厂。

## Goals / Non-Goals

**Goals:**
- 以最小生产代码改动接入 FP16 输入，保持现有图像和输出接口。
- 为模型结构、数值语义和集成行为提供分别可审查的证据。

**Non-Goals:**
- 不增加动态形状、Float32 原生 YOLO 输入、彩色处理或可配置归一化。
- 不修改 NanoTrack、检测阈值、状态机、线程边界、ROS 接口或资源所有权。
- 不重新转换或训练模型，不提交模型二进制，不将性能或检测质量提升作为本次承诺。

## Decisions

### 1. 在 YOLO 专属校验中按类型分支

选择：公共部分检查输入数量、尺寸、NHWC 布局和六输出结构；INT8 分支保留原 scale/zp 检查；FP16 分支接受通用会话认可的 NONE/AFFINE 标记，不约束其整数 scale/zp。其他类型明确拒绝。

原因：通用会话已检查字节数、元素数量与合法表示。选择只扩展已明确需要的 FP16 输入。

未采用：删除所有输入类型检查，或顺带开放 Float32 输入。后果：原 INT8 不兼容模型仍被拒绝，新增支持范围可由少量测试完整覆盖。

### 2. 共用 UINT8 非直通提交和 Float32 输出

选择：保留 `yoloContract()`、`ByteInput` 及 `RknnRuntime::execute()` 的 UINT8 提交。`pass_through=0` 表示由 Runtime 按模型要求转换，不直接把缓冲当成模型原生编码。保留 `want_float=1`，即请求 SDK 返回 Float32（三十二位浮点）输出。

原因：预处理已经生成正确尺寸和数值范围，通用会话允许提交类型不同于模型类型。模型原生 FP16 的 2,457,600 字节不应替代程序 UINT8 缓冲的 1,228,800 字节。

未采用：应用程序手动归一化并提交 FP16，或新建专用推理路径。后果：无需新增半精度转换和缓冲管理，也不改变异步检测输入的所有权。

输入过程示例：
1. Gray8（每像素一个八位灰度值）图像经等比例缩放和补边到 640×640，补边值 114。
2. 灰度复制为三个相同通道，像素 150 仍为 UINT8 的 150。
3. RKNN 按 mean=0/std=255 配置处理，数值含义约为 0.588235。
4. 模型以 FP16 表示并计算，输出通过 SDK 转为 Float32 后进入现有解码。

这描述等效数值过程，不要求 SDK 分配某种中间数组或固定内部运算顺序。

### 3. 归一化作为兼容契约和独立验证项

选择：使用说明要求模型提供方保证 mean=0/std=255，并由转换记录、模型元数据和固定输入对照支持该结论。生产代码不解析私有文件结构。描述输出明确区分“查询到的属性”与“兼容要求”。

原因：普通输入属性不足以可靠证明 mean/std。FP16 的 AFFINE 标记也不表示应套用整数反量化。

未采用：依赖字符串扫描作为生产验证器，或按输出范围自动猜测归一化。后果：结构符合但数值语义不符的模型仍可能通过初始化，不能将加载成功表述为完整兼容证明。

### 4. 用分层验证约束接入风险

选择：扩展 `rknn_runtime_test.cpp` 的模拟 SDK 属性参数，并在 `tracker_assembly_test.cpp` 加入 FP16 YOLO 完整装配用例。模拟回调检查 UINT8/NHWC/pass_through=0、字节数和实际像素值，覆盖 0、114、150、255。覆盖 FP16 NONE/AFFINE、非法输入类型/形状/布局、INT8 非法参数和既有错误回收用例。

实机在开发板 2 先独立推理，再数值对照，最后固定样本检测和相机集成。两种参考方式按可用证据选择：
- 优先使用与该 RKNN 对应的六输出 ONNX，输入为同一预处理图像除以 255 后的 Float32。必须先核实模型来源和输出角色，不能仅凭同目录文件名认定对应。
- 缺少对应 ONNX 时，使用同一 RKNN 的归一化 FP16 直通输入。验证工具应按实际查询属性准备布局和大小，不改变生产提交路径。该对照只证明两条输入路径一致，不证明转换前后网络等价。

数值判定前，将参考路径、各输出的绝对/相对误差容差及选择依据写入验证记录。先确定容差再判定，不在失败后无依据放宽。报告最大绝对误差、平均绝对误差及相对误差的分母处理方式。至少使用非均匀固定图像；常量像素可补充覆盖数值端点，不能替代真实样本。

未采用：只检查加载成功，或要求 FP16 与 Float32 逐位相等。后果：允许有依据的浮点误差，同时能发现重复归一化、通道错误和输入字节数错误。无法得到可靠参考或真实目标样本时，相关验收保留未完成。

## Risks / Trade-offs

- FP16 模型缺少可确认的归一化来源 → 明确兼容前提，以固定输入对照补充证据，不自动推测。
- 测试替身不执行真实 SDK 转换 → 单元测试只声明提交正确，归一化必须实机验证。
- 相机输入是复制三通道的灰度，而原模型可能按彩色训练 → 保持现有语义，独立报告灰度检测效果，不通过修改阈值掩盖问题。
- 非均匀输入的 FP16 舍入影响输出 → 判定前记录参考方法与容差，不把不同精度输出差异直接判为代码错误。
- 历史模型或链接目标可能变化 → 实施前重新记录目标板模型哈希；本文指纹仅用于追溯，不是白名单。
- 容器 SDK 与实机版本不同 → 构建按 AGENTS.local.md，实机以 2.3.2/0.9.8 为准，不用容器结果替代 NPU 验证。

1. 完成契约和诊断改动，扩展测试与使用说明。
2. 按 AGENTS.local.md 执行 `./build.sh --test`，保存构建和测试结果。
3. 在开发板 2 使用隔离的测试产物验证原模型，记录文件指纹，不覆盖系统 RKNN 库。
4. 完成数值对照、类别 0 的固定样本检测、与现有 NanoTrack 的相机集成，并回归旧 INT8 模型。
5. 验证后替换部署二进制；模型路径可保持原 FP16 路径。若回滚二进制，须同时恢复兼容 INT8 模型路径，因为旧版本会拒绝 FP16。

实施结果记录在本 change 的 validation.md。只有检查实际完成才勾选任务；前序回放变更中未完成的质量验收不因本变更通过而自动完成。
