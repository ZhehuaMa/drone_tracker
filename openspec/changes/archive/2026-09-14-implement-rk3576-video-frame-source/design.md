## Context

RK3576 缺少能持续供帧的生产视频入口，已有独立回放在处理慢时整体放慢。本变更将已有队列式视频输入移植到 RK3576，动机见 proposal.md。

已核对 `src/mv_camera/mv_video.cpp`、`mjpeg_writer.cpp`、Jetson 工厂及 `git show jetson:src/mv_camera/mv_video.cpp`：源实现只接收 MJPEG，将 JPEG 的亮度分量写入灰度图，并按视频 PTS（显示时间）累计值生成帧时间。录像器把绝对微秒基准写入容器 `Artist` 元数据。源代码存在包引用未及时释放、正常结尾运行标志不更新、重启不重新定位等边界问题，这些不是应复制的正确行为。

已有 `FrameSource` 公共接口、`waitForLatestFrame()` 消费逻辑与 RK3576 `copyGrayFrame()` 可直接复用。`MVCameraBase` 包含 VPI 类型，不能作为 RK3576 的基类。现有队列使用构造参数 30，内部按块分配，不等于严格容量 30。

## Goals / Non-Goals

**Goals:**
- 提供可由现有公共消费循环使用的生产视频帧源，单独验证时间、像素及生命周期。
- 将从头重启、非法时间拒绝和可靠停止定义为 RK3576 的明确行为。
- 通过可注入读取器和时钟测试并发边界，不让测试依赖 YOLO 检测效果。

**Non-Goals:**
- 不继承 Jetson 采集基类，不移动或修复 Jetson 实现。
- 不接入 ROS，不验证跟踪器跨轮复位、旋转补偿或模型质量。
- 不把 `ReplayReader` 改为队列读取，不扩展其配置。

## Decisions

### 1. 使用独立的软件视频目标

选择新增 `Rk3576VideoFrameSource` 实现 `FrameSource`，内部由 `MjpegVideoReader` 读取本地普通文件。使用 FFmpeg 的 avformat/avcodec/avutil 处理容器与包，使用 JPEG 库解码，OpenCV 仅承载主机图像。首个视频流必须为 MJPEG；音频包跳过。支持本仓库生成的 MOV/MJPEG，以及可被同一读取路径解析的合法 MJPEG 容器，不按扩展名判定格式。

拒绝复用 OpenCV `ReplayReader`，因为其接口没有帧 PTS 和历史时间元数据；也不链接 `mv_camera`，避免引入 Jetson 依赖。后果是保留两种读取器，公共消费接口保持原样。

只接受本地普通文件，不接受 URL、管道或设备。建立 FFmpeg 上下文后先安装停止中断检查，再打开文件。阻塞文件系统调用仍不承诺可被强制中断；测试中的等待必须有界，不能以强制销毁线程正在使用的对象换取退出。

### 2. 输出原尺寸的 JPEG 亮度

选择支持八位灰度 JPEG 及常见八位 YCbCr JPEG（灰度或 4:2:0、4:2:2、4:4:4 采样）；YCbCr 中 Y 是亮度，另外两个分量保存颜色。输出 Y 的有效宽高区域，保持原始尺寸与数值范围，不先转 BGR，不做范围拉伸。其他颜色编码、位深或采样返回不支持的诊断。视频配置中的相机宽高、fps、翻转、镜像继续忽略，符合 Jetson 视频路径；`getImageSize()` 返回实际解码尺寸。

JPEG 解码器使用每实例局部缓冲区，完整处理 MCU 边缘填充。MCU 是 JPEG 按块解码的最小单元，非整块尺寸必须只复制有效像素。固定使用与对照一致的整数 IDCT 设置；IDCT 是把压缩系数还原成像素的步骤。以相同 JPEG 数据的独立亮度解码作为逐像素一致性门槛；不能把这称为未经实机运行的 Jetson 等价性证明。

选择复用 `copyGrayFrame()` 深拷贝形成不可变主机帧。拒绝借用可覆盖的解码内存，也不移植旧 VPI/NvBuffer 分配。后果是首版多一次明确的像素复制，换取可验证的所有权。

### 3. 时间戳和播放时钟分离

帧时间使用 `base_us + pts_us`，PTS 通过视频流 time_base 换算成微秒。换算、加法和等待截止时间全部检查溢出；范围限定为正的 int64 微秒，便于下游安全使用。首帧 PTS 可为零，非零偏移保留；后续换算后的 PTS 必须严格递增。缺失、负值和重复时间均失败，不以 fps 猜测补齐。

历史模式严格解析 `Artist` 为正的十进制 int64 微秒基准；字段名按不区分大小写匹配，歧义或非法值拒绝。实时模式忽略该元数据，在本轮工作线程启动前记录 system_clock 微秒基准。播放等待另取同轮 steady_clock 起点，截止时刻为 `steady_origin + pts_us`，系统时间调整不会改变播放节奏。

例如，基准 1700000000000000、PTS 100000 得到 1700000000100000 微秒，并在本轮单调起点后 100 ms 供帧。首帧 PTS 为零时立即可供帧。解码已落后则不再等待，后续按原时间表继续，允许追赶；不额外加一帧间隔，也不主动跳过压缩帧。积压由现有队列策略处理。

选择可注入时钟与可中断的条件变量等待。拒绝沿用不可打断的 sleep_until 和 high_resolution_clock 的隐含 epoch 假设。后果是停止可立即唤醒长 PTS 等待，历史与实时模式只改变帧时间基准。

### 4. 一个生产线程与现有队列

使用 `BlockingReaderWriterQueue<FrameRef>`，沿用构造参数 30 和 `try_enqueue()`，禁止自动扩容入队。它是 SPSC 队列，即运行期间只有一个线程入队、一个线程出队。满队列时丢弃当前新帧，生产者不得取旧帧腾位置。消费者继续使用 `waitForLatestFrame()`。

控制方法 start/stop 由一个控制方串行调用。首次 start 或再次 start 前，调用方保证没有取帧调用进行中；析构前保证消费者退出。stop 可以与单一消费者取帧并发，但只停止生产，不清空队列。start 在旧生产线程已 join 且消费者静止后清空旧队列、重新建立新队列实例，避免跨轮残留或并发清理。join 表示等待线程真正退出。

`waitFrame()` 沿用队列限时等待，超时上限由传入参数决定；stop 不新增提前唤醒消费者的保证。`tryFrame()` 非阻塞。两者返回 false 时清空输出。正常读完后允许取完尾帧；`isRunning()==false` 只说明生产已停止，不表示队列已空。

拒绝额外中转队列和控制线程代替消费者排空运行队列。后果是保持现有生产/消费假设，停止与重新启动的调用前置条件需明确文档化。

### 5. 每轮从头播放，重建文件读取状态

创建时打开文件并验证首帧，保存该帧的灰度像素和 PTS，供首次 start 交付；创建不启动线程。这样 getImageSize 可以在 start 前使用。后续 start 重新打开并预读首帧，拒绝与初次尺寸不同的文件；不使用 seek 恢复旧解码状态。start 前置校验失败返回 false，不启动线程。

状态为 Ready、Running、Stopped、Eof、Failed，分别表示可启动、生产中、主动停止、读完和失败。只有 Running 的 isRunning 为 true；运行中再次 start 返回 false。其他状态可尝试 start，成功后进入 Running。每轮重置 PTS 检查、统计和时间基准。

停止顺序为设置停止标记、唤醒播放等待、等待生产线程、保留队列中已交付帧。重复 stop 成功。自然结束或失败时线程设置状态并退出，但对象仍负责 join；不能仅在 Running 时 join。线程启动抛异常时清理本轮读取状态并返回 false。

用户已明确选择从头重启。拒绝隐式续播或正常结尾自动循环。历史模式重启会再次产生相同录像时间；本次只保证帧源不混入旧队列，调用方后续必须单独处理跟踪器复位。

### 6. 失败诊断与资源管理

读取器区分正常解复用 EOF、读取错误、JPEG 解码错误、时间错误及尺寸变化。EOF 表示容器读取器正常结束，不证明文件绝对完整；不靠声明帧数声称排除所有截断。明显损坏 JPEG 或读取负错误码不记 EOF。错误停止当前轮，下一次 start 可从头重试。

公共 FrameSource 方法签名保持不变。初始化诊断使用 PlatformResult，运行诊断通过平台内部可注入回调记录状态、路径、帧序号、PTS、底层原因，以及每轮读取/入队/满队列丢弃计数。测试可以观察该内部快照，不依赖解析随意日志文本。生产默认日志输出线程安全；诊断不得抛异常逃逸工作线程。返回 false 本身仍无法区分超时与结尾，明确保留这一公共接口限制。

资源按所有权封装：每个包在下一次读取前释放引用，包括非视频包；文件、解码器和缓冲区只在工作线程结束后销毁。JPEG 错误处理转换为普通失败，不直接 exit。若库错误机制需要跳转，限制在不跨越 C++ 析构对象的薄适配边界，显式回收分配资源。

拒绝照搬静态像素数组、进程终止式 JPEG 错误处理及只依赖运行标志的析构。后果是坏文件能作为普通测试输入，已交付帧不依赖文件或工厂存活。

### 7. 工厂、构建和验证入口

工厂对 Video 创建真实帧源，对 Camera 保持不支持。视频帧源目标独立声明软件依赖，不反向链接 RKNN。现有 RK3576 独立顶层配置仍要求 ARM64/RKNN SDK；这不意味着视频测试需要加载模型或设备执行。公共测试的纯模拟部分继续无需设备。实现时更新 assembly 测试原有“相机和视频均拒绝”断言。

新增专用测试驱动，经真实工厂、FrameSource 和 waitForLatestFrame 运行正常及慢消费者，记录像素摘要、帧时间、轮次和结束原因。不扩展原回放命令，也不增加面向用户的第二套跟踪程序。拒绝为此开放根目录 ROS 构建或加载真实模型。结果是验收完全不受 YOLO 质量阻塞。

### 8. 与尚未归档变更的规格协调

当前主规格的公共帧源条款需要增加 RK3576 从头重启的例外。本变更修改完整条款并追加视频可用性要求。前序 `assemble-rk3576-tracker-replay` 的未同步 delta 仍有“独立装配不宣称生产帧源可用”，包含拒绝视频的旧限制。

选择保留旧变更及验收记录不动。在后续规格同步阶段，先保留前序非冲突的模型装配与回放要求，再应用本变更；协调旧限制为“拒绝相机，视频按 rk3576-video-frame-source 提供，根目录构建仍拒绝 rk3576”。若旧变更晚归档，必须先处理同一冲突，不能机械追加旧拒绝条款。不得因新帧源完成而勾选前序质量验收。拒绝现在修改主规格或伪造前序完成，后果是同步/归档时有明确需审核的冲突点。

## Risks / Trade-offs

- JPEG 解码库版本及 IDCT 设置影响像素 → 固定设置并记录版本，用相同压缩包逐像素对照；Jetson 实机未执行时单独注明。
- 历史时间重启重复 → 每轮独立验收，后续调用方负责重置算法状态，不在本次承诺整套 ON/OFF 正确性。
- 异常 PTS 间隔可能很长 → 等待可被 stop 中断，不设未经确认的间隔上限。
- 本地文件系统可能阻塞 → 限定普通文件，设置可用的中断回调，记录超时失败，不强行释放仍在访问的资源。
- 缺少 MJPEG 或依赖 → 生成小型可复现素材并核对现有容器软件库；不重建约定镜像，不用其他编码冒充覆盖。
- 像素拷贝消耗 CPU → 先验证正确性，记录耗时；本次无吞吐或零拷贝优化目标。

## Migration Plan

1. 实现读取、像素与时间边界及可控测试，再实现线程、队列和重启。
2. 接通工厂及独立构建，运行公共回归与真实文件测试。
3. 在约定 ARM64 容器构建；RK3576 实机执行慢消费、重启和资源验证，记录证据。
4. 更新平台使用说明和迁移计划，明确保留 ReplayReader，核验 delta 与实现一致。
5. 不在本次实施中自动归档。同步时按上述冲突规则审查；回退则停用新增帧源并恢复工厂对 Video 的拒绝，原独立回放继续可用。
