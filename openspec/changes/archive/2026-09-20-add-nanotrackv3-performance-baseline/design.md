## Context

现有工具不能完整测量从解码到跟踪结果的处理成本，也不能从原始记录定位各阶段开销。本设计在保留当前算法和模型数据交接方式的前提下增加可复查的性能测量；动机见 `proposal.md`。

已检查的实现边界：

- `src/platform/rk3576/rk3576_nanotrack_probe.cpp` 在视频读取后开始计时，且采用 OpenCV 彩色转灰度路径。
- `mjpeg_video_reader.cpp` 使用 FFmpeg 解封装，即从容器取出压缩帧；随后使用 JPEG 库直接输出亮度。其构造函数会提前解码并缓存首帧。
- `nanotrack_preprocessor.cpp` 先把整幅 Gray8（每像素八位灰度）转为 Float32（32 位浮点），再填充、裁剪、线性缩放和复制通道。
- `rknn_nanotrack_backend.cpp` 保留模板特征，逐帧运行搜索 backbone 和 head。Backbone 提取图像特征，head 比较模板与搜索特征。
- `rknn_session.cpp` 使用 Float32 提交，`pass_through=0`；以 `want_float=1` 取得输出，再复制为主机存储。成功取得输出是本实现确认结果完成的边界。
- `src/hybrid_tracker/nano_tracker.cpp` 负责公共前后处理和目标状态更新。现有可注入后端与前处理器、RKNN 模拟 API、JPEG 测试素材可用于无设备测试。

FP16 表示 16 位浮点模型。模型采用 FP16 不意味着 CPU 前后处理或模型间交接也改成 FP16。已存在的相关规格保持有效，本次仅新增性能测试能力。迁移架构继续遵循 `RK3576_REFACTORING_PLAN.md` 的公共算法与平台后端边界。

## Goals / Non-Goals

**Goals:**

- 使用真实复用代码完成 NanoTrackV3 解码至结果的顺序处理基线。
- 获得可重算、可归因、可区分预热与初始化的测量数据。
- 以相同输入下的框、分数和调用次数验证观测接口没有改变行为。

**Non-Goals:**

- 不包含 YOLO、DCF、卡尔曼滤波或 ROS 消息发布，不执行完整 HybridTracker 管线。
- 不测文件读取或解封装性能，不提供 `read_to_result`、`read_demux` 或墙钟吞吐率。
- 不引入硬件解码、零拷贝、异步流水线、模型转换或算法优化。
- 不将性能完成解释为跟踪质量、Jetson 等价性或实时相机系统验收通过。

## Decisions

### 1. 独立 C++ 程序复用现有算法

选择在 `tests/nanotracev3_performance_benchmarks/baseline` 提供 C++17 程序、配置、统计、报告及测试。独立 CMake 入口复用公共跟踪库、RK3576 后端和视频读取库；同时提供仓库构建接入。默认不依赖 ROS 启动，不自动运行实机性能测试。

拒绝复制一份 NanoTrack 算法或扩展完整回放入口，因为两者分别容易发生算法漂移和引入无关工作量。结果是 benchmark 专属代码集中在指定目录，共用源码仅增加必要的可选观测接口及构建接入。

建议文件为 `main.cpp`、`benchmark_runner.h/.cpp`、`timing_recorder.h/.cpp`、`result_writer.h/.cpp`、`statistics.h/.cpp`、`config.example.yaml`、`README.md`、`CMakeLists.txt` 和 `tests/`。使用现有 OpenCV 配置/JSON 与 OpenSSL SHA-256 方案；SHA-256 是文件内容指纹，用于追溯而非限制合法模型替换。

### 2. 固定 MJPEG 亮度解码，顺序处理不跳帧

选择现有 `MjpegVideoReader` 和 `copyGrayFrame()`，保留原尺寸、灰度值范围和帧复制。仅接受本地普通文件的首个 MJPEG 视频流，编码支持范围沿用生产读取器。拒绝 OpenCV 彩色解码后再转灰度、预先解码全部录像或使用生产定时队列，因为这些选择会改变像素或处理负载。

程序读取压缩帧后立即开始本帧解码至结果区间，完成更新后才读取下一帧。原始 PTS（录像中的显示时间）及其时间单位保留作帧身份，不用于休眠或延迟计算；缺失 PTS 明确记录，不伪造时间。生产帧源本身的 PTS 校验与调度规则不变。

特别处理首帧：在读取器内部的解码入口记录时间，通过可选观察接口关联首帧。首帧解码后至初始化完成之间不插入模型加载、指纹计算、日志刷盘等准备工作；无法移出的原有调用开销仍计入区间。禁止把缓存首帧的 `next()` 耗时充当解码耗时。

### 3. 使用真实 FP16 模型，保持 Float32 主机路径

选择复用 `loadNanoTrack()`、`NanoTracker` 及现有前处理。NCHW 表示批次、通道、高、宽的数组排列。模板输入为 `[1,3,127,127]`，搜索输入为 `[1,3,255,255]`，均保持 Float32 NCHW、0～255。越界填充使用初始化帧均值，保留裁剪舍入和先转浮点再缩放的顺序。

模板特征为 `[1,96,8,8]`，搜索特征为 `[1,96,16,16]`。head 输出分类 `[1,2,15,15]` 和位置 `[1,4,15,15]`，角色匹配、布局转换、复制及输出释放均沿用当前实现。返回框为原图左上角 `x/y` 与宽高；返回分数为当前选中位置的分类概率，不替换成加入窗口权重后的评分。

拒绝运行时强行转换精度、移除复制或每帧重跑模板，因为这些都会改变基线。结果是每次初始化执行一次模板 backbone，每次正常更新执行一次搜索 backbone 和一次 head。

启动时查询三模型属性，并读取与模型指纹绑定的导出证据。配置提供模型证据清单，包含角色、SHA-256、声明精度和导出记录路径；保存记录指纹与内容副本。运行时接口类型无法单独证明内部算子精度。明确 INT8 或混合精度模型拒绝运行；缺失或相互矛盾的 FP16 证据记录 `precision_unverified` 并在正式测量前失败，不重新转换模型。浮点属性上的 AFFINE 元数据不单独作为拒绝依据，与现有契约一致。

### 4. 统一且不重复累计的计时层级

选择 `std::chrono::steady_clock` 单调时钟，原始值保存相对本进程起点的整数纳秒。唯一端到端延迟为 `decode_to_result`，从进入当前压缩帧解码到 `update()` 返回框与分数；初始化对应区间终止于 `init()` 返回，并标明结果种类是模板初始化。

| 顶层阶段 | 边界与内容 |
| --- | --- |
| decode | JPEG 解码入口到原尺寸灰度结果完成 |
| frame_copy | 灰度帧封装与复制 |
| preprocess | 初始化/搜索几何计算、灰度转浮点、均值及填充、裁剪、缩放、通道复制 |
| inference | 模型后端调用，包含同步结果取得、转换、复制及模型交接 |
| postprocess | 更新输出校验、概率与框计算、评分选择、状态更新 |
| other | 区间内未被以上阶段覆盖的调用、校验和清理 |

`inference` 子区间区分 `template_backbone`、`search_backbone`、`head`。每个模型继续区分输入整理、`inputs_set`、`run`、`outputs_get`、输出复制/释放/规范化；其余后端开销记为该层 residual（未归入已列子阶段的剩余时间）。这些主机调用时间不称为纯 NPU 计算时间。

顶层阶段互斥；父区间包含子区间，汇总不重复相加。初始化没有后处理和预测分数，未执行字段为空。失败时关闭已开始区间，保存部分数据，不形成成功的完整延迟样本。`other` 由总区间减去互斥顶层区间计算，负值视为计时数据错误而非截断为零。

拒绝只在外层包围 `update()` 或仅测 `rknn_run`，因为前者不能归因，后者不能涵盖取得可用输出的全部成本。观测只记录已有调用，不增加模型调用或设备同步。

### 5. 可选观察接口与有界记录缓冲

选择默认空的、平台无关观察接口。生产调用者不需要配置，接口不泄漏 RKNN 类型。每帧在同一处理线程记录带父区间 ID 的时间事件，使用预分配缓冲，阶段边界不序列化字符串、不刷盘。观察器生命周期覆盖全部被观察对象的使用期；写入错误由运行器在安全边界处理，不从 SDK 清理路径抛出。

当前帧区间结束后批量写盘，缓冲满时同步排空而非丢记录。文件读取、输出写盘和环境采样都在端到端计时外，不为它们增加性能指标。拒绝异步日志线程和无界内存缓存，结果是记录流程容易核对，且不额外引入线程竞争。阶段观测的自身开销不从原始时间中估算扣除，而通过独立对照实验量化。

### 6. 配置、预热与重复轮次

选择单 YAML 配置入口；相对路径相对于配置目录解析，不进行 shell 展开。配置包含 `schema_version=1`、三个模型路径、精度证据清单、本地录像路径、首帧 `bbox: [x,y,width,height]`、`warmup_updates`、`max_updates`、`repeats`、输出目录及环境采样间隔。默认预热 30 次更新、正式重复 3 轮；`max_updates=0` 表示到 EOF（文件结束），重复数必须为正，预热允许为零。所有框坐标必须有限，宽高为正，部分越界沿用当前初始化规则。输出目录必须不存在，防止混合记录。

完整执行顺序：

1. 校验配置和输入路径，创建运行目录并写入 `running` 状态。
2. 完成指纹计算、模型加载与精度检查、静态环境记录及缓冲准备。
3. 从首帧执行预热初始化和指定次数更新，全部记录为 `phase=warmup`；素材不足时明确失败，不静默减少预热数量。
4. 每轮正式运行前重置跟踪器并重新打开录像，使用相同首帧框。模型会话复用，模板与前处理目标均值重新建立。
5. 首帧记录 `operation=init`，后续帧记录 `operation=track`；`phase=measure` 区分正式数据。帧号每轮从 0 开始，轮次 ID 唯一。
6. 正式帧全部保留，不因慢帧、低分或漂移重置、重试或丢弃。有效低分仍计入成功更新。
7. 到 EOF、帧上限、中断或错误时排空记录并生成报告。

拒绝把录像前 30 帧直接删除后继续正式统计，因为那会改变正式轮的初始状态。重开和重置使每轮使用同一输入轨迹；预热不代表清空系统文件缓存，也不宣称冷启动性能。

### 7. 原始记录、恢复和报告

选择以下输出，各文件均有格式版本说明：

| 文件 | 内容 |
| --- | --- |
| manifest.json | 解析后配置、代码/程序/模型/视频指纹、模型属性、证据、环境和最终状态 |
| frames.csv | 每帧身份、阶段分类、结果、全部顶层耗时及错误 |
| spans.csv | 区间 ID、父 ID、模型角色、开始/结束纳秒、完成状态 |
| environment.csv | 相对时间、可读取温度和频率等环境观测 |
| summary.json | 可机器处理的分组统计及完整性信息 |
| report.md | 中文人类可读报告 |
| diagnostics.log | 参数、模型、解码和输出诊断 |

每帧至少有 `run_id,repeat_id,phase,operation,frame_index,pts,pts_valid,status,bbox_valid,x,y,width,height,score,decode_ns,frame_copy_ns,preprocess_ns,inference_ns,postprocess_ns,other_ns,decode_to_result_ns`。PTS 的时间基准存于 manifest。原始区间文件覆盖细分测量，失败、预热和初始化均保留。初始化框标记为输入框，不伪装预测；分数为空。非有限数保存空值/null，另记错误。CSV 正确转义文本，浮点值保留可往返精度；JSON 中纳秒、PTS 等 64 位整数用十进制字符串避免读取端精度丢失。

环境记录包括板号、系统、内核、实际 Runtime/驱动、CPU/NPU 频率策略与亲和性、库版本、编译参数、代码提交和工作区差异指纹。无法读取的环境字段记缺失与原因，不自动提权或改频。代码有修改时保留差异快照以便追溯。源码身份在每次构建使用该身份的目标之前重新检查，包括提交号、工作区差异及相关新增源码。使用独立 CMake 脚本生成头文件，内容不变时不更新时间戳，避免无改动构建反复编译。Git 查询或文件读取失败时阻断构建，不能沿用旧身份宣称构建成功。新增构建脚本本身也纳入快照。

每个正式轮分别汇总初始化和有效更新，各阶段输出样本数、均值、总体标准差、最小、最大、P50/P90/P95/P99。分位数使用排序后第 `ceil(p*N)` 项；空样本为 null。重复轮额外报告合并样本分布和每轮均值的范围。失败区间另表汇总，不混入成功完整延迟。

可显示的速率仅为“解码至结果处理速率”：`有效正式更新数 / 对应 decode_to_result 秒数之和`。例如两帧耗时 20 ms 和 30 ms，速率为 40 帧/秒；它不代表含读盘、写盘和等待的系统吞吐率。禁止平均逐帧倒数。无有效更新时为 null，测试不能算完成。

选择将 `running` 状态在结束时原子替换为 `complete/interrupted/failed`。正常结束原因是 `eof` 或 `frame_limit`；已处理的中断为 `interrupted`；读、解码、模型、记录失败均单列。失败立即停止，不以重试改变工作量。退出码 0 仅用于有有效正式更新且原始记录和报告完整的正常结束；配置错误为 2，运行失败为 1，中断为 130。可处理退出尽力生成部分报告；输出介质失败时通过 stderr 报告，不能保证在同一故障介质写出总结。SIGKILL/断电不保证尾部缓冲和汇总完整，遗留 running 状态与完整 CSV 行可供诊断。

拒绝仅输出汇总，因为无法重新统计或定位异常；选择流式原始文件使存储增长与样本数一致，汇总可结束后分阶段读取文件计算精确分位数。报告一致性测试从磁盘原始数据独立重算。

### 8. 验证与基线身份

选择受控测试、ARM64 构建和 RK3576 实机三层证据。受控测试覆盖像素、阶段归属、首帧、模型调用次数、错误和报告重算；不能替代硬件性能。实机固定 Runtime 2.3.2、驱动 0.9.8，使用同一 FP16 模型组、录像和初始框至少三轮。

数值对照使用相同生产解码路径和有/无观测的同一公共算法。受控输入要求结果完全相同；实机允许绝对误差：框各分量不超过 1e-4 像素、分数不超过 1e-6。超限需调查并保留失败，不能自动放宽。对照开销实验保持相同输入和环境，比较关闭细分观测但保留总计时与完整观测的重复延迟分布，报告差值，不设未经证据支持的性能门槛。

拒绝用模型能加载、容器测试通过或旧彩色 probe 的输出作为基线等价证明。结果是验收记录明确列出板号、模型、录像、容差和未运行项。记录环境温度变化，但不自动修改系统策略。

## Risks / Trade-offs

- 计时本身有开销 → 采用预分配轻量记录，并报告细分观测开销对照，不事后扣除估算值。
- 构造器预解码首帧容易漏测 → 在内部解码点观测，并以已知首帧耗时的受控测试验证。
- 模型接口类型不能证明内部精度 → 要求与文件指纹绑定的导出证据，无法核实即不形成正式 FP16 基线。
- 写盘与温度可能影响后续帧 → 固定记录方式，保存环境采样与重复轮结果；不把排除写盘区间解释为零干扰。
- 细分源码接入影响共用库 → 默认关闭、复用原逻辑，回归现有测试及有/无观测结果。
- 模型设备故障可能触发现有致命退出 → 不更改设备安全停止策略；保留已落盘记录和未完成状态，外部超时记失败。

## Migration Plan

1. 增加可选观察边界，保持现有调用兼容，完成回归测试。
2. 新增独立程序、配置和报告，接入现有构建但不自动执行实机基准。
3. 在既有 ARM64 环境构建，部署到明确记录编号的 RK3576 开发板；不覆盖板端 Runtime。
4. 完成同输入对照、三轮测量和数据重算，记录未执行项。
5. 回退时停用新程序；原生产入口无需配置迁移，已有测试数据按格式版本保留。
