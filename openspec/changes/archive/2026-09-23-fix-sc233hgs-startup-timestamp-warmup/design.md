# SC233HGS 有界启动预热设计

## Context

生产相机启动时返回重复时间戳，程序在开始跟踪前就退出。目标是在有限启动观察期内丢弃观察帧，时间连续递增后才向下游交付。动机和实机依据见 [proposal.md](proposal.md)。

当前 `Rk3576CameraCaptureBase::next()` 负责 Linux V4L2 相机接口的出队、元数据校验、时间映射、灰度复制及缓冲归还。`CameraTiming::map()` 对非递增时间抛异常。SC233HGS 复用 `Ar0234CameraFrameSource` 的线程和队列；后者把没有 `frame` 的结果解释为没有出队，因此不能仅返回空图像表示预热丢弃。现有序号检查也在上层且只检查有图像的结果。

主规格当前规定任意时间重复均失败，本变更明确收窄为正常阶段失败、预热阶段有限兼容。现有测试 `camera_timing_test.cpp` 覆盖严格映射和未知时钟回退，必须保留。录像尚在规划，分流边界须与 `add-rk3576-camera-recording` 协调。

## Goals / Non-Goals

**Goals:** 在不改帧时间数值的前提下接纳启动重复；限制等待和元数据内存；让停止保持可唤醒；每个驱动缓冲有明确归还或停止回收路径。

**Non-Goals:** 不证明曝光或图像质量稳定；不修内核或 ISP（图像信号处理器）链路；不容忍时间倒退；不改算法、模型、业务消息或 AR0234 行为；不实施录像功能。

## Decisions

### 1. SC233HGS 固定策略，单轮只预热一次

选择仅由 SC233HGS 设备启用内部预热策略。阈值为成功 `STREAMON`（驱动开流）后的 2000000 微秒、120 次成功出队、连续 8 个合格时间样本。固定值便于生产验证；不新增参数矩阵，也不按当前看到的前四帧写死丢弃数量。代价是每轮增加观察延迟，低于约 4 帧/秒的输入可能无法在期限内成功；不据此自动延长期限。

连续计数首样本为 1，后续时间更大则加一，相等则当前帧丢弃并将计数重置为 1。第 8 个样本直接成为首个可输出帧。倒退或其他校验失败立即终止。计数只说明时间单调性，不用帧间隔阈值证明稳定帧率。序号向前缺口只计数、不重置稳定计数；序号重复/倒退仍失败，自然无符号回绕沿用既有规则。

```text
STREAMON --> WarmingUp --> Streaming --> Stopped
                 |             |
                 +--> Failed <--+
                 |
                 +--> Stopped (OFF)
```

`WarmingUp` 是内部采集阶段诊断，公共帧源可以仍表示线程运行中。`Streaming` 不能自动退回预热。每次新轮重置所有观察状态，不通过捕获异常并重建计时器延续旧轮。

### 2. 时间观察与正式输出校验分开

选择在公共采集基类的元数据安全检查后、像素复制前运行预热判断。独立观察状态验证全部预热样本；正式 `CameraTiming` 只接收合格输出帧，保留严格递增检查。拒绝人工加一、按帧率补时和遇重复切换出队时间，避免合成时间进入姿态匹配与录像。

本轮固定时钟偏移仍在开流前采样，不在预热完成时重采样。第一份元数据即固定时间策略，预热样本也检查合法字段、换算溢出及正的映射值。标记单调时钟时比较原始驱动时间，时间来源未知时沿用已有 `dequeue_fallback`：以成功出队的主机单调时间映射，明确它只是出队时刻。该既有回退不会因本变更新增、删除，也不用于挽救明确单调驱动时间的重复。未知策略下原始字段仍须合法；其无语义的大小关系不作为驱动时间比较依据。任何策略改变均失败。

原始零值仍遵守现有合法字段与正映射值规则，不隐式引入新的时钟域判断。对出队时钟、时间来源和固定偏移的校验与预热计数解耦，以免跳过被丢弃帧上的异常。

处理顺序：

1. 检查停止请求及单调时钟期限；限时等待并取得缓冲区。
2. 保存出队时间，校验缓冲、驱动序号和时间元数据。所有成功出队都参与序号检查，保持单一检查责任，避免上下层各自漏算或重复计数。
3. 再检查预热截止时间；到期不交付该帧。合法样本推进观察计数。
4. 未就绪则归还缓冲、返回带元数据的预热丢弃结果。无灰度复制，也不调用未来录像提交入口。
5. 就绪则正式映射时间，在缓冲有效期内复制合格图像，正常归还，再进入原队列路径。

例如 `100,100,117,117,134,151,168,185,202,219,236` 的计数为 `1,1,2,1,2,3,4,5,6,7,8`，首个输出保留 `236 + offset`。

### 3. 明确采集结果，不新增线程或缓存图像

内部采集结果区分 `NoSample`（未成功出队）、`WarmupDiscarded`（已归还的预热帧）和 `FrameReady`（可输出独立图像）。这些名称是拟定实现标识，不暴露为 ROS 消息。拒绝“空帧兼作预热丢弃”的方式，因为上层需要更新最后成功出队时间并记录原始序号。

上层单生产者线程处理全部出队结果；只有 `FrameReady` 入原跟踪队列。序号检查移至共同的元数据检查路径或等效单一边界，不能等返回 `FrameReady` 才检查。预热状态由生产线程拥有，诊断快照用现有同步保护；停止线程只发出停止并唤醒，等采集线程退出后释放设备。

预热丢弃必须成功 `QBUF`（归还缓冲）后才能继续。归还失败保留错误并请求本轮停止，不报告成功丢弃。非法索引不盲目归还；进入原停止回收路径。已出队但失败/取消而未走正常归还路径的帧，单列终止处置数，清理完成前不宣称设备资源全部回收。

### 4. 两类超时独立，停止优先

预热期限固定从开流成功后的主机 `CLOCK_MONOTONIC` 取样起计。收到帧或重复时间不重置它；等待时长取原等待预算与剩余期限的较小值，无帧、EINTR（系统调用被信号中断）、EAGAIN（暂时无数据）也回到截止检查。不得在内部循环无限吞掉预热帧。

在同一次判断中，已收到的 OFF 优先于超时及就绪提交；停止时不再输出新样本。到期 `now >= deadline` 优先于稳定成功，拒绝期限外样本。第 120 帧若在期限内满足稳定条件则允许成功，否则归还后以检查量超限失败；不读取第 121 个预热样本。首次出队都没有则报采集无帧超时，已经出队但未稳定则报预热未稳定，并区分时间或帧数上限。正常阶段保留连续 2 秒无成功出队失败。

逻辑上两秒后不再接受预热成功，不将非实时用户态线程的调度误差描述为硬实时退出保证；报告实际超时检测与停止耗时。`start()` 不等待稳定，预热在原采集线程中推进，避免两秒同步等待影响 OFF。

### 5. 对账与有界证据

保留 `read` 表示通过检查并交付队列路径的合格帧，保持它与原入队统计的关系；新增 `dequeued_total` 表示全部成功出队。记录 `warmup_examined`、`warmup_discarded`、`warmup_repeats`、阶段、耗时、终止原因、最终连续计数及首个合格帧身份。

预热最多存 120 条元数据：原始时间、标志、序号、出队时间、判断和计数，不保存像素。独立验收工具在结束时导出完整观察记录；正式节点输出有限汇总并保留可提取的诊断快照。常规汇总每秒最多一次，成功/失败转换单独记录。避免逐帧同步写盘拖慢采集。

清理后的终态按互斥类别对账：`dequeued_total = warmup_discarded + read + terminal_discarded`；其中终止处置包括致命校验失败或停止期间已取得但未交付的缓冲。`read = enqueued + queue_dropped`。预热成功帧计入 `warmup_examined` 和 `read`，不计入 `warmup_discarded`。驱动序号缺口是未取得的帧，不加进出队总量。

### 6. 与录像分流及规划同步的边界

选择在预热通过后才允许录像取得同帧 NV12（含亮度和色度的完整图像）。拒绝先录像再过滤算法输入，否则异常时间会进入视频。当前变更不增加录像代码；录像 change 明确依赖本变更完成的帧边界，并在同一接口位置集成。

录像 ON 可先准备资源和会话元数据，第一份合格帧才开始视频内容；首个被录像接受的合格帧建立视频时间起点。预热观察记录不进入视频逐帧记录。零帧 OFF 或失败仍保留会话原因，不生成“可播放视频已完成”的结论。具体文件与健康计时由录像 change 定义。

同步主规格时先同步本变更，再同步录像变更。两者都修改 ROS 的 ON/OFF requirement，录像增量必须包含这里的预热段落和场景；否则整段替换会丢失规则。本变更不复制录像能力进入自身增量。

## Risks / Trade-offs

- [有限窗口无法保证后续正常] → 正常阶段仍严格失败，生产板执行重复启动和 20 分钟负载，不无限扩大窗口。
- [预热增加首帧延迟并丢弃可见内容] → 报告首个合格帧延迟与丢弃量，录像从该边界开始，不补帧。
- [共享实现影响 AR0234] → 仅 SC233HGS 开启策略，完整回归原时间、触发、队列及停止测试。
- [真实底层时钟可能与标志不一致] → 保留原策略及原始证据，不将解决重复等同于曝光同步或时钟精度验收。

## Migration Plan

1. 实现纯时间观察测试和采集结果边界，运行现有 ARM64 构建/相机测试。
2. 在指定生产板独立验收：20 轮 ON/OFF、100 次新建销毁、20 分钟持续采集含慢消费者；每轮时间证据可对账，停止与资源门槛不变。
3. 使用正式模型完成 ROS 首帧、OFF、失败恢复和业务消息回归。记录模型、输入、程序和板卡身份，目标捕获质量单独报告。
4. 更新部署记录后才将相机问题标记已解决。若失败，回滚原程序版本并注明其仍受启动重复限制；不修改系统 RKNN Runtime，也不静默放宽阈值。
5. 录像实现基于通过验证的预热边界集成，重新验证联合行为；主规格同步和归档分别按工作流执行。
