## Context

现有 RK3576 工具分别验证检测和单目标跟踪，还无法通过统一入口运行整套跟踪算法。本设计把已验证的后端接入公共跟踪器，使用一份配置驱动录像并留下可复查记录，动机见 [proposal.md](proposal.md)。

已核对的代码边界：

- `ModelPaths` 仅有 `yolo/backbone/head`；`loadNanoTrack()` 实际需要模板 Backbone、搜索 Backbone、Head 三个路径。Backbone 从图像提取特征，Head 比较模板和搜索特征。
- `copyGrayFrame()` 已有独立灰度存储，但公共帧创建规格还要求保留 BGR 三通道彩色输入。
- `HybridTracker` 已接受完整组件，负责异步 YOLO、NanoTrack、DCF 辅助跟踪及卡尔曼预测。卡尔曼预测根据历史测量估计当前目标位置。
- 旧 `replay_harness.cpp` 固定 20 ms 帧间隔，并包含气球参数和相机内参；新入口不能照搬这些默认值。
- `reset()` 清空跟踪缓存和帧编号，但未显式排空检测器结果。本次不引入运行中循环或 OFF/ON。
- 根目录生产构建仅支持 Jetson；RK3576 独立 CMake 已能构建两个模型 probe，目标基线为 Runtime 2.3.2、驱动 0.9.8。

## Goals / Non-Goals

**Goals:**

- 让独立回放和后续生产入口可以复用同一 RK3576 模型装配。
- 所有运行选项只来自一份配置，参数解析、时间推进和结果序列可独立测试。
- 完整调用真实公共算法，保留检测工作线程与主跟踪线程的边界。
- 只安排纯 FP16、纯 INT8 的新增实机验收，分别报告正确性、质量、耗时和资源情况。

**Non-Goals:**

- 不把独立工厂等同于生产采集已完成；不开放根目录 RK3576 ROS 构建。
- 不引入相机、ROS、变帧率/历史绝对时间回放、旋转数据输入或硬件图像加速。
- 不修改公共状态数值、检测/跟踪仲裁、阈值默认值、模型数值契约或混合精度支持。
- 不保证真实异步回放逐帧完全相同，也不把成功退出视为跟踪质量合格。

## Decisions

### 1. 独立工厂与顺序录像读取器

选择新增 `platform_rk3576`，实现 `CreatePlatformFactory()`、帧创建及整套模型装配。`createFrameSource()` 对相机和生产视频均返回明确的不支持诊断；回放通过 `src/replay/ReplayReader` 同步读取 OpenCV 解码帧。

原因是生产帧源还有队列、启停和历史时间戳约定。拒绝把简单录像读取器伪装成完成这些约定的生产帧源，也不在工具内手工选择模型后端。结果是本次可验证完整算法，但相机/ROS 集成仍需后续变更。主规格中生产入口场景继续适用于现有 Jetson；本次以追加的独立 RK3576 要求表达扩展。

```text
CONFIG.yaml --> ReplayConfig --> ReplayReader --> Gray8
                    |                             |
                    v                             v
          CreatePlatformFactory() ----------> FrameBuilder
                    |                             |
                    v                             v
            TrackerComponents --------------> HybridTracker
                                                  |
                                                  v
                                      frames.csv + run.json
```

### 2. 保持共享路径兼容，追加拆分路径

选择在 `ModelPaths` 末尾追加 `template_backbone`、`search_backbone`，前三个字段及顺序不变。Jetson 只接受共享 `backbone`；RK3576 要求两个拆分路径且共享字段为空。所有平台均拒绝共享/拆分混填、拆分缺一项以及模型角色路径为空。

原因是旧三字段聚合初始化必须继续工作。拒绝把 `backbone` 改解释为模板模型，也不从目录或文件名推断搜索模型。后果是 Jetson 增加早期配置诊断，已有合法配置保持不变；四文件由显式角色绑定。新入口以 `ModelPaths` 为唯一模型加载依据，`TrackerSettings` 中已有路径字段不再构成第二配置源，不把拆分路径传播成公共算法重新加载模型的能力。

### 3. 装配失败不交出半套资源

选择可注入加载器的 `rk3576::assembleTracker()` 与生产加载绑定分离。顺序为 YOLO、模板 Backbone、搜索 Backbone、Head，再创建预处理器和兼容性检查。复用已有 `loadYoloBackend()`、`loadNanoTrack()` 和会话契约；不复制 RKNN 数据布局、量化及释放代码。

原因是需要验证每个加载点失败后的释放。拒绝允许只返回检测器的降级运行。结果是创建成功必定完整，失败诊断包含平台、真实失败角色、路径及底层原因，且检测线程尚未启动。目标类别范围在检测线程启动之前检查；模型角色检查不能仅依据名称。

### 4. 主机帧保留格式，跟踪只接受灰度

选择扩展私有 HostFrame 支持 Gray8 和 BGR8，并提供后端内部可验证真实存储类型的入口。Gray8 每像素一个八位灰度值，BGR8 每像素三个颜色字节。保留 `copyGrayFrame()` 现有调用行为。帧创建深拷贝，按实际行跨度读取非连续图像；视图持有底层存储，不借用工厂。

拒绝只通过像素格式枚举判断平台兼容性，也不让帧创建器偷偷把彩色变灰度。原因是公共规格要求复制时保留像素。结果是工厂能保存两种格式，而当前跟踪兼容性检查只接受本平台 Gray8；彩色及其他平台帧在时间和状态更新前被拒绝。回放边界显式执行 BGR→Gray8，然后送入已验证的灰度预处理。非空一通道和三通道八位解码图像可用，其他类型报错。

### 5. 一个配置文件是唯一运行参数来源

选择命令 `rk3576_tracker_replay CONFIG.yaml`，恰好一个位置参数。无参数或多参数返回配置错误及用法，不支持 `--model`、`--fps`、`--output` 等覆盖。配置不支持 include、继承、环境变量插值或运行中重载。模型、录像等数据文件不是附加配置文件。

采用 OpenCV FileStorage 可读取的 YAML 1.0 子集，示例文件带 `%YAML:1.0` 标头；复用现有 OpenCV 依赖，拒绝额外建立 ROS 参数节点或维护第二套命令行优先级。配置中的布尔值统一以整数 0/1 表达并严格检查。只接受一个 YAML 文档，映射键唯一，未知键、缺字段、错误类型和非有限数值均拒绝，不依赖读取器静默覆盖重复键。

所有运行字段显式填写；程序不从旧 ROS YAML 或 `TrackerSettings` 默认值补齐缺项。算法实现中的固定常量不是可选配置。配置 schema_version 固定为 1，未识别版本报错。相对路径以配置文件所在目录解析，不进行 shell 展开。拒绝覆盖已有输出目录；每次运行使用新目录，避免混合证据。

字段结构如下，示例数值仅展示格式，不是相机标定或质量验收结论：

```yaml
%YAML:1.0
---
schema_version: 1
models:
  yolo: "models/yolo.rknn"
  template_backbone: "models/fp16/template_backbone.rknn"
  search_backbone: "models/fp16/search_backbone.rknn"
  head: "models/fp16/head.rknn"
input:
  video: "videos/clip.mp4"
  fps: 30.0
  max_frames: 0
camera:
  fx: 800.0
  fy: 800.0
  cx: 320.0
  cy: 256.0
tracker:
  yolo_target_class_id: 2
  yolo_conf_threshold: 0.5
  yolo_nms_threshold: 0.45
  yolo_interval: 4
  yolo_recall_relax_ratio: 1.0
  iou_reset_threshold: 0.4
  iou_calibrate_threshold: 0.8
  max_position_jump: 150.0
  max_size_jump_ratio: 2.0
  max_box_area_ratio: 0.8
  tracking_roi_scale_factor: 2.0
  lost_max_count: 5
  frame_buffer_size: 30
  jump_tolerance: 3
  enable_dcf: 1
  dcf_fixed_template: 1
  dcf_learning_rate: 0.01
  dcf_lambda: 0.0001
  dcf_psr_thresh: 5.0
  dcf_max_div_factor: 0.5
  dcf_model_sz: 96
  dcf_pad: 1.0
  dcf_sigma_factor: 0.1
  dcf_eps: 0.00001
  kf_r_pos: 4.0
  kf_r_size: 4.0
  kf_q_a: 50000.0
  kf_q_size: 1000.0
  kf_history_len: 60
output:
  directory: "runs/fp16-001"
```

`max_frames=0` 表示到文件结束，正整数表示主动限制帧数，后者结束原因记为 `frame_limit`。相机参数单位为像素，必须对应解码尺寸，不自动缩放或套用旧相机参数。`camera.fx/fy/cx/cy` 映射到 `kf_fx/kf_fy/kf_cx0/kf_cy0`；跟踪字段沿用现有 ROS YAML 名称，`tracking_roi_scale_factor` 映射到 `roi_scale_factor`，`dcf_*` 映射到已有 DCF 参数，其他字段直接映射同名设置。不增加独立模型精度选择器，真实属性和文件指纹由模型查询报告。

字段校验按下表执行。所有数值必须有限，整数转换必须检查范围和溢出。

| 字段类别 | 范围 |
| --- | --- |
| fps | (0, 1000000] |
| 相机 fx/fy；cx/cy | fx/fy 为正；cx/cy 为有限数 |
| 目标类别 | 非负整数，模型加载后确认小于类别数 |
| 概率、IoU 阈值和 DCF learning rate | [0,1] |
| recall ratio、max_box_area_ratio | (0,1] |
| 尺寸跳变倍率、ROI 倍率 | 至少为 1 |
| 位置跳变、DCF lambda/发散倍率/sigma_factor/eps、KF 测量噪声 | 正数 |
| DCF pad/PSR 阈值、KF 过程噪声 | 非负数 |
| 间隔、计数、缓存及历史长度 | 正整数 |
| DCF model_sz | 至少为 2 的整数 |

新增 dcf_model_sz/pad/sigma_factor/eps 显式映射当前已有 DCF 设置，示例沿用代码原默认值。PSR 是 DCF 响应主峰相对背景的强弱指标。ROI 是围绕预测位置优先搜索的图像区域，倍率决定该区域的扩展幅度。IoU 是两个框交集面积除以并集面积，用于判断检测和跟踪框的重合程度。

### 6. 固定录像时间轴与受控送帧

选择固定帧率、顺序不跳帧模式。第 i 帧时间为 `1,000,000 + round(i * 1,000,000 / fps)` 微秒，从 i=0 开始；每次由帧号计算，检查正值、递增和 int64 范围。30 FPS 的前三帧为 1000000、1033333、1066667。读取器报告有效帧率时，与配置相差超过 `max(0.01, fps*0.001)` 即报错；无有效元数据时记录缺失并采用显式配置。

主线程以单调墙钟安排帧提交，不受系统时间调整影响。下一帧计划时刻为 `max(上一帧计划时刻 + 帧间隔, 上一次 update 返回时刻 + 帧间隔)`；解码过慢时可以更晚，不能补发一串帧追赶。记录实际间隔和进度落后，承认处理越慢则整体回放越慢。`now_us` 等于帧时间，两份旋转矩阵为单位阵；不把墙钟混入预测时间。

原因是旧工具的固定 50 FPS 不适用于通用录像，最快送帧还可能在首次异步检测结束前耗尽缓存。拒绝同步等待每帧 YOLO 或按生产“排空取最新帧”策略丢帧。结果是顺序回放适合算法集成诊断，不构成实时吞吐量或旋转补偿验收。首版只接受使用者确认的固定帧率素材；不能通过平均帧率推断变帧率素材有效。

### 7. 保留真实算法与异步结果时序

选择真实 `HybridTracker::update()`，从 Detecting=0 开始，不提供人工首框，不重复提交帧来等待结果，不复制 YOLO 间隔、补帧或仲裁。DCF 开关按配置执行，TargetFound=1、Tracking=2、TargetLost=3 数值保持不变。

原因是本次要验证后端组合，而非另写一个算法。拒绝为得到逐帧相同输出而强制同步 YOLO。结果是真实线程调度可能使检测结果在不同帧被消费；精确状态测试使用可控模型输出，实机每种纯精度重复三次并报告切换帧差异，不以 CSV 字节相同作为门槛。`consumed=false` 仍记录，但不能称为成功更新；不解析 `info` 文本来重构内部事件。

### 8. 生命周期、结束原因和错误边界

选择每进程处理一段录像，不循环复用状态。完整流程为：

1. 解析唯一配置，检查字段及路径，确认输出目录尚不存在。
2. 打开视频并读取首帧，验证尺寸、格式和帧率，准备运行记录。
3. 创建工厂、帧创建器和完整组件；静态契约通过后初始化跟踪器。
4. 首帧及后续帧依次转灰度、复制、提交、记录，不丢失用于检查的首帧。
5. 到达结尾、帧限制、中断或错误时停止送帧。
6. 销毁跟踪器并等待检测线程退出，再释放仍被任务访问的帧和模型。
7. 完成报告并关闭文件；退出前检查输出流错误。

拒绝在结尾制造虚拟帧消费最后的检测结果。末尾等待只用于安全释放，不产生额外状态行。信号处理器只设置中断标记，清理由主线程执行；SIGKILL 和断电不保证最终汇总。`run.json` 在运行开始写入 `running`，正常结束才替换为最终状态，保留异常终止可见性。

OpenCV read 失败不总能区分 EOF 和损坏。声明帧数为正且未达到就结束，记 `decode_error`；达到声明帧数可记 `eof`，不宣称验证文件无损；无可信帧数则记 `end_unverified`，不能算完整验收通过。成功处理到帧上限记 `frame_limit`。无法送帧的映射/解码/输出错误终止回放。公共模型内部的普通推理失败继续沿用已有算法行为，本次不能从缺少目标推断设备故障；启动和运行诊断按现有信息记录。设备无法确认停止的致命路径沿用既有策略。

退出码约定：0 为 `eof` 或 `frame_limit`，2 为参数/配置错误，1 为初始化或运行错误及 `end_unverified`，130 为正常处理的用户中断。所有结束原因另写入报告；0 不表示有目标或质量合格。

### 9. 可复查输出与配置快照

选择流式 `frames.csv`、结构化 `run.json` 和 `diagnostics.log`，避免把整段录像或全部结果留在内存。输出路径全部取自配置。报告通过 OpenCV JSON 输出；SHA-256 文件内容指纹使用 OpenSSL Crypto，避免自写密码算法或调用 shell。该通用依赖仅加在回放工具，不加到公共算法及旧 probe。

每次 update 记录：输入帧号、帧时间、now_us、consumed、tracking、状态、显示框和实时预测框及各自有效标记、NanoTrack 原始框及有效标记/分数、info、解码耗时、灰度转换与复制耗时、update 耗时和墙钟提交时刻。显示/预测框列名为 `*_cx/cy/width/height`；原始 NanoTrack 框为 `nano_x/y/width/height`。无效框坐标及非有限分数留空，CSV 正确转义逗号、双引号和换行。int64 时间戳和帧号不能经过双精度中转损失精度；JSON 中超出可靠整数表示范围的整数采用十进制字符串并记录 schema。

汇总包含报告版本、代码提交与工作区是否修改、程序/配置/四模型/录像 SHA-256、解析后的完整配置与绝对路径、实际张量和 Runtime/驱动属性、OpenCV 版本及解码后端、输入尺寸、声明/读取/提交/接受帧数、状态分布及切换帧、各阶段均值/P95、墙钟总耗时和结束原因。P95 取排序后 `ceil(0.95*N)` 样本；空样本输出 null。图像转换和 update 耗时不包含等待；update 不称作总模型耗时，因为 YOLO 异步执行。

拒绝只保留日志或用成功退出代表质量。报告中的模型属性复用装配查询，不再次加载模型。已有模型 diagnostic stdout/stderr 必须与 CSV 分流；报告失败不静默返回成功。

### 10. 独立构建和验证矩阵

选择在已有 ARM64 独立 CMake 接入 `rk3576_tracker_assembly`、`platform_rk3576` 和 `rk3576_tracker_replay`。工具链接 `hybrid_tracker` 与 `platform_rk3576`，原 probe 保留。通用配置、时钟、报告和注入装配测试不要求真实 RKNN 设备；静态依赖检查确认 RK3576 产物无 Jetson 库。

原因是根目录平台开放会同时牵涉 ROS/采集。拒绝在本次放宽根目录平台选择测试。沿用 AGENTS.local.md 的现有临时 ARM64 容器和 SDK，不重建镜像；OpenSSL 开发库可用性只做具体构建检查，缺失时记录依赖阻塞，不静默自写哈希替代。

新增实机验收仅有两组：纯 FP16（模板/搜索/Head 均 FP16）与纯 INT8（三者均 INT8）。YOLO 使用同一已验证模型。每组在同一输入和参数下重复三次，DCF 开/关均有覆盖。混合精度不列为待办或完成门槛，不移除已有支持或为了裁剪矩阵删除已有低成本单元测试。

素材覆盖自动捕获、持续跟踪、目标离开和重新进入、无目标。现有 309 帧录像用于回归，不能假定覆盖所有状态。精确状态测试与真实模型录像分别报告；缺录像就保留对应实机任务未完成。标注只用于离线评估，不用于初始化或纠正跟踪。报告跟踪占比、首次捕获/恢复时刻及有标注帧的 IoU 和中心误差；IoU 是预测与标注框交集面积除以并集面积。未确认质量门槛前只报告量化结果，不声称质量达标。

每组安排重复创建销毁至少 20 轮；选择两组各自配置进行至少 30 分钟稳定性检查，不合并成混合精度。可使用单段足够长录像或测试驱动顺序创建全新实例，报告边界次数；不得通过运行中 reset 循环。记录驻留内存、线程、文件描述符和停止结果，未测设备内存明确注明。持续增长或停止失败必须调查，不能由平均值掩盖。

## Risks / Trade-offs

- 异步结果到达时机影响状态帧号 → 用受控测试验证精确语义，实机报告三次重复的差异，不承诺字节级一致。
- 解码器无法可靠区分所有 EOF/损坏 → 记录声明与实际帧数，无法证明结束时使用 end_unverified，不作为完整通过。
- 旧 reset 可能保留异步结果 → 每段使用全新实例，运行中触发隔离留给后续变更。
- 灰度转换与 Jetson MJPEG 原始亮度读取可能不同 → 记录像素转换方式，本次不宣布 Jetson 像素或跟踪等价。
- 固定时间轴且 now 等于帧时间 → 不覆盖真实采集延迟和旋转外推，不把节奏控制后的墙钟速度作性能达标证据。
- 单份配置字段较多 → 提供完整带注释示例和逐字段错误；拒绝缺省值和多配置合并造成难以复现的参数来源。
- CPU 拷贝及浮点特征转换可能影响性能 → 先取得完整链路证据，优化另立变更，不改阈值掩盖问题。
- 设备提交后挂起不能保证有界退出 → 沿用已有 Runtime 致命安全约定；外部测试超时必须记失败，不强制回收仍在用的存储。

## Migration Plan

1. 扩展公共路径和帧能力，运行现有契约回归，保持 Jetson 合法三路径调用。
2. 加入可注入 RK3576 装配及独立平台目标，验证各模型加载失败释放。
3. 加入配置、读取、时钟和报告模块及独立入口，提供完整纯 FP16/纯 INT8 示例配置。
4. 运行无硬件测试、ARM64 构建和目标板两组验收，将证据放入本 change 的 validation.md 并标注未执行范围。
5. 更新使用说明和迁移计划，再核验规格一致性。现有 probe、ROS 配置和根目录入口不迁移；回退时停用新增工具，继续使用旧独立入口，无数据格式迁移需求。
