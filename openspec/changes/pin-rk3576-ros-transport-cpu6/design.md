# Design

## Context

任务状态在跟踪进程内迟到，造成视频状态文字延后更新。本设计让通信线程从创建起使用 CPU 6，同时让控制和跟踪继续使用 CPU 4。动机见 `proposal.md`。

CPU 亲和性是线程允许执行的核心集合。Linux 新线程通常继承创建线程的亲和性；DDS 是 ROS 消息交付、接收和节点发现使用的中间件。生产板使用 ROS 2 Humble 和 Fast DDS 2.6.12，本变更沿用现有版本。

现有 `src/drone_tracker_main.cpp` 在 ROS 初始化前调用 `initializeControl()`。节点构造函数在基类已构造后再次调用它。`setupDisplay()` 创建遥测订阅，`setup()` 又混合模型初始化和业务订阅、发布者创建，因此单改一处调用顺序不足以覆盖全部通信资源。`initializeControl()` 使用线程局部的一次性标志；线程临时离开 CPU 4 后，再调用该函数不能保证回到 CPU 4。

2026-10-30 在生产板 `HZ-RK3576_WuKong Board`（ADB 序列号 `a4649c048860c947`、内核 `6.1.141-rt36`）完成过临时试验。八个经运行栈识别的通信相关线程从 CPU 4 移到 CPU 6，随后全部恢复。三次尝试的任务状态发布至回调为 0.35–1.35 ms，确认 OFFBOARD 至 HDMI 提交为 4–32 ms，桥接器接受 MISSION 至提交为 1.10–1.48 s。传输接收线程每三秒等待调度约 20–35 ms，恢复 CPU 4 后回升到约 650 ms。该结果支持分离通信核心；它不是本次候选实现的验收结果。

现场还观察到控制和部分推理线程的 nice 值为 -19，通信线程为 0。nice 值影响普通线程的调度权重。其改变来源尚未证实，本设计不改变优先级，也不把这一来源写成已确认根因。

## Goals / Non-Goals

**Goals:**

- 用创建阶段的明确职责分配替代临时移动已运行线程。
- 使通信资源创建、模型初始化和回调执行具有可验证的核心边界。
- 保留旧版本 1 策略与未配置运行方式。
- 通过同版本中间件及生产板验证实际继承，而不是仅验证配置成功读取。

**Non-Goals:**

- 不修改飞行模式显示、任务确认条件、ROS 接口或算法状态。
- 不修复拦截进程额外的 0.80–1.30 秒任务启动延迟。
- 不升级 Fast DDS，不修改系统 RKNN 库，不增加实时调度策略。
- 不将隔离通信压力检查等同于实飞或真实目标跟踪质量验收。

## Decisions

### 1. 独立通信职责，兼容版本 1

选择在 `Policy` 和 `Role` 中增加 `ros_transport`，部署模板显式指定 6。旧的按职责策略未提供该字段时使用 `control`。C++ 加载器与 `deployment/cpu-policy.py` 对显式字段使用一致的整数、在线核心和允许范围校验；显式空值属于错误。`inherit` 和无配置继续不实施逐职责绑定。

原因是生产映射需要独立调整通信职责，私有回归策略仍可能只有原六职责。拒绝直接把 `control` 改成 6，因为这也移动回调执行器，偏离已验证试验；拒绝强制升级所有旧策略。结果是既有文件继续有效，新的生产模板明确表达传输核心。

### 2. 在 ROS 创建边界应用核心，不扫描运行线程

选择让主入口在 `rclcpp::init` 前应用通信职责。受管节点构造路径也必须在 `rclcpp::Node` 基类构造前确认该职责，覆盖测试或嵌入式调用直接构造节点的路径。可以通过构造参数准备函数或等价的受控前置入口实现；不能只在构造函数体内绑定，因为那时中间件可能已创建线程。

节点内拆开通信资源创建与模型、相机后端初始化。遥测适配器中的订阅、业务订阅与发布者、`StatusPublisher` 的发布者和 ROS 默认节点资源都在通信阶段创建。创建发布者可以早于模型就绪；执行器只在完整构造成功后才开始处理回调。显示线程继续在其入口确认 Display 职责。

原因是接收、发现和事件线程可能分别由不同的创建调用触发。拒绝硬编码八个线程编号、匹配线程名称或事后扫描迁移；线程身份和数量会随进程与 DDS 行为变化。结果是实现依赖职责边界，不依赖一次试验的线程快照。只读栈、符号和 `/proc` 掩码可以用于测试证据，但不能进入生产绑定路径。

### 3. 明确恢复控制职责，保留后续创建边界

选择在通信阶段完成后直接应用并读回 Control 职责，然后才初始化模型和创建业务工作。恢复不能经过已置位的一次性 `initializeControl()` 快捷路径。后续受管端点创建使用相同通信边界，结束后恢复调用线程进入前的掩码。已在 CPU 6 运行的通信线程自行创建辅助线程时继续继承 CPU 6。

建议的启动顺序如下：

1. 读取 CPU 策略，检查在线核心与允许列表。
2. 主入口确认通信 CPU 6，初始化 ROS。
3. 节点基类及应用通信资源在 CPU 6 完成创建。
4. 主线程明确确认控制 CPU 4，再初始化相机与模型后端。
5. 开始服务；Tracking=4、YOLO=5、Display=6、Capture=7、Recording=7 的入口分别读回自身职责。
6. 单线程执行器在 CPU 4 处理回调。

例如，线程先在 CPU 4，临时进入 CPU 6 创建新订阅，离开阶段后必须再次读回 CPU 4。新订阅引出的通信线程继续使用 CPU 6，恢复创建者不会移动已有辅助线程。

原因是职责切换可能嵌套或发生在重复构造时。拒绝依赖线程局部“已应用”标志推断当前核心。结果是初始化与恢复使用可重复调用的绑定操作；临时范围正常结束和异常结束均恢复调用者。恢复失败必须明确传播到启动或服务失败路径，不能只记录日志后继续。实现不得在析构函数异常传播中引入二次异常终止；应采用有明确错误交付方式的关闭路径。

### 4. 定向验证实际中间件与有界竞争负载

选择增加轻量的真实 ROS 通信验证程序或等价集成测试。它复用生产亲和性入口，使用同版本 Fast DDS；消息携带单调时钟时间和序号，分别报告发布至中间件接收、发布至回调的延迟。单调时钟只随运行时间推进，避免系统校时造成负延迟或虚假尖峰。使用中间件提供的源和接收时间时，必须说明其时钟来源。

测试覆盖以下阶段：通信资源创建、控制恢复、外部进程加入发现、新端点创建与销毁、至少两轮启停、至少 20 秒的 CPU 4 竞争窗口。竞争辅助进程固定 CPU 4，设置有限运行时间和占空比，不占用其他核心。记录负载方式及 nice 值，确保进程退出即可撤销。生产逻辑仍不修改优先级。延迟报告至少给出消息数、丢失数、P50、P95、最大值；隔离域检查不得出现 1 秒及以上交付停顿。

在生产板以只读方式观察实际 DDS/ROS 接收、发现及事件线程的掩码和调度等待。发现线程身份可以使用运行栈或符号；无法辨认的线程标记未知，不能把所有非业务线程默认归为 DDS。测试不能假设恰好存在八个线程。

拒绝仅用普通 `std::thread` 继承测试替代真实中间件验证，也拒绝把临时台架的性能数字直接作为新实现结果。结果是自动检查验证边界和失败分支，板端记录验证 Fast DDS 实际行为。

实现时确认：同一离线容器中，选定 QEMU 用户态运行器的两个 ARM64 进程无法完成节点发现；显式回环初始对端也未修复。相同源码的原生 x86_64 程序在该容器通过，真正 ARM64 生产板也通过。交叉构建因此在独立目录构建相同探针的原生版本，执行完整双进程断言；ARM64 探针仍构建并在生产板运行。该选择不放宽断言，不把原生结果当作 ARM64 验收。节点构造与控制恢复测试仍使用 ARM64/QEMU 程序。

### 5. 临时候选验收与生产状态恢复

选择先保存生产 release、策略和原服务状态，再从独立目录运行候选程序。测试使用隔离 `ROS_DOMAIN_ID`（即互不发现的 ROS 通信域），与在线飞控桥接和拦截控制隔离。必要时停止这些服务以避免设备或通信冲突。候选启动使用既有三个模型和相机配置的测试副本，先验证预览与职责入口，再在隔离域内执行节点自身 ON/OFF。不得向在线域发送解锁、任务开始或飞控模式命令。

原因是用户授权了板端测试与停止服务，未要求替换正式发布。拒绝直接覆盖生产二进制和系统推理库。结果是完成检查后终止候选和负载辅助进程，保留原生产链接和配置，恢复原先运行的服务。缺少真实目标或录像窗口时，报告对应项未验证，不把扫描负载写成持续跟踪通过。

## Risks / Trade-offs

- CPU 6 与显示及诊断采集共享：记录 CPU 使用率、通信调度等待和 HDMI/诊断运行状态；出现明显退化时只补测受影响窗口。
- DDS 存在延迟创建路径：用首次发现、后续端点和重复启停验证实际继承；遗漏路径必须回到创建边界修复，不能增加扫描迁移器。
- 拆分构造顺序使回调持有尚未初始化的成员：保持执行器在构造完成后启动，失败时按原生命周期销毁订阅、显示和后端资源。
- 初始化阶段的第三方库可能改变优先级：先完成通信创建，再进入模型阶段；记录实际 nice 值，不主动修复第三方调度行为。
- 临时试验未证明整机所有延迟都消失：独立记录拦截器上游延迟和新的通信验收结果。

## Migration Plan

1. 通过版本 1 兼容、非法字段、职责恢复和中间件集成自动检查，使用 `./build.sh --test` 构建 ARM64 候选。
2. 保存生产板型号、序列号、内核、release、配置指纹及四个服务状态；将候选复制到独立验收目录。
3. 在隔离域执行通信压力和候选入口验证，保存掩码、阶段日志、延迟及观察边界。
4. 完成所有测试后停止辅助进程并恢复原先运行的服务，核对正式 release、配置和系统 Runtime 指纹未被替换。
5. 只有另行选择正式发布时才部署新策略和候选二进制；本次定向验收不默认切换生产 release。回退使用原二进制和原策略，两者必须成对恢复，因为旧程序不会识别新的职责含义。
